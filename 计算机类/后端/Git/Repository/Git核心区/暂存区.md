# 暂存区 —— Staging Area（Index / 索引）

> [!abstract] 一句话
> ==暂存区（Staging Area）是一个**"待提交清单"**==：你在工作目录里改的东西，**不会**自动进入下一次提交；只有先 `git add` 放进暂存区，`git commit` 才会把它们打包。它的技术名字叫 **索引（Index）**，实体是 `.git/index` 这一个二进制文件。

---

## 一、为什么 Git 要多此一举

> [!info] 暂存区是 Git 区别于老式版本控制的**灵魂设计**
> 像 SVN 之类的老工具，改动是"要么提交、要么不提交"——**全有或全无**。
> Git 插了一个暂存区，让你能把**一堆不相干的改动，拆成若干次目的明确的提交**。

看个例子。你一下午干了三件事：

```text
工作目录里同时有：
  ✎ 修好了登录 bug          （fix/ 目录）
  ✎ 顺手写了新功能的一半      （feature/ 目录）
  ✎ 又调了下日志格式          （utils.js）
```

如果只有"全提交/全不提交"，你只能把它们**搅成一个大提交**——以后想单独回滚"修 bug"就难了。有了暂存区：

```bash
git add login/            # 只把 bug 修复收进来
git commit -m "fix: 修复登录态失效"

git add utils.js
git commit -m "style: 统一日志格式"

# feature/ 的一半暂时不提交，留在工作目录继续做
```

> [!success] 价值一句话
> 暂存区让**"提交"成为一个有意识的选择**，而不是"把当前状态的快照一股脑扔进去"。

## 二、三棵树中的位置

```text
 ①工作目录            ②暂存区                ③仓库(提交)
 Working Directory     Staging Area / Index   Repository / HEAD
┌──────────────┐      ┌──────────────┐       ┌──────────────┐
│  你编辑的文件  │ ──①──│ 待提交的清单  │ ──②──│  永久历史快照  │
│              │ add  │  .git/index  │commit │ .git/objects │
└──────────────┘      └──────────────┘       └──────────────┘
        ▲                                              │
        └──────────────── checkout / restore ──────────┘
```

| 动作 | 方向 | 命令 |
| --- | --- | --- |
| **暂存** | 工作目录 → 暂存区 | `git add` |
| **取消暂存** | 暂存区 ← 工作目录（退回） | `git restore --staged` / `git reset` |
| **提交** | 暂存区 → 仓库 | `git commit` |
| **检出** | 仓库 → 工作目录 + 暂存区 | `git checkout` / `git switch` |

> [!note] 索引里存的是"引用"，不是文件副本
> `.git/index` 记录的**不是文件内容本身**，而是每个文件的**路径 + 元数据（mtime、大小）+ 对应 blob 对象的哈希**。
> 内容早已以对象形式写进 `.git/objects`，索引只是一张"下一次提交该包含哪些对象"的**清单**。

## 三、对暂存区的操作

### 3.1 放进去：`git add`

```bash
git add <文件>            # 暂存单个文件的改动
git add <目录>/           # 暂存整个目录
git add .                 # 暂存当前目录下所有改动（含新增、删除）
git add -A                # 暂存整个仓库的所有改动（等价 git add --all）
git add -u                # 只暂存"已追踪文件"的改动，不含新增

git add -p                # ★ 逐块（hunk）挑选，交互式暂存
git add -i                # 进入交互式菜单
```

> [!tip] `git add -p` 是最值得练的技能
> 它把每个文件的改动切成若干"块"，逐块问你 `y/n`。
> 这样你能在**一个文件里**只提交其中一部分——比如只提交调试日志的删除，把真正的逻辑改动留到下次。
> 配合 `s`（拆分块）、`e`（手工编辑）几乎能做到任意粒度的提交。

### 3.2 看里面有什么

```bash
git diff                  # 工作目录 vs 暂存区（还没交的改动）
git diff --staged         # ★ 暂存区 vs 仓库（即将被提交的改动）
git diff --cached         #   同上，--cached 是 --staged 的同义词

git status -s             # 短状态，第一列就是暂存区状态：
#  M  ← 左列非空 = 已暂存；右列非空 = 工作目录还有改动
#   M ← 只改了工作目录，还没 add
#  MM ← 暂存了 A 版，之后又改成了 B 版（两列都非空）
# ??  ← 未追踪文件
```

> [!tip] 提交前必看 `git diff --staged`
> `git diff` 看的是"我还没交的"，而 `git diff --staged` 看的才是**"这次 commit 到底会装进什么"**。
> 提交前瞟一眼它，能挡掉绝大多数"手滑把无关文件也提交了"的事故。

### 3.3 拿出来（取消暂存）

```bash
# 新版 Git（2.23+）推荐写法
git restore --staged <文件>     # 只把文件从暂存区退回，工作目录的原改动保留
git restore --staged .          # 整批取消暂存

# 老写法，效果相同
git reset HEAD <文件>
git reset                       # 取消全部暂存（工作目录不动）
```

> [!warning] `reset` 的软硬程度要分清
> | 命令 | 暂存区 | 工作目录 | 用途 |
> | --- | --- | --- | --- |
> | `git reset --soft HEAD~1` | 保留改动 | 保留 | 撤销上次**提交**，改动回到暂存区 |
> | `git reset HEAD <文件>`（默认 `--mixed`） | 撤销 | 保留 | **取消暂存**，改动回工作目录 |
> | `git reset --hard HEAD~1` | 清空 | **清空** | ⚠️ 连工作目录一起抹掉，**不可逆** |
>
> 只想"取消暂存"，用 `git restore --staged` 最安全，绝不会误伤工作目录。

### 3.4 停止追踪但不删除文件

```bash
git rm --cached <文件>     # 从暂存区/追踪中移除，磁盘文件保留
echo '<文件>' >> .gitignore  # 通常配合忽略规则一起做
```

> [!info] `git rm` 与 `git rm --cached` 的区别
> - `git rm <文件>`：**删除文件** + 把删除动作放入暂存区。
> - `git rm --cached <文件>`：**只让 Git 不再追踪**，磁盘上文件**原样保留**。
> 后者常用于"一个本来被提交的文件，后来想改成忽略"（如误提交的 `.env`）。

## 四、完整示例：把一坨乱改拆成两个提交

```bash
# 工作目录里已经改乱了：bug 修复 + 新功能 + 日志调整
git status -s
#   M src/login.js
#   M src/feature.js
#   M src/logger.js

# 1. 逐块挑选，只把 bug 修复暂存进来
git add -p src/login.js      # 对每个 hunk 选 y / n
git diff --staged            # 确认清单里只有修复

git commit -m "fix: 修复登录态失效"

# 2. 再把日志调整单独提交
git add src/logger.js
git diff --staged
git commit -m "style: 统一日志格式"

# 3. 新功能还没做完，继续留在工作目录
git status                   # 只剩 src/feature.js 是 modified
```

> [!success] 结果
> 两次目的清晰的提交，各自可独立回滚；没做完的功能安安静静待在草稿纸上，没被裹进历史。

## 五、常见困惑

> [!question] 我 `add` 之后又改了文件，提交的会是哪个版本？
> **提交的是你 `add` 进去的那个版本**（暂存区里的），后续再改的内容**不会**被这次提交带走。
> `git status -s` 会显示 `MM`，提醒你"暂存的和工作目录的不一样"。
> 想让新改动一起进去，**再 `add` 一次**即可。

> [!question] 暂存区能"空提交"吗？
> 不能。如果暂存区相对 HEAD 没有任何变化，`git commit` 会拒绝：
> ```text
> nothing to commit, working tree clean
> ```
> （除非显式 `git commit --allow-empty`，那通常用于触发 CI 之类的特殊场景。）

> [!question] `git commit -a` 是不是跳过了暂存区？
> 不是绕过，是**自动帮你 add**——`-a` 会对所有**已追踪**文件的改动执行一次 `git add`，再提交。
> 它**不会**包含未追踪的新文件（那些还得手动 `git add`）。

> [!question] 索引（Index）和暂存区（Staging Area）是同一个东西吗？
> 是。**Index 是它的正式名**，Staging Area 是教学化的叫法，`--cached` 里的 "cache" 也是它。
> 三者指的都是 `.git/index`。

---

> [!quote] 一句话记忆
> **暂存区 = 提交前的"购物车"**：工作目录是货架，你挑拣（`git add`）放进购物车，结账（`git commit`）时才真正买单；挑错了还能放回货架（`restore --staged`）。
