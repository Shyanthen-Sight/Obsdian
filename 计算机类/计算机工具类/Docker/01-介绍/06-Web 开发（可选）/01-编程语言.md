# 编程语言

Docker 不挑语言，但语言决定了镜像怎么分层。编译型语言可以把构建工具留在构建阶段，最终镜像只放二进制；解释型语言得把运行时和依赖一起带上，重点变成"别把开发依赖装进去"。

| 语言 | 常见构建方式 | 运行镜像里留什么 |
| --- | --- | --- |
| Go | 静态编译 + 多阶段 | 一个二进制，甚至 scratch |
| Rust | release 构建 + 多阶段 | 二进制和 libc |
| Node | `npm ci` + 多阶段 | `node_modules` 和构建产物 |
| Python | 虚拟环境/uv + 多阶段 | 解释器、依赖、源码 |
| Java | Maven/Gradle + JRE | jar 和 JRE |

Go 的典型写法：

```dockerfile
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /app ./cmd/server

FROM gcr.io/distroless/static-debian12
COPY --from=build /app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]
```

`CGO_ENABLED=0` 得到静态二进制，才能放进没有 libc 的 distroless/static 或 scratch；`-ldflags="-s -w"` 去掉符号表和调试信息，体积能小几 MB。`COPY go.mod go.sum` 单独一层，源码改动时依赖缓存还能命中。

Node 项目：

```dockerfile
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --from=build /app/dist ./dist
USER node
CMD ["node", "dist/server.js"]
```

`npm ci` 按 lockfile 安装，比 `npm install` 可复现；`--omit=dev` 去掉测试和构建依赖。带原生模块的包（`sharp`、`bcrypt`）在 Alpine 上可能要装 `python3 make g++`，或者干脆用 `node:20-slim`。

Python 和 Java 的思路一样：构建阶段装编译器/构建工具，运行阶段只留产物。Python 注意 `--no-cache-dir`，Java 用 JRE 而不是 JDK，Spring Boot 可以分层解包 jar 提升缓存命中。

> [!tip] 先写 .dockerignore
> `node_modules`、`.git`、`target`、`dist`、本地 `.env` 都排除掉。构建上下文小，`COPY . .` 才不会把无关文件塞进镜像，也能避免密钥泄漏。

## 编译型 vs 解释型：镜像策略不同

语言决定了“构建阶段”和“运行阶段”各需要什么，也决定了镜像能压到多小：

| 类型 | 构建阶段需要 | 运行阶段需要 | 最终镜像量级 | 关键问题 |
| --- | --- | --- | --- | --- |
| 编译型（Go、Rust、C/C++） | 编译器、工具链、头文件、构建缓存 | 二进制 + libc，或完全静态 | 几 MB 到几十 MB | 静态链接、glibc/musl、CGO |
| 解释型（Node、Python、Ruby） | 运行时 + 构建工具 + 全部依赖 | 运行时 + 生产依赖 + 源码 | 几十到几百 MB | 开发依赖、原生模块、缓存 |
| JVM（Java、Kotlin、Scala） | JDK + Maven/Gradle | JRE + jar/class | 几十到几百 MB | JRE vs JDK、分层 jar、堆参数 |

核心原则是 **构建期和运行期分离**：编译器、测试依赖、构建缓存只在构建阶段出现，最终镜像只放运行必需的东西。多阶段构建就是把这条原则落到 Dockerfile 里的标准做法。

## 多阶段构建为什么是默认答案

单阶段构建会把整个工具链留在镜像里：Go 的 `golang` 镜像约 800 MB，Maven + JDK 也差不多，Node 的 `node_modules` 加上构建工具能到几百 MB。这些工具在运行时用不到，却会：

- 增大镜像体积，拉取和分发变慢；
- 扩大攻击面，编译器、包管理器、shell 都可能被利用；
- 把构建缓存、源码、测试文件带进生产环境。

多阶段构建用多个 `FROM`，只有最后一个阶段进入最终镜像：

```dockerfile
FROM golang:1.23 AS build
# ... 编译 ...

FROM gcr.io/distroless/static-debian12
COPY --from=build /app /app
ENTRYPOINT ["/app"]
```

`build` 阶段的层仍然会被缓存，方便增量构建，但不会出现在最终镜像里。`docker build --target build` 可以只构建到某个阶段，用于调试或 CI 中的测试阶段。

配合 BuildKit 的缓存挂载，还能把包管理器的下载缓存跨构建复用，而不写进镜像：

```dockerfile
RUN --mount=type=cache,target=/root/.cache/go-build \
    --mount=type=cache,target=/go/pkg/mod \
    go build -o /app ./cmd/server
```

## 各语言的典型写法

### Go

```dockerfile
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /app ./cmd/server

FROM gcr.io/distroless/static-debian12
COPY --from=build /app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]
```

- `CGO_ENABLED=0` 关掉 C 语言互操作，得到静态二进制，才能放进没有 libc 的 `scratch`/`distroless/static`。代价是某些依赖 C 库的包（SQLite、某些加密库）不能用。
- `-trimpath` 去掉构建机器的绝对路径，构建可复现。
- `-ldflags="-s -w"` 去掉符号表和调试信息，体积小几 MB，但 panic 栈的可读性会下降。
- `COPY go.mod go.sum` 单独一层，源码改动时依赖缓存仍能命中。
- `distroless/static-debian12` 自带 CA 证书和基础用户文件；纯 `scratch` 需要自己复制。

### Rust

```dockerfile
FROM rust:1.82 AS build
WORKDIR /src
COPY Cargo.toml Cargo.lock ./
RUN mkdir src && echo 'fn main() {}' > src/main.rs \
 && cargo build --release --locked
COPY . .
RUN cargo build --release --locked

FROM debian:bookworm-slim
COPY --from=build /src/target/release/app /usr/local/bin/app
CMD ["app"]
```

先复制 `Cargo.toml`/`Cargo.lock` 并构建一个空 main，是为了把依赖编译缓存单独成层；源码改动时不用重编所有依赖。`--locked` 保证使用 lockfile 里的版本。想要完全静态，可以加 `--target x86_64-unknown-linux-musl`，再放进 `scratch`/`distroless`；但 musl 和 glibc 在 DNS、locale、某些系统调用上行为不同，要测过再换。

### Node

```dockerfile
FROM node:20-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-slim
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --from=build /app/dist ./dist
USER node
CMD ["node", "dist/server.js"]
```

- `npm ci` 严格按 `package-lock.json` 安装，比 `npm install` 可复现，也不会改 lockfile。
- `--omit=dev` 去掉测试、构建、lint 依赖；构建阶段仍然需要它们。
- 带原生模块的包（`sharp`、`bcrypt`、`canvas`）在 Alpine 上需要 `python3 make g++`，或者直接换 `node:20-slim`，glibc 兼容性更好。
- `USER node` 用镜像自带的非 root 用户；`NODE_ENV=production` 影响部分库的行为和日志。
- 如果构建产物需要 `node_modules`，只复制生产依赖；不要 `COPY . .` 把宿主机的 `node_modules` 带进去，用 `.dockerignore` 排除。

### Python

```dockerfile
FROM python:3.12-slim AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1
COPY --from=build /install /usr/local
WORKDIR /app
COPY . .
USER 1001
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]
```

- `--no-cache-dir` 不把 pip 缓存写进镜像；构建阶段可以用缓存挂载加速。
- `--prefix=/install` 把依赖装到独立目录，再整体复制到运行阶段，避免把编译工具带过去。
- `PYTHONUNBUFFERED=1` 让日志立即输出，不然 `docker logs` 可能延迟；`PYTHONDONTWRITEBYTECODE=1` 不生成 `.pyc`。
- Alpine 的 musl 和 manylinux wheel 不兼容，科学计算包经常要现场编译；没有明确收益时优先 `-slim`。
- 依赖用 `requirements.txt` + 锁文件（`pip-compile`、`uv lock`、Poetry），别在镜像里 `pip install` 不锁版本。

### Java

```dockerfile
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B -DskipTests package

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /app/target/app.jar ./app.jar
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/app.jar"]
```

- 构建用 JDK，运行用 JRE：JDK 带编译器，JRE 只带运行时，体积和攻击面都小。
- `dependency:go-offline` 先把依赖拉下来，源码改动时这层缓存还能用。
- `-XX:MaxRAMPercentage=75` 让 JVM 按容器内存限额计算堆，而不是按宿主物理内存；不设的话容器里容易 OOM。
- Spring Boot 3.3+ 可以用 `java -Djarmode=tools -jar app.jar extract` 把 jar 拆成依赖层，提升镜像层缓存命中；老版本用 `layertools`。
- 更小的运行镜像可以用 `distroless/java` 或 `jlink` 裁剪的 JRE，但排障会麻烦一些。

## 基础镜像怎么选

| 基础镜像 | 适合 | 不适合 | 备注 |
| --- | --- | --- | --- |
| `scratch` | 完全静态的 Go/Rust 二进制 | 需要 libc、CA 证书、时区、shell 的程序 | 最空，也最需要自己补文件 |
| `distroless/static` | 静态二进制，需要 CA/时区 | 需要动态链接库 | 没有 shell，排障靠旁路 |
| `distroless/base` | 动态链接的 C/C++/Go（CGO） | 需要包管理器、shell | 有 glibc，没有包管理 |
| `alpine` | 追求小体积、能接受 musl | 预编译 glibc 二进制、manylinux wheel、原生模块 | 先测兼容性 |
| `debian:slim` | Python、Java、Node 原生模块 | 极致小体积 | 兼容性最稳 |
| `ubuntu` | 需要 Ubuntu 特有包或较新版本 | 极致小体积 | 比 slim 大 |
| 语言官方镜像 | 构建阶段 | 直接上生产 | 构建用完整版，运行换 slim/distroless |

一句话：**构建阶段用“什么都有”的镜像，运行阶段用“只够跑”的镜像**。不要为了省事先用完整镜像上线，再回头优化；也不要为了小体积一上来就 Alpine，最后被原生模块卡住。

## 常见坑

- **`COPY . .` 放在依赖安装之前**：源码一改，依赖层缓存全失效，构建从几秒变成几分钟。先复制依赖清单，装完再复制源码。
- **没有 `.dockerignore`**：`node_modules`、`.git`、`target`、`dist`、`.env` 全进构建上下文，镜像变大，密钥还可能泄漏。
- **`npm install` 代替 `npm ci`**：锁文件被改写，构建不可复现。
- **Python 依赖不锁版本**：今天构建和下周构建拿到不同版本，问题难复现。
- **Alpine 上装原生模块**：报 `gyp ERR!` 或 `ModuleNotFoundError`，先换 `-slim`，或者补 `python3 make g++`。
- **JVM 不设容器内存参数**：JVM 看到的是宿主内存，堆开太大，容器被 OOM kill。
- **忘了 CA 证书**：`scratch` 里 HTTPS 请求失败，不是网络问题。
- **用 root 跑应用**：镜像里加 `USER`，并确保工作目录属主正确。
- **多架构没测**：Apple Silicon 上构建的镜像推到 amd64 集群，报 `Exec format error`；用 `--platform linux/amd64` 明确目标。
- **把构建密钥写进 `ARG`/`ENV`**：会留在镜像历史里；用 BuildKit secret 挂载。
