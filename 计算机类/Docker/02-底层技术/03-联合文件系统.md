# 联合文件系统

镜像分层不是 Docker 造的格式，底层是内核的联合挂载。Linux 上默认用 overlay2，把多个只读目录和一个可写目录合成一个 merged 视图。容器看到的 `/` 是叠加后的结果，镜像层本身始终只读。

## 镜像为什么分层

一个镜像由 manifest、config 和一组 layer 组成。每层是一个文件系统 diff，通常打包成 tar，按内容寻址（sha256）。相同内容的层在不同镜像之间共享，构建缓存也以层为单位。

| 层 | 内容 | 共享范围 |
| --- | --- | --- |
| 基础层 | 发行版用户态、shell、基础库 | 所有基于同一基础镜像的镜像 |
| 依赖层 | 语言运行时、系统包、第三方库 | Dockerfile 前缀相同的构建 |
| 应用层 | 代码、静态资源、配置 | 每个版本一份 |
| 可写层 | 运行时修改 | 每个容器一份，不共享 |

分层的直接好处是拉取和存储省空间：十个基于 `nginx:1.27` 的镜像，基础层只存一份；构建时没变的层也能直接复用缓存。

## OverlayFS 的四个目录

OverlayFS 把多个目录叠成一个视图，四个关键位置：

- `lowerdir`：一个或多个只读层，冒号分隔，最左边优先级最高；
- `upperdir`：可写层，所有修改都落在这里；
- `workdir`：内核内部用的工作目录，必须为空、和 upperdir 在同一个文件系统；
- `merged`：挂载点，进程看到的就是它。

手动挂一次最直观：

```bash
mkdir -p /tmp/ovl/{lower,upper,work,merged}
echo "base image" > /tmp/ovl/lower/a.txt
echo "v1" > /tmp/ovl/lower/b.txt

sudo mount -t overlay overlay \
  -o lowerdir=/tmp/ovl/lower,upperdir=/tmp/ovl/upper,workdir=/tmp/ovl/work \
  /tmp/ovl/merged

cat /tmp/ovl/merged/a.txt            # base image
echo "v2" > /tmp/ovl/merged/b.txt    # 触发 copy-up
echo "new" > /tmp/ovl/merged/c.txt
ls /tmp/ovl/upper                    # b.txt  c.txt

rm /tmp/ovl/merged/a.txt
ls -la /tmp/ovl/upper                # c--------- ... a.txt  <- whiteout
```

改 lower 里的文件时，内核会先把整个文件复制到 upperdir，再在副本上修改，这叫 copy-up。大文件第一次写入会明显卡顿，因为复制发生在写入路径上。

删文件不动 lower，而是在 upper 里放一个 whiteout（字符设备 0/0），merged 视图里就看不见了。删除一个下层目录再重建同名目录时，upper 里会带 opaque 标记（`trusted.overlay.opaque`），把 lower 中该目录的内容整体遮住。重命名目录通常需要 `redirect_dir` 支持，否则可能退化成 copy-up 或返回 `EXDEV`；`metacopy` 则允许只复制元数据，真正写数据时再复制内容，是否启用取决于内核和挂载选项。

## Docker 里的对应关系

```bash
docker inspect web -f '{{json .GraphDriver.Data}}' | jq
# {
#   "LowerDir": "/var/lib/docker/overlay2/l/ABC...:/var/lib/docker/overlay2/l/DEF...",
#   "MergedDir": "/var/lib/docker/overlay2/xxx/merged",
#   "UpperDir": "/var/lib/docker/overlay2/xxx/diff",
#   "WorkDir": "/var/lib/docker/overlay2/xxx/work"
# }
```

- `LowerDir` 的每一项对应一层镜像，最左边是最上面的层；`/l/` 下是短链接，指向真正的层目录。
- 容器的可写层就是 `UpperDir`，容器运行时的所有修改都落在 `diff/` 里。
- `MergedDir` 是最终挂给容器看的视图，`pivot_root` 之后成为容器的 `/`。
- 多个容器用同一个镜像时，`LowerDir` 指向同一批目录，磁盘上只有一份。这是一个 nginx 镜像起十个容器不占多少空间的原因。

`docker diff web` 输出的 `A/C/D` 就是 upperdir 相对镜像层的变化：新增、修改、删除。`docker ps -s` 里的 `SIZE` 是容器可写层的大小，`virtual` 则包含共享的镜像层，两者不要混着看。

## 构建镜像同理

每条会改动文件系统的指令都会产生一层，删除操作只会在新层里留下 whiteout，不会让下层字节从镜像里消失：

```dockerfile
# 差：下载物留在第一层，第二层删掉也不减体积
RUN curl -fsSL https://example.com/tool.tar.gz -o /tmp/tool.tar.gz
RUN tar -xzf /tmp/tool.tar.gz -C /usr/local/bin && rm /tmp/tool.tar.gz

# 好：下载、解压、清理在同一层完成
RUN curl -fsSL https://example.com/tool.tar.gz -o /tmp/tool.tar.gz && \
    tar -xzf /tmp/tool.tar.gz -C /usr/local/bin && \
    rm /tmp/tool.tar.gz
```

后者没有中间产物进入已提交层；前者即使后面删了文件，前一层字节仍随镜像分发。

几条构建时的规则：

- `RUN`、`COPY`、`ADD` 会产生层；`ENV`、`CMD`、`ENTRYPOINT`、`EXPOSE`、`WORKDIR`、`USER`、`LABEL` 只改配置，不新增层。
- 层顺序要考虑缓存：不常变的部分放前面，代码放最后，改代码时才不会让依赖层全部失效。
- `.dockerignore` 能避免把 `.git`、`node_modules`、日志打进构建上下文，既省时间又省层。
- 用 `docker history <镜像>` 看每层大小和创建命令，定位“哪一步把镜像撑大了”。

## 多阶段构建

编译型语言最典型：构建阶段需要完整工具链，运行阶段只需要二进制。多阶段构建让最终镜像只包含最后一阶段的层：

```dockerfile
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app ./cmd/app

FROM gcr.io/distroless/static-debian12
COPY --from=build /out/app /app
ENTRYPOINT ["/app"]
```

`COPY --from=build` 只把产物复制进最终镜像，Go 工具链、源码、模块缓存都留在构建阶段，不会进入交付物。Python、Java 也常用同样结构：builder 里装编译依赖，runtime 里只留虚拟环境或 jar。

## 卷和绑定挂载不经过 overlay

容器的可写层随容器删除一起消失。需要保留的数据放 [[02-卷挂载|卷]] 或 [[03-绑定挂载|绑定挂载]]，它们直接挂进容器的挂载表，不经过 overlay 的 copy-up：

- **命名卷**：挂载点会遮住镜像里同路径的内容；如果卷是空的，Docker 会把镜像中该目录的现有内容复制进卷一次，之后以卷为准。
- **绑定挂载**：宿主机目录直接映射进容器，不复制、不叠加，宿主机上是什么就是什么。
- **tmpfs**：只存在内存里，容器停止即消失，适合临时文件和敏感数据。

`docker commit` 会把当前可写层固化成新镜像层，调试时方便，但不该进正式流程：它把运行时的手工修改变成了不可复现的产物，也没有构建记录。

## 其他存储驱动

```bash
docker info --format '{{.Driver}}'
```

| 驱动 | 机制 | 适用场景 | 注意 |
| --- | --- | --- | --- |
| overlay2 | 联合挂载 + copy-up | Linux 默认，通用 | 需要 `d_type` 支持 |
| fuse-overlayfs | 用户态 overlay | rootless、内核不支持 overlay | 性能略低 |
| btrfs / zfs | 快照和子卷 | 已有对应文件系统 | 配置复杂，内存占用高 |
| vfs | 每层完整复制 | 调试、测试 | 占空间大、慢 |
| windowsfilter | Windows 分层 | Windows 容器 | 仅 Windows |

rootless Docker 在内核不允许非特权 overlay 时，会退到 `fuse-overlayfs`；嵌套容器（容器里再跑 Docker）也常遇到 overlay-on-overlay 的限制，需要 `fuse-overlayfs` 或特权模式。

## overlay2 的限制

- 底层文件系统要支持 `d_type`；xfs 必须 `ftype=1`，否则 overlay2 无法正常工作。
- NFS、CIFS 等网络文件系统通常不能作为 `/var/lib/docker` 的底层存储，行为不可靠。
- 层数有上限，层太多会消耗 inode 并拖慢挂载；合并 `RUN`、定期 `docker image prune` 能缓解。
- 大量小文件会放大元数据开销，构建和启动都变慢；这类场景要考虑合并文件或用卷。
- SELinux 环境下需要正确的标签，否则容器读写挂载目录会被拒绝。
- `/var/lib/docker` 不能简单拷贝到另一台机器当备份，镜像和层之间有硬链接与元数据关系；迁移用 `docker save` / registry。

空间排查：

```bash
docker system df
docker system df -v
```

前者看镜像、容器、卷、构建缓存各占多少，后者能按对象列出具体大小。

## 性能与体积

- **首次写入慢**：copy-up 要复制整个文件，大文件、数据库文件尤其明显。数据库应把数据目录放卷，而不是留在可写层。
- **page cache 共享**：多个容器读同一镜像层时，内核页缓存可以共享，内存不会按容器数线性增长。
- **构建缓存**：层缓存能省掉重复安装依赖的时间；BuildKit 的 `--mount=type=cache` 还能把包管理器缓存挂进来，不进入镜像层。
- **镜像大小 ≠ 容器大小**：镜像大小是所有层的和；容器占用主要是可写层增量，`docker ps -s` 分开显示。

## 常见误区

- **“删掉文件镜像就变小了”**：不会，删除只是在新层加 whiteout，旧层字节仍在。
- **“镜像大，容器占用的磁盘也一样大”**：不会，镜像层共享，容器只多出可写层。
- **“层数越少越好”**：不完全对。合并 `RUN` 能减层，但过度合并会破坏缓存粒度，改一行就让整层重建。按“变更频率”分层更实际。
- **“卷里的数据在镜像里”**：不在，卷是独立存储，镜像里只有挂载点目录。
- **“`docker commit` 可以代替 Dockerfile”**：调试可以，交付不行，产物不可复现、无审计记录。
