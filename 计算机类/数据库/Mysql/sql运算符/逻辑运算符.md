# SQL 逻辑运算符

> 逻辑运算符不只是"与或非"。SQL 是**三值逻辑（3VL）**：除了 TRUE / FALSE，还有 **UNKNOWN**。
> 90% 的 SQL 静默错误（查不出数据、多查出数据）都源于忽略 UNKNOWN。

---

## 一、运算符总览

| 运算符 | 名称 | 别名 | 返回值 | 说明 |
|--------|------|------|--------|------|
| `AND` | 与 | `&&` | TRUE / FALSE / UNKNOWN | 两边都为 TRUE 才为 TRUE |
| `OR` | 或 | `\|\|` | TRUE / FALSE / UNKNOWN | 有一边为 TRUE 即为 TRUE |
| `NOT` | 非 | `!` | TRUE / FALSE / UNKNOWN | 一元运算符，`NOT NULL` → UNKNOWN |
| `XOR` | 异或 | 无 | TRUE / FALSE / UNKNOWN | 恰好一边为 TRUE 才为 TRUE（MySQL 独有） |

```sql
SELECT TRUE AND FALSE, TRUE OR FALSE, NOT TRUE, TRUE XOR TRUE;
# 0  1  0  0   （MySQL 中 TRUE=1，FALSE=0）
```

**三个必背事实：**

1. 逻辑表达式在 MySQL 中的**结果值就是整数 1/0**，可以直接参与算术：`SELECT (1=1) + 1;` → `2`。
2. **UNKNOWN 不是 FALSE**，但 `WHERE` 会把它俩一视同仁地**丢弃**（下一节详述）。
3. `&&` / `||` / `!` 只是别名，较新版本已不推荐使用；且 **`||` 在不同数据库含义不同**（见第九节），生产代码一律写全称。

---

## 二、核心：三值逻辑真值表

### AND

| `AND` | TRUE | FALSE | UNKNOWN |
|-------|------|-------|---------|
| **TRUE** | TRUE | FALSE | UNKNOWN |
| **FALSE** | FALSE | FALSE | **FALSE** |
| **UNKNOWN** | UNKNOWN | **FALSE** | UNKNOWN |

### OR

| `OR` | TRUE | FALSE | UNKNOWN |
|-------|------|-------|---------|
| **TRUE** | TRUE | **TRUE** | **TRUE** |
| **FALSE** | TRUE | FALSE | UNKNOWN |
| **UNKNOWN** | **TRUE** | UNKNOWN | UNKNOWN |

### NOT / XOR

| 表达式 | 结果 |
|--------|------|
| `NOT TRUE` | FALSE |
| `NOT FALSE` | TRUE |
| `NOT UNKNOWN` | **UNKNOWN** |
| `TRUE XOR TRUE` | FALSE |
| `TRUE XOR FALSE` | TRUE |
| `TRUE XOR UNKNOWN` | **UNKNOWN** |
| `UNKNOWN XOR UNKNOWN` | **UNKNOWN** |

**从表中提炼三条"反直觉"规律：**

```sql
# 规律 1：UNKNOWN 会被 FALSE 吞掉（AND）
SELECT NULL AND FALSE;   # 0   ← 不是 NULL！FALSE 是绝对失败，无需求助 UNKNOWN
SELECT NULL AND TRUE;    # NULL

# 规律 2：UNKNOWN 会被 TRUE 吞掉（OR）
SELECT NULL OR TRUE;     # 1   ← 不是 NULL！TRUE 是绝对成功
SELECT NULL OR FALSE;    # NULL

# 规律 3：XOR 遇到 NULL 永远得不到确定值
SELECT NULL XOR NULL;    # NULL
```

> 记忆口诀：**「AND 遇假即为假，OR 遇真即为真」**。
> 短路求值（short-circuit）的思想正是从规律 1、2 来的。

### UNKNOWN 从哪来？

几乎全部来自 **NULL 参与比较或运算**：

```sql
SELECT NULL = 1;        # NULL (UNKNOWN)
SELECT NULL <> 1;       # NULL
SELECT NULL > 1;        # NULL
SELECT NULL + 1;        # NULL
SELECT 1 IN (2, NULL);  # NULL   ← 1 不等于任何值，与 NULL 比较得 UNKNOWN
SELECT NULL IS NULL;    # 1      ← 例外！IS NULL 特殊处理，恒为 TRUE/FALSE
SELECT NULL <=> NULL;   # 1      ← 例外！空安全比较，恒为 TRUE/FALSE
```

## 三、关键规则：WHERE 只保留 TRUE

==`WHERE` 子句只让条件为 **TRUE** 的行通过；**FALSE 和 UNKNOWN 的行都被丢弃，且没有任何提示**。==

这是理解本节所有坑的总纲。

```sql
SELECT 1 WHERE NULL;        # 0 行
SELECT 1 WHERE FALSE;       # 0 行
SELECT 1 WHERE NULL OR TRUE;  # 1 行（OR 遇真即为真）
```

再看一个值层面的区别（**同一个表达式，在 WHERE 里和在 SELECT 里表现不同**）：

```sql
CREATE TABLE t (a INT);
INSERT INTO t VALUES (1), (NULL), (2);

SELECT a, a = 1 AS cond FROM t;      # 1->1, NULL->NULL, 2->0
SELECT a FROM t WHERE a = 1;         # 只有 1
SELECT a FROM t WHERE NOT (a = 1);   # 只有 2   ← NULL 那一行被 UNKNOWN 吃掉了
```

**这就是最经典的 SQL 陷阱**：想查"不等于 1"的数据，NULL 行会凭空消失。

## 四、NULL 引发的四个高频 Bug

以下示例共用这张表：

```sql
CREATE TABLE emp(
  id     INT,
  name   VARCHAR(20),
  dept   VARCHAR(20),
  salary DECIMAL(10,2),
  bonus  DECIMAL(10,2)
);
INSERT INTO emp VALUES
 (1,'张三','销售',  8000,  1000),
 (2,'李四','销售', 12000,  NULL),
 (3,'王五','研发', 15000,  NULL),
 (4,'赵六','研发',  9000,  2000),
 (5,'钱七', NULL,   7000,  NULL);   -- dept 为 NULL
```

### Bug 1：`<>` / `!=` 漏掉 NULL 行

```sql
-- 需求：找出"不是销售部"的员工
SELECT * FROM emp WHERE dept <> '销售';
# 返回 3、4 —— 少了钱七！

-- 原因：钱七的 dept = NULL，(NULL <> '销售') 结果 UNKNOWN → 被 WHERE 丢弃
```

**三种修复方案（语义不同，按需求选）：**

```sql
-- 方案 A：显式补 NULL（最直白，跨库通用）
SELECT * FROM emp WHERE dept <> '销售' OR dept IS NULL;

-- 方案 B：空安全比较 <=>（MySQL / PostgreSQL 写法最简）
SELECT * FROM emp WHERE NOT (dept <=> '销售');
# <=> 对 NULL 也返回确定的 0/1，(NULL <=> '销售') = 0，NOT 0 = 1 → 钱七入选 ✓

-- 方案 C：COALESCE 把 NULL 映射成一个哨兵值后再比较
SELECT * FROM emp WHERE COALESCE(dept, '未知') <> '销售';
# 注意：方案 C 在"哨兵值恰好等于目标值"时会出错
```

> ==选型要点==：方案 A 保留 3VL 语义（"我不知道钱七是不是销售"），方案 B/C 强制二值化（"钱七就当不是销售"）。
> 业务上必须明确：**"部门未知"算不算"不是销售部"？** 这是需求问题，不是语法问题。

### Bug 2：`NOT IN` 遇到 NULL 子查询 → 结果恒空

这是最阴险的一个，**不报错、不警告，直接返回空集**。

```sql
CREATE TABLE customer(id INT, name VARCHAR(20));
INSERT INTO customer VALUES (1,'A'), (2,'B'), (3,'C');

CREATE TABLE orders(id INT, customer_id INT);
INSERT INTO orders VALUES (1, 1), (2, NULL);   -- 有一条脏数据 customer_id = NULL

-- 需求：找出没下过单的客户
SELECT * FROM customer WHERE id NOT IN (SELECT customer_id FROM orders);
# 返回 0 行！期望是 B、C
```

**为什么？** `NOT IN` 会展开成 AND 链：

```sql
-- id NOT IN (1, NULL) 等价于：
--   id <> 1 AND id <> NULL
-- 对 id=2：  (2<>1)=TRUE  AND  (2<>NULL)=UNKNOWN  →  TRUE AND UNKNOWN = UNKNOWN
-- 对 id=3：  同理 = UNKNOWN
-- WHERE 只留 TRUE → 全部丢弃
```

**对比：`IN` 不受影响**（因为 OR 遇真即为真）：

```sql
SELECT * FROM customer WHERE id IN (SELECT customer_id FROM orders);
# 正常返回 A —— id=1 匹配 TRUE，OR 链直接短路为真
```

**修复：**

```sql
-- ✅ 首选：NOT EXISTS，语义清晰且对 NULL 免疫（不构成"相等"即算通过）
SELECT * FROM customer c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- ✅ 兜底：先剔除 NULL
SELECT * FROM customer
WHERE id NOT IN (SELECT customer_id FROM orders WHERE customer_id IS NOT NULL);
```

> ==铁律==：**`NOT IN` + 子查询 = 定时炸弹**。子查询列上只要有 `NOT NULL` 约束才能用；否则一律用 `NOT EXISTS`。
> 另外注意：`NOT IN (1, 2, NULL)` 这种**字面量写法**同样会返回空集，不是子查询的问题。

### Bug 3：`= NULL` 永远查不到东西

```sql
SELECT * FROM emp WHERE dept = NULL;      # 0 行（应为 IS NULL）
SELECT * FROM emp WHERE dept IS NULL;     # 1 行：钱七 ✓
SELECT * FROM emp WHERE dept <=> NULL;    # 1 行：钱七 ✓（等价写法）
SELECT * FROM emp WHERE dept <> NULL;     # 0 行，同样不对
```

`= NULL` 是 SQL 里**唯一"永远为 UNKNOWN"** 的写法，永远不会返回任何行。

### Bug 4：`NOT` 与 `IS NOT TRUE` 不等价

```sql
-- 需求：找出"不完全满足 dept='销售'"的人（含 dept 未知的）
SELECT * FROM emp WHERE NOT (dept = '销售');        # 3、4
SELECT * FROM emp WHERE (dept = '销售') IS NOT TRUE;  # 3、4、5 ✓
```

| 表达式 | 钱七的结果 | 是否入选 |
|--------|-----------|---------|
| `dept = '销售'` | UNKNOWN | ❌ |
| `NOT (dept = '销售')` | UNKNOWN | ❌ |
| `(dept = '销售') IS TRUE` | FALSE | ❌ |
| `(dept = '销售') IS NOT TRUE` | **TRUE** | ✅ |

**规则**：`IS TRUE` / `IS NOT TRUE` / `IS FALSE` / `IS NOT FALSE` / `IS UNKNOWN` 会把 UNKNOWN **强制二值化**，永不返回 UNKNOWN。

> 注意：`WHERE a IS TRUE` 与 `WHERE a` 是**等价**的（都只留 TRUE）；但 `WHERE a IS NOT TRUE` 与 `WHERE NOT a` **不等价**。

## 五、优先级：AND > XOR > OR

MySQL 逻辑相关优先级（从高到低）：

| 优先级 | 运算符 |
|--------|--------|
| 高 | 比较运算 `=`、`<=>`、`>`、`<`、`<>`、`IS`、`LIKE`、`IN`、`BETWEEN` |
| ↓ | `NOT` |
| ↓ | `AND`、`&&` |
| ↓ | `XOR` |
| 低 | `OR`、`\|\|` |

**要点：`NOT` 低于比较运算，但高于 `AND`。**

```sql
NOT dept = '销售'          # 解析为 NOT (dept = '销售')，不是 (NOT dept) = '销售'
NOT a BETWEEN 1 AND 10     # 解析为 NOT (a BETWEEN 1 AND 10)
NOT a = 1 AND b = 2        # 解析为 (NOT (a=1)) AND (b=2)
```

### 经典 Bug：AND / OR 混用不加括号

```sql
-- 需求：销售部或研发部中，工资 > 10000 的人
SELECT * FROM emp
WHERE dept = '销售' OR dept = '研发' AND salary > 10000;

-- 实际解析（AND 优先）：
--   dept = '销售' OR (dept = '研发' AND salary > 10000)
-- 结果：所有销售部员工都被选入，哪怕工资只有 3000 —— 需求写错了
```

**正确写法（括号是义务，不是装饰）：**

```sql
SELECT * FROM emp
WHERE (dept = '销售' OR dept = '研发') AND salary > 10000;
```

> ==实战建议==：任何 `AND` 与 `OR` 共存的表达式，**一律加括号**。
> 没有人应该靠背优先级表来读懂 SQL；可读性比"我知道优先级"值钱得多。

## 六、德摩根定律：正确的条件改写

三值逻辑下，德摩根定律**依然成立**（对 TRUE/FALSE/UNKNOWN 全枚举验证通过）：

```
NOT (A AND B)  ≡  (NOT A) OR  (NOT B)
NOT (A OR  B)  ≡  (NOT A) AND (NOT B)
```

**用途：把 "NOT 大条件" 改成 "正面条件"，让 SQL 更可读、更容易走索引。**

```sql
-- 需求：排除"销售部且工资 > 10000"的人
-- 写法 1（直译需求，可读）
SELECT * FROM emp WHERE NOT (dept = '销售' AND salary > 10000);

-- 写法 2（德摩根展开，MySQL 实际执行形态）
SELECT * FROM emp WHERE dept <> '销售' OR salary <= 10000;

-- 写法 3（真正的意图，把 NULL 语义显式化）
SELECT * FROM emp
WHERE (dept IS NULL OR dept <> '销售') OR salary <= 10000;
```

**三个写法的结果对比（用上面的 5 行数据）：**

| id | dept | salary | 写法1 | 写法2 | 写法3 |
|----|------|--------|-------|-------|-------|
| 1 | 销售 | 8000 | ✅ | ✅ | ✅ |
| 2 | 销售 | 12000 | ❌ | ❌ | ❌ |
| 3 | 研发 | 15000 | ✅ | ✅ | ✅ |
| 4 | 研发 | 9000 | ✅ | ✅ | ✅ |
| 5 | NULL | 7000 | ✅ | ✅ | ✅ |

> 本例中写法 2 恰好正确，**纯属运气**（钱七的 `salary <= 10000` 为 TRUE，把 UNKNOWN 救回来了）。
> 若把写法 3 的意图套到 "dept 为 NULL 且 salary=20000" 的行上，写法 2 会返回 UNKNOWN 丢行，写法 3 会保留。
>
> ==结论==：德摩根帮你**重写形式**，但不解决 **NULL 语义**；涉及 NULL 的列必须显式 `IS NULL` / `IS NOT NULL` 表态。

## 七、短路求值：不要依赖

MySQL 的表达式求值器**通常**对 `AND`/`OR` 做从左到右的短路：

```sql
SELECT 1 WHERE TRUE OR (SELECT COUNT(*) FROM huge_table WHERE ...);
# 实践中右侧子查询往往被跳过
```

**但优化器有权重排、拆分 WHERE 条件**（例如按选择率排序、条件下推、索引条件下推 ICP），因此**书面语义上不保证求值顺序**。

```sql
-- ❌ 危险：想靠 AND 短路避免除零/报错
SELECT * FROM t WHERE b <> 0 AND a / b > 1;
# 优化器可能先算 a/b。虽然 MySQL 的 a/0 在 SELECT 中返回 NULL 不报错，
# 但会污染 warning，且换到严格模式或别的数据库就直接抛错。

-- ✅ 安全：用 CASE（CASE 的分支是真正惰性的）
SELECT * FROM t WHERE CASE WHEN b <> 0 THEN a / b ELSE 0 END > 1;

-- ✅ 更简洁：把 0 转成 NULL
SELECT * FROM t WHERE a / NULLIF(b, 0) > 1;
```

> ==铁律==：**任何带副作用的逻辑（可能报错、可能产生 warning、有性能代价）都不能靠逻辑运算符短路来保护。**
> 依赖 `AND` 顺序写业务逻辑，等于把正确性押在优化器的实现细节上。

## 八、XOR 的用途：判断"恰好一个成立"

`XOR` 在业务里对应"**互斥**"语义，写得比 `(a AND NOT b) OR (NOT a AND b)` 直观得多。

```sql
-- 需求：订单状态必须"已付款"和"已发货"恰好其一（不允许同时、也不允许都没有）
SELECT * FROM orders WHERE paid = 1 XOR shipped = 1;

-- 等价写法（跨库通用）
SELECT * FROM orders WHERE (paid = 1) <> (shipped = 1);
```

> MySQL 中 `a XOR b` ≡ `a <> b`（对布尔值）。所以 **XOR 可以完全用 `<>` 替代**，后者跨库更通用。

**XOR 的 NULL 陷阱：**

```sql
SELECT (1 = 1) XOR (bonus IS NOT NULL) FROM emp WHERE id = 2;
# 李四：TRUE XOR FALSE = TRUE ✓

SELECT TRUE XOR NULL;  # NULL  ← 只要有一边 UNKNOWN，XOR 就 UNKNOWN
```

因为没有「TRUE 吞掉一切」的传播规则，**XOR 对 NULL 的敏感度远高于 AND/OR**，用 XOR 前务必先 `COALESCE` 二值化：

```sql
SELECT * FROM orders WHERE (paid = 1) XOR (shipped = 1);   -- 若 shipped 有 NULL，结果不可控
SELECT * FROM orders WHERE COALESCE(paid,0) XOR COALESCE(shipped,0);  -- 显式二值化
```

## 九、性能：`OR` / `NOT` 与索引失效

逻辑运算符本身不慢，慢的是它们**破坏 sargability（可搜索性）**。

```sql
-- ❌ OR 跨列：通常无法用单索引，优化器要么全表扫描，要么走 index_merge（代价常常更高）
SELECT * FROM emp WHERE dept = '销售' OR salary > 10000;

-- ✅ 改写成 UNION
--    注意用 UNION 而非 UNION ALL：OR 不会产生重复行，
--    而 UNION 的隐式去重恰好对齐这个语义（两边都命中的行只出现一次）
SELECT * FROM emp WHERE dept = '销售'
UNION
SELECT * FROM emp WHERE salary > 10000;
```

```sql
-- ✅ 同一列上的 OR：优化器会改写成 IN，可以正常走索引
SELECT * FROM emp WHERE dept = '销售' OR dept = '研发';
# 优化器等价改写为 dept IN ('销售','研发') —— B+Tree 连续区间扫描

-- ✅ a = 1 OR a IS NULL：range 优化器支持 IS NULL，照样走索引
SELECT * FROM emp WHERE dept = '销售' OR dept IS NULL;
```

```sql
-- ❌ <> / != / NOT IN：无法映射为 B+Tree 的连续区间
SELECT * FROM emp WHERE dept <> '销售';
# 只能全表扫描或全索引扫描 + 过滤，代价远高于 =。这是"反条件"的固有代价。

-- ❌ 对列做运算/函数 → 索引失效（与逻辑运算符无关，但经常一起出现）
SELECT * FROM emp WHERE UPPER(dept) = '销售';
```

**索引使用对照表：**

| 条件写法 | 能否走索引 | 说明 |
|----------|-----------|------|
| `a = 1 AND b = 2` | ✅ | 单列索引走一个；复合索引 `(a,b)` 最优 |
| `a = 1 OR a = 2` | ✅ | 优化器改写为 `a IN (1,2)` |
| `a = 1 OR a IS NULL` | ✅ | range 优化器支持 `IS NULL` |
| `a = 1 OR b = 2`（不同列） | ⚠️ | 需 `index_merge`，通常不如改写为 `UNION` |
| `a <> 1` / `a NOT IN (...)` | ❌ | 非连续区间，退化为扫描 |
| `a IS NULL` | ✅ | NULL 在 MySQL B+Tree 中正常存储 |
| `a = NULL` | ❌ | 恒为空，优化器直接短路 |

> ==复合索引与 AND 的顺序==：`WHERE a = 1 AND b = 2` 用索引 `(a,b)` 时，
> 优化器会自动选择把哪一列作为前导，**你写的顺序不影响结果**（但影响可读性）。
> 真正的规则是**最左前缀**：`WHERE b = 2` 单独出现时，索引 `(a,b)` 用不上。

## 十、布尔值的本质与其他细节

**1. 逻辑表达式就是 0/1 整数：**

```sql
SELECT 1 = 1, 1 = 2, TRUE, FALSE;       # 1  0  1  0
SELECT (1 = 1) + (2 = 2);               # 2
SELECT TRUE + TRUE;                     # 2
SELECT SUM(dept = '销售') FROM emp;      # 2   ← 计数技巧，等价 COUNT(CASE WHEN ...)
```

**2. 非布尔值参与逻辑运算时按「真值性」转换**（非 0 即 TRUE）：

```sql
SELECT 2 AND 3;      # 1
SELECT 0 AND 1;      # 0
SELECT 5 OR 0;       # 1
SELECT 'abc' AND 1;  # 0   ← 'abc' 隐式转数字得 0（FALSE），并抛 warning
SELECT 0.0 OR 0;     # 0
```

**3. 聚合函数忽略 NULL，逻辑运算符不忽略** —— 这是两套规则：

```sql
SELECT SUM(bonus) FROM emp;             # 3000   ← 跳过 3 个 NULL
SELECT SUM(bonus > 500) FROM emp;       # 2      ← 只有张三、赵六给出确定结果，3 个 NULL 行被跳过
```

**4. `BETWEEN` 里的 `AND` 是语法的一部分，不是逻辑运算符：**

```sql
WHERE a BETWEEN 1 AND 10 AND b = 2
# 解析为 (a BETWEEN 1 AND 10) AND (b = 2)  ✓

WHERE NOT a BETWEEN 1 AND 10
# 解析为 NOT (a BETWEEN 1 AND 10)  ✓  （BETWEEN 优先级高于 NOT）

# ⚠️ BETWEEN 对 NULL 也返回 UNKNOWN：1 BETWEEN NULL AND 10  →  NULL
```

**5. `IF(cond, a, b)` 把 UNKNOWN 当 FALSE 处理**（3VL 在流程控制里的泄漏点）：

```sql
SELECT IF(NULL, 'yes', 'no');            # 'no'
SELECT IF(1 = NULL, 'yes', 'no');        # 'no'
SELECT CASE WHEN NULL THEN 'y' ELSE 'n' END;  # 'n'
# 对比：NULL 本身不等于 FALSE
SELECT NULL = FALSE;                     # NULL  ← 不是 1！
```

> 含义：`IF(cond, a, b)` 与 `CASE WHEN cond THEN a ELSE b END` 行为一致，
> 都把 UNKNOWN 归入 ELSE 分支。**写业务判断时，UNKNOWN 会被静默当成"否"**，要特别警惕。

**6. `1=1` 惯用法（动态 SQL 拼接）：**

```sql
-- 拼接 WHERE 时先写一个恒真条件，后续统一用 AND 追加，避免判断"是不是第一个条件"
SELECT * FROM emp WHERE 1 = 1 AND dept = '销售' AND salary > 5000;
```

## 十一、跨数据库差异

| 特性 | MySQL | PostgreSQL | SQL Server | Oracle |
|------|-------|-----------|-----------|--------|
| 三值逻辑 / UNKNOWN | ✅ | ✅ | ✅ | ✅ |
| `NOT IN` 遇 NULL 返空 | ✅ | ✅ | ✅ | ✅ |
| 布尔字面量 | `TRUE`/`FALSE` = 1/0 | 真布尔类型 `boolean` | ❌ 用 `1`/`0` | ❌ SQL 层无布尔类型 |
| 空安全比较 | `<=>` | `IS NOT DISTINCT FROM` | ❌（用 `ISNULL` 组合） | ❌（用 `DECODE`） |
| `IS TRUE` / `IS UNKNOWN` | ✅ | ✅ | ❌ | ❌ |
| `XOR` | ✅ | ❌（用 `<>`） | ❌（`^` 是位异或） | ❌ |
| `\|\|` 的含义 | 逻辑 **OR** | 字符串**拼接** | 逻辑 **OR** | 字符串**拼接** |
| `&&` / `!` 别名 | ✅ | ❌ | ❌ | ❌ |
| 布尔值参与算术 | ✅ `TRUE+1=2` | ❌ 需 `::int` | ✅（bit） | ❌ |

> **`||` 是最容易跨库翻车的运算符**：`WHERE name = 'a' || 'b'` 在 PostgreSQL 里是拼接字符串，
> 在 MySQL 里是 `name='a' OR 'b'`——后者 `'b'` 转数字为 0，等价于 `name='a' OR FALSE`，
> **不报错但结果完全错误**。所以：**永远不要用 `||` 表示逻辑或**，写 `OR`。

## 十二、实战案例

### 案例 1：多条件筛选的分组错误（占比最高的事故）

```sql
-- 需求：查"研发部"或"销售部中，入职超过 3 年"的员工
-- ❌ 错误写法
SELECT * FROM emp
WHERE dept = '研发' OR dept = '销售' AND hire_date < DATE_SUB(NOW(), INTERVAL 3 YEAR);

-- ✅ 正确写法：需求描述里的"或"和"且"边界要靠括号显式划出来
SELECT * FROM emp
WHERE dept = '研发'
   OR (dept = '销售' AND hire_date < DATE_SUB(NOW(), INTERVAL 3 YEAR));

-- ✅ 更清晰：用 IN 收敛同类条件，再用括号包住"或"组
SELECT * FROM emp
WHERE dept IN ('研发', '销售')
  AND (dept = '研发' OR hire_date < DATE_SUB(NOW(), INTERVAL 3 YEAR));
```

> 排错技巧：**把 `WHERE` 条件逐个改写成一列 0/1，用 `SELECT` 看真值**，比盯着 SQL 猜快十倍。
>
> ```sql
> SELECT id, dept,
>        (dept = '研发')                  AS c1,
>        (dept = '销售')                  AS c2,
>        (hire_date < DATE_SUB(NOW(), INTERVAL 3 YEAR)) AS c3,
>        (dept = '研发' OR dept = '销售' AND hire_date < DATE_SUB(NOW(), INTERVAL 3 YEAR)) AS final
> FROM emp;
> ```

### 案例 2：用 `<=>` 做"变更检测"（CHANGE 场景）

```sql
-- 前后端比对时，NULL 与 NULL 应视为"未变更"。用 = 会误判为 UNKNOWN
SELECT * FROM product_staging s
JOIN product p ON p.id = s.id
WHERE NOT (s.name <=> p.name)     -- 名称真的变了
   OR NOT (s.price <=> p.price)   -- 或价格真的变了
   OR NOT (s.tags <=> p.tags);    -- 或标签（可能为 NULL）真的变了
```

### 案例 3：`NOT IN` 事故的完整复盘

```sql
-- 现场：报表"本月未下单客户"始终为空，业务方以为全部客户都下单了

-- ❌ 原始 SQL
SELECT * FROM customer
WHERE id NOT IN (SELECT customer_id FROM orders WHERE order_date >= '2024-01-01');
-- 根因：orders.customer_id 允许 NULL（未登录下单），NULL 进入 NOT IN 列表 → 恒空

-- ✅ 修复 1：NOT EXISTS（推荐，且能利用外键/索引）
SELECT * FROM customer c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.id AND o.order_date >= '2024-01-01'
);

-- ✅ 修复 2：LEFT JOIN ... IS NULL（性能最好，语义等价）
SELECT c.* FROM customer c
LEFT JOIN orders o
       ON o.customer_id = c.id AND o.order_date >= '2024-01-01'
WHERE o.id IS NULL;

-- ✅ 修复 3：把 NULL 排除掉（最快，但依赖于"NULL 无业务含义"）
SELECT * FROM customer
WHERE id NOT IN (SELECT customer_id FROM orders
                 WHERE order_date >= '2024-01-01' AND customer_id IS NOT NULL);
```

> ==复盘要点==：这个 Bug **不会报错、不会警告、EXPLAIN 也一切正常**，
> 唯一防线是**用真实数据跑一遍、核对行数**。任何 `NOT IN` 上线前都要人工确认子查询列可为 NULL。

### 案例 4：软删除 + 多状态筛选（真实业务组合）

```sql
-- 需求：查有效订单，状态为"待付款"或"已付款"，且金额 > 100，且不属于测试账户
SELECT * FROM orders
WHERE deleted_at IS NULL                              -- 软删除：必须用 IS NULL
  AND status IN ('PENDING', 'PAID')                   -- 同列多值用 IN，可走索引
  AND amount > 100
  AND NOT (user_name LIKE 'test%');                   -- NOT + LIKE
```

**两个反模式提醒：**

```sql
-- ❌ 反模式 1：用 NOT 包住整块条件，NULL 列会集体寄掉
WHERE NOT (status = 'CANCELLED' AND user_name LIKE 'test%')
-- → 等价于 status <> 'CANCELLED' OR user_name NOT LIKE 'test%'
--   status 为 NULL 的订单全部丢失。应显式写：
WHERE (status IS NULL OR status <> 'CANCELLED') OR user_name NOT LIKE 'test%'

-- ❌ 反模式 2：用 OR 跨列，索引失效
WHERE status = 'PENDING' OR amount > 1000
-- → 若无 index_merge，退化为全表扫描。改 UNION 或拆查询
```

## 十三、速查小结

1. **SQL 是三值逻辑**：TRUE / FALSE / **UNKNOWN**。UNKNOWN 来自 NULL 的比较与运算。
2. ==`WHERE` 只保留 TRUE==，FALSE 和 UNKNOWN 一起被丢弃 —— 所有坑的总根源。
3. 口诀：**`AND` 遇假即为假，`OR` 遇真即为真，`NOT UNKNOWN` 还是 UNKNOWN**。
4. `<>` / `!=` / `NOT` / `NOT IN` 遇到 NULL 都会"吞行"。修复三件套：`IS NULL`、`<=>`、`NOT EXISTS`。
5. ==`NOT IN` + 可为 NULL 的子查询 = 恒返回空集==，铁律是改用 `NOT EXISTS`。
6. `= NULL` 永远为 UNKNOWN，永远查不到；用 `IS NULL` 或 `<=> NULL`。
7. `NOT a` 与 `a IS NOT TRUE` **不等价**；后者会把 UNKNOWN 转为 TRUE。
8. 优先级：比较运算 > `NOT` > `AND` > `XOR` > `OR`。**AND/OR 混用一律加括号**。
9. 德摩根定律在 3VL 下成立，能帮你改写形式，但**不解决 NULL 语义**。
10. **不要依赖短路求值**；需要惰性求值就用 `CASE` 或 `NULLIF`。
11. `XOR` 对 NULL 极敏感，业务上可用 `(a) <> (b)` 替代以跨库通用。
12. 索引友好度：`=` / `IN` / `IS NULL` ✅；`<>` / `NOT IN` / 跨列 `OR` ❌。

## 十四、常见面试题

**Q1：为什么 `WHERE col <> 'x'` 查不出 `col` 为 NULL 的行？**
> 因为 `NULL <> 'x'` 的结果是 **UNKNOWN** 而非 TRUE，而 `WHERE` 只保留 TRUE 的行。修复：`OR col IS NULL`、`NOT (col <=> 'x')`，或 `COALESCE(col,'') <> 'x'`（需确保哨兵值不冲突）。

**Q2：`NULL AND FALSE`、`NULL OR TRUE` 分别等于什么？**
> `NULL AND FALSE` = **FALSE**（0），`NULL OR TRUE` = **TRUE**（1）。规律是「AND 遇假即为假，OR 遇真即为真」。其余组合中只要结果不能由已知操作数确定，就是 NULL（UNKNOWN）。

**Q3：`WHERE id NOT IN (SELECT customer_id FROM orders)` 为什么可能永远返回空？**
> 若 `orders.customer_id` 含 NULL，`NOT IN` 展开为 `id<>a AND id<>b AND id<>NULL`，最后一项恒为 UNKNOWN，整条 AND 链无法得到 TRUE，故所有行被 `WHERE` 丢弃。改用 `NOT EXISTS` 或先过滤 NULL。

**Q4：`NOT (a = 1)` 和 `(a = 1) IS NOT TRUE` 有什么区别？**
> 当 `a` 为 NULL 时：前者为 UNKNOWN（被 `WHERE` 丢弃），后者为 TRUE（行被保留）。`IS NOT TRUE` 把 UNKNOWN 明确归类为"非真"，实现了二值化。

**Q5：`SELECT * FROM t WHERE a = 1 OR b = 2 AND c = 3` 怎么解析？**
> `AND` 优先级高于 `OR`，解析为 `a = 1 OR (b = 2 AND c = 3)`。若意图是 `(a=1 OR b=2) AND c=3`，必须加括号 —— 这是最常见的 SQL 逻辑错误。

**Q6：为什么 `WHERE a = 1 OR b = 2` 会导致索引失效，而 `WHERE a = 1 OR a = 2` 不会？**
> 同列的 `OR` 会被优化器改写为 `a IN (1,2)`，是 B+Tree 上的连续区间扫描；跨列 `OR` 需要 `index_merge` 或多个索引分别扫描后合并去重，代价通常高于全表扫描，因此优化器常常放弃索引。跨列 `OR` 建议改写为 `UNION`。

**Q7：德摩根定律在三值逻辑下还成立吗？**
> 成立。对 A、B 各自取 TRUE/FALSE/UNKNOWN 共 9 种组合全枚举，`NOT(A AND B) ≡ NOT A OR NOT B` 均成立。但要注意：**它只保证形式等价，不解决 NULL 语义**。若业务要求"把 NULL 也纳入某一边"，仍需显式 `IS NULL`。

**Q8：能不能靠 `AND` 的短路求值避免除零报错？**
> 不能。优化器可以重排/拆分 `WHERE` 条件，SQL 标准也不保证求值顺序。正确做法是用 `CASE WHEN b <> 0 THEN a/b END`（分支真正惰性）或 `a / NULLIF(b, 0)`（把 0 转为 NULL）。

**Q9：`SELECT * FROM t WHERE NULL` 返回什么？**
> 返回 **0 行**。`NULL` 作为条件求值为 UNKNOWN，被 `WHERE` 丢弃。而 `WHERE NULL OR TRUE` 返回全表，因为 OR 遇真即为真。

**Q10：一条 WHERE 里既有 `IN` 又有 `NOT IN`，`NOT IN` 那个一定有问题吗？**
> 不一定。若 `NOT IN` 的列表是**字面量且不含 NULL**、或子查询列有 `NOT NULL` 约束，则安全。风险只来自"列表里可能混入 NULL"。工程上建议统一用 `NOT EXISTS` 消除这类隐性依赖。
