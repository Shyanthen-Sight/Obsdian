# CREATE VIEW —— 创建视图

> [!abstract] 一句话
> 视图（View）是**一条保存下来的 `SELECT` 语句**：外表像表，底层不存数据；每次查询视图，MySQL 都实时执行它背后的查询。

---

## 一、视图到底是什么

```sql
CREATE VIEW v_student_public AS
SELECT id, stu_no, name, gender, class_id
FROM student;
```

创建完成后，可以像查表一样查它：

```sql
SELECT * FROM v_student_public WHERE gender = 'F';
```

但数据库里**并没有多出一张叫 `v_student_public` 的数据表**，只多了一条"视图定义"（保存在数据字典中）。视图的行和列都来自基表，用到时才计算。

### 1.1 视图 vs 基表

| 对比项 | 基表（Base Table） | 视图（View） |
| --- | --- | --- |
| 是否存数据 | ✅ 实际存储行数据 | ❌ 只存 `SELECT` 定义 |
| 占用空间 | 数据 + 索引 | 仅元数据 |
| 能否建索引 | ✅ | ❌ MySQL 不允许 |
| 能否建触发器 | ✅ | ❌ MySQL 不支持 `INSTEAD OF` 触发器 |
| 能否 `INSERT/UPDATE/DELETE` | ✅ | 仅**可更新视图**可以 |
| 删除后影响 | 数据、结构全没 | 只删定义，基表不受影响 |
| 结果是否缓存 | — | ❌ 每次实时计算，不是物化视图 |

> [!warning] 视图不是"性能优化"
> 视图不会把结果缓存起来，也不会自动变快。它省的是**写 SQL 的重复**，不是**查询的时间**。
> 复杂聚合视图甚至可能更慢，见 §八 的 `TEMPTABLE`。

### 1.2 命名空间：表名和视图名不能重复

同一个数据库里，**基表和视图共享同一套名字**：

```sql
CREATE TABLE v_student_public (id INT);  -- 若同名视图已存在 → ERROR 1050
```

因此视图命名建议统一加前缀 `v_`，一眼区分"这是视图，不是表"。

## 二、语法骨架

```sql
CREATE
    [OR REPLACE]
    [ALGORITHM = {UNDEFINED | MERGE | TEMPTABLE}]
    [DEFINER = 'user'@'host']
    [SQL SECURITY {DEFINER | INVOKER}]
    VIEW 视图名 [(列名1, 列名2, ...)]
    AS 查询语句
    [WITH [CASCADED | LOCAL] CHECK OPTION];
```

| 部分                  | 是否必须 | 说明                        |
| ------------------- | ---- | ------------------------- |
| `CREATE VIEW 视图名`   | ✅    | 视图名可与库名限定：`db.v_name`     |
| `AS 查询语句`           | ✅    | 绝大多数 `SELECT` 都行，也可嵌套其他视图 |
| `OR REPLACE`        | ❌    | 视图已存在时覆盖定义，详见 [[修改视图]]    |
| `ALGORITHM`         | ❌    | 视图的处理算法，默认 `UNDEFINED`    |
| `DEFINER`           | ❌    | 视图的"定义者"，默认当前用户           |
| `SQL SECURITY`      | ❌    | 执行时按谁的身份校验权限，默认 `DEFINER` |
| `(列名...)`           | ❌    | 显式指定视图的列名                 |
| `WITH CHECK OPTION` | ❌    | 限制通过视图写入的行，见 §七           |

最小可用写法：

```sql
CREATE VIEW v_student_basic AS
SELECT id, stu_no, name FROM student;
```

> [!tip] 列一定要写清楚，不要 `SELECT *`
> 视图定义在**创建那一刻就"冻结"**了。用 `SELECT *` 建视图，之后基表新增的列**不会**自动出现在视图里；基表删列，查询视图则直接报 `ERROR 1356`。
> 想要新列 → 必须重建/修改视图定义。

## 三、三个常用例子

### 3.1 单表：只暴露部分列

```sql
CREATE VIEW v_student_public AS
SELECT id, stu_no, name, gender, class_id
FROM student;
-- 不给 age、不给其他敏感字段
```

### 3.2 多表 JOIN：把复杂连接藏起来

```sql
CREATE VIEW v_student_class AS
SELECT s.id        AS student_id,
       s.stu_no,
       s.name      AS student_name,
       c.name      AS class_name
FROM student s
LEFT JOIN class c ON s.class_id = c.id;
```

之后业务只需要：

```sql
SELECT * FROM v_student_class WHERE class_name = '软件 1 班';
```

### 3.3 聚合：把统计口径固定下来

```sql
CREATE VIEW v_class_stat AS
SELECT c.id                          AS class_id,
       c.name                        AS class_name,
       COUNT(s.id)                   AS student_count,
       ROUND(AVG(sc.score), 1)       AS avg_score
FROM class c
LEFT JOIN student s ON s.class_id = c.id
LEFT JOIN sc       ON sc.sid      = s.id
GROUP BY c.id, c.name;
```

```sql
SELECT * FROM v_class_stat WHERE avg_score > 80;
```

> [!note] 聚合视图是只读的
> 含 `GROUP BY` / 聚合函数的视图不能 `INSERT/UPDATE/DELETE`，强行写入报 `ERROR 1288`（UPDATE/DELETE）或 `ERROR 1471`（INSERT）。原因见 §六。

## 四、列名规则

### 4.1 视图列名必须唯一

`SELECT` 里两列重名，创建视图会失败（`Duplicate column name`）：

```sql
-- ❌ student 和 class 都有 name
CREATE VIEW v_bad AS
SELECT s.name, c.name
FROM student s JOIN class c ON s.class_id = c.id;

-- ✅ 起别名
CREATE VIEW v_ok AS
SELECT s.name AS student_name, c.name AS class_name
FROM student s JOIN class c ON s.class_id = c.id;
```

### 4.2 表达式列必须起别名

```sql
-- ❌ 列名会变成 "COUNT(*)" 这种表达式文本，引用时要反引号，非常难用
CREATE VIEW v_bad2 AS SELECT COUNT(*) FROM student;

-- ✅
CREATE VIEW v_ok2 AS SELECT COUNT(*) AS total FROM student;
```

> [!warning] 别名最长 64 个字符
> 视图列名按**列名上限 64** 检查，而不是别名上限 256。表达式不写别名时，默认列名就是表达式原文，过长会直接建失败，也会让 `mysqldump` 出来的定义无法重新导入。

### 4.3 列清单：给外部一个稳定的接口

```sql
CREATE VIEW v_score (student_no, student_name, score) AS
SELECT s.stu_no, s.name, sc.score
FROM student s
JOIN sc ON sc.sid = s.id;
```

- 列清单的数量**必须等于** `SELECT` 的列数，否则报 `ERROR 1353`
- 适合"基表列名会变，但视图对外承诺不变"的场景
- 顺序按列清单走，和 `SELECT` 的书写顺序一一对应

## 五、视图的四个作用

| 作用 | 说明 | 典型场景 |
| --- | --- | --- |
| **简化查询** | 把多表 JOIN、聚合封装成一个名字 | 报表 SQL、频繁复用的复杂查询 |
| **数据安全** | 只暴露部分行/列，隐藏敏感字段 | 学生表只给看姓名学号，不给看身份证 |
| **逻辑独立性** | 基表拆分、改名后，用视图兼容旧 SQL | 订单表拆成主表+明细，旧接口仍查 `v_order` |
| **统一口径** | 指标定义只写一处 | "平均分""活跃用户"全公司用同一个视图 |

```sql
-- 安全示例：只把视图的查询权给业务账号，不给基表
GRANT SELECT ON school.v_student_public TO 'app_user'@'%';
-- 不授予 student 表的任何权限
```

> [!tip] 视图安全的前提是 `SQL SECURITY`
> 默认 `SQL SECURITY DEFINER`：调用者只要有视图的 `SELECT` 权限，就能通过视图读基表。
> 如果改成 `INVOKER`，调用者还必须**自己拥有基表权限**，视图就不再是"权限收口"的工具了。详见 §十。

## 六、可更新视图

视图能不能写入，不取决于你的意愿，而取决于它的定义是否与基表**逐行一一对应**。

### 6.1 这些视图不可更新（只读）

只要包含以下任一构造，视图就是只读的：

- 聚合函数（`SUM` / `COUNT` / `AVG` / `MIN` / `MAX` …）或窗口函数
- `DISTINCT`
- `GROUP BY` / `HAVING`
- `UNION` / `UNION ALL`
- `SELECT` 列表里的子查询
- 某些 `JOIN`（外连接；多表视图只有在 `MERGE` + 内连接时才可能更新，且一次只能改其中一张表）
- `FROM` 中引用了另一个不可更新视图
- `WHERE` 子查询引用了 `FROM` 中的表
- 只引用字面量、不引用任何基表
- `ALGORITHM = TEMPTABLE`
- 同一基表列被引用多次（`INSERT` 不允许；`UPDATE` / `DELETE` 可以）

### 6.2 想 `INSERT`，还要额外满足

- 视图列名不重复
- 视图包含基表中**所有没有默认值的列**
- 视图列必须是**简单列引用**，不能是 `col1 + 3`、`UPPER(col2)`、常量、子查询等表达式

```sql
-- 可更新：简单列映射
CREATE VIEW v_student_upd AS
SELECT id, stu_no, name, age, class_id FROM student;

UPDATE v_student_upd SET age = 19 WHERE id = 1;   -- ✅ 改的是 student
INSERT INTO v_student_upd (stu_no, name) VALUES ('2026001', '张三');  -- ✅

-- 只读：含聚合
CREATE VIEW v_class_stat AS
SELECT class_id, COUNT(*) AS cnt FROM student GROUP BY class_id;

UPDATE v_class_stat SET cnt = 10;   -- ❌ ERROR 1288
INSERT INTO v_class_stat VALUES (1, 10);  -- ❌ ERROR 1471
```

### 6.3 查一个视图能不能更新

```sql
SELECT TABLE_NAME, IS_UPDATABLE
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = DATABASE();
```

`IS_UPDATABLE = YES` 只代表 `UPDATE/DELETE` 可用，**不代表一定能 `INSERT`**（还要满足 6.2）。

> [!warning] 通过视图写入，约束仍然生效
> 视图只是查询的"壳"，写入最终落到基表。基表的 `NOT NULL`、`UNIQUE`、`CHECK`、外键一条都不会少。
> 反过来，触发器也不会因为走了视图就失效。

## 七、WITH CHECK OPTION

默认情况下，通过视图写入的行可以"写了却看不见"：

```sql
CREATE VIEW v_adult AS
SELECT id, name, age FROM student WHERE age >= 18;

INSERT INTO v_adult (id, name, age) VALUES (99, '张三', 10);
-- 插入成功，但 SELECT * FROM v_adult 查不到这一行
```

加上 `WITH CHECK OPTION` 后，MySQL 会拒绝"写入后不满足视图 `WHERE` 条件"的操作：

```sql
CREATE OR REPLACE VIEW v_adult AS
SELECT id, name, age FROM student WHERE age >= 18
WITH CHECK OPTION;

UPDATE v_adult SET age = 10 WHERE id = 1;   -- ❌ ERROR 1369: CHECK OPTION failed
INSERT INTO v_adult VALUES (99, '张三', 10); -- ❌ ERROR 1369
```

### `CASCADED` vs `LOCAL`

嵌套视图时才有区别：

```sql
CREATE VIEW v1 AS SELECT id, name, age FROM student WHERE age >= 18;
CREATE VIEW v2 AS SELECT * FROM v1 WHERE age <= 60
WITH LOCAL CHECK OPTION;
```

| 选项 | 校验范围 |
| --- | --- |
| `CASCADED`（默认） | 当前视图 + **所有底层视图**的条件都校验 |
| `LOCAL` | 只校验当前视图自己的条件，不主动检查底层视图 |

> [!warning] `CHECK OPTION` 只约束"以后"的写入
> 给已有视图加上它，**不会**回头清理基表里已经存在的不合规数据。那些行只是不出现在视图结果里。

## 八、ALGORITHM：视图怎么被执行

| 值 | 行为 | 特点 |
| --- | --- | --- |
| `MERGE` | 把视图定义**合并进**外层查询 | 通常最快；可用基表索引；可更新 |
| `TEMPTABLE` | 先把视图结果放进临时表，再查 | 有物化开销；**不可更新**；用不上基表索引 |
| `UNDEFINED`（默认） | 能 `MERGE` 就 `MERGE`，否则物化 | 大多数情况的最优解 |

`MERGE` 的展开过程：

```sql
CREATE ALGORITHM = MERGE VIEW v_merge AS
SELECT id, name FROM student WHERE age >= 18;

SELECT * FROM v_merge WHERE id < 10;
-- 实际执行：
SELECT id, name FROM student WHERE age >= 18 AND id < 10;
```

> [!tip] 什么时候显式写 `TEMPTABLE`
> 1. 希望**尽早释放基表锁**（临时表建好后即可解锁）
> 2. 要绕开"不能在子查询里读、同时又在外部改同一张表"的限制
>
> 其余情况别手写 `TEMPTABLE`——它会让视图失去可更新性，也失去索引优势。

> [!note] 指定 `MERGE` 却合并不了
> 含聚合、`DISTINCT`、`GROUP BY`、`UNION`、`LIMIT` 等构造时无法合并。此时写 `ALGORITHM = MERGE` 会得到一条 warning，并自动降级为 `UNDEFINED`。

## 九、查看视图

```sql
-- 完整定义（含 ALGORITHM / DEFINER / SQL SECURITY / CHECK OPTION）
SHOW CREATE VIEW v_student_public\G

-- 当前库有哪些视图
SHOW FULL TABLES WHERE Table_type = 'VIEW';

-- 视图的元信息
SELECT TABLE_NAME,
       IS_UPDATABLE,
       CHECK_OPTION,      -- NONE / CASCADE / LOCAL
       DEFINER,
       SECURITY_TYPE,     -- DEFINER / INVOKER
       VIEW_DEFINITION
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = DATABASE();

-- 列结构
DESC v_student_public;
```

> [!info] 查看定义需要 `SHOW VIEW` 权限
> 只有 `CREATE VIEW` 和 `SELECT` 权限的用户，可能看得到视图、却执行不了 `SHOW CREATE VIEW`。备份账号尤其要注意补上 `SHOW VIEW`。

## 十、权限与 DEFINER

创建视图至少需要：

- 视图本身：`CREATE VIEW`
- `SELECT` 里引用的每一列：某种列级权限（通常是 `SELECT`）
- 若带 `OR REPLACE` 且视图已存在：还要视图上的 `DROP`

执行视图时按谁的身份校验基表权限，由 `SQL SECURITY` 决定：

| 模式 | 校验基表权限时用谁的身份 | 适用场景 |
| --- | --- | --- |
| `DEFINER`（默认） | 视图定义者 | 想让业务账号只拥有视图权限 |
| `INVOKER` | 调用视图的用户 | 想让权限严格跟随调用者 |

```sql
CREATE DEFINER = 'app_reader'@'%' SQL SECURITY DEFINER VIEW v_student_public AS
SELECT id, stu_no, name FROM student;
```

> [!failure] ERROR 1449：The user specified as a definer does not exist
> 把库从 A 服务器导到 B 服务器，视图定义里仍写着 A 上的 `'app_reader'@'%'`，但 B 上没这个账号。
> 解决：创建对应账号，或用 `ALTER VIEW ... DEFINER = 当前用户 ...` 改掉。**导入 dump 前先检查 definer**。

## 十一、常见报错与对策

| 报错 | 原因 | 对策 |
| --- | --- | --- |
| `ERROR 1050` Table already exists | 视图名与已有表/视图重名 | 换名，或用 `CREATE OR REPLACE VIEW` |
| `ERROR 1060` Duplicate column name | `SELECT` 中两列同名 | 给列起别名 |
| `ERROR 1353` View's SELECT and view's field list have different column counts | 列清单数量 ≠ `SELECT` 列数 | 一一对齐 |
| `ERROR 1356` View references invalid table(s) or column(s) | 基表被删/列被改名，或底层视图失效 | 修基表或重建视图 |
| `ERROR 1369` CHECK OPTION failed | 写入后的行不满足视图条件 | 调整数据或视图条件 |
| `ERROR 1449` definer does not exist | 定义者账号不存在 | 建账号或改 `DEFINER` |
| `ERROR 1288 / 1471` not updatable / not insertable-into | 对只读视图写入 | 改基表，或重写为可更新视图 |
| `ERROR 1347` is not BASE TABLE | 对视图用了 `ALTER TABLE` / `CREATE INDEX` | 用 `ALTER VIEW`；MySQL 视图不能建索引 |

> [!failure] ERROR 1356 是最常见的"视图坏了"
> 视图定义里引用的表或列不存在时，**创建视图不会报错**，直到你查询它才炸。
> 检查手段：`CHECK TABLE 视图名;`，或直接 `SELECT * FROM 视图名 LIMIT 0;`。

## 十二、建视图自查清单

- [ ] 视图名用 `v_` 前缀，避免和基表混淆
- [ ] 列逐个写出，不用 `SELECT *`
- [ ] 每个表达式列都有别名，且不超过 64 字符
- [ ] 需要对外稳定列名时，使用列清单
- [ ] 明确是否需要写入；只读就接受它只读
- [ ] 需要限制写入范围时加 `WITH CHECK OPTION`
- [ ] 需要"仅暴露部分数据"时，确认 `SQL SECURITY` 的语义
- [ ] 生产脚本显式写 `DEFINER`，避免迁移后 1449
- [ ] 视图层级别超过 2～3 层就停下来重新设计
- [ ] 不用视图替代索引或缓存，性能问题回基表解决

---

> [!quote] 一句话记忆
> **视图 = 存起来的 SELECT**：不存数据、实时计算、能查不一定能改；定义建好就冻结，`SELECT *` 尤其会坑你。
