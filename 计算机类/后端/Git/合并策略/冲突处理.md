# 冲突处理 —— 当同一处被两边都改过

> [!abstract] 一句话
> ==冲突（conflict）不是 Git 出错，而是它在说"**这里两边都动过，我不敢替你拍板，请你裁决**"==。它发生在 merge、rebase、cherry-pick、revert 等"整合两条改动线"的操作里。处理的本质只有三件事：**看清两边的意图 → 编辑出最终内容 → 标记已解决**。

> [!info] 先分清：冲突 ≠ 错误
> - 只有**同一处**（同一文件的相邻/重叠区域）被**两边同时修改**，才会冲突。
> - 只有一边改、另一边没动 → Git **自动采用**改动的那边，不打扰你。
> - 所以冲突恰恰说明"这处代码被认真对待过"，值得你花心思。

---

## 一、冲突从哪来

任何"把两条改动线拼起来"的操作都可能冲突：

| 操作 | 冲突含义 |
|---|---|
| `git merge` | 当前分支 vs 被合进来的分支 |
| `git rebase` | 你正在重放的提交 vs 目标分支已有内容 |
| `git cherry-pick` | 被挑的提交 vs 当前分支 |
| `git revert` | 反向改动 vs 现有内容 |
| `git stash pop` | 暂存的改动 vs 工作区现状 |
| `git pull` | 远程改动 vs 本地改动（本质是 fetch + merge/rebase） |

> [!tip] 冲突的本源
> 只要一句话：**两边都改了同一段**。理解这点，就理解了为什么"改不同文件"从不冲突，而"改同一文件的同一行"必然冲突。

## 二、冲突长什么样

### 2.1 状态层面

```bash
git status
```

会看到 `Unmerged paths`（未合并路径）区块，分两类：

```text
Unmerged paths:
  both modified:   src/app.js        # 两边都改了
  both added:      config/new.yml    # 两边都新建了同名文件
  deleted by us:   old.txt           # 你删了，对方改了
  deleted by them: legacy.js         # 对方删了，你改了
```

### 2.2 文件层面

Git 在冲突处插入**冲突记号**：

```text
<<<<<<< HEAD
当前分支（接收方）的版本
=======
要整合进来的那一侧的版本
>>>>>>> feature
```

> [!info] 记号怎么读
> - `<<<<<<< HEAD` 之下、`=======` 之上：==**"我方 / 当前 HEAD"**== 的内容。
> - `=======` 之下、`>>>>>>> feature` 之上：==**"对方"**==（被合入/rebase 的源头）的内容。
> - 多个冲突段会在同一文件里**重复出现多组**记号。
>
> 你的任务：**把整段替换成最终想要的样子**（保留一边、另一边，或二者融合），并**删掉那三行记号**。

> [!warning] 常见低级错误
> - 只删了一部分记号，留下 `>>>>>>>` 在文件里 → 代码报错。
> - 忘了 `git add` 就 commit → 未解决的文件不会被提交（会被拦下）。
> - 用 `--ours/--theirs` 无脑选一边而**没读懂两边意图** → 悄悄丢功能。

## 三、标准处理流程

```bash
# 1. 看冲突范围
git status
git diff --name-only --diff-filter=U      # 只列冲突文件清单

# 2. 逐个打开冲突文件，编辑成最终内容，删掉 <<<< ==== >>>> 记号
#    （或借助工具 / 整份取舍，见第四节）

# 3.（可选）确认自己改对了
git diff                                  # 看工作区改动
git diff --check                          # 检查是否还残留冲突记号

# 4. 标记为"已解决"
git add <解决好的文件>

# 5. 继续完成当前操作——注意命令随操作不同而不同：
git merge   --continue        # 若在 merge
git rebase  --continue        # 若在 rebase
git cherry-pick --continue    # 若在 cherry-pick
# 或者：merge/cherry-pick 情形下直接 git commit 也可以

git status                    # 确认不再有 Unmerged paths
```

> [!success] 成功标志
> `git status` 里 **`Unmerged paths` 消失**，操作完成。若在 merge，`git log --graph` 会出现合并提交。

> [!note] `--continue` 是哪个？
> merge、rebase、cherry-pick 各有各的 `--continue`。用错了会提示"没有进行中的操作"。拿不准就 `git status` 看它当前处于哪种状态。

## 四、快速取舍与可视化工具

### 4.1 整份采用一边

```bash
git checkout --ours   <文件>    # 采用"我方"的整份文件
git checkout --theirs <文件>    # 采用"对方"的整份文件
git add <文件>                  # 别忘 add
```

> [!warning] ⚠️ `--ours` / `--theirs` 在 merge 与 rebase 里**含义相反**
> - **merge 时**：`--ours` = **当前分支**（接收方），`--theirs` = 被合进来的分支。
> - **rebase 时**：Git 在"重放我的提交"，所以 ==**`--ours` 反而是 upstream（对方）一侧，`--theirs` 才是你正在重放的提交**==。
>
> 记不住就别用它，直接手改，或依赖 `git status` 给出的提示。这是最常踩的坑。

### 4.2 图形化工具

```bash
git mergetool                   # 用配置好的图形工具逐个解决
```

> [!tip] 用好 mergetool
> 它把"我方/对方/共同祖先/结果"四栏摆出来，比手改记号直观。
> 先配一次：`git config --global merge.tool <工具名>`，例如 vimdiff、meld、vscode。

### 4.3 记住解决方式（rerere）

```bash
git config --global rerere.enabled true
```

> [!info] rerere = reuse recorded resolution
> Git 记住你**曾经怎么解决**某个冲突；下次遇到同样的冲突**自动套用**。
> 对"反复 rebase 同一分支、每次都撞同样的冲突"特别省事。

## 五、继续 / 跳过 / 放弃

```bash
git merge       --continue     # 解决完，完成合并
git rebase      --continue     # 解决完，重放下一个提交
git rebase      --skip         # 跳过当前提交（当它已无意义）
git cherry-pick --continue     # 完成挑选

git merge       --abort        # 放弃合并，完整回到 merge 之前
git rebase      --abort        # 放弃 rebase，回到 rebase 之前
git cherry-pick --abort        # 放弃挑选
```

> [!success] 放弃是安全的
> `--abort` 把工作区和暂存区**完整还原**到该操作开始之前。搞乱了就大胆 abort，不会丢已提交的工作。
> 若是已经 commit 完才发现不对，用 [[Rebase]] 第八节的 `reflog` 找回。

## 六、减少冲突的日常习惯

> [!tip] 六个习惯
> 1. **勤同步**：常 `git pull --rebase`，别让分支偏离主干太久。
> 2. **小步提交、短命分支**：分支活得越短，撞车概率越低。
> 3. **分工分文件**：并行任务尽量别改同一批文件（对人对 AI 都成立）。
> 4. **合并前先看清**：`git diff main...feature`，心里有数再合。
> 5. **不格式大改**：一次提交里别混入无关的格式化/重排，那是冲突制造机。
> 6. **开 rerere**：反复撞同样的冲突时自动复用解法。

## 七、常见困惑

> [!question] 冲突解决到一半能先干别的吗？
> 别急着切分支（多数情况 Git 会拦住你）。真想暂离，可以先 `git stash` 或记下当前进度；更稳妥是**当场解决完**再走。

> [!question] 怎么确认没有残留的冲突记号？
> `git diff --check` 会标出残留的 `<<<<<<<` 等记号；`grep -rn "<<<<<<<" .` 也能扫一遍。

> [!question] 解决完发现解决错了，能重来吗？
> - 还没 commit：直接改文件、重新 `git add`。
> - 已经 commit：`git merge --abort` 已不适用（操作结束了），用 `git reset --hard <操作前的哈希>` 或 `reflog` 回退。

> [!question] 冲突文件里 `<<<<<<< HEAD` 中的 HEAD 是什么？
> 是**当前所在分支的提交**。merge 时它代表"接收方"；rebase 时，因为 HEAD 在被重放，记号会显示被重放的提交信息，读起来容易绕——**以 `git status` 的说明为准**。

> [!question] 两个人改同一个文件一定冲突吗？
> 不一定。只有**改到了同一处**（重叠的行区域）才冲突；改文件不同位置，Git 通常能自动合并。

> [!question] 能把冲突"交给工具自动选一边"全解决吗？
> 能（`--ours/--theirs`），但**危险**：它不判断语义，可能让某一方的完整功能被丢弃。==**默认为数不多的冲突，值得人读一遍。**==

---

> [!quote] 一句话记忆
> **冲突 = 同一处两边都改过，Git 请你当裁判**。三步：**看两边意图 → 编出最终内容、删掉记号 → `git add` 后 `--continue`**。==**记不住时：`--ours/--theirs` 在 merge 和 rebase 里是反的，宁可手改。**==
