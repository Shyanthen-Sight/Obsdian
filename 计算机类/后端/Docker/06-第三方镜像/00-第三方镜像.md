# 第三方镜像

大部分项目不需要从零造镜像。数据库、缓存、消息队列、CI 工具，官方镜像已经把初始化、配置加载、信号处理这些脏活做完了。会用别人的镜像，前提是会挑、会读文档、会看标签。

挑镜像时看几件事：

- 维护方：带 `Official Image` 标记的，或者 Docker 认证发布者；个人镜像先翻 Dockerfile 和更新记录
- 更新时间：一两年没动的镜像，基础系统大概率已经积累了一堆 CVE
- 标签：`latest` 不可复现，至少固定大版本，关键环境固定到 digest
- 架构：`docker manifest inspect` 看有没有 arm64，Apple Silicon 上尤其重要
- 默认行为：以什么用户跑、数据目录在哪、暴露哪些端口、需要哪些环境变量

挑之前可以先看镜像的默认配置：

```bash
docker image inspect redis:7-alpine \
  --format 'user={{.Config.User}} ports={{json .Config.ExposedPorts}}'
docker buildx imagetools inspect redis:7-alpine | grep -i platform
```

`Config.User` 为空表示默认 root，`ExposedPorts` 是镜像声明的端口；`imagetools` 能看到 amd64/arm64 等平台。两分钟就能判断这个镜像是否适合当前环境。

一个镜像的 README 通常比任何教程都准。数据目录写错、初始化变量拼错，容器照样启动，只是数据悄悄写进了可写层，等删容器的时候才发现。

另一个判断依据是 Dockerfile 是否公开。官方镜像的构建脚本在 GitHub 上可查，能看到它用什么基础镜像、装了什么包；源码不公开的镜像，等于把供应链交给陌生人。

[[01-数据库|数据库]] 和 [[02-命令行工具|命令行工具]] 是两个高频场景：前者重点在数据持久化和初始化顺序，后者重点在临时使用、别污染宿主环境。

这一阶段学完，应该能独立判断一个镜像能不能直接上生产、需要补哪些配置，以及出问题时从哪查起。镜像来源本身也是安全边界，Docker Hub 上的相似名字和重新打包的镜像不少，拉之前核对一下发布者。
