# 镜像安全

镜像是一堆只读层加一份配置，运行时会被解开并执行。基础镜像里的漏洞、装错的依赖、误提交的密钥，会原样进入每一个由它启动的容器。镜像安全要做的，是在构建和发布环节就把这些东西挡在门外。

## 从基础镜像和版本开始

优先官方镜像或可信维护者，固定版本甚至 digest。`nginx:latest` 今天和下周可能不是同一个东西，出问题时你连现场都复现不了。

```bash
docker pull nginx:1.27.3-alpine
docker inspect --format '{{index .RepoDigests 0}}' nginx:1.27.3-alpine
# nginx@sha256:8a5f4b... 用 digest 拉取，内容才真正不可变
```

Alpine 体积小、攻击面小，但 musl libc 与 glibc 的差异会带来兼容问题；distroless 更彻底，没有 shell 和包管理器，排障只能靠日志和临时调试容器。选哪种，取决于团队能否接受相应的运维方式。基础镜像不是越小越好，能持续打补丁的镜像才值得长期使用。

## 别把秘密烤进层里

`COPY . .` 很容易把 `.env`、私钥、`.git` 一起带进去。层是永久的，后面再用 `RUN rm` 删除也没用，文件仍留在前面的层里，`docker history` 和导出的镜像都能翻出来。先用 `.dockerignore` 挡住：

```dockerignore
.git
.env*
*.pem
node_modules
```

构建期确实需要凭据时，用 BuildKit 的 secret mount，它在构建时可见，不会落进层：

```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci --omit=dev
```

把 secret 直接挂成 `.npmrc`，命令结束后挂载消失，不会写进镜像层。`npm config set` 会把 token 落到用户配置文件里，反而可能把密钥留在层中。

运行期密钥应由编排平台注入环境变量或挂载文件，而不是写进镜像。另外，镜像里加 `USER app` 让进程以非 root 运行，这属于镜像和运行时都要管的交叉项。

## 扫描、签名与 SBOM

```bash
trivy image --severity HIGH,CRITICAL --ignore-unfixed my-app:1.0
docker scout cves my-app:1.0
```

看扫描结果别只盯总数，重点判断三件事：漏洞有没有修复版本、受影响的包是否真的会被加载、升级基础镜像能否一并解决。把扫描放进 CI，有修复版本的 HIGH/CRITICAL 直接失败；暂时没有修复的记录下来，别为了绿灯整包 ignore。

更严格的供应链会用 cosign 签名、syft 生成 SBOM，部署前校验签名，出事时按 SBOM 定位影响范围。小团队至少做到：镜像来自受控构建、扫描结果进流水线、发布标签不可变。

> [!warning] 扫描通过不等于安全
> 漏洞库有滞后，业务逻辑漏洞和错误配置同样扫不出来。扫描是底线，不是免死金牌。
