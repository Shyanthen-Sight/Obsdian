# 绑定挂载

绑定挂载把宿主机上的目录或文件直接映射进容器，没有中间层。改宿主文件，容器里立刻能看到；容器里写的文件，宿主的编辑器和 Git 也立刻能看到。开发时的热重载基本都靠它。

```bash
docker run --rm -it -p 3000:3000 \
  -v "$(pwd)":/app -w /app \
  node:20 sh -c 'npm install && npm run dev'
```

路径必须是绝对路径（compose 里可以写相对路径，由 compose 解析）。`-w /app` 把工作目录设过去，否则命令还在镜像默认目录里跑。

Node 项目很快会撞上依赖目录的问题：宿主机的 `node_modules` 是按宿主平台装的，挂进 Linux 容器里二进制不兼容；而且 macOS/Windows 上大量小文件跨文件系统读写很慢。常见做法是再用一个命名卷把容器内的依赖目录盖住：

```yaml
services:
  web:
    build: .
    volumes:
      - ./src:/app/src
      - node_modules:/app/node_modules
volumes:
  node_modules:
```

第一个是绑定挂载，只同步源码；第二个是命名卷，容器第一次启动时从镜像里拷出 `node_modules`，之后宿主目录里的那份完全不参与。这样既保留热重载，又避开平台和性能问题。

权限是另一个高频坑。容器里默认以 root 跑，写出来的文件在宿主上属主就是 root；换成非 root 用户，UID 又可能和宿主用户对不上，出现 `Permission denied`。临时排查可以显式指定用户：

```bash
docker run --rm -it --user "$(id -u):$(id -g)" \
  -v "$(pwd)":/work -w /work alpine touch out.txt
```

生产上不建议用绑定挂载放数据：容器直接接触宿主文件系统，隔离弱，路径依赖也让镜像没法在其他机器上原样跑。另外挂单个文件时要注意，很多编辑器保存时会替换 inode，容器里看到的还是旧文件；挂目录更稳。

SELinux 开启的宿主机上，挂载还需要 `:z` 或 `:Z` 重新打标签，否则容器进程没有读权限，报错信息通常只有一句 permission denied，很容易误判成用户问题。

> [!warning] 宿主目录不存在时
> Docker 会静默创建一个空目录，容器启动不报错，但里面什么都没有。应用报“配置缺失”时先 `docker inspect` 看 Mounts 的 Source 对不对。
