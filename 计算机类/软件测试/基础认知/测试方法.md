

> [!abstract] 一句话定义
> 测试方法是**为了用尽可能少的用例发现尽可能多的问题**，对"如何设计测试、如何执行测试"做出的系统安排。它回答三个问题：==测什么（范围）、怎么测（手段）、测到什么程度（充分性）==。

---

## 一、先建立分类坐标系

同一个测试可以同时属于多个分类，不要把它们当成互斥选项。

### 1. 按是否运行程序

| 类型   | 是否运行 | 典型活动                      | 能发现什么                |
| ---- | ---- | ------------------------- | -------------------- |
| 静态测试 | 否    | 需求评审、设计评审、代码审查、静态分析（SAST） | 歧义、遗漏、规范问题、潜在缺陷、安全漏洞 |
| 动态测试 | 是    | 执行程序、输入数据、观察结果            | 运行时行为错误、性能、兼容性       |

> [!tip] 静态测试性价比很高
> 代码审查和静态分析不需要环境、不需要数据，能在编码阶段发现大量问题，是"左移"的重要抓手。

### 2. 按测试阶段/对象

| 层次 | 测试对象 | 关注点 | 谁来主导 |
|---|---|---|---|
| 单元测试 | 函数/类/模块 | 逻辑正确、边界、异常 | 开发 |
| 集成测试 | 模块间接口/依赖 | 契约、数据传递、事务、时序 | 开发 + 测试 |
| 系统测试 | 完整系统 | 端到端功能、非功能、场景 | 测试 |
| 验收测试 | 交付物 | 是否满足业务/用户需求 | 用户/业务/客户 |
| 回归测试 | 已有功能 | 变更是否破坏原有行为 | 测试/自动化 |
| 冒烟测试 | 核心主流程 | 版本是否具备可测性 | 测试 |

验收测试的常见形式：

- **Alpha 测试**：在开发方现场，由内部人员/受控用户执行。
- **Beta 测试**：在真实用户环境中，由外部用户执行。
- **UAT**：用户验收测试，按业务场景验证。

### 3. 按是否了解内部结构

| 类型 | 依据 | 优点 | 局限 |
|---|---|---|---|
| 黑盒测试 | 需求/规格/输入输出 | 贴近用户、不依赖实现 | 可能漏掉内部路径 |
| 白盒测试 | 代码/结构 | 覆盖内部逻辑、发现隐藏分支 | 成本高、可能脱离业务 |
| 灰盒测试 | 部分内部信息 | 兼顾效率与深度 | 需要一定技术能力 |

> [!note] "黑 / 白"是一个比喻
> 把被测系统想象成一只盒子：**黑盒**只看到盒子外面的接口——给它输入，观察它输出；**白盒**则把盒子打开，直接检查内部的代码、分支和数据流。灰盒介于两者之间，只知道部分内部信息（如接口、数据库结构、日志）。

#### 黑盒测试（Black-box Testing）

**定义**：不关心程序内部如何实现，只依据需求规格和用户视角，通过"输入 → 输出 / 行为"验证系统是否符合预期。测试者把系统当成一个不透明的盒子，只能通过外部接口操作它。

- **依据**：需求文档、原型、接口说明、用户场景。
- **不看**：源代码、内部函数、数据流。
- **核心问题**：给定这些输入，系统是否给出正确的输出和行为？
- **典型方法**：等价类划分、边界值分析、判定表、因果图、正交实验、场景法、错误推测（见下文[[#二、黑盒测试方法]]）。
- **优点**：<font color="#c00000">贴近用户真实使用；不依赖实现</font>，代码重构后用例依然有效；测试人员不必读懂代码。
- **局限**：不知道哪些内部路径没被覆盖；可能漏掉"输入输出都正确、但内部走错分支"的缺陷；覆盖率难以精确度量。
- **例子**：登录框输入错误密码，预期提示"密码错误"且不进入系统——至于后端是如何比对的，黑盒不关心。

#### 白盒测试（White-box Testing）

**定义**：基于程序内部结构设计用例，检查代码中的语句、判定、条件、路径是否被正确执行。测试者打开盒子，直接对着代码和控制流图设计测试。

- **依据**：源代码、控制流图、数据流、模块结构。
- **不看**：业务是否真正满足用户需求——它只保证"代码按写好的逻辑运行"。
- **核心问题**：每条语句 / 每个分支 / 每条路径是否都被执行，且结果正确？
- **典型方法**：逻辑覆盖（语句、判定、条件、路径）、基本路径测试、循环测试、静态分析（见下文[[#三、白盒测试方法]]）。
- **优点**：能发现隐藏分支、死代码、异常路径等问题；覆盖率可量化，适合核心算法和工具类代码。
- **局限**：<font color="#c00000">成本高</font>（要读代码、要搭环境）；测的是"实现"，**需求本身错了它照样会通过**；无法发现需求遗漏。
- **例子**：`if (a > 0 && b > 0)`，白盒会要求 a、b 取不同真假组合，把条件组合尽量都跑到，而不只是验证整体判断的结果。

#### 灰盒测试（Gray-box Testing）

**定义**：<font color="#c00000">介于黑盒与白盒之间</font>。测试者掌握**部分内部信息**（如接口契约、数据库表结构、日志格式、消息队列、调用链、架构设计），但仍从外部接口驱动测试，用这些内部信息来设计用例和判定结果。可以理解为"操作上像黑盒，判定上带白盒视角"。

- **依据**：需求/规格 + 部分设计信息（API 文档、数据模型、日志规范、服务依赖图）。
- **不看**：完整源码细节，也不追求逐行、逐分支的结构覆盖。
- **核心问题**：接口返回正确的同时，内部的数据、状态、调用是否也正确？
- **典型方法**：接口测试、契约测试、基于数据库/日志断言的端到端测试、结合 schema 的 Fuzz、性能测试中结合监控指标、故障注入（详见下文[[#四、灰盒测试方法]]）。
- **优点**：比黑盒更有洞察力，能定位问题出在链路哪一环；比白盒成本低、更贴近业务；特别适合微服务、前后端分离、第三方依赖多的系统。
- **局限**：内部信息可能不完整，实现变更后用例容易失效；不能替代严格的单元测试和白盒覆盖。
- **例子**：测试下单接口时，黑盒只看"返回 200 且订单号正确"；灰盒还会进一步校验订单表状态、库存是否扣减、消息队列是否发出、日志是否记录，从而判断整条链路是否真的走对。

> [!tip] 灰盒在工程中很常见
> 很多团队做的"接口测试 + 查库校验"其实就是灰盒：不读源码，但知道表结构和接口定义。它的价值在于用较低成本获得接近白盒的观察能力。

#### 三者的关系

| 维度   | 黑盒测试    | 白盒测试                                 | 灰盒测试    |
| ---- | ------- | ------------------------------------ | ------- |
| 设计依据 | 需求 / 规格 | <font color="#c00000">代码 / 结构</font> | 部分内部信息  |
| 观察视角 | 用户      | 开发                                   | 测试 / 开发 |
| 覆盖度量 | 功能点、场景  | 语句、分支、路径                             | 接口、数据流  |
| 典型阶段 | 系统、验收   | 单元、集成                                | 接口、集成   |
| 主要盲区 | 内部路径    | 需求正确性                                | 两边都不够彻底 |

> [!important] 不是二选一，而是互补
> 黑盒回答"用户要的对不对"，白盒回答"代码实现得对不对"。同一个功能通常要从两个角度验证：先用黑盒确认业务正确，再用白盒补足内部路径。灰盒（如接口测试、结合日志/数据库校验的端到端测试）是工程中的常见折中。

> [!warning] 常见误解
> "黑盒 = 功能测试、白盒 = 单元测试"只是大致的对应，并不严格：黑盒同样可以做性能、兼容性、安全测试；白盒方法虽然主要用在单元和集成阶段，也不等于只能测函数。

## 二、黑盒测试方法

### 2.1 等价类划分（Equivalence Partitioning）

**思想**：把输入域划分为若干子集，同一子集中任取一个值，暴露缺陷的概率相近。于是每个子集只需取少量代表值。

- **有效等价类**：合法输入。
- **无效等价类**：非法输入。

**步骤**：

1. 分析输入条件。
2. 划分有效/无效等价类。
3. 编号。
4. 设计用例覆盖所有有效等价类（可合并）。
5. 为每个无效等价类单独设计用例。

**示例**：年龄输入，要求 18–60 的整数。

| 等价类         | 编号  | 代表值   |
| ----------- | --- | ----- |
| 有效：18–60 整数 | V1  | 30    |
| 无效：<18      | I1  | 10    |
| 无效：>60      | I2  | 70    |
| 无效：非整数      | I3  | 25.5  |
| 无效：非数字      | I4  | "abc" |
| 无效：空        | I5  | 空     |

> [!warning] 无效等价类不要合并
> 如果一条用例同时输入"年龄=10、姓名=空"，当程序先校验姓名时，年龄的问题就被掩盖了。无效类应==逐个单独测试==，避免互相掩盖。

### 2.2 边界值分析（Boundary Value Analysis）

**思想**：大量缺陷发生在边界附近。边界值分析是等价类划分的补充，专门盯住"边缘"。

对闭区间 `[a, b]`：

- **上点**：a、b（边界上的点）
- **内点**：区间内任意点
- **离点**：紧邻边界的区间外点，如 a−1、b+1

**示例**：`[18, 60]`

| 类型 | 取值 |
|---|---|
| 上点 | 18、60 |
| 内点 | 30 |
| 离点 | 17、61 |

> [!note] 开区间与健壮性测试
> 若区间是 `(18, 60)`，上点为 19、59，离点为 18、60。**健壮性边界测试**还会额外考虑略小于最小值、略大于最大值、以及非法类型（如 null、字符串）。

### 2.3 判定表（Decision Table）

**思想**：当业务逻辑由多个条件的组合决定时，用表格穷举"条件组合 → 动作"。

组成：

- **条件桩**：列出所有条件。
- **动作桩**：列出所有可能的动作。
- **条件项**：每个条件取真/假。
- **动作项**：对应组合下应执行的动作。

若有 n 个条件，完整判定表有 **2ⁿ 条规则**。

**示例**：订单折扣规则——条件：是否会员？金额是否 ≥ 200？

| 规则 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 会员 | Y | Y | N | N |
| 金额≥200 | Y | N | Y | N |
| 8 折 | ✓ | | | |
| 9 折 | | ✓ | | |
| 无折扣 | | | ✓ | ✓ |

> [!tip] 合并规则
> 如果某个条件取值不影响结果，可以把规则合并（用 "—" 表示无关），减少用例数量。上例中"非会员"无论金额多少都无折扣，规则 3、4 可合并。

### 2.4 因果图（Cause-Effect Graphing）

**思想**：从需求中找出"原因（输入条件）"和"结果（输出/动作）"，画出逻辑关系，再转成判定表。

- 基本关系：与、或、非。
- 约束：
  - **E**（互斥）：至多一个成立。
  - **I**（包含）：至少一个成立。
  - **O**（唯一）：有且仅有一个成立。
  - **R**（要求）：a 成立则 b 必须成立。
  - **M**（屏蔽）：a 成立则 b 必须不成立。

实际工作中，因果图常被**直接写判定表**替代；但因果图有助于在需求评审时发现遗漏的组合。

### 2.5 正交实验法（Orthogonal Array Testing）

**思想**：多因素、多水平的组合数量爆炸时，用正交表挑选少量组合，使**任意两个因素的水平组合都至少出现一次**。

记号：`Lₙ(mᵏ)` 表示 n 次实验、k 个因素、每个因素 m 个水平。

**示例**：3 个因素（浏览器、系统、网络），每个 3 个水平 → 全组合 27 种；用 `L9(3⁴)` 只需 9 种。

| 用例 | 浏览器 | 系统 | 网络 |
|---|---|---|---|
| 1 | Chrome | Windows | WiFi |
| 2 | Chrome | macOS | 4G |
| 3 | Chrome | Linux | 弱网 |
| 4 | Firefox | Windows | 4G |
| 5 | Firefox | macOS | 弱网 |
| 6 | Firefox | Linux | WiFi |
| 7 | Safari | Windows | 弱网 |
| 8 | Safari | macOS | WiFi |
| 9 | Safari | Linux | 4G |

> [!note] 成对测试（Pairwise）
> 实际工程中更常用 pairwise 工具生成"覆盖所有两两组合"的用例集。它与正交实验目标相近，但不要求严格正交表。

### 2.6 场景法（Scenario Testing）

**思想**：从用户完成任务的过程出发，覆盖**基本流（happy path）+ 备选流 + 异常流**。

- **基本流**：一切顺利的主路径。
- **备选流**：合法但非主路径（如改用优惠券支付）。
- **异常流**：错误、中断、失败。

示例：电商下单

1. 浏览商品 → 加入购物车 → 登录 → 填写地址 → 选择支付 → 支付成功（基本流）
2. 库存不足（异常）
3. 支付超时（异常）
4. 地址校验失败（异常）
5. 重复提交订单（异常）

场景法特别适合**端到端测试**和**验收测试**。

### 2.7 错误推测法（Error Guessing）

基于经验、缺陷模式和直觉，列出"最可能出错"的情况，针对性设计用例。

常见猜测点：

- 空值、null、0、负数、超长、特殊字符、emoji。
- 重复提交、并发、刷新、后退。
- 权限越界、越权访问。
- 时区、跨天、闰年、夏令时。
- 数据迁移、脏数据、历史数据。
- 第三方超时、重试、幂等。

> [!tip] 错误推测不是瞎猜
> 它应该建立在**缺陷模式库、历史事故、同类产品缺陷**之上，并与等价类/边界值配合使用。

### 2.8 其他黑盒方法

| 方法 | 适用场景 |
|---|---|
| 状态迁移测试 | 有明确状态机的对象（订单、审批流、账号状态） |
| 分类树法 | 多维度输入的分类与组合 |
| 成对测试/Pairwise | 参数组合多、全组合不可行 |
| 决策表 | 业务规则密集、条件组合明确 |
| 随机测试/Fuzz | 输入空间大、安全性/健壮性 |
| 基于模型的测试 | 有形式化或半形式化模型 |

## 三、白盒测试方法

### 3.1 逻辑覆盖

按覆盖的"逻辑元素"从弱到强：

| 覆盖标准 | 要求 | 强度 | 说明 |
|---|---|---|---|
| 语句覆盖 SC | 每条可执行语句至少执行一次 | 最弱 | 可能漏掉分支 |
| 判定覆盖 DC（分支覆盖） | 每个判定的真/假分支至少各一次 | 较弱 | 不保证每个条件都取到真假 |
| 条件覆盖 CC | 每个条件的真/假至少各一次 | 较弱 | 不保证判定结果被覆盖 |
| 判定/条件覆盖 CDC | 同时满足 DC 和 CC | 较强 | 工程常用 |
| 条件组合覆盖 MCC | 每个判定中所有条件组合至少一次 | 强 | 组合爆炸 |
| 路径覆盖 | 覆盖程序中所有可能路径 | 最强 | 路径数可能指数级 |

几个容易混淆的关系：

- 100% 判定覆盖 ⇒ 100% 语句覆盖。
- 100% 条件覆盖 ⇏ 100% 判定覆盖（条件都取到真假，但判定结果可能只出现一种）。
- 100% 判定/条件覆盖 ⇒ 判定覆盖且条件覆盖。
- 100% 条件组合覆盖 ⇒ 判定/条件覆盖。
- 100% 路径覆盖 ⇒ 判定覆盖；但不一定 ⇒ 条件组合覆盖（短路求值可能让某些组合不可达）。

> [!example] 一个判定
> ```c
> if (a > 0 && b > 0) { ... }
> ```
>
> - 条件：`a > 0`、`b > 0`
> - 判定：`a > 0 && b > 0`
> - 条件覆盖：`(a>0真, b>0真)`、`(a>0假, b>0假)` 即可，但两次判定都为假。
> - 判定覆盖：需要判定真一次、假一次。
> - 条件组合覆盖：需要 (T,T)、(T,F)、(F,T)、(F,F) 四种。

### 3.2 基本路径测试

**步骤**：

1. 根据代码画出**控制流图**。
2. 计算**环形复杂度** `V(G)`。
3. 导出**基本路径集**（独立路径数 = V(G)）。
4. 为每条路径设计用例。

**环形复杂度**的三种算法（结果一致）：

- `V(G) = E − N + 2`（E 边数，N 节点数）
- `V(G) = 判定节点数 + 1`
- `V(G) = 平面被划分的区域数`

> [!note] 独立路径
> 独立路径是指至少引入一条新边的路径。基本路径集不一定覆盖所有路径，但能保证每条边至少被执行一次，是"最小充分"的路径集合。

### 3.3 循环测试

- **简单循环**：0 次、1 次、2 次、典型次数、最大次数、最大+1。
- **嵌套循环**：由内向外，固定外层，测内层；再逐步外推。
- **串接循环**：若相互独立，分别测试；若相关，按嵌套处理。
- **非结构循环**：先重构，再测试。

### 3.4 静态分析

- 编码规范检查（lint）。
- 复杂度度量（圈复杂度、嵌套深度）。
- 数据流分析（未初始化、未使用变量）。
- 类型检查。
- 安全扫描（SAST）：注入、硬编码密钥、危险函数。
- 依赖漏洞扫描（SCA）。

## 四、灰盒测试方法

灰盒测试的核心不是"知道多少源码"，而是**用哪些信息来判断结果是否正确**。它在黑盒的外部操作之上，增加了内部状态和运行痕迹作为观察点。

### 4.1 灰盒的三类观察点

| 观察层 | 能看到什么 | 典型断言 |
|---|---|---|
| 接口层 | 状态码、响应体、错误码、耗时、幂等性 | 返回结构符合契约、错误码正确、重复请求不产生重复数据 |
| 数据层 | 数据库记录、缓存、消息队列、文件/对象存储 | 订单落库、库存扣减、消息已发出、缓存与库一致 |
| 运行时层 | 日志、调用链（trace/span）、指标、配置 | 关键步骤有日志、调用链完整、无异常指标、降级/重试被触发 |

> [!note] 灰盒的本质是"可观测性"
> 黑盒只能看"结果对不对"，白盒能看"代码怎么走"，灰盒则通过接口、数据、日志、链路这些**可观测点**推断"系统内部发生了什么"。所以灰盒测试设计得好不好，很大程度上取决于系统的可观测性建设。

### 4.2 常见灰盒测试方法

#### 接口测试（API Testing）

最典型的灰盒：依据接口契约设计输入，同时断言响应和副作用。

- **依据**：OpenAPI / Swagger、Protobuf、接口文档、数据模型。
- **覆盖**：正常参数、边界值、缺参/类型错误、鉴权与越权、幂等与并发、错误码。
- **断言**：响应结构、业务码、关键字段；再补一条"副作用断言"（数据是否真的写入/更新）。
- **工具**：Postman / Bruno、pytest + requests、RestAssured、Supertest。

#### 契约测试（Contract Testing）

- **消费者驱动**：调用方定义"我期望的请求/响应"，形成契约。
- **提供方验证**：服务提供方用同一份契约跑验证，确保接口演进不破坏调用方。
- **价值**：把"接口不兼容"的问题挡在集成之前，比端到端测试更快、更稳定。
- **代表工具**：Pact、Spring Cloud Contract。

#### 数据层断言

接口返回成功不等于业务成功。灰盒会继续检查数据落点：

- 数据库：记录是否存在、状态是否正确、金额/库存是否一致。
- 缓存：更新后缓存是否失效或同步。
- 消息队列：事件是否发出、消息体是否正确、是否重复消费。
- 文件/对象存储：上传、删除、权限是否符合预期。

> [!warning] 断言要落在"业务状态"上
> 灰盒断言应关注**契约和业务状态**（订单状态、库存数量、消息内容），而不是私有实现细节（某张内部临时表、某个缓存 key 的具体命名）。后者会让用例随实现频繁碎裂。

#### 可观测性驱动测试

利用日志、调用链、指标来验证"内部真的走对了"：

- **日志断言**：关键分支是否记录、错误日志是否出现、敏感信息是否脱敏。
- **调用链断言**：一次请求是否经过预期服务、span 是否完整、是否有异常跨度。
- **指标断言**：错误率、延迟、队列积压、连接池使用是否在阈值内。

#### 故障注入（Fault Injection）

灰盒知道依赖关系，因此可以精准地在链路上制造故障：

- 下游超时、返回 5xx、慢响应。
- 网络分区、连接重置。
- 数据库主从延迟、消息重复/丢失。
- 验证：重试、熔断、降级、补偿、幂等是否按设计生效。

#### 基于 schema 的模糊测试

用 OpenAPI / Protobuf / JSON Schema 自动生成合法与非法输入，覆盖手工难穷举的参数组合，重点发现崩溃、500、契约违背和注入类问题。

#### 结合监控的性能测试

压测时不只看 TPS 和响应时间，还看数据库慢查询、连接池、GC、队列积压、下游耗时，从而定位瓶颈在链路哪一环。

### 4.3 设计流程（以接口测试为例）

1. **拿到契约**：接口文档、数据模型、依赖关系、关键日志与链路标识。
2. **梳理链路**：接口调用哪些服务、读写哪些数据、发出哪些消息。
3. **设计输入**：等价类 + 边界值 + 鉴权/幂等/并发/异常。
4. **设计断言**：响应断言 + 数据副作用断言 + 日志/链路断言。
5. **准备数据与环境**：数据隔离、可重复执行、执行后清理，避免用例互相污染。
6. **自动化**：接入 CI，契约变更时自动触发相关用例。
7. **评估覆盖**：接口覆盖率、参数覆盖率、关键链路覆盖率、异常分支覆盖率。

> [!example] 下单接口的灰盒用例
> 请求 `POST /orders`（商品、数量、优惠券）：
>
> - **黑盒断言**：返回 201、订单号非空、金额计算正确。
> - **数据断言**：订单表新增记录且状态为 `CREATED`；库存扣减正确；优惠券标记已使用；outbox 表新增订单事件。
> - **运行时断言**：调用链包含库存锁定与支付预授权 span；无 ERROR 日志。
> - **异常分支**：库存不足时返回 409，订单不落库，库存与优惠券均不变。
>
> 这样一条用例同时验证了"用户看到的结果"和"系统内部的状态"，定位问题时也能直接指出是响应、数据还是链路出了问题。

### 4.4 什么时候值得用灰盒

| 场景 | 是否适合 | 原因 |
|---|---|---|
| 微服务、前后端分离 | 很适合 | 接口是天然边界，内部状态可查 |
| 数据一致性要求高（支付、库存、订单） | 很适合 | 只看响应无法发现脏数据与不一致 |
| 依赖多、链路长 | 适合 | 结合日志/链路/故障注入定位问题 |
| 单体简单 CRUD | 一般 | 黑盒 + 少量接口测试通常够用 |
| 核心算法、纯函数 | 不必 | 白盒 + 单元测试更直接 |
| 内部实现频繁变动 | 谨慎 | 过度依赖内部结构的断言容易失效 |

### 4.5 常见误区

> [!warning] 灰盒不是"黑盒 + 随便查一下库"
> 查库必须对应明确的业务不变量（如"支付成功后订单状态必须是 PAID"），否则只是增加噪声，不能提高发现缺陷的能力。

> [!warning] 不要用灰盒替代单元测试
> 灰盒运行慢、依赖环境、定位粒度粗。它适合验证"跨组件的协作与状态"，而不是替代对函数级逻辑的快速验证。

> [!note] 测试金字塔中的位置
> 单元测试在底层，接口/契约/组件测试（灰盒）在中层，端到端测试在顶层。灰盒通常承担"中层主力"的角色：比端到端快且稳定，比单元测试更接近真实协作。

## 五、基于经验的方法

### 5.1 探索性测试（Exploratory Testing）

**定义**：学习、设计、执行**同时进行**的测试方式。不是"随便点点"，而是有目标、有时间盒、有记录的探索。

常见组织方式：**基于会话的测试管理（SBTM）**

- 设定 charter（探索目标）。
- 时间盒（如 60–90 分钟）。
- 记录覆盖范围、发现、问题、后续思路。

适合：需求不清晰、时间紧、需要快速建立产品认知、发现"用例之外"的问题。

### 5.2 检查表（Checklist）

把经验固化为清单，降低遗漏：

- 输入校验、边界、异常。
- 权限、安全、隐私。
- 兼容性、性能、可用性。
- 数据一致性、事务、幂等。
- 日志、监控、告警。

### 5.3 漫游测试（Tours）

借鉴旅游路线：

- **商业区漫游**：核心功能。
- **历史区漫游**：旧功能、遗留代码。
- **恶街区漫游**：最容易出问题的区域。
- **博物馆漫游**：只读、展示类功能。
- **碰运气漫游**：随机操作。

## 六、按目的的常见测试类型

| 类型 | 目的 |
|---|---|
| 冒烟测试 | 快速确认版本基本可用，决定是否继续测 |
| 回归测试 | 确认变更没有破坏已有功能 |
| 验收测试 | 确认满足业务/用户需求 |
| 兼容性测试 | 不同浏览器、系统、设备、分辨率 |
| 性能测试 | 响应时间、吞吐、资源、稳定性 |
| 压力测试 | 超出预期负载下的表现 |
| 负载测试 | 预期负载下的表现 |
| 稳定性/浸泡测试 | 长时间运行是否泄漏、退化 |
| 安全测试 | 认证、授权、注入、加密、隐私 |
| 可用性测试 | 用户能否顺利完成目标 |
| 无障碍测试 | 残障用户可访问性 |
| 本地化/国际化测试 | 语言、时区、货币、格式 |
| A/B 测试 | 对比方案效果 |
| 猴子测试/Fuzz | 随机/变异输入找崩溃 |
| 变异测试 | 评估测试用例本身的有效性 |
| 契约测试 | 服务间接口契约一致性 |
| 端到端测试 | 完整业务链路 |

## 七、方法怎么选

没有"最好的方法"，只有"当前风险下最合适的方法"。

| 场景 | 推荐组合 |
|---|---|
| 输入校验、表单 | 等价类 + 边界值 + 错误推测 |
| 复杂业务规则 | 判定表 + 场景法 |
| 多参数组合 | 正交实验/成对测试 |
| 有状态流程 | 状态迁移 + 场景法 |
| 微服务、前后端分离 | 接口测试 + 契约测试 + 数据层断言（灰盒） |
| 数据一致性要求高 | 灰盒断言 + 场景法 + 故障注入 |
| 核心算法/工具类 | 白盒覆盖 + 单元测试 + 性质测试 |
| 遗留系统、需求缺失 | 探索性测试 + 错误推测 + 回归 |
| 高风险核心链路 | 场景法 + 端到端 + 性能/安全 |
| 时间紧、范围大 | 风险驱动 + 优先级排序（见 [[测试优先级分配]]） |

> [!important] 组合使用
> 实际测试设计几乎从不只用一种方法。等价类保证"面"，边界值保证"边"，判定表保证"组合"，场景法保证"链路"，探索性测试补"意外"。

## 八、测试设计的一般流程

1. **分析需求**：功能、约束、用户、依赖。
2. **识别测试条件**：要验证什么。
3. **选择方法**：根据输入结构、逻辑复杂度、风险。
4. **设计用例**：
   - 编号、标题
   - 前置条件
   - 步骤与数据
   - **预期结果（预言机）** → [[测试预言机]]
   - 优先级 → [[测试优先级分配]]
5. **评审用例**：覆盖度、可执行性、可判定性。
6. **执行与记录**。
7. **评估充分性**：覆盖率、缺陷发现、风险剩余。

> [!warning] 没有预期结果的不是用例
> 只写"输入 A，点击 B"而不写"应该发生什么"，执行时只能靠感觉判断，无法稳定复现和自动化。预期结果必须有明确依据（见 [[测试预言机]]）。
