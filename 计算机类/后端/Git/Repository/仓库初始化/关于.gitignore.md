# 关于 .gitignore —— 忽略规则

> [!abstract] 一句话
> ==`.gitignore` 是一个**纯文本清单**，逐条告诉 Git "这些文件请**假装看不见**"==：被它匹配的文件既不进 `Untracked files`，也 `add` 不进去——它们从头到尾**不会出现在任何提交里**。它管的是**未追踪文件**，用来把编译产物、依赖、密钥、临时文件挡在仓库之外。

---

## 一、为什么需要它

工作目录里其实混着两类东西：**该进版本库的源码**，和**不该进的垃圾**。

```text
my-project/
├── src/                ← 源码，要提交
├── package.json        ← 配置，要提交
├── node_modules/       ← 依赖，几万文件，能重建，别提交
├── dist/               ← 构建产物，能重建，别提交
├── .env                ← ★密钥，绝不能提交
├── *.log               ← 运行日志，别提交
└── .DS_Store / Thumbs.db  ← 操作系统生成，别提交
```

> [!info] 忽略不是"删除"，是"视而不见"
> `.gitignore` **不动磁盘上的文件**，也不会删掉它。它只是让 Git 在扫描工作目录时**跳过**这些路径。
> 文件照样在你电脑上，编辑器照样打开它，只是 Git 的账本里永远没有它。

> [!warning] 为什么密钥绝不能提交
> `.env`、`id_rsa`、`*.pem` 这类文件一旦提交，就会**永久留在历史里**——即使下个提交删掉它，用 `git log -p` 仍能翻出来。
> 公开仓库里的密钥分分钟被爬虫扫走。**提交前把 `.gitignore` 写对，比事后 `filter-repo` 洗历史便宜一万倍。**（参见 [[提交]] 第六节）

## 二、它放在哪：三个层次的忽略文件

同一个忽略效果，可以写在**三个不同的文件**里，作用范围层层收窄：

| 文件                     | 作用范围          | 是否进版本库      | 典型用途                            |
| ---------------------- | ------------- | ----------- | ------------------------------- |
| `.gitignore`           | 当前目录及其**子目录** | **进**（团队共享） | 项目级规则，随仓库分发                     |
| `.git/info/exclude`    | 仅**本仓库**      | **不进**      | 个人本地规则，不想打扰别人                   |
| 全局 `core.excludesFile` | 本机**所有仓库**    | 不进          | 操作系统/编辑器产生的文件（见 [[git config]]） |

```bash
# 全局忽略文件：一次配置，处处生效
git config --global core.excludesFile ~/.gitignore_global
```

> [!tip] 怎么选哪一层
> - **整个团队都该忽略的**（`node_modules/`、`dist/`）→ 写进 `.gitignore`，提交上去，大家一起用。
> - **只有你自己烦的**（编辑器临时文件、本地调试脚本）→ 写进 `.git/info/exclude`。
> - **换个项目还是一样的**（`.DS_Store`、`Thumbs.db`、`*.swp`）→ 写进全局 `core.excludesFile`。

> [!note] `.gitignore` 的规则是"**向下继承**"的
> 子目录里可以再放一个 `.gitignore`，它只影响该子目录及更深层。
> 比如 `src/legacy/.gitignore` 里的规则**管不到** `src/` 的其他部分。就近的规则优先。

## 三、语法规则：怎么写

`.gitignore` 一行一条规则，遵循 **gitignore 模式匹配**（不是标准 glob，别和 shell 搞混）：

| 写法               | 含义                                      |
| ---------------- | --------------------------------------- |
| `*.log`          | 忽略所有 `.log` 结尾的文件（**任意目录层级**）           |
| `/dist`          | 只忽略**仓库根目录**下的 `dist`                   |
| `dist/`          | 忽略**任何**名为 `dist` 的**目录**               |
| `**/temp`        | `**` 跨任意层级；`doc/**` 匹配 `doc/` 下**所有**东西 |
| `build`          | 忽略任何层级下名为 `build` 的文件或目录                |
| `!important.log` | **例外**：取消忽略（`!` = 白名单）                  |
| `# 注释`           | `#` 开头是注释                               |
| `docs/*.md`      | 只忽略 `docs/` **直接子级**的 `.md`（不含更深处）      |

```gitignore
# 依赖与构建产物
node_modules/
dist/
build/
*.o
*.class

# 日志与临时文件
*.log
*.tmp
.DS_Store
Thumbs.db

# 环境与密钥
.env
.env.local
*.pem
*.key

# 但保留示例文件
!.env.example
```

> [!warning] `!` 例外有个坑
> 如果**父目录**已经被忽略了，`!` 就**救不回**它里面的文件。Git 不会进入一个被忽略的目录去寻找例外。
> ```gitignore
> dist/         # 整个目录被忽略
> !dist/keep   # ✗ 无效！Git 根本不进 dist/
> ```
> 正确做法是**不忽略父目录**，只忽略它里面的内容：
> ```gitignore
> dist/*
> !dist/keep   # ✓ 有效
> ```

> [!danger] 三条高频踩坑
> 1. **`/` 开头的锚定**：`/dist` 只管根目录；写 `dist` 则管所有层级。
> 2. **末尾 `/` 只匹配目录**：`build/` 忽略目录 `build`，但不忽略同名文件 `build`。
> 3. **`*` 不跨 `/`，但无 `/` 的模式自带"任意层级"语义**：`*.log` 能匹配 `a/b/c.log`。想限定单层请显式写 `a/*.log`。

## 四、已经追踪的文件，忽略规则对它无效

> [!question] 我把文件加进 `.gitignore` 了，可 `git status` 还显示它，提交也还在？
> 这是**新手第一大坑**：`.gitignore` **只对未追踪文件生效**。
> 一个文件**一旦被 `git add` 过、进过提交**，Git 就一直在追踪它，`.gitignore` 里的规则对它**完全无效**。

想让它"从此被忽略"，得**先把它从追踪中摘掉，再让忽略规则接管**：

```bash
# 1. 只从 Git 中移除，磁盘文件保留（切勿用 git rm 而不带 --cached）
git rm --cached .env

# 2. 确认 .gitignore 里有对应规则
echo '.env' >> .gitignore

# 3. 提交这次"移除"
git commit -m "chore: 停止追踪 .env 并加入忽略"
```

> [!warning] `git rm` vs `git rm --cached`
> - `git rm .env` → **同时删除磁盘文件**并放入暂存区。（你会丢掉本地文件！）
> - `git rm --cached .env` → **只取消追踪**，磁盘文件原样保留。（这才是你要的）
>
> 详见 [[暂存区]] 第 3.4 节。

> [!tip] 已经误提交的密钥怎么办
> `git rm --cached` 只能让**未来的提交**不含它；**历史里的那份仍在**。
> 若已推到远程：必须用 `git filter-repo` 重写历史，**并立刻更换那把泄露的密钥**（撤销无效，只能作废重建）。
> 参见 [[提交]] 第 6 节与 [[查看commit历史]]。

## 五、调试：规则到底有没有生效

忽略规则一多，很容易"以为忽略了其实没有"。用这两条命令排查：

```bash
# 1. 问 Git：这个文件为什么被忽略（或为什么没被忽略）？
git check-ignore -v path/to/file
#   输出示例：.gitignore:5:*.log    debug.log
#            ↑规则来自哪    ↑行号  ↑模式   ↑被匹配的文件

# 2. 看看当前“已经被忽略”的文件有哪些
git status --ignored          # 完整列出
git status --ignored -s       # 短格式
```

> [!tip] `git check-ignore -v` 是排查神器
> 它直接告诉你**是哪一份文件的第几行、哪条模式**命中了这个路径。
> "我明明写了规则怎么还被追踪"——九成是第四节那个坑，用这条一秒定位。

## 六、完整示例：给新项目配一套忽略规则

```bash
cd my-project
git init -b main

# 1. 先写忽略规则，再 add —— 顺序很重要
cat > .gitignore <<'EOF'
# 依赖
node_modules/

# 构建产物
dist/
*.o
*.class

# 日志与临时文件
*.log
*.tmp
.DS_Store
Thumbs.db

# 环境与密钥
.env
.env.local
*.pem

# 保留示例模板
!.env.example
EOF

# 2. 现在 add，垃圾文件会被自动跳过
git add .
git status                    # 确认 .env / node_modules 没出现在待提交里

# 3. 验证某文件是否被忽略
git check-ignore -v .env      # 应输出 .gitignore:XX:.env

# 4. 提交
git commit -m "chore: 初始提交并配置 .gitignore"
```

> [!success] 成功标志
> `git status` 里**看不到** `node_modules/`、`.env`、`*.log`；
> `git check-ignore -v .env` 能打出命中的规则行；
> `git status --ignored` 会把这些文件列在 `Ignored files` 之下。

## 七、进阶：更细的语法与"变通招式"

### 7.1 模式语法补全

第三节列的是高频写法，这里补齐剩余细节：

| 写法 | 含义 |
| --- | --- |
| `?` | 匹配**单个**字符：`log?.txt` 匹配 `log1.txt`，不匹配 `log10.txt` |
| `[abc]` / `[0-9]` | 字符集合 / 范围：`file[0-9].log` 匹配 `file3.log` |
| `\#foo` | 转义：匹配**真的叫** `#foo` 的文件（否则被当注释） |
| `\!foo` | 转义：匹配真的叫 `!foo` 的文件（否则被当例外） |
| `foo\ ` | 转义**行尾空格**，才能匹配带空格的目录名 |

> [!note] 几个"隐式规则"
> - **空行**被忽略，`#` 开头的行是注释（除非转义）。
> - 每行**行尾的空格**会被自动去掉；想匹配带空格的名字，用 `\ ` 转义。
> - `**` 只在特定位置生效：`a/**/b`（中间任意层）、`**/b`（开头任意层）、`a/**`（结尾任意层）。

### 7.2 文件必须被追踪，但我不想提交本地改动

有些文件**天生该进仓库**（比如配置模板 `config.example.js`），可你在本地总忍不住改它——又不想把自己的改动提交上去。这时 **`.gitignore` 完全帮不上忙**（文件已被追踪，见第四节），要靠 `skip-worktree`：

```bash
# 让 Git 暂时"无视"这个文件在工作目录里的改动
git update-index --skip-worktree config.example.js

# 撤销该设置，恢复正常追踪
git update-index --no-skip-worktree config.example.js

# 列出当前所有被 skip 的文件
git ls-files -v | grep '^S'
```

> [!warning] `--skip-worktree` vs `--assume-unchanged`，别选错
> | 命令 | 本意 | 适合场景 | 风险 |
> | --- | --- | --- | --- |
> | `--skip-worktree` | **故意**忽略本地改动，且尽量保住它 | 改配置文件但不提交 | 上游更新该文件时可能冲突 |
> | `--assume-unchanged` | 是**性能优化**，等于保证"它没变" | 大文件/巨量目录加快 `status` | 上游一改，本地改动可能被**覆盖丢失** |
>
> 想"改文件但不提交"，**用 `--skip-worktree`**；`--assume-unchanged` 是给性能用的，被误当忽略手段用迟早出事。

### 7.3 `git clean` 与忽略文件：`-x` 和 `-X` 的区别

[[工作目录]] 里讲过 `git clean` 用来删未追踪文件，但它和忽略规则的配合有个**关键的字母差**：

```bash
git clean -n              # 演习：列出将要删的未追踪文件
git clean -f              # 删未追踪文件，但**不动被忽略的**
git clean -fdX            # 只删**被忽略**的文件（保留还没 add 的新源码）
git clean -fdx            # ✗ 删除**全部**未追踪**含被忽略**（build/、.env 一起没）
```

> [!danger] `git clean -fdx` 是"回到纯净检出"的重锤
> `-x` 会把 `.gitignore` 忽略的一切也删掉——构建产物、`node_modules/`，甚至你的 **`.env`**。
> 它常用于"想要一个像刚 clone 下来那样干净的目录"，但**执行前务必先 `-n` 演习**，确认清单里没有你要留的东西。

### 7.4 现成的忽略模板，不必从零写

主流语言 / 框架的忽略规则早有权威范本，直接抄：

- **GitHub 官方模板库**：`github/gitignore`（按语言分文件，如 `Node.gitignore`、`Python.gitignore`、`Java.gitignore`）。
- **在线生成器**：`gitignore.io`（选语言 + 编辑器 + 系统，一键拼好）。
- **全局兜底**：把操作系统 / 编辑器产生的文件（`.DS_Store`、`Thumbs.db`、`.idea/`、`*.swp`）写进 `core.excludesFile`，让所有仓库一次清净。

> [!tip] 模板"宁缺毋滥"
> 忽略规则**越精准越好**。抄模板后删掉用不上的条目——否则某天真需要提交的文件被静默忽略了，反而更难排查。

## 八、常见困惑

> [!question] 空目录会被提交吗？
> 不会。Git 只追踪文件，**不追踪空目录**。想让一个目录（如 `logs/`）保留在仓库里，惯例是在里面放一个 `.gitkeep`：
> ```bash
> touch logs/.gitkeep
> ```

> [!question] `.gitignore` 自己会被忽略吗？会被提交吗？
> 不会被忽略（除非你特意写了规则），**应该提交**——它是团队共享的规则，正是靠提交才能让所有人生效。

> [!question] 我在 `.gitignore` 里写 `*.log`，为什么 `logs/app.log` 还是被追踪了？
> 两个可能：① 它**在写规则之前就已经被提交过**（第四节的老坑，需 `git rm --cached`）；
> ② 你看的其实是缓存 —— 用 `git check-ignore -v logs/app.log` 确认规则是否真的命中。

> [!question] 忽略规则写完，历史里那些文件就不占空间了吗？
> 不占"新提交"的空间，但**历史里的对象依然在**，仓库体积不会因此变小。
> 要真正清除，必须重写历史（`git filter-repo`）+ 强推，仅建议在"泄露了密钥"等必要场景做。

> [!question] `.gitignore` 和 `.gitattributes` 有什么区别？
> - `.gitignore`：**哪些文件不纳入版本控制**（本章主题）。
> - `.gitattributes`：**纳入版本控制的文件，该怎么处理**（换行符、二进制标记、diff 策略等）。参见 [[git config]] 里 `autocrlf` 的说明。

> [!question] 我只想保留本地对某文件的修改、不提交，为什么 `.gitignore` 没用？
> 因为该文件**早已被追踪**，`.gitignore` 对已追踪文件一律无效（见第四节）。
> 正确工具是 `git update-index --skip-worktree <文件>`，用 `--no-skip-worktree` 恢复——详见第 7.2 节。

---

> [!quote] 一句话记忆
> **`.gitignore` = 仓库的"谢绝入内"名单**：列在上面的人，Git 一辈子当没看见；但**已经进过门的客人，得先请他出去**（`git rm --cached`），名单才会生效。
