# 数据约束 —— 概述与导航

> [!abstract] 一句话
> 约束（Constraint）是**写在表结构上的"安检规则"**：每次 `INSERT` / `UPDATE` / `DELETE` 时由数据库自动校验，不合规的数据直接被拦下报错——它是**数据正确性的最后一道防线**。

---

## 一、为什么需要约束

数据库存的是"事实"，但写数据的人（程序、脚本、手抖的运维）不可靠。约束把**业务规则下沉到数据库层**，让"脏数据根本进不来"，而不是"先进来再写代码去查"。

> [!tip] 约束最大的价值：**防呆**
> 应用层校验是"君子协定"，绕过接口（直连数据库、手动改表、多套程序并发写）就失效；
> 数据库约束是**物理墙**，任何写入路径都绕不过去。

---

## 二、四类完整性（理论源头）

| 完整性          | 含义              | 靠谁实现                          |
| ------------ | --------------- | ----------------------------- |
| **实体完整性**   | 每一行都能被唯一区分      | 主键 `PRIMARY KEY`              |
| **参照完整性**   | 外键的值必须在被参照表中存在  | 外键 `FOREIGN KEY`              |
| **域完整性**    | 每个字段的值落在合法范围内   | 数据类型 / `NOT NULL` / `DEFAULT` / `CHECK` |
| **用户定义完整性** | 具体业务规则（如年龄 ≥ 18） | `CHECK` / 触发器 / 应用层           |

---

## 三、七大约束速查表

| 约束               | 关键字              | 作用                    | 是否可多列组合 | 本篇链接        |
| ---------------- | ---------------- | --------------------- | ------- | ----------- |
| **非空**           | `NOT NULL`       | 该列必须有值                | ❌       | [[NOT NULL]]    |
| **默认值**          | `DEFAULT`        | 不写时自动填一个值             | ❌       | [[DEFAULT]]     |
| **主键**           | `PRIMARY KEY`    | 唯一 + 非空，一行的身份证        | ✅ 联合主键  | [[PRIMARY KEY]] |
| **唯一**           | `UNIQUE`         | 值不能重复，**但允许多个 NULL**  | ✅       | [[UNIQUE]]      |
| **自增**           | `AUTO_INCREMENT` | 自动 +1，**必须依附在键上**     | ❌       | [[AUTO_INCREMENT]] |
| **检查**           | `CHECK`          | 满足表达式才允许写入            | ✅       | [[CHECK]]       |
| **外键**           | `FOREIGN KEY`    | 值必须来自另一张表的键           | ✅       | [[FOREIGN KEY]] |

> [!info] 记住分类，别死背
> - **管"有没有值"**：`NOT NULL`、`DEFAULT`
> - **管"值唯一不唯一"**：`PRIMARY KEY`、`UNIQUE`、`AUTO_INCREMENT`
> - **管"值合不合法"**：`CHECK`
> - **管"和别的表对不对得上"**：`FOREIGN KEY`

## 四、约束 vs 应用层校验

| 对比项      | 数据库约束            | 应用层（Java / 前端）校验      |
| -------- | ---------------- | -------------------- |
| 拦截范围     | ==所有写入路径==，包括手改表 | 只拦走该接口的请求            |
| 并发安全     | ✅ 由数据库保证          | ❌ 先查后写存在竞态           |
| 错误提示     | 报错信息较原始，需翻译       | 可定制成友好提示             |
| 灵活性      | 改约束要改表结构          | 改代码即可                |
| 性能       | 校验发生在存储引擎，几乎无额外成本 | 多一次数据库往返             |

> [!success] 正确姿势：**两边都要**
> 应用层做**友好提示**（"手机号已被注册"），数据库约束做**兜底保证**（唯一索引挡住并发写入）。
> 只信应用层，迟早出现重复数据；只信数据库，用户体验差。

## 五、列级约束 vs 表级约束

```sql
CREATE TABLE t (
    id   BIGINT NOT NULL,               -- 列级：只涉及一个字段，直接跟字段写
    name VARCHAR(20) NOT NULL,
    PRIMARY KEY (id),                   -- 表级：写在字段列表之后
    UNIQUE KEY uk_name (name)           -- 表级才能给约束起名字
);
```

| 写法   | 位置         | 能组合多字段 | 能起约束名 |
| ---- | ---------- | ------ | ----- |
| 列级约束 | 跟在该字段定义后   | ❌      | ❌     |
| 表级约束 | 所有字段定义之后   | ✅      | ✅     |

> [!tip] 起名字为什么重要
> 报错信息里显示 `uk_stu_no` 比显示一串随机名（`t_ibfk_1`、`my_table_chk_1`）好排查太多。
> ==凡是可能报错的约束，都建议表级 + 显式命名。== 命名规范：`pk_` 主键、`uk_` 唯一、`fk_` 外键、`chk_` 检查。

## 六、本篇统一示例表

后续各篇共用同一套 schema，方便互相印证：

```sql
-- 班级表（主表）
CREATE TABLE class (
    id   INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(30) NOT NULL UNIQUE
);

-- 学生表（从表）
CREATE TABLE student (
    id       BIGINT AUTO_INCREMENT,
    stu_no   CHAR(10)   NOT NULL,               -- 学号：业务主键
    name     VARCHAR(50) NOT NULL,              -- 非空
    gender   CHAR(1)    DEFAULT 'U',            -- 默认 'U'
    age      TINYINT CHECK (age BETWEEN 0 AND 150),
    class_id INT,                               -- 外键 → class.id
    PRIMARY KEY (id),
    UNIQUE KEY uk_stu_no (stu_no),
    CONSTRAINT chk_gender CHECK (gender IN ('M', 'F', 'U')),
    CONSTRAINT fk_student_class
        FOREIGN KEY (class_id) REFERENCES class (id)
        ON DELETE SET NULL ON UPDATE CASCADE
);

-- 选课表（联合主键 + 检查）
CREATE TABLE sc (
    sid   BIGINT,
    cid   INT,
    score DECIMAL(4,1) CHECK (score BETWEEN 0 AND 100),
    PRIMARY KEY (sid, cid)
);
```

## 七、查看 / 添加 / 删除约束

### 7.1 查看某张表的所有约束

```sql
SELECT CONSTRAINT_NAME, CONSTRAINT_TYPE
FROM INFORMATION_SCHEMA.TABLE_CONSTRAINTS
WHERE TABLE_SCHEMA = '你的库名'
  AND TABLE_NAME   = 'student';
```

| `CONSTRAINT_TYPE` | 对应约束        |
| ----------------- | ----------- |
| `PRIMARY KEY`     | 主键          |
| `UNIQUE`          | 唯一          |
| `FOREIGN KEY`     | 外键          |
| `CHECK`           | 检查          |

### 7.2 增删约束的统一入口

约束的增删大多通过 `ALTER TABLE` 完成，语法**各不相同**（详见各篇）：

| 约束        | 添加                                                     | 删除                              |
| --------- | ------------------------------------------------------ | ------------------------------- |
| 非空        | `ALTER TABLE t MODIFY c 类型 NOT NULL;`                   | `ALTER TABLE t MODIFY c 类型 NULL;` |
| 默认值       | `ALTER TABLE t MODIFY c 类型 DEFAULT 值;`                 | `ALTER TABLE t MODIFY c 类型;`     |
| 主键        | `ALTER TABLE t ADD PRIMARY KEY (c);`                     | `ALTER TABLE t DROP PRIMARY KEY;`  |
| 唯一        | `ALTER TABLE t ADD CONSTRAINT uk_c UNIQUE (c);`          | `ALTER TABLE t DROP INDEX uk_c;`   |
| 外键        | `ALTER TABLE t ADD CONSTRAINT fk_c FOREIGN KEY (c) ...;` | `ALTER TABLE t DROP FOREIGN KEY fk_c;` |
| 检查        | `ALTER TABLE t ADD CONSTRAINT chk_c CHECK (...);`        | `ALTER TABLE t DROP CONSTRAINT chk_c;` |

> [!warning] 加约束前先清理脏数据
> 表里已有不满足条件的数据时，`ALTER TABLE ... ADD 约束` 会**直接失败**。
> 顺序永远是：**先补数据 → 再加约束**。

> [!quote] 一句话记忆
> **约束 = 表上的"门禁"**：非空是"必须刷卡"，默认是"没刷卡就自动放行"，主键是"一人一卡不重复"，唯一是"卡号不重复但允许空卡"，检查是"卡符合条件才放行"，外键是"必须有上级批条"。
