# 数据库

在容器里跑数据库，核心就一件事：数据目录必须挂出来。各家的路径不统一，记不住就查文档：

| 数据库 | 数据目录 | 常用环境变量 |
| --- | --- | --- |
| PostgreSQL | `/var/lib/postgresql/data` | `POSTGRES_PASSWORD`、`POSTGRES_DB` |
| MySQL | `/var/lib/mysql` | `MYSQL_ROOT_PASSWORD`、`MYSQL_DATABASE` |
| Redis | `/data` | 无，靠配置文件开 AOF |
| MongoDB | `/data/db` | `MONGO_INITDB_ROOT_USERNAME` |

PostgreSQL 的最小启动命令：

```bash
docker run -d --name pg \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=app \
  -p 5432:5432 \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16
```

`POSTGRES_PASSWORD` 是必填的，不填容器直接退出。`POSTGRES_DB` 会建一个同名库，不写则默认 `postgres`。端口映射只在需要从宿主连的时候加，容器间通信走 Docker 网络，不用暴露到宿主。

初始化脚本放到 `/docker-entrypoint-initdb.d/`，容器第一次初始化时按文件名顺序执行 `.sql`、`.sh`、`.sql.gz`。触发条件是数据目录为空，重启、`docker restart` 都不会再跑。已经初始化过的库要加脚本，只能手动执行或者重建。

compose 里通常会再加健康检查，避免应用比数据库先起来：

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 10

  api:
    build: .
    depends_on:
      db:
        condition: service_healthy

volumes:
  pgdata:
```

`pg_isready` 返回 0 才算健康，`condition: service_healthy` 会等健康检查通过再启动 api。只写 `depends_on: [db]` 只保证启动顺序，不保证数据库能接受连接，应用照样可能在启动时连接被拒。

几个实际踩过的坑：

- 卷挂到 `/var/lib/postgresql/data` 时，某些文件系统根目录有 `lost+found`，`initdb` 会拒绝初始化。加 `-e PGDATA=/var/lib/postgresql/data/pgdata` 把数据放到子目录即可。
- MySQL 的 `MYSQL_DATABASE` 只在首次初始化时建库，改了 compose 文件重启不会生效。
- 升级大版本（比如 15 到 16）不能直接换标签，数据目录格式不兼容，要按官方文档 dump/restore 或 `pg_upgrade`。
- Redis 默认不开持久化，重启就空。要保留就挂 `/data` 并加 `redis-server --appendonly yes`。

备份用镜像自带的客户端最稳：

```bash
docker exec pg pg_dump -U postgres app > app-$(date +%F).sql
```

> [!warning] 容器化不等于无状态
> 数据库仍然是有状态的。备份、监控、资源限制、版本升级方案，一样都不能省。
