# 底层技术

Docker 的命令行只是外壳，真正干活的是 Linux 内核的三套机制。把这三样分清楚，容器的大多数“怪现象”都能当场解释，不用翻文档。

| 机制 | 管什么 | 典型现象 |
| --- | --- | --- |
| 命名空间 | 进程能看见什么 | 容器里 `ps` 只有几个进程，`ip addr` 是自己的网卡 |
| cgroups | 进程能用多少资源 | 超过 `--memory` 被杀，退出码 137 |
| 联合文件系统 | 文件系统怎么叠起来 | 镜像层共享，容器写操作落在最上面的可写层 |

`docker run` 一条命令同时用到了三者：

```bash
docker run -d --name web --memory=256m --cpus=1 -p 8080:80 nginx
```

- 为新进程创建 PID、NET、MNT、UTS、IPC 命名空间，所以它有自己的 1 号进程、网卡和根文件系统；
- 在 cgroup v2 里建一个 scope，写入 `memory.max=268435456`、`cpu.max=100000 100000`；
- 用 overlay2 把 nginx 的只读镜像层和一层空的可写目录挂成 `/`；
- `-p 8080:80` 在宿主机的网络命名空间里加转发规则，把流量送进容器的 80 端口。

学习顺序按“隔离 → 限制 → 存储”来：先看 [[01-命名空间|命名空间]]，能解释 `docker exec` 和 `--network=host`；再看 [[02-控制组|控制组]]，能解释 OOMKilled 和 CPU 跑不满；然后是 [[03-联合文件系统|联合文件系统]]，能解释镜像大小和容器数据为什么丢。

> [!tip] 这些不是 Docker 发明的
> 命名空间、cgroups、OverlayFS 都是内核特性，Docker 做的是组合和编排。真正执行 `clone()`、`unshare()`、`mount()` 的是 OCI 运行时（默认 runc），所以换 Podman 或 containerd 时这些行为基本一致。Windows 和 macOS 上的容器跑在一个 Linux 虚拟机里，原因也在这里。
