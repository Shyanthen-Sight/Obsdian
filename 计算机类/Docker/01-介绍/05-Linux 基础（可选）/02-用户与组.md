# 用户与组

容器默认以 root 运行，这是很多安全问题的起点。镜像里用 `USER` 指定非 root 用户，运行时用 `--user` 覆盖：

```dockerfile
FROM alpine:3.20
RUN addgroup -S app && adduser -S -G app app
WORKDIR /app
COPY --chown=app:app . .
USER app
CMD ["./server"]
```

`addgroup -S` / `adduser -S` 创建系统用户，`-G` 指定主组；`COPY --chown` 让文件属主一次到位，省掉一层 `chown`。Debian 系则是 `groupadd --system app && useradd --system --gid app app`。

## UID 才是硬通货

宿主机和容器共享内核的 UID/GID 空间（没开 userns-remap 时）。绑定挂载能不能写，看的是数字 UID 是否匹配，用户名根本不参与：

```bash
$ id
uid=1000(shyanthen) gid=1000(shyanthen)
$ docker run --rm -v "$PWD":/work alpine touch /work/a.txt
$ ls -l a.txt
-rw-r--r-- 1 root root 0 ... a.txt
```

容器里 root 是 UID 0，写出来的文件在宿主上也归 root。反过来，镜像里 `USER app` 的 UID 如果是 100，宿主目录属于 1000，就会 `Permission denied`。排查时两边都跑 `id`，别只看用户名。

运行时覆盖：

```bash
docker run --rm --user 1000:1000 -v "$PWD":/work alpine id
```

## 几个边界

- 非 root 进程默认不能绑定 1024 以下端口，要么改端口，要么加 `CAP_NET_BIND_SERVICE`
- 镜像里 `USER` 之后再 `RUN apt-get install` 会失败，装包要放在切换用户之前
- OpenShift 会随机分配 UID，镜像要保证组 0 对配置目录有写权限
- userns-remap 能把容器 root 映射成宿主普通用户，但卷和权限会变复杂

## root 与非 root：到底差在哪

Linux 的权限检查只看两件事：进程的 uid/gid，以及文件的属主和权限位。uid 0 在传统模型里绕过大部分 DAC 检查（`CAP_DAC_OVERRIDE`），所以容器里的 root 能读写根文件系统里几乎所有文件；镜像层本身只读，写入会落到可写层。

但容器里的 root 并不是“完整的 root”，它还受四层限制：

- **capabilities**：Docker 默认只给 root 一部分 capability，`CAP_SYS_ADMIN`、`CAP_SYS_MODULE`、`CAP_SYS_TIME` 等默认没有。
- **seccomp**：默认配置拦截一批危险 syscall。
- **AppArmor/SELinux**：限制文件、网络、挂载等操作。
- **mount 命名空间**：看不到宿主的大部分文件系统。

问题在于，这些是“减少攻击面”，不是“改变 uid 语义”。默认不启用 user 命名空间时，容器里的 uid 0 在宿主上也是 uid 0。绑定挂载写出的文件归宿主 root；如果攻击者利用内核漏洞或运行时漏洞逃逸，拿到的也是宿主 root。

非 root 用户则是从源头降权：没有 uid 0 的绕过能力，默认也没有那些 capability。应用被攻破时，攻击者只能动这个用户能动的文件，影响范围小得多。代价是：

- 不能绑定 1024 以下端口，除非加 `CAP_NET_BIND_SERVICE` 或改端口。
- 不能改系统目录、不能装包、不能写 `/var/lib` 下属于 root 的路径。
- 需要提前把工作目录、日志目录、缓存目录的属主设对。

生产镜像的常见组合是：`USER` 指定非 root、根文件系统只读、`--cap-drop ALL`、`--security-opt no-new-privileges`，需要写的目录用卷或 tmpfs。

## USER、--user、userns-remap 与 rootless

这三个机制经常被混着说，但它们作用的层面完全不同：

| 机制 | 层面 | 作用 | 优先级 | 注意 |
| --- | --- | --- | --- | --- |
| `USER`（Dockerfile） | 镜像 | 设定镜像默认运行用户，影响后续 `RUN`、`ENTRYPOINT` | 最低，可被运行时覆盖 | `USER` 之后的 `RUN apt-get install` 会失败 |
| `--user`（`docker run`） | 单次容器 | 覆盖镜像的 `USER`，可写 uid、uid:gid 或用户名 | 最高 | 用户名必须在容器 `/etc/passwd` 里能解析 |
| `userns-remap`（daemon） | 宿主全局 | 把容器 uid 映射到宿主的高位 uid 区间 | 全局生效，`--userns=host` 可退出 | 卷、绑定挂载的属主会变，需要重新规划 |
| rootless 模式 | 宿主全局 | 整个 daemon 以普通用户运行，容器 root 映射到该用户 | 全局 | 端口、cgroup、网络、存储驱动有限制 |

优先级可以记成：`--user` > 镜像 `USER` > 默认 root。`userns-remap` 不改变“容器里看到什么 uid”，它改变的是“这个 uid 在宿主上对应谁”。开了 remap 之后，容器里的 uid 0 在宿主上可能是 100000，绑定挂载写出的文件也归 100000，原来按 1000 规划的目录权限就要跟着调整。

查看当前配置：

```bash
docker inspect web --format '{{.Config.User}}'
docker info --format '{{json .SecurityOptions}}'
```

## UID/GID 才是硬通货

内核不认识用户名。`/etc/passwd` 只是用户态用来把 uid 翻译成名字的表，权限检查全程用数字。所以：

- 镜像里 `USER app` 的 uid 是 100，宿主目录属于 uid 1000，写不进去，报 `Permission denied`。
- 容器里 root 是 uid 0，绑定挂载写出的文件在宿主上也归 uid 0。
- `--user 1000:1000` 能让容器进程以宿主的普通用户身份写目录，但容器里可能没有 uid 1000 对应的用户名，`whoami` 会失败，`id` 仍然能显示数字。

排查时两边都跑 `id`，再用 `ls -ln` 看数字属主，不要只看用户名：

```bash
id
ls -ln /work
docker run --rm -v "$PWD":/work alpine id
```

命名卷和绑定挂载的行为也不同：空的命名卷第一次挂载时，Docker 会把镜像里对应目录的内容和属主复制进去；绑定挂载直接暴露宿主目录，属主完全由宿主决定。所以“镜像里 chown 过”不代表绑定挂载也能写。

OpenShift 这类平台会给容器随机分配 uid，但保证 gid 0。镜像要兼容这种环境，通常把配置目录设成组 0 可写：

```dockerfile
RUN chgrp -R 0 /app && chmod -R g=u /app
USER 1001
```

## 排查 permission denied 的顺序

| 步骤 | 命令 | 看什么 |
| --- | --- | --- |
| 1. 确认身份 | 容器内 `id`，宿主机 `id` | uid/gid 是否匹配 |
| 2. 看数字属主 | `ls -ln`、`stat` | 不要被用户名误导 |
| 3. 确认挂载类型 | `docker inspect --format '{{json .Mounts}}'` | 绑定挂载还是命名卷，是否只读 |
| 4. 检查只读根文件系统 | `docker inspect --format '{{.HostConfig.ReadonlyRootfs}}'` | 需要写的目录是否挂了 tmpfs/卷 |
| 5. 检查 SELinux | `ls -Z`、`docker run -v ...:z` | 宿主机启用 SELinux 时需要标签 |
| 6. 检查 capability | `docker inspect --format '{{json .HostConfig.CapDrop}}'` | 是否缺 `CAP_DAC_OVERRIDE`、`CAP_NET_BIND_SERVICE` |
| 7. 检查 userns/rootless | `docker info`、`podman info` | uid 是否被映射到高位区间 |
| 8. 检查 umask | 容器内 `umask` | 新文件权限是否符合预期 |

多数 `Permission denied` 不是“容器坏了”，而是数字 uid 不匹配，或者目录被只读挂载。先做第 1、2 步，能省掉一半排查时间。

## 数据库镜像为什么不能乱改 USER

官方 PostgreSQL、MySQL、MariaDB 镜像的 entrypoint 通常以 root 启动，先检查数据目录、`chown` 给数据库用户，再用 `gosu`/`su-exec` 降权启动数据库。这个流程依赖 root 权限。

如果你在 Dockerfile 里提前 `USER postgres`，或者 `docker run --user 1000` 覆盖，entrypoint 就没有权限改数据目录，初始化直接失败。要改，必须同时保证卷的属主已经是数据库用户的 uid，或者改用镜像支持的初始化方式。先读镜像文档，再动 `USER`。

> [!tip] 数据库镜像别乱改 USER
> 官方 PostgreSQL、MySQL 镜像的 entrypoint 会用 root 做数据目录 chown，再降权启动。自己覆盖 `USER` 或 `--user` 之前先读镜像文档，否则初始化直接失败。
