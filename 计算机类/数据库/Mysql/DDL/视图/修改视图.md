# ALTER VIEW —— 修改视图

> [!abstract] 一句话
> 视图只保存一条 `SELECT` 定义，"修改视图"就是**替换这段定义**。
> 两种写法：`ALTER VIEW`（视图必须已存在）和 `CREATE OR REPLACE VIEW`（不存在就新建，存在就覆盖）。
> **不要用 `DROP VIEW` + `CREATE VIEW` 来改定义**——会丢授权，还会让依赖它的视图短暂失效。

---

## 一、两种改法

### 1.1 `ALTER VIEW`

```sql
ALTER
    [ALGORITHM = {UNDEFINED | MERGE | TEMPTABLE}]
    [DEFINER = 'user'@'host']
    [SQL SECURITY {DEFINER | INVOKER}]
    VIEW 视图名 [(列名1, 列名2, ...)]
    AS 查询语句
    [WITH [CASCADED | LOCAL] CHECK OPTION];
```

### 1.2 `CREATE OR REPLACE VIEW`

```sql
CREATE OR REPLACE
    [ALGORITHM = ...]
    [DEFINER = ...]
    [SQL SECURITY ...]
    VIEW 视图名 [(列名...)]
    AS 查询语句
    [WITH ... CHECK OPTION];
```

### 1.3 两者怎么选

| 对比项 | `ALTER VIEW` | `CREATE OR REPLACE VIEW` |
| --- | --- | --- |
| 视图不存在时 | ❌ 报错 `ERROR 1146` | ✅ 直接创建 |
| 视图已存在时 | ✅ 替换定义 | ✅ 替换定义 |
| 适合场景 | 确认视图一定存在，只想改它 | 初始化脚本、部署脚本、可重复执行 |
| 额外权限限制 | 必须是 **definer**，或有 `SET_USER_ID` | 没有这条限制，权限够就能覆盖 |
| 所需权限 | `CREATE VIEW` + `DROP` + 列权限 | `CREATE VIEW` + 列权限；替换时还要 `DROP` |

> [!warning] `CREATE OR REPLACE VIEW` 能覆盖"别人的"视图
> 它不要求你是原 definer，只要你有 `CREATE VIEW` 和 `DROP`。
> 生产环境里，这两项权限不要随手给业务账号。
> 而 `ALTER VIEW` 明确限定：**只有 definer 或持有 `SET_USER_ID` 的用户能改**。

---

## 二、能改什么、不能改什么

| 想做的事 | 正确做法 |
| --- | --- |
| 改查询体、过滤条件、连接方式 | `ALTER VIEW ... AS 新 SELECT` |
| 改视图列名 | 在 `SELECT` 里起别名，或用列清单 |
| 增加/删除一列 | 重写整个 `SELECT`（视图没有 `ADD COLUMN`） |
| 改处理算法 | `ALTER VIEW ALGORITHM = ...` |
| 改定义者 / 安全模式 | `ALTER VIEW DEFINER = ... SQL SECURITY ...` |
| 加/去 `WITH CHECK OPTION` | 重写定义时加上或去掉 |
| 改视图名 | `RENAME TABLE 旧名 TO 新名`（不能跨库） |
| 把视图改成基表 | 先 `DROP VIEW`，再 `CREATE TABLE` |
| 给视图加索引 / 触发器 | ❌ MySQL 不支持 |
| 用 `ALTER TABLE` 改视图 | ❌ 报 `ERROR 1347: is not BASE TABLE` |

> [!danger] 视图没有"增删列"语法
> `ALTER VIEW` 是**整体替换**，不是增量修改。想加一列，必须把完整的新 `SELECT` 重写一遍。
> 也正因如此，定义里写 `SELECT *` 的视图在基表加列后**不会自动更新**，只能靠重写视图定义来"刷新"。

## 三、常见修改示例

### 3.1 增加一列

原视图：

```sql
CREATE VIEW v_student_public AS
SELECT id, stu_no, name, gender, class_id FROM student;
```

加一列 `age`：

```sql
CREATE OR REPLACE VIEW v_student_public AS
SELECT id, stu_no, name, gender, class_id, age
FROM student;
```

### 3.2 改过滤条件

```sql
ALTER VIEW v_student_public AS
SELECT id, stu_no, name, gender, class_id
FROM student
WHERE is_active = 1;
```

> [!warning] 改过滤条件不会影响已有查询的权限，但会影响结果
> 原来能查到 1000 行，改完可能只剩 800 行。依赖这个视图的报表、接口会"悄悄少数据"。
> 改之前先 `SELECT COUNT(*)` 对比新旧条件。

### 3.3 加 `WITH CHECK OPTION`

```sql
ALTER VIEW v_adult AS
SELECT id, name, age FROM student WHERE age >= 18
WITH CHECK OPTION;
```

### 3.4 用列清单改列名

```sql
ALTER VIEW v_student_public
    (student_id, student_no, student_name, gender, class_id)
AS
SELECT id, stu_no, name, gender, class_id FROM student;
```

列清单数量必须和 `SELECT` 列数完全一致，否则报 `ERROR 1353`。

### 3.5 改算法与安全模式

```sql
ALTER ALGORITHM = MERGE
      SQL SECURITY INVOKER
      VIEW v_student_public AS
SELECT id, stu_no, name FROM student;
```

> [!danger] 没写的属性会回到默认值
> `ALTER VIEW` / `CREATE OR REPLACE VIEW` 都是**整体重建定义**。如果你省略了 `DEFINER`，定义者会变成**当前执行语句的用户**；省略 `SQL SECURITY`，会回到 `DEFINER`；省略 `ALGORITHM`，会回到 `UNDEFINED`。
> 生产环境改视图，先 `SHOW CREATE VIEW` 把原定义完整抄下来，再在它基础上改，并**显式保留 `DEFINER`**。

## 四、修改的影响面

### 4.1 对"依赖它的上层视图"

MySQL **不会级联更新视图定义**。下层视图改了列名或删了列，上层视图不会在修改时报错，而是**查询时才报 `ERROR 1356`**。

```sql
CREATE VIEW v_base AS SELECT id, name, age FROM student;
CREATE VIEW v_top  AS SELECT id, name FROM v_base;

-- 改掉 v_base 的列名
CREATE OR REPLACE VIEW v_base AS
SELECT id, name AS student_name, age FROM student;

SELECT * FROM v_top;
-- ERROR 1356: View 'db.v_top' references invalid table(s) or column(s) ...
```

找依赖者只能靠定义文本搜索：

```sql
SELECT TABLE_SCHEMA, TABLE_NAME
FROM information_schema.VIEWS
WHERE VIEW_DEFINITION LIKE '%v_base%';
```

> [!note] 这种搜索只能"尽量找"
> `VIEW_DEFINITION` 是规范化后的文本，注释会被去掉；同名字符串也可能误命中。
> 视图超过两三层，依赖关系就会变得难以维护——这是控制嵌套层数的最好理由。

### 4.2 对应用和查询

| 改动 | 对使用方的影响 |
| --- | --- |
| 新增一列 | `SELECT *` 的使用方会多收到一列，ORM 映射可能报"未知列" |
| 删除一列 | 任何引用该列的 SQL 立刻报 `1054 Unknown column` |
| 重命名列 | 同上，属于**破坏性变更** |
| 调整列顺序 | 依赖列位置的代码（少见但存在）会出错 |
| 改过滤条件 | 结果集变多变少，业务口径可能被悄悄改变 |

> [!tip] 兼容式演进
> 不要原地改列名。更稳的做法是：
> 1. 新建 `v_student_public_v2`（新列名）
> 2. 应用逐步切到新视图
> 3. 观察一段时间后再删旧视图
>
> 代价是多一个对象，收益是**随时可回滚**。

### 4.3 对权限

| 操作 | 视图上的授权 |
| --- | --- |
| `ALTER VIEW` | ✅ 保留（对象没有被删除） |
| `CREATE OR REPLACE VIEW` | ✅ 保留（对象没有被删除） |
| `DROP VIEW` + `CREATE VIEW` | ❌ 全部丢失，必须重新 `GRANT` |
| `RENAME TABLE` 改视图名 | ❌ 不会迁移到新名字，需要重新授权 |

### 4.4 事务与锁

- 视图是 DDL，执行前**隐式提交**当前事务，`ROLLBACK` 救不回来
- MySQL 8.0 的 DDL 是原子的：语句失败不会留下半成品
- `ALTER VIEW` 需要元数据锁；如果基表上有长事务/长查询，可能被阻塞
- 改定义本身不碰数据，**不会**修改基表里的任何一行

## 五、重命名视图

`ALTER VIEW` 不能改名字，用 `RENAME TABLE`：

```sql
RENAME TABLE v_student_public TO v_student_info;
```

> [!warning] 三个限制
> 1. **不能跨数据库**重命名视图（表可以，视图不行）
> 2. **授权不会跟着走**：新名字上没有任何针对该视图的授权，应用可能立刻报权限错误
> 3. 别的视图里写的是旧名字，重命名后上层视图会失效（同样报 1356）
>
> 重命名后记得重新 `GRANT`，并检查依赖。

> [!tip] 不想改名字，只想"下线"
> 可以先改名成 `zz_deprecated_v_xxx` 观察一段时间，再删除。但考虑到授权不会迁移，这条路只适合"确定没人用了"的场景；否则直接保留原名、限制权限更稳妥。

## 六、修改前后怎么核对

```sql
-- 1. 改之前：完整备份定义
SHOW CREATE VIEW v_student_public\G

-- 2. 改完后：确认属性符合预期
SELECT TABLE_NAME, IS_UPDATABLE, CHECK_OPTION,
       DEFINER, SECURITY_TYPE, VIEW_DEFINITION
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'v_student_public';

-- 3. 验证定义本身没坏
CHECK TABLE v_student_public;
SELECT * FROM v_student_public LIMIT 0;

-- 4. 抽查结果
SELECT * FROM v_student_public LIMIT 10;
```

> [!info] 建议把 `SHOW CREATE VIEW` 的输出纳入版本控制
> 改视图前先存一份定义，出问题时可以原样恢复。这比"凭记忆重写"可靠得多。

## 七、常见报错与对策

| 报错 | 原因 | 对策 |
| --- | --- | --- |
| `ERROR 1146` Table doesn't exist | `ALTER VIEW` 的目标不存在 | 改用 `CREATE OR REPLACE VIEW` |
| `ERROR 1050` Table already exists | 用了普通 `CREATE VIEW`，但名字已被占用 | 加 `OR REPLACE`，或先删旧对象 |
| `ERROR 1353` different column counts | 列清单数量与 `SELECT` 列数不一致 | 对齐数量 |
| `ERROR 1356` View references invalid ... | 基表/列不存在，或上层视图引用了失效视图 | 修定义；`CHECK TABLE` 定位 |
| `ERROR 1369` CHECK OPTION failed | 写入后的行不满足视图条件 | 调整数据或条件 |
| `ERROR 1449` definer does not exist | 定义者账号不存在 | 建账号，或显式改 `DEFINER` |
| `ERROR 1347` is not BASE TABLE | 对视图用了 `ALTER TABLE` | 改用 `ALTER VIEW` |
| `ERROR 1044 / 1142` Access denied | 缺 `CREATE VIEW` / `DROP` / 列权限 | 补授权 |

> [!failure] `ALTER VIEW` 报 1146，不一定是你写错了
> 先确认三件事：`SELECT DATABASE();` 是不是目标库、视图名大小写是否一致（Linux 区分大小写）、当前账号是否真的能看到这个视图。
> 在 MySQL 的报错里，视图常被称作 "Table"，别被措辞带偏。

## 八、安全修改视图的流程

- [ ] `SELECT DATABASE();` —— 确认环境，别改错库
- [ ] `SHOW CREATE VIEW 视图名\G` —— 保存原定义（含 `DEFINER` / `ALGORITHM` / `SQL SECURITY`）
- [ ] 查依赖：`information_schema.VIEWS` 中搜视图名
- [ ] 评估列变更：有没有删列/改名/调顺序
- [ ] 用 `CREATE OR REPLACE VIEW`，并显式写回 `DEFINER` 等属性
- [ ] `SELECT * FROM 视图 LIMIT 0;` 验证定义可解析
- [ ] 抽查 10～20 行，确认结果符合预期
- [ ] 检查视图上的授权是否仍然有效
- [ ] 通知使用方（报表、接口、其他视图）
- [ ] 把新定义纳入版本控制

---

> [!quote] 一句话记忆
> **改视图 = 换掉那条 SELECT**：`ALTER VIEW` 要求已存在，`CREATE OR REPLACE` 可幂等；整体替换、没写的属性回默认，授权保留但依赖不会自动跟。
