# SELECT FROM VIEW —— 查询视图

> [!abstract] 一句话
> 查询视图和查询基表**语法完全一样**：`SELECT ... FROM 视图名`。
> 视图里没有数据，每次查询时 MySQL 都会把视图定义**展开进外层查询**（`MERGE`）或**先物化再查**（`TEMPTABLE`）。
> 所以"查视图慢"通常不是视图的错，而是它背后那条 `SELECT` 或基表索引的问题。

> [!info] 与其它笔记的分工
> - 视图是什么、怎么建、可更新性与 `CHECK OPTION`：[[创建视图]]
> - 改定义：[[修改视图]]
> - 删定义：[[删除视图]]
> - 表子查询的写法：[[派生表]]
> - 执行计划与索引分析：[[查询优化]]、[[管理索引]]
>
> 本篇只讲：**怎么从视图取数据，以及取的时候发生了什么。**

## 一、基本用法：像查表一样查

```sql
-- 全查
SELECT * FROM v_student_public;

-- 过滤 + 排序
SELECT id, name FROM v_student_public
WHERE gender = 'F'
ORDER BY id;

-- 和基表连接
SELECT v.name, c.name AS class_name
FROM v_student_public v
JOIN class c ON v.class_id = c.id;
```

视图可以出现在**查询语句的任何表位置**：

| 位置 | 示例 | 说明 |
| --- | --- | --- |
| `FROM` | `SELECT * FROM v_student_public` | 最常见 |
| `JOIN` | `... FROM v_student_public v JOIN class c ON ...` | 视图就是一张"表" |
| 子查询 | `WHERE id IN (SELECT class_id FROM v_class_stat)` | 相关子查询里也照用 |
| 派生表 | `FROM (SELECT * FROM v_student_public) t` | 可以，但层数越多越难优化 |
| 再建视图 | `CREATE VIEW v2 AS SELECT ... FROM v1` | 嵌套视图 |
| 备份 | `mysqldump` 导出的是**定义**，不是数据 | 恢复时重新执行 |

### 1.1 三个必须记住的规则

- 外层查询只能看到**视图暴露的列名**，看不见没暴露的基表列
- 视图定义里的列别名，在外层就是真正的列名
- 外层的 `WHERE` / `GROUP BY` / `ORDER BY` 作用在**视图的输出**上

> [!warning] `SELECT *` 查视图 ≠ 查基表全部列
> 视图列的集合在**创建那一刻就冻结**了。基表后来新增的列不会冒出来；基表删掉的列会让查询直接报 `ERROR 1356`。
> 另外，不要依赖视图定义里的 `ORDER BY`：外层语句一旦自带 `ORDER BY`，视图里的排序会被忽略。

### 1.2 视图 vs 派生表

| | 视图 | 派生表 |
| --- | --- | --- |
| 生命周期 | 持久保存在数据字典 | 只存在于当前语句 |
| 写法 | `FROM v_name` | `FROM (SELECT ...) 别名` |
| 能否跨语句复用 | ✅ | ❌ |
| 能否单独授权 | ✅ | ❌ |
| 优化方式 | `MERGE` / `TEMPTABLE` | 合并或物化 |

一句话：**视图 = 起了名字、存进数据字典的派生表。**

## 二、查询视图时，MySQL 到底做了什么

视图的执行方式由 `ALGORITHM` 决定，默认 `UNDEFINED`（能合并就合并，不能就物化）。

### 2.1 三种取值

| 值 | 行为 | 特点 |
| --- | --- | --- |
| `MERGE` | 把视图定义**合并进**外层查询 | 通常最快；可用基表索引；可更新 |
| `TEMPTABLE` | 先把视图结果放进临时表，再查 | 有物化开销；**不可更新**；用不上基表索引 |
| `UNDEFINED`（默认） | 能 `MERGE` 就 `MERGE`，否则物化 | 大多数情况的最优解 |

### 2.2 `MERGE`：把定义"粘贴"进外层查询

```sql
CREATE ALGORITHM = MERGE VIEW v_adult AS
SELECT id, name, age FROM student WHERE age >= 18;

SELECT * FROM v_adult WHERE id < 10;
-- 实际按这个执行：
SELECT id, name, age FROM student WHERE age >= 18 AND id < 10;
```

- 外层的 `id < 10` 会**下推到基表**，照样能用基表索引
- 不产生临时表，通常最快
- 可更新视图一般来自 `MERGE`

### 2.3 `TEMPTABLE`：先算完，再在外层筛

```sql
CREATE ALGORITHM = TEMPTABLE VIEW v_stat AS
SELECT class_id, COUNT(*) AS cnt FROM student GROUP BY class_id;

SELECT * FROM v_stat WHERE class_id = 1001;
```

执行顺序是：

1. 把视图的 `GROUP BY` 整个算完，结果放进**临时表**
2. 再用 `class_id = 1001` 过滤临时表

问题在于第 1 步**无法被外层的条件裁剪**：哪怕只查一个班，也要先统计所有班。而且临时表没有索引，外层过滤只能扫。

> [!tip] 什么时候显式写 `TEMPTABLE`
> 1. 希望**尽早释放基表锁**（临时表建好后即可解锁）
> 2. 要绕开"不能在子查询里读、同时又在外部改同一张表"的限制
>
> 其余情况别手写 `TEMPTABLE`——它会让视图失去可更新性，也失去索引优势。

> [!warning] `TEMPTABLE` 视图是只读的
> `ALGORITHM = TEMPTABLE` 的视图 `IS_UPDATABLE = NO`，不能 `INSERT / UPDATE / DELETE`。
> 详见 [[创建视图]] §六。

### 2.4 哪些构造会强制物化

出现下面任一构造，基本就与 `MERGE` 无缘：

- 聚合函数（`SUM` / `COUNT` / `AVG` / `MIN` / `MAX`）或窗口函数
- `DISTINCT`
- `GROUP BY` / `HAVING`
- `UNION` / `UNION ALL`
- `LIMIT`
- `SELECT` 列表里的子查询
- 显式 `ALGORITHM = TEMPTABLE`

> [!note] 指定 `MERGE` 却合并不了
> 含聚合、`DISTINCT`、`GROUP BY`、`UNION`、`LIMIT` 等构造时无法合并。此时写 `ALGORITHM = MERGE` 会得到一条 warning，并自动降级为 `UNDEFINED`。

### 2.5 用 `EXPLAIN` 看视图的真实计划

```sql
EXPLAIN SELECT * FROM v_student_public WHERE gender = 'F';
```

- MySQL 8.0 通常直接展示**展开后的基表**，结果里根本不出现视图名
- 发生物化时，`table` 列会出现 `<derived2>` 之类的派生表，`Extra` 里常带 `Using temporary`
- 想看细节用 `EXPLAIN FORMAT=JSON`，搜索 `materialized_from_subquery`

```sql
EXPLAIN FORMAT = JSON
SELECT * FROM v_class_stat WHERE avg_score > 80;
```

> [!tip] 判断视图有没有拖后腿
> 计划里只有基表 + 合适的索引 → 视图没有额外开销，慢就是基表慢。
> 计划里出现 `<derivedN>` + `Using temporary` → 视图被物化了，这才是要处理的地方。

### 2.6 视图自己没有统计信息和索引

优化器估算视图成本时，用的是**基表的行数、索引和统计信息**。视图本身：

- 没有索引（`CREATE INDEX` 不能作用在视图上）
- 没有行数统计
- 没有直方图（8.0 的直方图也建在基表列上）

所以"给视图加个索引让它快点"这条路不存在，只能回头优化基表，见 [[管理索引]]。

## 三、查询视图需要什么权限

### 3.1 视图本身的权限

```sql
GRANT SELECT ON school.v_student_public TO 'app_user'@'%';
```

只需要视图上的 `SELECT`，**不需要**基表的 `SELECT`——前提是视图用默认的 `SQL SECURITY DEFINER`。

### 3.2 `SQL SECURITY` 决定校验谁

| 模式 | 执行时检查谁对基表的权限 | 结果 |
| --- | --- | --- |
| `DEFINER`（默认） | 视图定义者 | 业务账号只拿视图权限即可，权限被"收口" |
| `INVOKER` | 调用视图的用户 | 调用者自己也必须有基表的 `SELECT` |

```sql
-- 看当前视图用的是哪种
SELECT TABLE_NAME, DEFINER, SECURITY_TYPE
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = DATABASE();
```

> [!danger] 默认模式下的两个隐形依赖
> 1. **definer 账号不能删**：删了账号，查视图报 `ERROR 1449`
> 2. **definer 的基表权限不能收**：收掉后，业务账号查视图报 `ERROR 1142`
>
> 从 A 库导到 B 库后查不了视图，多半就是这两条。导入前先查 `DEFINER`。

### 3.3 看定义还要额外权限

`SHOW CREATE VIEW` 和 `information_schema.VIEWS.VIEW_DEFINITION` 需要 **`SHOW VIEW`** 权限。
只有 `SELECT` 的用户能查数据，但看不到定义，`VIEW_DEFINITION` 返回 `NULL`。

## 四、查询视图的元数据

查数据之外，日常排查还要能查"视图本身是什么样"。

```sql
-- 1. 当前库有哪些视图
SHOW FULL TABLES WHERE Table_type = 'VIEW';

-- 2. 完整定义（含 ALGORITHM / DEFINER / SQL SECURITY / CHECK OPTION）
SHOW CREATE VIEW v_student_public\G

-- 3. 列结构
DESC v_student_public;
SHOW COLUMNS FROM v_student_public;

-- 4. 元信息总表
SELECT TABLE_NAME,
       IS_UPDATABLE,     -- YES / NO
       CHECK_OPTION,     -- NONE / CASCADE / LOCAL
       DEFINER,
       SECURITY_TYPE,    -- DEFINER / INVOKER
       VIEW_DEFINITION
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'v_student_public';

-- 5. 定义是否还有效（定位 1356）
CHECK TABLE v_student_public;

-- 6. 视图的"表状态"
SHOW TABLE STATUS LIKE 'v_student_public'\G

-- 7. 视图没有索引，这条通常返回空结果
SHOW INDEX FROM v_student_public;
```

`SHOW TABLE STATUS` 对视图会显示 `Comment: VIEW`，而 `Engine`、`Rows`、`Data_length` 都是 `NULL`——因为它不存数据。

> [!note] `VIEW_DEFINITION` 是"规范化后"的文本
> 注释会被去掉，标识符可能被加反引号和库名限定，`ON` 条件也可能被重写。
> 所以拿它做依赖搜索只能"尽量找"，不能当精确的依赖关系用。

## 五、查询视图的常见坑

### 5.1 列被"冻结"

```sql
CREATE VIEW v_a AS SELECT id, name FROM student;
-- 之后基表加了 age 列
SELECT * FROM v_a;              -- 只有 id、name，没有 age
SELECT age FROM v_a;            -- ❌ ERROR 1054 Unknown column 'age'
```

### 5.2 外层不能用基表列名

```sql
-- ❌ 视图没有暴露 stu_no
SELECT stu_no FROM v_student_public;
-- ERROR 1054: Unknown column 'stu_no' in 'field list'
```

视图对外只承诺它自己的列名。基表改列名时，视图定义不变、外层 SQL 也不用改——这正是"逻辑独立性"的价值。
反过来，**外层**查询可以用视图列名做 `WHERE`，因为那时视图已经是一张"表"了。

### 5.3 类型是推导出来的

视图列的类型来自 `SELECT` 表达式，不是基表原样照搬：

| 表达式 | 推导类型 |
| --- | --- |
| `COUNT(*)` | `BIGINT` |
| `SUM(int_col)` | `DECIMAL` |
| `AVG(...)` | `DECIMAL` / `DOUBLE` |
| 字符串拼接 | 取较宽的长度 |

所以拿视图列和字面量比较时，可能出现隐式转换，导致索引失效，见 [[查询优化]]。

### 5.4 视图嵌套越深越难查

```sql
CREATE VIEW v1 AS SELECT ... FROM student;
CREATE VIEW v2 AS SELECT ... FROM v1;
CREATE VIEW v3 AS SELECT ... FROM v2;
```

- 每层都可能触发一次展开或物化
- 出问题时 `EXPLAIN` 里是一堆 `<derivedN>`
- 改下层列名，上层要到**查询时**才报 1356

> [!tip] 层数控制在 2～3 层以内
> 超过这个深度，排查成本和性能风险都会明显上升。更多时候应该回到基表重写 SQL。

### 5.5 常见报错对照

| 报错 | 原因 | 对策 |
| --- | --- | --- |
| `ERROR 1356` View references invalid table(s) or column(s) | 基表被删/改列，或底层视图失效 | `CHECK TABLE` 定位；重建定义 |
| `ERROR 1449` The user specified as a definer does not exist | `DEFINER` 账号不存在 | 建账号，或 `ALTER VIEW ... DEFINER = ...` |
| `ERROR 1142` SELECT command denied | 视图或基表权限不足（看 `SQL SECURITY`） | 补 `SELECT`；检查 definer 权限 |
| `ERROR 1054` Unknown column | 引用了视图未暴露的列 | 用视图里的列名，或改视图 |
| `ERROR 1109` Unknown table ... in information_schema | 视图定义损坏或元数据不一致 | `SHOW CREATE VIEW` 核对，重建 |
| 查询很慢、`Using temporary` | 视图被物化 | 去掉聚合/`DISTINCT`/`LIMIT`，或直接查基表 |

> [!failure] 1356 是"查询时才炸"的典型
> 创建视图时不校验基表列是否存在，直到你 `SELECT` 它才报错。
> 最快验证：`SELECT * FROM 视图名 LIMIT 0;`——不取数据，只验证定义能否解析。

## 六、性能：查视图慢怎么办

视图**不缓存、不加速**，它只是一层语法封装。慢的根因永远在下面三处：

| 根因 | 表现 | 处理 |
| --- | --- | --- |
| 基表缺索引 | `EXPLAIN` 显示 `type: ALL` | 给基表加索引，见 [[管理索引]] |
| 视图被物化 | `Extra: Using temporary`、`<derivedN>` | 简化视图；或外层的强过滤条件下沉到基表 |
| 视图定义低效 | 大表 `JOIN`、无谓的 `DISTINCT` | 重写定义，见 [[修改视图]] |
| 嵌套过深 | 多层 `<derivedN>` | 合并成一层，或直接查基表 |

### 6.1 优化顺序

```sql
-- 1. 先看展开后的计划
EXPLAIN SELECT ... FROM 视图名 WHERE ...;

-- 2. 确认是否物化
EXPLAIN FORMAT = JSON SELECT ... FROM 视图名 WHERE ...;

-- 3. 把视图里的 SELECT 单独拿出来跑，对比耗时
SELECT ...;   -- 视图背后的原始 SQL
```

如果原始 SQL 本身就慢，问题在基表，改视图没有意义。

### 6.2 想要"缓存结果"怎么办

MySQL **没有物化视图**。真正需要"提前算好、查得快"时，用**汇总表 + 定时刷新**：

```sql
-- 汇总表
CREATE TABLE class_stat_cache (
    class_id       INT PRIMARY KEY,
    student_count  INT,
    avg_score      DECIMAL(5,2)
);

-- 定时任务里刷新（或事件调度器）
REPLACE INTO class_stat_cache
SELECT class_id, COUNT(*), ROUND(AVG(score), 2)
FROM student JOIN sc ON ...
GROUP BY class_id;
```

代价是要自己处理刷新时机和数据新鲜度；收益是查询变成主键点查。

> [!warning] 视图解决的是"复用"，不是"性能"
> 指望用视图替代缓存或索引，方向就错了。视图省的是**写 SQL 的重复**，不是**查询的时间**。

## 七、查询视图前的自查清单

- [ ] 确认查的是库里的视图，不是同名表：`SHOW FULL TABLES LIKE '名字';`
- [ ] 需要哪些列？视图有没有暴露（`DESC 视图名`）
- [ ] 定义是否用了 `SELECT *`？基表加列后视图不会自动更新
- [ ] 大致判断会不会物化（有聚合 / `DISTINCT` / `LIMIT` 吗）
- [ ] 慢查询先 `EXPLAIN`，看是否出现 `<derivedN>`
- [ ] 权限报错先查 `SQL SECURITY`、`DEFINER` 是否还在
- [ ] 报 1356 先 `CHECK TABLE 视图名`
- [ ] 不要把 `ORDER BY` 写进视图定义里依赖它
- [ ] 嵌套层数控制在 2～3 层
- [ ] 需要"预计算"时用汇总表，不要幻想物化视图

---

> [!quote] 一句话记忆
> **查视图 = 查一条会现场展开的 SELECT**：语法和查表一样，`MERGE` 时谓词下推、`TEMPTABLE` 时先物化；视图不存数据、不缓存、没有索引，慢就回基表查。
