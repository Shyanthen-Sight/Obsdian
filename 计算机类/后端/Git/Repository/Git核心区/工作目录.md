
> [!abstract] 一句话
> ==工作目录（Working Directory / Working Tree）就是你**真正用编辑器打开、敲字、保存**的那个项目文件夹==。它和 `.git/` 里的历史**完全分离**：你在这里改的任何东西，Git 一开始都**不管**——它只是磁盘上的一堆普通文件，等你用 `git add` 主动"交上去"。

---
## 一、先记住"三棵树"

==Git 的核心就是**三个区域**在来回倒腾内容==。工作目录是这三棵树里**唯一你能直接摸到的**：

```text
 ①工作目录                ②暂存区                  ③仓库(提交)
 Working Directory     Staging Area / Index   Repository / HEAD
┌──────────────┐      ┌──────────────┐       ┌──────────────┐
│  你编辑的文件  │ ──①──│ 待提交的清单  │ ──②──  │永久历史快照    │
│  磁盘上的真实文件│ add │ .git/index   │ commit│ .git/objects │
└──────────────┘      └──────────────┘        └──────────────┘
        ▲                                              │
        └──────────────── checkout / restore ──────────┘
```

| 区域 | 别名 | 存在形式 | 谁来读写 |
| --- | --- | --- | --- |
| **工作目录** | 工作区 / working tree | 磁盘上的**普通文件** | 你的编辑器 |
| **暂存区** | 索引 / index / staging | `.git/index` 一个二进制文件 | `git add`（见 [[暂存区]]） |
| **仓库** | 提交 / HEAD / 版本库 | `.git/objects` 里的对象 | [[提交\|git commit]] |

> [!tip] 三个区域 = 三种"看待改动"的视角
> - **工作目录 vs 暂存区** → `git diff`：我改了什么还没交？
> - **暂存区 vs 仓库** → `git diff --staged`：我交了但还没提交什么？
> - **工作目录 vs 仓库** → `git diff HEAD`：相对上次提交，我总共改了什么？

## 二、工作目录到底包含什么

克隆或检出后，工作目录里的一切都能归到两类：

| 类别                 | 含义                 | `git status` 里的样子          |
| ------------------ | ------------------ | -------------------------- |
| **已追踪（Tracked）**   | 上一次快照里就有、且被 Git 盯着 | 干净时**不显示**；改了会列在 `Changes` |
| **未追踪（Untracked）** | 从没被 `add` 过的新文件    | 列在 `Untracked files`       |

已追踪文件又有三种状态：

- **未修改（unmodified）**：和上次提交一模一样。
- **已修改（modified）**：内容变了，但**还没 add**。
- **已暂存（staged）**：改动已经放进暂存区，**等着 commit**。

> [!info] `.gitignore` 管的就是"未追踪"
> 被 `.gitignore` 匹配的文件，Git 会**假装看不见**——不进 `Untracked files`，也 `add` 不进去。
> 详见 [[关于.gitignore]]。它是让工作目录保持干净的头号工具。

> [!note] 工作目录不一定等于"仓库里的一棵子树"
> 大多数时候 `git clone` 会把工作目录铺满：文件都在、`.git/` 藏在里面。
> 但**裸仓库（`git init --bare`）根本没有工作目录**——那里只有历史，没人能编辑文件。
> 这也解释了为什么服务器端仓库不能 `commit`，只能收 `push`。

## 三、在工作目录上做的事

### 3.1 查看状态

```bash
git status                # 全景：已暂存 / 已修改 / 未追踪
git status -s             # 极简模式（短状态），一眼看清
git diff                  # 工作目录 vs 暂存区：还没交的改动
git diff --stat           # 只看改了哪些文件、加删了多少行
```

### 3.2 把改动交给 Git

```bash
git add <文件>            # 把工作目录的改动放进暂存区
git add .                 # 当前目录下所有改动（含新增）
git add -p                # ★逐块挑选要不要暂存，做"精挑细选"的提交
```

> [!tip] `git add` 是"从工作目录拿东西"，`git commit` 是"从暂存区打包"
> 这两步分开，正是 Git 最反直觉、也最强大的地方。
> 你可以在工作目录里改十个文件，却只把其中三个 `add` 进去，commit 出一次**干净、单一目的**的提交。

### 3.3 丢弃工作目录的改动

```bash
git restore <文件>        # 用暂存区的版本覆盖工作目录（新版 Git 推荐）
git checkout -- <文件>    # 老写法，效果相同
git restore .             # 丢弃当前目录下所有未暂存的改动
```

> [!danger] 丢弃是**不可逆**的
> `restore` / `checkout --` 会用已保存的版本**直接覆盖**工作目录，你没 `add` 过的修改**当场蒸发**，没有垃圾箱。
> 删完后悔，只能靠编辑器的本地历史（如 VS Code 的 Timeline）碰运气。**执行前先想清楚。**

### 3.4 清理未追踪的文件

```bash
git clean -n              # 演习：列出"将要被删的"未追踪文件
git clean -f              # 真的删掉未追踪文件
git clean -fd             # 连未追踪的目录一起删
```

> [!warning] `git clean -f` 不碰 `.gitignore` 之外就随便删
> 它删的是**从未被追踪**的文件——比如编译产物、临时脚本、刚写一半还没 add 的代码。
> **先 `git clean -n` 看清单，再 `-f` 执行**。写好的新文件一旦被清理，同样找不回来。

## 四、完整示例：一次典型的工作循环

```bash
# 1. 看看现在什么样
git status

# 2. 编辑代码……（用你的编辑器）
#    README.md 改了，新加了 utils.js 和 debug.log

git status
#   modified:   README.md        ← 已追踪，改了还没交
#   Untracked files:
#     utils.js
#     debug.log                  ← 新文件，Git 不认识

# 3. debug.log 不该进仓库 → 写进忽略规则
echo '*.log' >> .gitignore

# 4. 逐块挑选要提交的改动
git add -p README.md
git add utils.js
git add .gitignore

# 5. 确认暂存区内容
git status
git diff --staged

# 6. 提交（从暂存区打包成快照）
git commit -m "feat: 新增 utils 工具并补充忽略规则"

# 7. 工作目录重新变干净
git status                # nothing to commit, working tree clean
```

> [!success] 成功标志
> `git status` 显示 `nothing to commit, working tree clean`——说明工作目录、暂存区、HEAD **三者一致**，没有悬空的改动。

## 五、常见困惑

> [!question] 我改了文件，`git status` 怎么啥都不显示？
> 要么 Git 认为它没变（可能被 `core.autocrlf` 换行符转换"骗"了，见 [[git config]]），
> 要么这个文件被 `.gitignore` 忽略了，要么你根本站错目录了。

> [!question] 删除一个文件，怎么让 Git 也记下来？
> 用 `git rm <文件>`：它**同时**删掉工作目录里的文件**并**把"删除"这个动作放进暂存区。
> 直接手动删文件的话，还得补一个 `git add <文件>`（或 `git add -A`）Git 才知道。

> [!question] `git status` 里的 `working tree clean` 是什么意思？
> "工作树干净"——**工作目录没有未记录的改动**。它是每一次提交完成后你最想看到的一句话。

---

> [!quote] 一句话记忆
> **工作目录 = 你的"草稿纸"**。在这里怎么改都行、都不算数；只有 `git add` 把它抄进暂存区，改动才被 Git 正式"登记在案"。
