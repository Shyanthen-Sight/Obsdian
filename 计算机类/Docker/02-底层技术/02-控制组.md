# 控制组

cgroups 决定容器能用多少 CPU、内存、IO 和进程数。它和命名空间正交：可以给容器独立视野却不限资源，也可以限死资源但让它共享网络。命名空间回答“看得见什么”，cgroups 回答“最多用多少”。

## v1 与 v2

| 维度 | v1 | v2 |
| --- | --- | --- |
| 层级 | 每个控制器一棵树 | 单棵树，统一层级 |
| 挂载点 | `/sys/fs/cgroup/cpu`、`memory` 等 | `/sys/fs/cgroup` |
| 进程归属 | 同一进程可属于多棵树 | 一个进程只属于一个 cgroup |
| 内部进程 | 允许 | 默认不允许（no internal process） |
| 压力指标 | 各自实现 | 统一 PSI |
| 限额文件 | `cpu.cfs_quota_us`、`memory.limit_in_bytes` | `cpu.max`、`memory.max` |

```bash
stat -fc %T /sys/fs/cgroup        # cgroup2fs 表示 v2
docker info --format '{{.CgroupVersion}} {{.CgroupDriver}}'
```

v2 统一成单树后，控制器下放和委托更清晰，PSI 也能直接看到“资源不够造成多少等待”。老系统上仍可能是 v1 或混合模式，路径和文件名不同，排查前先确认版本。

## cgroup v2 的树

v2 把所有控制器收进一棵树，挂在 `/sys/fs/cgroup`。每个进程只属于一个 cgroup，父节点通过 `cgroup.subtree_control` 把控制器下放给子节点：

```bash
cat /sys/fs/cgroup/cgroup.controllers
# cpuset cpu io memory hugetlb pids rdma misc
cat /sys/fs/cgroup/cgroup.subtree_control
# cpuset cpu io memory pids
```

有子 cgroup 的节点不能再放进程，这是 v2 的 no-internal-process 规则。systemd 因此把每个容器塞进独立 scope，而不是把服务进程和子 cgroup 混在同一层。用 systemd cgroup driver 时，容器目录是：

```bash
CID=$(docker inspect -f '{{.Id}}' web)
ls /sys/fs/cgroup/system.slice/docker-$CID.scope/
# cpu.max  cpu.stat  cpu.weight  memory.current  memory.events  memory.max  pids.max
```

driver 是 `cgroupfs` 或 cgroup v1 时，路径和文件名都不一样。`cgroupfs` 下通常是 `/sys/fs/cgroup/<controller>/docker/<CID>/`，排查前先用 `docker info` 确认。

## 看容器的真实限额

容器里的 `/proc/self/cgroup` 和宿主机的 scope 指向同一个对象，只是视图不同。以下命令从宿主机直接读：

```bash
CID=$(docker inspect -f '{{.Id}}' web)
CG=/sys/fs/cgroup/system.slice/docker-$CID.scope

cat "$CG/memory.max"     # 268435456
cat "$CG/cpu.max"        # 100000 100000
cat "$CG/pids.max"       # max 或具体数字
cat "$CG/cgroup.procs"   # 容器内所有进程的宿主机 PID
```

`docker inspect` 里的 `HostConfig.NanoCpus` 是纳秒单位，1.5 核等于 1500000000；`HostConfig.Memory` 是字节。命令只是把参数翻译成 cgroup 文件里的值。

## 内存限制怎么生效

```bash
docker run -d --name hog --memory=128m --memory-swap=128m \
  python:3.12-alpine python -c 'x = bytearray(256 * 1024 * 1024); print(len(x))'

docker inspect hog -f '{{.State.OOMKilled}} {{.State.ExitCode}}'
# true 137

CG=/sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' hog).scope
cat "$CG/memory.events"
# low 0
# high 0
# max 1
# oom 1
# oom_kill 1
```

退出码 137 是 128 + 9，进程收到 SIGKILL。`--memory` 写进 `memory.max`，进程触碰页面超过上限时内核先回收 page cache 和可回收的 slab；回收不动就触发 cgroup OOM，杀掉组内进程。

v2 的几档限制值得分清：

| 文件 | 作用 | 超限时 |
| --- | --- | --- |
| `memory.max` | 硬上限 | 触发回收，回收失败 OOM kill |
| `memory.high` | 软上限/节流 | 进程被限速，通常不杀 |
| `memory.low` / `memory.min` | 保护额度 | 回收时尽量不碰 |
| `memory.swap.max` | swap 上限 | 超过后不能再换出 |

`--memory-swap` 的语义容易记错：不写时，Docker 默认把“内存 + swap”总量设为 `--memory` 的两倍，也就是 swap 部分等于内存；写成和 `--memory` 相同的值表示禁用 swap；写 `-1` 表示不限制 swap（宿主机要有 swap）。`--memory-reservation` 对应软限制，不是硬保证；`--oom-kill-disable` 可以关闭 OOM kill，但容器会卡在分配上，通常不该用。

`memory.stat` 比 `docker stats` 更能说明问题：

```bash
grep -E '^(anon|file|slab|inactive_file) ' "$CG/memory.stat"
```

`anon` 是进程实际占用的匿名内存，`file` 是 page cache，后者可回收。cgroup v2 上 `docker stats` 的内存口径包含 page cache，所以数字涨得快不一定泄漏；判断泄漏看 `anon` 和 `memory.current` 的长期趋势。

## CPU 是配额不是绑核

```bash
docker run -d --name api --cpus=1.5 --cpu-shares=512 --cpuset-cpus=0-1 nginx
CG=/sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' api).scope
cat "$CG/cpu.max"      # 150000 100000
cat "$CG/cpu.weight"   # 20
```

`--cpus=1.5` 翻译成 quota 150000、period 100000，即每个 100ms 周期最多跑 150ms，允许短时用到 1.5 个核，但不保证在哪个核上跑。`--cpu-shares` 只在争抢时按权重分配，空闲时不限制；v2 里对应 `cpu.weight`，Docker 会按 shares 换算。要减少跨核缓存失效或跑 DPDK 这类场景，才用 `--cpuset-cpus` 真正绑核。

节流是 CPU 问题里最容易被忽略的一项：

```bash
cat "$CG/cpu.stat"
# usage_usec 1234567
# user_usec 900000
# system_usec 334567
# nr_periods 1000
# nr_throttled 120
# throttled_usec 8000000
```

`nr_throttled` 大于 0 说明有周期被限流，`throttled_usec` 是累计被压住的时间。表现为延迟周期性抖动、p99 变差，而平均 CPU 看起来不高。提高 `--cpus`、拆小工作单元、或检查应用线程数是否超出配额，都是常见处理方式。

## IO 与进程数

IO 限制按块设备设置：

```bash
docker run -d --name io --device-read-bps /dev/sda:10mb \
  --device-write-bps /dev/sda:10mb \
  --device-read-iops /dev/sda:1000 \
  --blkio-weight 500 nginx
```

对应 cgroup 文件是 `io.max`（`rbps`、`wbps`、`riops`、`wiops`）和 `io.weight`。`--blkio-weight` 的范围是 10–1000，v2 的 `io.weight` 是 1–10000，Docker 会做换算。注意容器写入往往经过 overlay，最终落到实际块设备上；如果底层是 loop 设备或网络存储，限制的位置和效果要单独确认。

`--pids-limit` 防 fork 炸弹，对应 `pids.max`：

```bash
cat "$CG/pids.current" "$CG/pids.max"
```

pids 控制器统计的是任务数，线程也计入。到达上限后 `fork`/`clone` 返回 `EAGAIN`，应用可能报“资源暂时不可用”，而不是直接崩掉。

## 其他控制器与压力指标

除了 cpu、memory、io、pids，v2 还可能有 cpuset、hugetlb、rdma、misc。PSI（Pressure Stall Information）是 v2 的实用补充：

```bash
cat "$CG/cpu.pressure" "$CG/memory.pressure" "$CG/io.pressure"
# some avg10=0.00 avg60=0.00 avg300=0.00 total=0
```

`some` 表示至少有一个任务因资源等待，`full` 表示所有任务都被卡住。它比利用率更能反映“慢”的原因：CPU 100% 不一定有问题，memory 的 `full` 持续升高通常意味着离 OOM 不远了。

## 应用要感知限制

运行时不一定认 cgroup 限制，这是容器里最常见的“配置明明够却崩了”的来源。

| 运行时 | 默认行为 | 需要做什么 |
| --- | --- | --- |
| JVM | JDK 10+ / 8u191+ 默认 `UseContainerSupport`，按 cgroup 算堆和 CPU | 用 `-XX:MaxRAMPercentage=75` 代替固定 `-Xmx`，必要时 `-XX:ActiveProcessorCount` |
| Node.js | 老生代上限跟宿主机内存走，线程池默认 4 | `--max-old-space-size`、`UV_THREADPOOL_SIZE` |
| Go | 1.25 之前 `GOMAXPROCS` 按宿主机核数；1.25 起感知 cgroup CPU 配额 | 老版本显式设 `GOMAXPROCS`；内存用 `GOMEMLIMIT` 配合 |
| .NET | 默认可能按宿主机内存 | `DOTNET_GCHeapHardLimit`、Server GC 配置 |
| nginx | `worker_processes auto` 按可用 CPU 算，不按 `cpu.max` 折算 | 显式写 `worker_processes` |
| Python | 基本不感知 | 自己读 cgroup 文件或用 `resource` 模块 |

JVM 的典型写法：

```bash
java -XX:+UseContainerSupport -XX:MaxRAMPercentage=75 \
     -XX:ActiveProcessorCount=2 -jar app.jar
```

`MaxRAMPercentage` 是相对容器内存上限的百分比，75% 留给堆，剩下给元空间、线程栈和堆外内存。设成 100% 很容易被 OOM。

## 排查顺序

| 现象 | 先看 | 命令 |
| --- | --- | --- |
| `Exited (137)`、`OOMKilled=true` | `memory.events`、`memory.max` | `cat memory.events`、`docker events` |
| 延迟周期性抖动 | CPU 节流 | `cat cpu.stat` |
| CPU 用不满 | quota、cpuset、应用线程数 | `cpu.max`、`nproc`、`cpu.stat` |
| 内存涨得快但没被杀 | page cache 与 anon | `memory.stat` |
| `fork` 失败 | pids 上限 | `pids.current`、`pids.max` |
| IO 慢 | `io.max`、设备层 | `io.stat`、`docker stats` |

补一条判断：137 不一定是 OOM。手动 `docker kill`、`docker stop` 超时后的 SIGKILL、以及 OOM 都会给出 137；`OOMKilled` 为 `true` 才是内存超限，为 `false` 就去 `docker events` 和操作记录里找信号来源。

## 常见误区

- **`--memory` 是预留**：不是，它只是上限；节点超卖时多个容器仍会互相挤压。
- **`docker stats` 的内存就是应用内存**：包含 page cache，看 `memory.stat` 的 `anon` 更准。
- **`--cpus=2` 会绑两个核**：不会，它只是配额；绑核要用 `--cpuset-cpus`。
- **`--cpu-shares` 会限速**：不会，它只在争抢时生效，空闲时容器可以用满。
- **cgroup 限制能防止节点 OOM**：只能限制单个容器；所有容器加起来超过物理内存，仍可能触发整机问题。
- **swap 默认关闭**：不写 `--memory-swap` 时默认允许用 swap，行为取决于宿主配置。
