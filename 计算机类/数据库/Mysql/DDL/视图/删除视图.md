# DROP VIEW —— 删除视图

> [!abstract] 一句话
> `DROP VIEW` **只删除"保存下来的 SELECT 定义"**，基表的行、列、索引、数据一根汗毛都不动。
> 名字看起来像表，但删它和删表的后果完全不是一回事。

---

## 一、基本语法

```sql
DROP VIEW [IF EXISTS]
    视图名1 [, 视图名2, ...]
    [RESTRICT | CASCADE];
```

| 部分 | 说明 |
| --- | --- |
| `DROP VIEW 视图名` | 删除一个或多个视图 |
| `IF EXISTS` | 视图不存在时只产生 `NOTE`，不报错 |
| 多个视图名 | 一次删多个，逗号分隔 |
| `RESTRICT` / `CASCADE` | **解析后忽略**，MySQL 不会级联删除依赖视图 |

```sql
-- 最常用：可重复执行的脚本写法
DROP VIEW IF EXISTS v_student_public;

-- 一次删多个
DROP VIEW IF EXISTS v_student_class, v_class_stat;

-- 不带 IF EXISTS：视图不存在就报 1051
DROP VIEW v_student_public;
```

> [!warning] MySQL 8.0 与 5.7 的行为差异
> **8.0**：列表里只要有任何一个视图不存在，整条语句失败，**一个都不删**（原子 DDL）。
> **5.7 及以前**：报错，但列表里存在的视图**照样会被删掉**（部分完成）。
> 这就是生产脚本必须写 `IF EXISTS` 的原因；否则从 5.7 复制到 8.0 的主从环境还可能因此中断复制。

## 二、删掉的到底是什么

| 对象 | `DROP VIEW` 后 |
| --- | --- |
| 视图定义（`SELECT` 语句） | ✅ 删除 |
| 视图的 `DEFINER` / `SQL SECURITY` / `ALGORITHM` 设置 | ✅ 删除 |
| 视图上的 `GRANT` 授权 | ✅ 随对象删除 |
| 基表的**数据** | ❌ 完全不受影响 |
| 基表的**结构、索引、约束、触发器** | ❌ 完全不受影响 |
| 依赖它的**上层视图** | ❌ 定义保留，但变成"坏视图" |
| 存储过程 / 函数里对它的引用 | ❌ 保留，运行时才报错 |
| 视图上的索引 / 触发器 | 本来就不允许，无需考虑 |

```sql
DROP VIEW v_student_public;

-- 基表照常可查
SELECT COUNT(*) FROM student;   -- ✅ 数据一行没少
```

> [!tip] 视图不是备份
> 视图不复制数据，所以删视图**不会丢数据**，也**不会释放多少空间**。
> 反过来，也不能把视图当"数据快照"来用——它永远反映基表的当前状态。

## 三、DROP VIEW vs DROP TABLE

| 对比项 | `DROP VIEW` | `DROP TABLE` |
| --- | --- | --- |
| 删除对象 | 视图定义 | 表结构 + 数据 + 索引 |
| 基表/数据 | **不受影响** | 全部消失 |
| 视图上的授权 | 删除 | 不适用 |
| 依赖对象 | 上层视图变坏，但保留 | 引用它的视图变坏，但保留 |
| 能否回滚 | ❌ DDL 隐式提交 | ❌ DDL 隐式提交 |
| 所需权限 | `DROP` | `DROP` |
| 用错对象类型 | `ERROR 1347: is not VIEW` | `ERROR 1347: is not BASE TABLE` |
| 适用场景 | 视图不再需要 | 表彻底废弃 |

```sql
-- 视图
DROP VIEW v_student_public;   -- ✅
DROP TABLE v_student_public;  -- ❌ ERROR 1347: '...' is not BASE TABLE

-- 基表
DROP TABLE student;           -- ✅
DROP VIEW student;            -- ❌ ERROR 1347: '...' is not VIEW
```

> [!danger] `IF EXISTS` 不会掩盖"类型不对"
> 它只处理"对象不存在"，不处理"对象存在但类型不是视图"。
> 所以批量清理脚本里，先确认对象类型，再决定用 `DROP VIEW` 还是 `DROP TABLE`。

确认对象类型：

```sql
SELECT TABLE_NAME, TABLE_TYPE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'v_student_public';
-- TABLE_TYPE: BASE TABLE / VIEW / SYSTEM VIEW

-- 或者
SHOW FULL TABLES WHERE Table_type = 'VIEW';
```

## 四、依赖关系：没有级联删除

MySQL 不会因为你删了一个视图，就自动删掉引用它的上层视图。

```sql
CREATE VIEW v1 AS SELECT id, name FROM student;
CREATE VIEW v2 AS SELECT id FROM v1;

DROP VIEW v1;          -- ✅ 成功

SELECT * FROM v2;      -- ❌ ERROR 1356:
                       -- View 'db.v2' references invalid table(s) ...
```

`DROP VIEW ... CASCADE` **不会**解决这个问题——`CASCADE` 在 MySQL 里只是被解析然后忽略。

### 正确顺序：先删上层，再删下层

```sql
-- 先删依赖别人的
DROP VIEW IF EXISTS v2;
DROP VIEW IF EXISTS v1;
```

MySQL 8.0 也可以用一条原子语句一起删：

```sql
DROP VIEW IF EXISTS v2, v1;
```

### 找依赖者

MySQL 没有暴露视图依赖表，只能搜定义文本：

```sql
SELECT TABLE_SCHEMA, TABLE_NAME
FROM information_schema.VIEWS
WHERE VIEW_DEFINITION LIKE '%v1%';
```

> [!note] 文本搜索有盲区
> 注释在保存定义时会被去掉；字符串里出现同样的词也可能误命中；跨库引用还要补上库名。
> 视图嵌套层数越多，删除前的人工确认成本越高。

> [!tip] 删完上层视图后，记得验证
> ```sql
> CHECK TABLE v2;                 -- 检查视图定义是否还有效
> SELECT * FROM v2 LIMIT 0;       -- 最直接的验证
> ```

## 五、删除会带走视图上的授权

授权是挂在对象上的。对象被 `DROP`，授权也跟着消失：

```sql
-- 曾经授予过
GRANT SELECT ON school.v_student_public TO 'app_user'@'%';

DROP VIEW v_student_public;

-- 之后重建同名视图
CREATE VIEW v_student_public AS SELECT id, name FROM student;

-- 授权不会自动回来，必须重新 GRANT
GRANT SELECT ON school.v_student_public TO 'app_user'@'%';
```

| 操作 | 视图上的授权 |
| --- | --- |
| `ALTER VIEW` | ✅ 保留 |
| `CREATE OR REPLACE VIEW` | ✅ 保留 |
| `DROP VIEW` + `CREATE VIEW` | ❌ 丢失，需重新授权 |
| `RENAME TABLE` 改视图名 | ❌ 不会迁移到新名字 |

> [!warning] 用 `DROP` + `CREATE` "改视图"是最差的做法
> 除了丢授权，还会让依赖它的视图瞬间失效、让正在执行的查询报错。
> 改定义请用 `ALTER VIEW` 或 `CREATE OR REPLACE VIEW`，见 [[修改视图]]。

## 六、能撤销吗？

> [!danger] 不能回滚
> `DROP VIEW` 属于 DDL，执行前隐式提交当前事务，`ROLLBACK` 无效。

```sql
START TRANSACTION;
DROP VIEW v_student_public;
ROLLBACK;                       -- ❌ 视图不会回来
```

但好消息是：**删除视图的恢复成本远低于删表**。基表数据还在，只要定义有留存，重建即可：

```sql
-- 删除前先备份定义
SHOW CREATE VIEW v_student_public\G
```

把输出保存到版本控制或变更单里，需要时原样执行 `CREATE VIEW` 就能恢复（授权仍需重新 `GRANT`）。

| 恢复途径 | 前提 |
| --- | --- |
| 从 `SHOW CREATE VIEW` 备份重建 | 事先保存过定义 |
| 从 `mysqldump` / 数据库备份恢复 | 备份里包含视图定义 |
| 从 binlog 反向解析 | 成本高，通常没必要——视图没有数据可救 |

> [!tip] 最实用的习惯
> 所有视图的 DDL 都纳入 Git 或迁移脚本管理。
> 视图是"代码"，不是"数据"，它天然适合版本控制。

## 七、批量查看与清理

### 7.1 列出当前库所有视图

```sql
SHOW FULL TABLES WHERE Table_type = 'VIEW';

SELECT TABLE_NAME, IS_UPDATABLE, DEFINER, SECURITY_TYPE, CHECK_OPTION
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = DATABASE();
```

### 7.2 找出引用了某张表的视图

```sql
SELECT TABLE_NAME
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = DATABASE()
  AND VIEW_DEFINITION LIKE '%student%';
```

### 7.3 生成批量删除语句（先审查再执行）

```sql
SELECT CONCAT('DROP VIEW IF EXISTS `', TABLE_NAME, '`;') AS stmt
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = 'school'
  AND TABLE_NAME LIKE 'v_tmp_%';
```

> [!danger] 不要直接执行生成的整段 SQL
> 先看一遍对象清单，确认命名规则没有误伤；再分批执行。
> 批量 DDL 出错时，定位成本比单条高得多。

### 7.4 清理"坏视图"

基表被删或列被改名后，视图定义还在，但已经查不了：

```sql
SELECT * FROM v_broken LIMIT 0;   -- ERROR 1356
CHECK TABLE v_broken;             -- 帮助定位定义是否有问题
```

确认不再需要后：

```sql
DROP VIEW IF EXISTS v_broken;
```

需要保留功能的，则按新结构重建，见 [[创建视图]]。

## 八、常见报错与对策

| 报错 | 原因 | 对策 |
| --- | --- | --- |
| `ERROR 1051` Unknown table | 视图不存在，且没写 `IF EXISTS` | 加 `IF EXISTS`，或先确认对象名 |
| `ERROR 1347` is not VIEW | 目标是基表，不是视图 | 改用 `DROP TABLE` |
| `ERROR 1347` is not BASE TABLE | 对视图用了 `DROP TABLE` | 改用 `DROP VIEW` |
| `ERROR 1356` references invalid ... | 依赖的视图/表已失效 | 修定义，或删掉坏视图 |
| `ERROR 1044 / 1142` Access denied | 缺少视图上的 `DROP` 权限 | 补授权 |
| DDL 被阻塞 | 有长事务持有元数据锁 | 等事务结束，或排查锁等待 |

> [!failure] ERROR 1051（42S02）：Unknown table 'db.v_name'
> 视图不存在。注意 MySQL 的报错里统一叫 "Table"，不等于你删的是表。
> 脚本里一律写 `DROP VIEW IF EXISTS`。

> [!failure] ERROR 1347（HY000）：'db.name' is not VIEW
> 你把一张基表当成视图删了。先查 `information_schema.TABLES.TABLE_TYPE`，再换正确的语句。
> 这条错误**不会**因为加了 `IF EXISTS` 而变成警告。

> [!failure] ERROR 1356（HY000）：View ... references invalid table(s) or column(s)
> 删除下层视图或基表后，上层视图失效。
> 处理顺序：先确认上层视图是否还需要 → 需要就重建定义，不需要就一并 `DROP VIEW`。

## 九、删除前清单

> [!danger] 逐条确认，尤其是生产库
> - [ ] `SELECT DATABASE();` —— 确认连的是哪个库
> - [ ] `SHOW FULL TABLES LIKE '视图名';` —— 确认对象类型是 `VIEW`
> - [ ] `SHOW CREATE VIEW 视图名\G` —— **保存定义**
> - [ ] 查依赖：`information_schema.VIEWS` 搜索视图名
> - [ ] 确认没有报表、接口、其他视图正在使用
> - [ ] 明确视图上的授权会一并消失
> - [ ] 脚本里使用 `IF EXISTS`
> - [ ] 批量删除先审查生成的清单
> - [ ] 生产环境走变更流程，有人知情
> - [ ] 优先 `ALTER VIEW` / `CREATE OR REPLACE VIEW`，只有真正废弃才 `DROP`

## 十、什么时候该删视图

| 场景 | 建议 |
| --- | --- |
| 业务下线，视图不再被查询 | ✅ 删除 |
| 视图已被新视图替代 | ✅ 确认无依赖后删除旧视图 |
| 基表结构变更导致视图永久失效 | ✅ 重建或删除 |
| 只是临时停用 | ⚠️ 不要靠改名"停用"（授权不迁移）；优先限制权限 |
| 想改视图定义 | ❌ 用 `ALTER VIEW` / `CREATE OR REPLACE VIEW` |
| 想清空数据 | ❌ 视图没有数据；应该处理基表 |
| 想省磁盘空间 | ❌ 删视图几乎不释放空间 |

> [!quote] 一句话记忆
> **DROP VIEW = 撕掉一张"查询说明书"**：说明书没了，账本（基表）还在；不会级联删上层视图，但会把它的说明书变成废纸（1356），授权也随说明书一起作废。
