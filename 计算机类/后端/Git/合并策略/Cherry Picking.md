# Cherry Picking —— 只要某一个提交

> [!abstract] 一句话
> ==`cherry-pick` 把**别的分支上的某一个（或某几个）提交**，单独"摘"过来，在当前分支上重新提交一遍。== 它不合并整条分支，只挑你要的那几次改动。代价和 [[Rebase]] 一样：**摘过来的是一份复制品，哈希变了**——所以它是"复制提交"，不是"移动提交"。

> [!note] 它和 merge / rebase 的根本区别
> - `merge`：把对方**整条分支**并进来。
> - `rebase`：把**自己**的一串提交搬到对方顶端。
> - `cherry-pick`：把**对方某几个**提交摘到**自己**头上。
>
> 前两者处理"分支"，cherry-pick 处理"提交"。这是它最独特的地方。

---

## 一、cherry-pick 到底做了什么

```text
【cherry-pick 前】
      A ── B ── C ── D        ← main
            \
             E ── F ── G      ← feature（你只想要 F 这一个提交）

【cherry-pick 后】git switch main && git cherry-pick F
      A ── B ── C ── D ── F'  ← main（F 被"复制"成 F'，内容相同、父不同）
            \
             E ── F ── G      ← feature（原样没动）
```

> [!info] 关键理解
> - `F` **没有被移动**，而是在 `main` 上生成了一个**新提交 `F'`**（哈希不同）。`feature` 上的 `F` 还在原地。
> - 于是同一个改动**在两条分支上各有一份提交**——这是 cherry-pick 的特征，也是它埋雷的地方（见第五节）。
> - 它**不建立任何合并关系**：Git 不会认为这两条分支"沟通过"。

> [!tip] 把它想成"打补丁"
> cherry-pick 本质是：把这一个提交的 **diff（相对它父提交的改动）** 取出来，像补丁一样在原当前 HEAD 上重新应用、重新提交。

---

## 二、基本用法

```bash
# 挑一个提交到当前分支
git switch main
git cherry-pick <提交哈希>

# 挑多个（按顺序应用）
git cherry-pick <哈希A> <哈希B> <哈希C>

# 挑一个区间（不含起点、含终点）
git cherry-pick A..B            # 挑 A 之后到 B（含 B）的所有提交

# 含起点
git cherry-pick A^..B           # 从 A 本身到 B
```

> [!info] 区间语法的坑
> `A..B` 是**左开右闭**：**不包含 A**，包含 B。想连 A 一起挑，写 `A^..B`（`^` 表示 A 的父）。
> 这一点和很多人的直觉相反，务必留意。

> [!note] 挑"分支最新提交"的简写
> 想挑某分支顶端的那个提交：`git cherry-pick <分支名>`，等价于挑它的 HEAD。

## 三、提交信息怎么处理

```bash
git cherry-pick <哈希>                # 沿用原提交信息
git cherry-pick -e <哈希>             # 应用前打开编辑器，改提交信息
git cherry-pick -x <哈希>             # ★ 在信息里附一行 "(cherry picked from commit <哈希>)"
git cherry-pick --no-commit <哈希>    # 只把改动放进工作区/暂存区，不自动提交
```

> [!success] 推荐加 `-x`
> `-x` 会留下溯源信息：
>
> ```text
> (cherry picked from commit a1b2c3d...)
> ```
>
> 将来读者能顺着这行找到**原始提交**。跨分支回移植（backport）时几乎是标配。

> [!tip] `--no-commit` 的用途
> 想先**攒几个提交再一起改**、或想**自己重写提交信息**、或想在提交前顺手调整，用它。改动会停在暂存区，由你决定何时 `git commit`。

## 四、Cherry Pick 撞车了怎么办

如果一个提交的改动和当前分支**在同一处**已有内容冲突，就会像 merge 一样停下来：

```bash
git status                     # 显示冲突文件（cherry-pick in progress）
# 编辑文件，删掉 <<<< ==== >>>> 记号
git add <解决好的文件>
git cherry-pick --continue     # 继续（应用下一个提交 / 完成）

git cherry-pick --skip         # 跳过当前这个提交
git cherry-pick --abort        # 整个放弃，回到 cherry-pick 之前
```

> [!warning] `--ours` / `--theirs` 在这里的含义
> cherry-pick 在语义上更像 rebase——**它是在"把别人的提交应用到我头上"**。这种情形下：
> - `--ours` ≈ **当前分支（接收方）**，
> - `--theirs` ≈ **被挑的那个提交**。
>
> 但不同 Git 版本/场景下容易记混。==**拿不准就别用，直接手改。**== 详见 [[冲突处理]]。

> [!note] 挑选多个提交时中途撞车
> Git 会**逐个**应用你列出的提交。撞到冲突就停在那个提交上；解决后 `--continue` 会接着应用**剩下的**。
> 想一次性处理完再决定，可先 `--no-commit` 逐个来。

## 五、最大的坑：重复提交与"消失的改动"

> [!warning] 坑一：同内容提交出现两次
> cherry-pick 生成了 `F'`，而原 `F` 依然在 feature 上。若之后又把 feature **整体合并进 main**，Git 会看到两个内容相同、哈希不同的提交，可能：
> - 产生**冲突**（一段代码被"两次"引入），或
> - 让你误以为改动丢了 / 被重复应用。
>
> 本质原因：**cherry-pick 不记录"这个改动已经来过了"**。

> [!warning] 坑二：后来 rebase 掉原提交，cherry-pick 的副本还在
> 如果你在 feature 上 `rebase` 把 `F` 改写/删除了，main 上的 `F'` 不会跟着变——它是独立的一份。**两边从此各走各的**。
> 长期维护的"回移植"分支尤其容易积累这种漂移。

> [!info] 那为什么还在用它
> 因为确实有 merge/rebase 覆盖不了的场景（见下一节）。==**它是把"整条分支"细化到"单个提交"的精准手术刀**——威力大，也要求你用的时候心里有数。==

## 六、什么时候该用

> [!success] 适合
> - **回移植（backport）**：主干上修了一个 bug，需要把**这一个修复**挑到维护分支 / 旧版本分支。
> - **救火**：急着上线的一个改动已在别的分支做好，先摘过来，不必等整条分支合并。
> - **挑走误提交**：某个提交本该在另一条分支，摘过去后在原分支处理掉。
> - **从实验分支挑成果**：只想要实验里的某几次有效提交，其余不要。
> - **跨仓库摘提交**：`git fetch <远程> <分支>` 后 cherry-pick 对方某个提交（需先 fetch 到本地）。

> [!warning] 不适合 / 要小心
> - **用 cherry-pick 代替 merge 长期同步两条分支** → 会积累重复提交和幽灵冲突。两条长期共存的线，用 merge/rebase。
> - **已推送到共享分支的提交**：挑过来会产生"两个哈希、同一改动"，给别人添乱。
> - **一次挑一大串**：那基本等于在手工重做 merge，不如直接用 [[Rebase]] 或 `merge`。

## 七、cherry-pick vs 其他"整合"方式

| 维度 | merge | rebase | cherry-pick |
|---|---|---|---|
| 作用对象 | 整条分支 | 自己的一串提交 | **任意某几个提交** |
| 方向 | 把对方并入我 | 把我搬到对方顶端 | 把对方某提交摘到我 |
| 原提交 | 不变 | 被重放（新哈希） | **留在原地**（另生成副本） |
| 是否记录关系 | 是（合并提交） | 否（直线） | **否** |
| 典型用途 | 汇入主干 | 整理本地保持线性 | 回移植 / 救火 |

> [!question] 和 rebase 的区别一句话
> `rebase` 搬的是**自己的**一串提交、通常针对同一批工作；`cherry-pick` 摘的是**别人的**某个提交、且**原提交不动**。两者都会**生成新哈希**。

## 八、安全网：搞乱了怎么回

```bash
git cherry-pick --abort        # 还没 commit 完就放弃，完整回到开始前
git reflog                     # 已经 commit 完才发现挑错了
git reset --hard HEAD@{2}      # 回到 cherry-pick 之前的位置
```

> [!success] 和 rebase 一样有兜底
> `--abort` 安全；已提交的话靠 `git reflog` + `git reset --hard` 回退。详见 [[Rebase]] 第八节。

## 九、几个实用变体

```bash
git cherry-pick -n <哈希>              # = --no-commit，只暂存不提交
git cherry-pick -x <哈希>              # 附溯源信息
git cherry-pick --ff                   # 若能用快进完成，就快进（少见）
git cherry-pick -m 1 <合并提交>        # 挑一个"合并提交"时，指定看哪一个父（通常 1）
```

> [!warning] 挑"合并提交"要谨慎
> 合并提交有两个父，含义模糊，必须用 `-m <父序号>` 告诉 Git 拿**哪个父作基准**来算 diff。挑它往往不是你要的，通常该挑的是其中某个**普通提交**。

## 十、常见困惑

> [!question] cherry-pick 会改原提交吗？
> 不会。**原提交原封不动**留在原分支，只是在新分支多了一份**新哈希的副本**。所以同一个改动会同时存在于两处。

> [!question] 为什么挑过来的提交哈希变了？
> 因为父提交不同（现在挂在当前分支的 HEAD 上）。哈希由内容和父共同决定，故哈希不同——和 rebase 同理。

> [!question] 挑完发现改动"丢了"？
> 多半是冲突时误用了 `--ours/--theirs` 选错边，或 `--skip` 跳过了它。用 `git reflog` 回到挑之前重来，并**逐个读冲突**再决定。

> [!question] 能一次挑一条分支的所有独有提交吗？
> 能（`git cherry-pick <base>..<branch>`），但那**几乎等价于做一次 merge 却不记录合并关系**——除非你明确知道后果，否则用 `merge` 或 `rebase` 更好。

> [!question] cherry-pick 和 `git apply` 有什么区别？
> cherry-pick 认的是**提交**（有作者、信息、父子关系等元数据，自动提交）；`git apply` / `git am` 认的是**补丁文件**（`.patch` / `.diff`）。跨仓库、无共同历史时常用 patch。

> [!question] 已经从 feature 挑过几个提交，feature 还要合并进来，会怎样？
> 那些被挑过的提交内容已在 main 上，合并时 Git 可能报冲突或识别为"已应用"（视情况）。==避免"又挑又整条 merge"混用同一批提交==，会绕晕。
> 若必须如此，挑的时候加 `-x`，至少留下溯源线索。

---

> [!quote] 一句话记忆
> **cherry-pick = 从别的分支"摘"某个提交，在当前分支复制一份重新提交**。原提交**留在原地**，新提交**哈希不同**，且**不记录任何合并关系**。==它是精准手术刀：适合回移植、救火、捞单点成果；不适合当成两条长期分支之间的日常同步方式。==
