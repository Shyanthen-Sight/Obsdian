# 安装

> [!abstract] 一句话
> 装 TypeScript 只需一条命令 ==`npm install -D typescript`==（前提是本机有 Node.js）。
> 装进项目后，TS 会出现在**源码、配置、脚本、测试、类型声明**等一堆位置；用它的方式主要有三种：==`tsc` 编译、`tsx`/`ts-node` 直接跑、交给打包器（tsc 只做类型检查）==。

---

## 一、前置条件：先有 Node.js

TypeScript 通过 npm 分发，所以先确认环境：

```bash
node -v      # 例：v20.11.0
npm -v       # 例：10.2.4
```

> [!info] 为什么要 Node
> - `npm` 用来下载 TypeScript 包；
> - `node` 用来运行编译后的 JS（以及 `ts-node` / `tsx` 这类直接跑 TS 的工具）。
> 没有 Node 的话，先去 [nodejs.org](https://nodejs.org) 装 LTS 版。

---

## 二、安装 TypeScript

### 2.1 推荐：装到项目里（本地）

```bash
npm init -y                       # 先生成 package.json（若还没有）
npm install --save-dev typescript # 装到 devDependencies
npx tsc --version                 # 用本地版本，输出如 Version 5.4.5
```

> [!tip] 为什么用本地安装 + `npx`，而不是 `-g`
> - **版本跟着项目走**：不同项目可以锁不同 TS 版本，团队一致。
> - **`npx tsc` 优先用本地版本**，不会误用全局的旧版本。
> - 全局安装 `npm i -g typescript` 虽然能省一次 `npx`，但**多项目时版本容易打架**，一般只作为临时备选。

### 2.2 写进 `package.json` 的常用脚本

```json
{
  "scripts": {
    "build": "tsc",
    "watch": "tsc --watch",
    "typecheck": "tsc --noEmit"
  }
}
```

之后用 `npm run build`、`npm run watch`、`npm run typecheck` 即可，不必记那串 `npx` 命令。

### 2.3 不装也能试：`npx` 直接跑

```bash
npx typescript@latest --version   # 临时拉一份最新版，不留痕
```

## 三、在项目中，TS 到底用在哪些地方

> [!info] 一句话定位
> TS 不是"另一种语言文件"，而是 ==项目里任何需要类型的 JavaScript 文件==——**源码、配置、脚本、测试**都可以是 `.ts`。
> 判断标准很简单：只要这个文件**由 TypeScript 编译器或它的转译工具处理**，它就属于"用 TS 的地方"。

### 3.1 一张图看项目里的 TS 文件

```text
my-project/
├── package.json
├── tsconfig.json               # ★ 项目总配置 —— 见下一节「配置」
├── vite.config.ts              # ★ 构建/工具配置也能写成 TS
├── vitest.config.ts
├── src/                        # ★ 业务代码的主体，几乎全是 TS
│   ├── main.ts                 # 应用入口
│   ├── App.tsx                 # 带 JSX 的组件（后缀 .tsx）
│   ├── types.d.ts              # 全局 / 补充类型声明（只描述类型）
│   ├── api/
│   │   └── user.ts
│   └── utils/
│       ├── math.ts
│       └── math.test.ts        # 测试文件
├── scripts/
│   └── seed.ts                 # 一次性 / 构建脚本
└── dist/                       # 编译产物（.js + .d.ts），一般不提交
```

### 3.2 逐个位置说明

| 位置 | 典型文件 | 作用 | 怎么跑起来 |
| --- | --- | --- | --- |
| **应用源码** | `src/**/*.ts` | 业务逻辑主体，日常写的就是它 | 编译成 `.js` 后运行，或交给打包器 |
| **JSX 组件** | `src/**/*.tsx` | React / Preact 组件（`jsx` 选项决定如何转译） | 打包器产出入包 |
| **类型声明** | `*.d.ts` | ==只描述类型、不产 JS==；给全局变量、第三方库补形状 | 不单独运行，供编译器读 |
| **工具配置** | `vite.config.ts`、`tailwind.config.ts`、`playwright.config.ts` | 构建 / 测试 / Lint 的配置也享受类型提示 | 工具内部用 esbuild 即时转译 |
| **测试** | `*.test.ts` / `*.spec.ts` | Vitest / Jest 用例 | 测试框架自己转译执行 |
| **脚本 / CLI** | `scripts/*.ts` | 构建、数据种子、运维脚本 | `tsx` / `ts-node` 直接跑最省事 |
| **库的类型出口** | `dist/*.d.ts` | 发布 npm 包时，消费方靠它拿到类型 | 由 `declaration: true` 产出 |

> [!tip] 不是所有 `.js` 都要改 `.ts`
> 老项目可以**混装**：TS 项目里允许存在 `.js`，也能反过来用 `checkJs` 给 JS 加检查。
> 迁移是一个文件一个文件来的——详见 [[TS 与 JS 的互操作性]]。

> [!note] 判断"这个文件算不算用 TS"的小窍门
> - 后缀是 `.ts` / `.tsx` / `.mts` / `.cts` → 是。
> - 后缀是 `.js` 但被 `allowJs` 纳入 → 也算（参与编译）。
> - `.d.ts` → 是，但它**只贡献类型**，不会生成任何 `.js`。

## 四、在项目中如何使用 TS：三种方式

> [!info] 核心前提
> **TS 不能被浏览器或 Node 直接运行**，必须先"过一道"。区别只在于——==这一道由谁来做==。
> 对应三种主流用法，选哪种取决于**项目类型**。

### 4.1 方式一：`tsc` 编译 → 再运行

适合**库、Node 服务、CI 构建**——自己掌控 `.ts → .js` 的全过程。

```text
src/index.ts ──tsc──▶ dist/index.js ──node──▶ 运行
                │
                └── 同时做类型检查、产出 .js.map / .d.ts
```

```bash
npx tsc              # 按 tsconfig.json 整体编译
node dist/index.js   # 运行产物（tsc 自己不运行）
```

- 产物是**真实文件**，可发布、可部署。
- `--watch` 可监听改动自动重编。

### 4.2 方式二：`tsx` / `ts-node` 直接跑

适合**本地脚本、开发调试、后端小服务**——省掉"先编译再运行"两步。

```bash
npx tsx src/index.ts        # 快（esbuild 驱动），几乎零配置
npx ts-node src/index.ts    # 传统方案，配置项更多
```

- **在内存里转译**，不落 `.js` 文件（因此**不做完整类型检查**，类型把关另跑 `tsc --noEmit`）。
- 运行前先 `npm i -D tsx`（或 `ts-node`）即可。

### 4.3 方式三：交给打包器，`tsc` 只做类型检查

适合**前端应用（Vite / Next / webpack）**——这也正是本页 `noEmit` 存在的意义。

```text
src/*.ts ──▶ Vite / esbuild / webpack ──▶ bundle.js ──▶ 浏览器
                    ▲
              tsc --noEmit 只做"类型门禁"，不产文件
```

```bash
npx tsc --noEmit    # 只检查类型，产物交给打包器
```

- 打包器（esbuild/swc）转译**飞快**但不查类型；类型这关由 `tsc --noEmit` 单独守。
- 配置里通常设 `"noEmit": true`，避免两套输出打架。

### 4.4 三种方式对照

| 方式 | 谁在转译 | 产出 `.js` | 类型检查 | 典型场景 |
| --- | --- | --- | --- | --- |
| `tsc` 编译 | TypeScript 官方编译器 | ✅ 落盘 | ✅ 完整 | 库、Node 构建、CI |
| `tsx` / `ts-node` | esbuild / ts-node（内存） | ❌ 不落盘 | ⚠️ 默认不做 | 脚本、开发调试 |
| 打包器 + `--noEmit` | Vite / webpack / esbuild | ✅（bundle） | ✅ 靠 `--noEmit` | 前端应用 |

> [!success] 一句选型口诀
> **自己发产物 → `tsc`；只想直接跑 → `tsx`；前端打包 → 打包器 + `tsc --noEmit`。**

## 五、编译与运行常用命令

```bash
npx tsc src/index.ts     # 编译单个文件（输出 index.js 在同目录）
npx tsc                  # 按 tsconfig.json 整体编译
npx tsc --watch          # 监听文件变化，自动重编
npx tsc --noEmit         # 只检查类型，不产出文件

npx tsx src/index.ts     # 直接运行 .ts（脚本 / 调试）
npx ts-node src/index.ts # 传统直跑方案
npx esbuild src/index.ts --bundle --outfile=dist/bundle.js  # 打包
```

| 工具 | 特点 | 适用 |
| --- | --- | --- |
| `tsc` | 官方，能产出 `.d.ts`、做完整类型检查 | 做库、CI 类型检查、标准构建 |
| `tsx` | 快（esbuild 驱动），几乎零配置 | 本地跑脚本、开发 |
| `ts-node` | 老牌，能力强、配置多 | Node 项目直接运行 TS |
| Vite / webpack + ts-loader | 集成进完整前端构建 | 前端应用 |

> [!note] 命令行细节见 [[tsc]] 与 [[ts-node]]
> 这里只留最常用的；`--outDir`、`--incremental`、`-b` 等完整选项，那两篇里有系统整理。

## 六、编辑器：VS Code 基本零配置

- **VS Code 内置 TypeScript**，打开 `.ts` 就有补全、报错、跳转、重构。
- 想统一团队编辑器版本：在工作区设置里指定 `"typescript.tsdk": "node_modules/typescript/lib"`，让 VS Code 用**项目本地**的 TS 版本，而非内置版。
- 复杂项目可用 **项目引用（`references`）+ `composite`** 拆分多个 `tsconfig`，增量编译更快。

## 七、安装相关常见问题

> [!question] 装完 `typescript`，为什么没生成 `tsconfig.json`？
> ==因为"装包"和"生成配置"是两件事==。`npm install typescript` 只装编译器，**不创建配置文件**（tsconfig 是可选的）。
> 要生成就显式执行 `npx tsc --init`；或干脆**手动新建一份 `tsconfig.json`** 粘贴进去。详见下一节「配置」。

> [!question] `tsc --init` 跑了，目录里却没看到文件？
> 常见两种原因：
> 1. **在错误的目录执行**——先 `cd` 到项目根，再运行；生成的是"当前目录"下的 `tsconfig.json`。
> 2. **已有同名文件**——`--init` **不覆盖**已存在的 `tsconfig.json`，它只会跳过。想换配置就手动改，或删掉重建。
> 若提示"不是内部或外部命令"，说明只本地装了却敲了裸 `tsc`，改用 `npx tsc --init`。

> [!question] 装完提示 `tsc : 无法将"tsc"项识别为 cmdlet / 不是内部或外部命令`？
> 说明用的是全局命令但没装全局，或装的全局版本不在 PATH。
> **正解**：用 `npx tsc`（用本地版本），或把命令写进 `package.json` 的 `scripts` 再 `npm run`。

> [!question] 编译报 `Cannot find module 'xxx' or its corresponding type declarations`？
> TS 找到了运行时包，却**没有它的类型声明**。
> 处理：装 `@types/xxx`，或自己写 `xxx.d.ts` —— 详见 [[TS 与 JS 的互操作性]]。

> [!question] 我该用 `tsc`、`tsx` 还是打包器？
> 看**产物归谁**：要自己发 `.js` / `.d.ts` → `tsc`；只想立刻跑起来 → `tsx`；前端应用 → 打包器负责产出、`tsc --noEmit` 负责类型。见第四节对照表。

# 配置

> [!abstract] 一句话
> 真正要花心思的是 **`tsconfig.json`** —— 它决定 ==编译目标、模块格式、严格程度、输出位置==。配好它，`npx tsc` 就能把 `.ts` 变成 `.js`。
> 本节只讲"够用的一套"；上百个选项的完整分类见 [[tsconfig.json]]。

---

## 一、`tsconfig.json` 从哪里来

> [!warning] 装包**不会**生成配置文件
> 上一节的 `npm install typescript` **只把编译器装进 `node_modules`**，不会创建任何配置——**tsconfig.json 是可选的**：
> - 只编单个文件 → 不需要它：`npx tsc src/index.ts` 照样能出 JS；
> - 要让 `tsc` **按项目整体编译**（编哪些文件、目标版本、输出到哪）→ 才需要一份 tsconfig.json。
>
> 所以"生成配置"是一条**独立的命令**（`tsc --init`），得你显式执行；脚手架（Vite / Next 等）之所以"一装就有"，是因为它替你把这一步做了。

```bash
npx tsc --init        # ★ 显式生成：在当前目录创建带注释的 tsconfig.json
```

> [!tip] 想跳过 `--init`：直接手放一份即可
> `tsc --init` 只是**生成模板**。你也可以**新建一个 `tsconfig.json` 手动粘贴**（见下方第四节「关键选项」与第 4.5 节的起步配置），效果完全一样。
> 另外 `tsc --init` **不会覆盖**已存在的同名文件；想换配置就手动改，或删掉重建。

> [!note] `tsconfig.json` 是什么
> 它是 TypeScript 项目的**总配置**：告诉编译器"编译哪些文件、按什么标准编译、输出到哪"。
> 有它之后，直接敲 `npx tsc`（不带文件名）就会**按配置整体编译**；没有它则只能一个个文件编译。
> 查找规则、`extends`、`references`、`files`/`include`/`exclude` 等组织方式，见 [[tsconfig.json]]。

---

## 二、`tsconfig.json` 关键选项

下面按"最常改"的顺序说明。完整项见 [TSConfig 参考](https://www.typescriptlang.org/tsconfig)。

### 2.1 编译目标与模块

```jsonc
{
  "compilerOptions": {
    "target": "ES2020",        // 编译成哪个 JS 版本：ES5 / ES2015 / ES2020 / ESNext
    "module": "ESNext",        // 输出哪种模块格式：CommonJS / ESNext / NodeNext
    "lib": ["ES2020", "DOM"],  // 可用的内置 API 环境（DOM 让 document 等有类型）
    "moduleResolution": "bundler" // 模块解析策略：node / node16 / bundler
  }
}
```

> [!warning] `target` 决定"降级"程度
> - `target: "ES5"` → 箭头函数、`const` 等会被转写成 ES5 写法，兼容老浏览器，但产物啰嗦。
> - `target: "ES2020"` → 几乎保留现代语法，产物干净，但要求运行环境较新。
> 到底选哪个，取决于**你的代码要跑在什么环境**（老浏览器 ←→ 现代 Node）。

> [!note] `module` 与 `moduleResolution` 要**配对**
> - 打包器负责构建的前端项目 → `module: "ESNext"` + `moduleResolution: "bundler"`。
> - 直接在 Node 跑 → `module: "NodeNext"` + `moduleResolution: "NodeNext"`。
> 二者错配是"模块找不到 / 导入报错"的头号来源。

### 2.2 严格程度（最重要的一组）

```jsonc
{
  "compilerOptions": {
    "strict": true   // 一把开启下面全部严格检查（强烈建议开）
  }
}
```

`strict: true` 等价于同时打开：

| 子选项 | 作用 |
| --- | --- |
| `noImplicitAny` | 禁止"隐式 any"，未标注且推不出的参数必须显式写类型 |
| `strictNullChecks` | ==`null` / `undefined` 不再能随意赋给别的类型==（最值钱的一项） |
| `strictFunctionTypes` | 函数参数按逆变检查，更安全 |
| `strictPropertyInitialization` | 类属性必须在构造里初始化 |
| `strictBindCallApply` | `bind` / `call` / `apply` 的参数也检查 |
| `noImplicitThis` | 禁止 `this` 隐式为 any |
| `useUnknownInCatchVariables` | `catch` 到的变量是 `unknown` 而非 `any` |
| `alwaysStrict` | 输出文件带 `"use strict"` |

> [!success] 强烈建议从第一天就 `strict: true`
> 严格模式下被"逼"出来的类型，恰恰是最有价值的。
> **新项目**：直接开。**老项目迁移**：可先关掉，把能编译过放在第一位，再逐项打开——详见 [[TS 与 JS 的互操作性]] 的渐进迁移。

### 2.3 输入与输出

```jsonc
{
  "compilerOptions": {
    "rootDir": "./src",       // 源码根目录，影响输出目录结构
    "outDir": "./dist",       // 编译产物输出目录
    "sourceMap": true,        // 生成 .js.map，便于调试 TS 源码
    "declaration": true,      // 生成 .d.ts 类型声明（做库时用）
    "noEmit": true            // 只做类型检查、不产出文件（配合打包器时常用）
  },
  "include": ["src/**/*.ts"], // 参与编译的文件
  "exclude": ["node_modules", "dist"]
}
```

> [!tip] `noEmit` 的用途
> 当用 Vite / webpack / esbuild 负责打包时，TypeScript 只当"类型检查器"：
> `tsc --noEmit` 专门跑检查，产出交给打包器，各司其职（对应上一节的方式三）。

### 2.4 互操作 / 兼容项

```jsonc
{
  "compilerOptions": {
    "esModuleInterop": true,              // 让 import x from "cjs 包" 更顺
    "allowSyntheticDefaultImports": true, // 类型层面允许默认导入（常随上一项开启）
    "skipLibCheck": true,                 // 跳过检查 node_modules 里的 .d.ts，提速
    "forceConsistentCasingInFileNames": true, // 大小写敏感，跨平台防坑
    "resolveJsonModule": true             // 允许 import xxx from "./a.json"
  }
}
```

### 2.5 一份可直接用的起步配置

```jsonc
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "lib": ["ES2020", "DOM"],
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "resolveJsonModule": true,
    "sourceMap": true,
    "rootDir": "./src",
    "outDir": "./dist"
  },
  "include": ["src/**/*.ts"],
  "exclude": ["node_modules", "dist"]
}
```

> [!tip] 其他场景的起步模板
> **Node 服务 / CLI**（`module: "NodeNext"` + `types: ["node"]`）、**前端应用**（加 `jsx` + `noEmit`）、**发布 npm 库**（开 `declaration`）、**老项目迁移**（先 `strict: false` + `allowJs`）——四份现成模板见 [[tsconfig.json]] 第八节。

## 三、配置相关常见问题

> [!question] 改了 `tsconfig.json`，但报错/行为没变？
> 先 `npx tsc --showConfig` 看**实际生效**的配置（可能被 `extends` 覆盖，或编辑器缓存了旧配置）。
> VS Code 里还可用命令面板 `TypeScript: Restart TS Server` 让语言服务重新读取。

> [!question] `document` / `window` / `console` 报"找不到名称"？
> `lib` 里缺 `DOM`。加上 `"lib": ["ES2020", "DOM"]`。
> 注意：**只要你显式写了 `lib`，默认就整套被覆盖**，得按需补齐。

> [!question] 只想检查类型，不想生成 `.js` 文件？
> `tsc --noEmit`，或在 `tsconfig` 里设 `"noEmit": true`。

> [!question] 产物目录结构莫名其妙多了一层 `src/`？
> 通常是**没设 `rootDir`**：`tsc` 会取所有源文件的公共父目录作为根，从而带上多余层级。显式写 `"rootDir": "./src"` 即对齐。

> [!question] 报 `Cannot write file ... because it would overwrite input file`？
> `outDir` 落在源码范围里了。把 `outDir` 指到独立的 `./dist`，并把它加进 `exclude`。

> [!question] 老项目开 `strict` 后满屏报错，怎么办？
> 别硬扛。**先关或调松**（如只开 `strictNullChecks`），让项目能编译过，再配合 `allowJs` / `checkJs` 逐个文件收紧。迁移节奏见 [[TS 与 JS 的互操作性]]。

> [!question] `target` / `module` / `lib` 到底啥关系？
> - `target`：**产出**的目标 JS 版本（降级到多低）。
> - `lib`：写代码时**可调用**哪些内置 API 的类型（决定 `Promise`、`document` 是否可用）。
> - `module`：**模块系统**格式（`import/export` 还是 `require`）。
> 三者独立，要按"运行环境 + 目标平台"搭配。
