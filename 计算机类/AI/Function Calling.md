# Function Calling

> 一句话：Function Calling 是**让 LLM 以结构化格式"申请"调用外部函数**的能力——==模型不执行函数，只产出"要调哪个、参数是什么"的 JSON==，真正执行的是你的程序。

## 一、先说清楚它不是什么

这是最容易误解的一点：

> ⚠️ **模型不会去执行任何函数。** 它既不联网、不读文件、也不运行代码。

模型做的只有一件事：**根据当前上下文，生成一段符合约定的结构化文本**（通常是 JSON），表达"我认为现在应该调用 `get_weather`，参数是 `{"city": "上海"}`"。

剩下的全部由**调用方的应用程序**完成：

1. 解析这段 JSON
2. 找到对应的真实函数并执行
3. 把执行结果塞回对话，再交给模型

所以 Function Calling 的本质是一种**约定好的"模型 → 程序"的通信格式**，而不是模型获得了什么新的执行能力。

### 那它为什么还算"新能力"

因为在 Function Calling 出现之前，想让模型输出结构化内容，只能靠 **Prompt 约定 + 字符串解析**：

```text
请你只输出 JSON，格式为 {"city": "..."}，不要输出其他内容。
```

这种做法脆弱得很——模型可能加一句"好的，这是结果："、可能用中文全角引号、可能某个字段漏了。而要处理多个不同函数时，还得把所有函数说明塞进 Prompt，越写越长、越写越糊。

## 二、完整调用流程

一次标准的 Function Calling 是一个 **多轮往返** 的过程，至少要两次请求模型：

| 步骤 | 角色 | 动作 |
| --- | --- | --- |
| 1 | 开发者 | 定义函数清单（名称、描述、参数的 JSON Schema），随请求一起发给模型 |
| 2 | 用户 | 发送问题，例如"上海今天天气怎么样" |
| 3 | 模型 | **不直接回答**，而是返回 `tool_calls`：要调用 `get_weather`，参数 `{"city":"上海"}`，并附带一个 `id` |
| 4 | 应用程序 | 按 `id` 与 `name` 找到真实函数，**真正执行**，拿到结果 |
| 5 | 应用程序 | 以 `tool` 角色、带 `tool_call_id` 把结果追加进对话历史 |
| 6 | 模型 | 读取工具返回结果，生成**面向用户的自然语言回答** |

用示意图表达：

```text
用户 ──▶ 模型 ──▶ tool_calls ──▶ 你的程序 ──▶ 真实函数
                    ▲                              │
                    └────── tool 结果 ◀────────────┘
```

> 💡 第 3 步返回的 `arguments` 是**模型"生成"的字符串**，不是程序算出来的——所以它可能是错的、可能缺参数、可能是幻觉出的函数名。

### 多工具与并行调用

- 模型可以**一次请求里返回多个 `tool_calls`**（并行调用），例如同时查上海和北京的天气
- 也可以**串行多轮**：先查城市编码，再拿编码查车票——这与 [[mcp详解]] 中"查 12306 车票"的例子是同一套机制
- 因此 Function Calling 是实现 **Agent 循环**（思考 → 调工具 → 观察 → 再思考）的基础积木

## 三、函数是怎么"定义"的

给模型的函数描述本质上是一份 **JSON Schema**，核心是三个字段：

| 字段 | 作用 | 注意事项 |
| --- | --- | --- |
| `name` | 函数标识 | 模型靠它选择调用哪个，命名要自解释 |
| `description` | **自然语言说明"这个函数干什么、什么时候用"** | ==最关键，写得好不好直接决定调用准确率== |
| `parameters` | 参数的类型、含义、是否必填 | 建议为每个参数都写 `description` |

一个典型定义：

```json
{
  "name": "get_weather",
  "description": "查询指定城市当前的真实天气情况。当用户询问天气、气温、是否下雨时使用。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string", "description": "城市名称，如：上海" },
      "unit": { "type": "string", "enum": ["celsius", "fahrenheit"] }
    },
    "required": ["city"]
  }
}
```

模型返回的调用请求：

```json
{
  "tool_calls": [
    {
      "id": "call_abc123",
      "type": "function",
      "function": {
        "name": "get_weather",
        "arguments": "{\"city\": \"上海\", \"unit\": \"celsius\"}"
      }
    }
  ]
}
```

> 注意 `arguments` 是**字符串**，需要自行 `JSON.parse`；而 `id` 在回传结果时必须原样带回，模型靠它把"请求"和"结果"配对。

### 写 description 的经验

因为**选哪个函数是模型自己判断的**（这一点与 MCP 完全一致），描述要：

- **面向使用场景**，而不是面向实现："当用户询问天气时使用"比"调用 API"有用得多
- **说清边界**："不要用于历史天气查询"这类负向说明在函数多时很关键
- **函数之间不要语义重叠**，否则模型会摇摆

## 四、它带来了什么

| 收益 | 说明 |
| --- | --- |
| **告别脆弱的字符串解析** | 输出由模型侧按 Schema 约束，程序侧拿到的是可解析结构 |
| **能力边界可扩展** | 模型训练后仍能通过挂载新函数获得新能力（查库、下单、发邮件） |
| **降低幻觉的抓手** | 计算、检索这类任务交给真实函数执行，而不是让模型"心算" |
| **Agent 的地基** | 有了"模型决定调用 → 程序执行 → 结果回灌"的闭环，才谈得上自主智能体 |

## 五、局限与坑

- **描述决定上限**：函数描述写得含糊，模型就会选错函数或漏调，这不是模型"变笨"，是接口设计问题
- **输出不保证合法**：早期版本可能给出不存在的函数名、缺失必填参数、类型错误——**参数校验必须在程序侧做**
- **不等于安全**：模型可能被 Prompt 注入诱导去调用敏感函数，**权限与确认逻辑要由程序控制**
- **成本与延迟**：每次调用至少两次模型请求，工具结果的长度也会吃 token
- **它不会"记得"**：函数定义与 `tool` 结果都需要你主动放进上下文，模型没有隐式记忆

## 六、与相关概念的关系

| 概念                     | 关系                                                                    |
| ---------------------- | --------------------------------------------------------------------- |
| **ReAct**              | 提出"推理 + 行动"交替的范式；Function Calling 是它在工程上的标准化落地                        |
| **Tool Calling**       | 更宽泛的叫法。除自定义函数外，还涵盖模型厂商**内置**的工具（联网搜索、代码执行、文件检索等）                      |
| **Structured Outputs** | 2024 年后引入的强化版约束：通过 `strict` 模式让输出**严格符合** Schema，缓解"参数不合法"问题          |
| **[[mcp详解\|MCP]]**     | Function Calling 是**模型能力**，每家格式各异；MCP 是**统一协议**，解决的是"外部工具如何被标准化发现与接入" |

> **一句话区分**：Function Calling 解决"模型怎么开口要工具"，MCP 解决"工具怎么被统一挂上来"。两者是互补关系，不是替代关系——MCP Server 暴露的 Tools，最终往往就是通过 Function Calling 被模型调用的。
