
> [!abstract] 一句话
> 隔离级别定义"**并发事务之间能互相看到多少**"。
> MySQL InnoDB 默认 `REPEATABLE READ`，靠 **MVCC（快照读）+ 锁（当前读）** 实现。

> [!info] 本篇在 TCL 中的位置
> [[ACID]] 中的 **I（Isolation）** 就是本篇；
> 事务边界见 [[BEGIN]] / [[COMMIT]] / [[ROLLBACK]]，局部回滚见 [[SAVEPOINT]]。

---

## 一、为什么需要隔离级别

多个事务同时读写同一批数据时，会出现四类问题：

| 问题 | 定义 | 例子 |
| --- | --- | --- |
| **脏读**（Dirty Read） | 读到其他事务**未提交**的修改 | T1 改余额未提交，T2 读到了 |
| **不可重复读**（Non-repeatable Read） | 同一事务内两次读**同一行**，结果不同 | T1 读余额 100，T2 改成 200 并提交，T1 再读变 200 |
| **幻读**（Phantom Read） | 同一事务内两次读**同一范围**，行数不同 | T1 查 `age > 20` 有 3 行，T2 插入 1 行并提交，T1 再查有 4 行 |
| **丢失更新**（Lost Update） | 两个事务基于旧值更新，后提交的覆盖先提交的 | 两人同时读 100，各自减 10，最终是 90 而不是 80 |

> [!note] 不可重复读 vs 幻读
> - **不可重复读**：同一行，**值**变了（`UPDATE` / `DELETE`）
> - **幻读**：同一范围，**行数**变了（`INSERT` / `DELETE`）
>
> 两者都针对"同一事务内两次读"，区别在"行变"还是"值变"。

> [!warning] 丢失更新不是隔离级别直接解决的
> 标准隔离级别主要解决前三个问题；丢失更新需要**当前读加锁**或**原子更新 / 乐观锁**来防。
> 详见 §七。

## 二、四种隔离级别

SQL 标准定义了四种级别，隔离性从弱到强：

| 级别 | 脏读 | 不可重复读 | 幻读 | 并发性能 |
| --- | --- | --- | --- | --- |
| `READ UNCOMMITTED` | ✅ 可能 | ✅ 可能 | ✅ 可能 | 最高 |
| `READ COMMITTED` | ❌ | ✅ 可能 | ✅ 可能 | 较高 |
| `REPEATABLE READ` | ❌ | ❌ | ⚠️ 标准说可能 | 中等 |
| `SERIALIZABLE` | ❌ | ❌ | ❌ | 最低 |

> [!important] 这是"SQL 标准"的表格
> MySQL InnoDB 的 `REPEATABLE READ` 在实际表现上**基本避免了幻读**，
> 但实现方式和标准不同，细节见 §五。

### 2.1 `READ UNCOMMITTED`（读未提交）

- 能读到其他事务**尚未提交**的修改
- 几乎没有隔离性，实际业务基本不用
- 可能读到"后来被回滚"的脏数据

```sql
-- T1
START TRANSACTION;
UPDATE account SET balance = 0 WHERE id = 1;   -- 未提交

-- T2（READ UNCOMMITTED）
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
START TRANSACTION;
SELECT balance FROM account WHERE id = 1;       -- 读到 0（脏读）

-- T1
ROLLBACK;                                        -- T2 读到的 0 从未真正存在
```

### 2.2 `READ COMMITTED`（读已提交）

- 只能读到其他事务**已提交**的修改
- **每条 `SELECT`** 都会创建新的 Read View
- 同一事务内两次读同一行，可能不同（不可重复读）
- 互联网高并发场景常用（如 Oracle、PostgreSQL 默认）

```sql
-- T1（READ COMMITTED）
START TRANSACTION;
SELECT balance FROM account WHERE id = 1;   -- 100

-- T2
UPDATE account SET balance = 200 WHERE id = 1;
COMMIT;

-- T1
SELECT balance FROM account WHERE id = 1;   -- 200（不可重复读）
```

### 2.3 `REPEATABLE READ`（可重复读）

- MySQL InnoDB **默认级别**
- **第一次快照读**时创建 Read View，整个事务复用
- 同一事务内多次普通 `SELECT`，看到的是同一个一致性快照
- 当前读（`FOR UPDATE` / `FOR SHARE` / DML）仍然读最新已提交版本

```sql
-- T1（REPEATABLE READ）
START TRANSACTION;
SELECT balance FROM account WHERE id = 1;   -- 100，快照建立

-- T2
UPDATE account SET balance = 200 WHERE id = 1;
COMMIT;

-- T1
SELECT balance FROM account WHERE id = 1;   -- 仍是 100（可重复读）
COMMIT;

-- 新事务
SELECT balance FROM account WHERE id = 1;   -- 200
```

> [!tip] 快照不是 `START TRANSACTION` 时建立的
> 而是**第一次快照读**时建立的。
> 如果事务先执行 `UPDATE` 再 `SELECT`，Read View 在 `SELECT` 时才创建。
> 想让快照在事务开始时就建立，用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。

### 2.4 `SERIALIZABLE`（串行化）

- 最强隔离，事务串行执行的效果
- InnoDB 会把普通 `SELECT` **隐式转换成** `SELECT ... FOR SHARE`（共享锁读）
- 读加共享锁、写加排他锁，读写互相阻塞
- 并发性能最差，只在特殊场景使用

```sql
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
START TRANSACTION;
SELECT * FROM account WHERE id = 1;   -- 实际按 SELECT ... FOR SHARE 处理
COMMIT;
```

> [!warning] `SERIALIZABLE` 容易死锁
> 共享锁 + 间隙锁会显著增加锁冲突。
> 除非业务确实需要，否则不要轻易把全局隔离级别改成 `SERIALIZABLE`。

## 三、如何设置隔离级别

### 3.1 查看

```sql
-- MySQL 8.0
SELECT @@transaction_isolation;
-- MySQL 5.7 及更早
SELECT @@tx_isolation;
```

### 3.2 设置

```sql
-- 只影响当前会话（之后的语句）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 影响新连接（已存在的连接不变）
SET GLOBAL TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 只影响下一个事务
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
START TRANSACTION;
-- ...
COMMIT;
```

> [!note] `SET TRANSACTION` 的位置很重要
> 它必须写在 `START TRANSACTION` **之前**，只对下一个事务生效。
> 写在事务中间不会改变当前事务的隔离级别。

### 3.3 配置文件

```ini
[mysqld]
transaction-isolation = REPEATABLE-READ
```

> [!tip] 修改全局级别后
> 只对**新建立的连接**生效；已有连接仍使用旧级别。
> 生产环境修改前要评估连接池、长连接的影响。

## 四、InnoDB 如何实现隔离：MVCC + 锁

> [!abstract] 一句话
> **普通 `SELECT` 走 MVCC（快照读，不加锁）；**
> **`FOR UPDATE` / `FOR SHARE` / `INSERT` / `UPDATE` / `DELETE` 走当前读（加锁）。**

### 4.1 快照读 vs 当前读

| 类型 | 语句 | 读什么 | 加锁 |
| --- | --- | --- | --- |
| **快照读**（一致性读） | 普通 `SELECT` | Read View 对应的历史版本 | ❌ |
| **当前读** | `SELECT ... FOR UPDATE` | 最新已提交版本 | ✅ 排他锁 |
| **当前读** | `SELECT ... FOR SHARE` | 最新已提交版本 | ✅ 共享锁 |
| **当前读** | `INSERT` / `UPDATE` / `DELETE` | 最新已提交版本 | ✅ 排他锁 |

```sql
-- 快照读：RR 下可能看到旧值
SELECT * FROM account WHERE id = 1;

-- 当前读：总是读最新已提交，并加锁
SELECT * FROM account WHERE id = 1 FOR UPDATE;
SELECT * FROM account WHERE id = 1 FOR SHARE;
```

> [!important] 隔离级别主要约束的是"快照读"
> 当前读永远读最新已提交数据，不受 Read View 影响。
> 所以"RR 下我加了 `FOR UPDATE` 怎么看到新数据了"不是 bug。

### 4.2 隐藏列与版本链

InnoDB 每行有隐藏字段：

| 隐藏列 | 作用 |
| --- | --- |
| `DB_TRX_ID` | 最后修改该行的事务 ID |
| `DB_ROLL_PTR` | 指向 undo log 中的上一个版本 |
| `DB_ROW_ID` | 无主键时生成的行 ID |

一次更新会形成版本链：

```text
当前行（trx 300，balance=300）
   │ DB_ROLL_PTR
   ▼
undo 版本（trx 200，balance=200）
   │
   ▼
undo 版本（trx 100，balance=100）
```

> [!tip] 快照读就是"沿着版本链找可见版本"
> 从最新版本开始，按 Read View 规则判断是否可见；不可见就顺着 `DB_ROLL_PTR` 往前找。

### 4.3 Read View

Read View 是事务在某个时刻的"活跃事务快照"，核心字段：

| 字段 | 含义 |
| --- | --- |
| `m_ids` | 创建 Read View 时**活跃（未提交）**的事务 ID 列表 |
| `min_trx_id` | `m_ids` 中的最小值 |
| `max_trx_id` | 创建 Read View 时**下一个**要分配的事务 ID |
| `creator_trx_id` | 当前事务自己的 ID |

可见性判断（简化版）：

```text
对某一版本的 DB_TRX_ID：
1. DB_TRX_ID == creator_trx_id        → 可见（自己的修改）
2. DB_TRX_ID <  min_trx_id            → 可见（快照前已提交）
3. DB_TRX_ID >= max_trx_id            → 不可见（快照后才开始）
4. min_trx_id <= DB_TRX_ID < max_trx_id：
     在 m_ids 中  → 不可见（快照时还活跃）
     不在 m_ids 中 → 可见（快照前已提交）
```

> [!note] RC 与 RR 的唯一区别
> - **RC**：每条 `SELECT` 都创建新的 Read View → 能看到最新提交
> - **RR**：整个事务复用第一次快照读创建的 Read View → 看不到之后提交的
>
> 底层机制相同，只是 Read View 的创建时机不同。

### 4.4 锁：记录锁、间隙锁、Next-Key Lock

| 锁类型 | 锁什么 | 作用 |
| --- | --- | --- |
| **Record Lock** | 单条索引记录 | 防止其他事务修改/删除该行 |
| **Gap Lock** | 两条索引记录之间的间隙 | 防止其他事务在间隙中插入 |
| **Next-Key Lock** | 记录 + 前面的间隙 | Record + Gap，RR 下防幻读的关键 |
| **Insert Intention Lock** | 插入意图 | 插入前对间隙加的意向锁 |

```text
索引值：  5      10      15
         │      │       │
间隙： (-∞,5) (5,10) (10,15) (15,+∞)

Next-Key Lock 锁 (5,10]：记录 10 + 间隙 (5,10)
```

> [!important] 间隙锁只在 RR 及更高级别生效
> `READ COMMITTED` 下，InnoDB 基本**关闭间隙锁**（外键检查、唯一键冲突检查除外）。
> 所以 RC 下锁范围更小、并发更高，但可能出现幻读。

### 4.5 加锁规则（简化）

| 场景 | 加锁 |
| --- | --- |
| 唯一索引等值命中 | Record Lock（可能退化为单行锁） |
| 唯一索引等值未命中 | Gap Lock |
| 非唯一索引等值 | Next-Key Lock + 间隙 |
| 范围查询 | Next-Key Lock |
| 无索引条件 | 可能锁全表/全部扫描记录 |
| 普通 `SELECT` | 不加锁（快照读） |

> [!warning] 没有索引的 `UPDATE` 可能锁很多行
> 即使只改一行，如果 `WHERE` 条件没有索引，InnoDB 可能扫描并锁住大量记录，甚至接近全表。
> 这也是"更新慢、锁等待"的常见原因。

## 五、MySQL 的 RR 到底防不防幻读

> [!important] 结论先行
> **快照读：RR 下不会幻读**（Read View 固定，看不到新插入的行）。
> **当前读：RR 下用 Next-Key Lock 防幻读**（锁住间隙，别人插不进来）。
> 但存在一些"看起来像幻读"的边界情况，面试常考。

### 5.1 快照读：看不到新行

```sql
-- T1（RR）
START TRANSACTION;
SELECT COUNT(*) FROM student WHERE age > 20;   -- 3，快照建立

-- T2
INSERT INTO student (name, age) VALUES ('新人', 25);
COMMIT;

-- T1
SELECT COUNT(*) FROM student WHERE age > 20;   -- 仍是 3
COMMIT;
```

> [!note] 这不是"幻读被解决了"，而是"快照看不到"
> T1 看到的是事务开始时的历史版本，新行根本不在它的视图里。
> 但 T1 如果执行当前读，就会看到新行。

### 5.2 当前读：Next-Key Lock 阻止插入

```sql
-- T1（RR）
START TRANSACTION;
SELECT * FROM student WHERE age > 20 FOR UPDATE;   -- 对范围加 Next-Key Lock

-- T2
INSERT INTO student (name, age) VALUES ('新人', 25);
-- 阻塞，直到 T1 提交/回滚

-- T1
COMMIT;   -- T2 才能插入
```

### 5.3 边界：快照读之后再当前读

```sql
-- T1（RR）
START TRANSACTION;
SELECT COUNT(*) FROM student WHERE age > 20;   -- 3，快照建立

-- T2
INSERT INTO student (name, age) VALUES ('新人', 25);
COMMIT;

-- T1
SELECT COUNT(*) FROM student WHERE age > 20 FOR UPDATE;  -- 当前读，看到 4
```

> [!warning] 这就是"RR 下也会看到幻影行"的经典场景
> 快照读看不到新行，但当前读会看到。
> 本质是**同一事务内混用了快照读和当前读**，不是隔离级别失效。

### 5.4 边界：先快照读，再更新

```sql
-- T1（RR）
START TRANSACTION;
SELECT COUNT(*) FROM student WHERE age > 20;   -- 3

-- T2
INSERT INTO student (name, age) VALUES ('新人', 25);
COMMIT;

-- T1
UPDATE student SET score = 0 WHERE age > 20;   -- 当前读，会更新到 4 行
```

> [!important] `UPDATE` 是当前读
> 它不仅读最新数据，还可能"看到"并修改快照里不存在的新行。
> 如果业务依赖"事务内行数不变"，必须用 `FOR UPDATE` 提前锁住范围。

### 5.5 面试标准回答

> [!question] MySQL 的 RR 能防止幻读吗？
> **分两种读法：**
> 1. **快照读**：能。整个事务复用同一个 Read View，看不到其他事务新插入的行。
> 2. **当前读**：能。InnoDB 用 Next-Key Lock（Record + Gap）锁住范围，阻止其他事务在间隙插入。
>
> 但要注意：同一事务里先快照读、再当前读（`FOR UPDATE` / `UPDATE`），当前读会看到新行，看起来像幻读。
> 这是"快照读和当前读混用"的结果，不是 RR 失效。
> 标准 SQL 的 RR 是允许幻读的；MySQL 的实现比标准更强，但不是绝对。

## 六、RC vs RR：怎么选

| 对比项 | `READ COMMITTED` | `REPEATABLE READ` |
| --- | --- | --- |
| Read View | 每条语句新建 | 第一次快照读后复用 |
| 不可重复读 | ✅ 可能 | ❌ 不会（快照读） |
| 幻读（快照读） | ✅ 可能 | ❌ 不会 |
| 间隙锁 | 基本关闭 | 启用 |
| 锁范围 | 较小 | 较大 |
| 并发性能 | 较高 | 较低 |
| 死锁概率 | 较低 | 较高 |
| 主从复制 | 建议 `binlog_format=ROW` | 兼容性更好 |
| 典型使用 | 互联网高并发、短事务 | MySQL 默认、需要事务内稳定视图 |

> [!tip] 互联网业务为什么常用 RC？
> - 间隙锁少，锁冲突和死锁更少
> - 每条语句读最新提交，业务语义更直观
> - 配合 `binlog_format=ROW`，主从一致性有保障
>
> 代价是同一事务内可能读到不同值，业务不能依赖"事务内快照不变"。

> [!warning] RC + `binlog_format=STATEMENT` 有风险
> 语句级 binlog 在 RC 下可能因执行顺序不同导致主从数据不一致。
> 使用 RC 时建议 `binlog_format=ROW`（MySQL 5.7+ 默认就是 ROW）。

### 6.1 修改隔离级别的注意事项

```sql
-- 查看当前
SELECT @@transaction_isolation, @@binlog_format;

-- 会话级切换
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

> [!failure] 不要只改会话就以为全局生效
> 连接池里的连接可能各自保持不同级别。
> 统一在中间件/连接初始化时设置，或在配置文件里设置全局默认值。

## 七、丢失更新与并发控制

> [!important] 隔离级别不直接解决丢失更新
> 即使 RR，两个事务"先读后写"仍可能互相覆盖。
> 需要显式加锁或原子操作。

### 7.1 错误示例

```sql
-- T1 和 T2 都执行同样的逻辑
START TRANSACTION;
SELECT balance FROM account WHERE id = 1;   -- 都读到 100
UPDATE account SET balance = 90 WHERE id = 1;  -- 都基于 100 减 10
COMMIT;
-- 最终 90，而不是 80：丢失了一次更新
```

### 7.2 方案一：当前读加锁

```sql
START TRANSACTION;
SELECT balance FROM account WHERE id = 1 FOR UPDATE;  -- 排他锁
UPDATE account SET balance = balance - 10 WHERE id = 1;
COMMIT;
```

> [!note] `FOR UPDATE` 要放在事务里
> 锁在事务提交/回滚时释放。如果放在自动提交模式下，锁立刻释放，起不到保护作用。

### 7.3 方案二：原子更新

```sql
UPDATE account SET balance = balance - 10 WHERE id = 1 AND balance >= 10;
```

> [!success] 推荐
> 让数据库在一条语句里完成"读 + 改"，避免应用层先读后写。
> 还能顺便用 `WHERE balance >= 10` 防止扣成负数。

### 7.4 方案三：乐观锁

```sql
UPDATE account
   SET balance = 90, version = version + 1
 WHERE id = 1 AND version = 5;

-- 影响行数为 0，说明版本已被别人修改，重试或报错
```

### 7.5 方案四：悲观锁 / 分布式锁

跨行、跨表、跨服务的复杂场景，可以用悲观锁、Redis 分布式锁等，但要注意锁粒度、超时、死锁。

## 八、隔离级别与锁等待、死锁

### 8.1 查看锁

```sql
-- MySQL 8.0
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;

-- 当前事务
SELECT * FROM information_schema.INNODB_TRX;

-- 引擎状态（含锁等待、死锁信息）
SHOW ENGINE INNODB STATUS\G
```

### 8.2 常见现象

| 现象 | 可能原因 |
| --- | --- |
| `ERROR 1205` 锁等待超时 | 有其他事务持锁未提交 |
| `ERROR 1213` 死锁 | 循环等待，InnoDB 回滚牺牲者 |
| 更新突然变慢 | 缺索引导致锁范围过大 |
| 大量事务堆积 | 长事务、未提交、连接泄漏 |

> [!warning] RR 下间隙锁更容易死锁
> 两个事务以不同顺序锁住相邻间隙，就可能互相等待。
> 如果业务允许，RC 能减少这类死锁；否则要统一加锁顺序、缩短事务。

## 九、隔离级别与复制

| 组合 | 风险 |
| --- | --- |
| `RC` + `STATEMENT` | 主从执行顺序不同，可能不一致 |
| `RC` + `ROW` | ✅ 推荐 |
| `RR` + `STATEMENT` | 相对安全，但仍有函数/随机数等坑 |
| `RR` + `ROW` | ✅ 安全，日志量大 |

> [!tip] 生产建议
> - `binlog_format=ROW`
> - 隔离级别按业务选择，默认 `REPEATABLE READ` 即可
> - 高并发短事务可评估 `READ COMMITTED`
> - 不要在会话中随意切换，保持连接池一致

## 十、最佳实践

> [!success] 隔离级别相关的九条经验
> 1. **默认 RR**：MySQL 默认值，多数业务够用
> 2. **高并发短事务可评估 RC**：减少间隙锁和死锁
> 3. **不要依赖"事务内快照不变"做写判断**：写操作是当前读
> 4. **需要最新数据 + 防并发修改**：用 `SELECT ... FOR UPDATE`
> 5. **能原子更新就不要先读后写**：`UPDATE ... SET x = x - 1`
> 6. **短事务**：事务越长，快照越旧、锁越久、undo 越多
> 7. **WHERE 条件必须有合适索引**：否则锁范围可能失控
> 8. **RC 配 ROW binlog**：避免主从不一致
> 9. **监控锁等待和长事务**：`INNODB_TRX`、`data_locks`、`INNODB STATUS`

```sql
-- 事务模板：需要防并发覆盖时
START TRANSACTION;
SELECT balance FROM account WHERE id = 1 FOR UPDATE;
-- 业务判断
UPDATE account SET balance = balance - 10 WHERE id = 1;
COMMIT;
```

> [!tip] 快照读与当前读不要混用
> 同一事务里先普通 `SELECT` 再 `FOR UPDATE`，会看到不同的数据。
> 如果业务要求一致，从一开始就用当前读，或者接受快照语义。

## 十一、常见面试问答

> [!question] Q1：事务的隔离级别有哪几种？
> `READ UNCOMMITTED`、`READ COMMITTED`、`REPEATABLE READ`、`SERIALIZABLE`。
> 隔离性从弱到强，并发性能从高到低。MySQL InnoDB 默认 `REPEATABLE READ`。

> [!question] Q2：脏读、不可重复读、幻读的区别？
> - 脏读：读到未提交的数据
> - 不可重复读：同一事务内两次读同一行，值不同
> - 幻读：同一事务内两次读同一范围，行数不同
>
> 前两者针对"值"，幻读针对"行集"。

> [!question] Q3：MySQL 默认隔离级别是什么？为什么？
> `REPEATABLE READ`。它能在大多数场景下提供稳定视图，配合 MVCC 和 Next-Key Lock 基本避免幻读，同时比 `SERIALIZABLE` 并发性能好。

> [!question] Q4：MVCC 是什么？
> 多版本并发控制。InnoDB 通过隐藏列 `DB_TRX_ID`、`DB_ROLL_PTR` 和 undo log 维护行的多个版本；普通 `SELECT` 按 Read View 判断哪个版本可见，实现"读不加锁"。

> [!question] Q5：RC 和 RR 的 MVCC 区别？
> 底层机制相同，区别在 Read View 的创建时机：
> - RC：每条 `SELECT` 新建 Read View
> - RR：第一次快照读创建，整个事务复用

> [!question] Q6：RR 能防止幻读吗？
> 快照读能（Read View 固定，看不到新行）；当前读能（Next-Key Lock 锁住间隙）。
> 但同一事务内先快照读再当前读，当前读会看到新行，看起来像幻读。标准 SQL 的 RR 允许幻读，MySQL 的实现更强。

> [!question] Q7：什么是当前读？什么是快照读？
> - 快照读：普通 `SELECT`，读 Read View 对应的历史版本，不加锁
> - 当前读：`FOR UPDATE`、`FOR SHARE`、`INSERT`、`UPDATE`、`DELETE`，读最新已提交版本并加锁

> [!question] Q8：间隙锁什么时候生效？
> RR 及更高级别下，对范围条件或非唯一索引等值条件加锁时生效，用于阻止其他事务在间隙插入。
> RC 下基本关闭（外键、唯一键检查除外）。

> [!question] Q9：如何解决丢失更新？
> - `SELECT ... FOR UPDATE` 当前读加锁
> - 原子更新：`UPDATE ... SET x = x - 1`
> - 乐观锁：`version` 字段
> - 悲观锁/分布式锁
>
> 隔离级别本身不直接解决丢失更新。

> [!question] Q10：为什么 RC 下死锁更少？
> RC 基本不使用间隙锁，锁范围更小，事务之间更不容易形成循环等待。
> RR 的 Next-Key Lock 会锁住间隙，增加冲突概率。

> [!question] Q11：`SERIALIZABLE` 在 InnoDB 中怎么实现？
> 普通 `SELECT` 被隐式转换为 `SELECT ... FOR SHARE`，读加共享锁、写加排他锁，使并发事务串行化。
> 并发性能差，容易死锁。

> [!question] Q12：长事务有什么危害？
> - 持有锁时间长，阻塞其他事务
> - Read View 长期不释放，undo log 无法 purge，history list 增长
> - 回滚慢、占用资源
> - 可能导致主从延迟、连接耗尽

---

> [!quote] 一句话记忆
> **隔离级别管"能看到多少"：RU 脏读、RC 不可重复读、RR 默认、SERIALIZABLE 全锁。**
> **InnoDB = MVCC 快照读 + Next-Key Lock 当前读；RC 每条语句新快照，RR 整个事务一个快照。**
