# Squash —— 把一堆提交压成一个

> [!abstract] 一句话
> ==Squash（压缩）就是把**多个提交合并成一个**==。Git 里它有两个入口：`git merge --squash`（把整条分支的效果一次性放进暂存区，由你提交成一个）和交互式 rebase 里的 `squash` / `fixup`（把分支内若干提交合并成一个）。共同目的：**让历史少些噪音，只留下有意义的那几次提交**。

> [!note] 两种入口，别混为一谈
> - `git merge --squash`：**跨分支**压——把对方所有提交的效果压成一个。
> - `git rebase -i` 的 `squash`/`fixup`：**分支内**压——把你自己的一串小提交压成一个。
>
> 两者都在"减少提交数量"，但作用对象和机制不同，下面分开讲。

---

## 一、为什么要压缩

开发一个功能，过程常常是这样的：

```text
添加登录接口
修个笔误
。。。
改 review 意见
再修笔误
加日志
```

这些**过程性提交**对当时的你是存档，对后来的读者却是噪音。压缩后：

```text
实现用户登录功能      ← 一个提交说清一件事
```

> [!tip] 判断标准
> 问自己："**别人需要看到这个中间步骤吗？**"不需要 → 可以压；需要（例如一个可独立回滚的实验、一次重要的重构节点）→ 保留。

## 二、入口 A：`git merge --squash`

```bash
git switch main
git merge --squash feature      # 把 feature 的所有改动"摊"进暂存区，但不提交
git commit -m "实现用户登录功能"  # 你亲自提交成一个普通提交
```

```text
【merge --squash 前】
      A ── B ── C            ← main
      │
      D ── E ── F            ← feature

【merge --squash 后】
      A ── B ── C ── S       ← main（S 是单父的普通提交，把 D+E+F 的效果一次并入）
      │
      D ── E ── F            ← feature（原封不动）
```

> [!warning] 头号陷阱：Git 不记录"这条分支被合并过"
> `S` 是**普通单父提交**，没有合并关系。后果：
> - `git branch -d feature` 会**拒绝**删除，说"未完全合并"——因为 Git 不知道它已并入，你得用 `-D` 强删。
> - 以后再 `merge` 一次 feature，可能**重复引入**改动或产生大量冲突。
>
> 所以 `--squash` 适合"**这条分支合并后就废弃、不再复用**"的场景。见 [[删除分支]]。

> [!info] `--squash` vs `--no-ff`
> - `--no-ff`：留合并提交，**记录**合并关系（分支可被识别为已合并）。
> - `--squash`：压成普通提交，**不记录**合并关系。
> - 对照见 [[Fast-Forward vs Non-FF]]。

## 三、入口 B：交互式 rebase 压缩

在**自己的特性分支**上，把一串提交整理成一个：

```bash
git rebase -i HEAD~5        # 整理最近 5 个提交
```

编辑器里把想合并的提交改成 `squash` 或 `fixup`：

```text
pick  a1b2c3d 添加登录接口
squash e4f5g6h 修个笔误
squash i7j8k9l 改 review 意见
fixup  m0n1o2p 再加点日志
```

> [!info] `squash` 与 `fixup` 的区别
> - `squash`：合并提交，并**弹出编辑器让你合并两者的提交信息**（可以留一部分）。
> - `fixup`：合并提交，**直接丢弃**本提交的信息，只保留前一个的（适合"纯笔误修正"）。
>
> 需要保留信息 → `squash`；信息毫无价值 → `fixup`。

> [!tip] 配合 `fixup!` 提交信息自动化
> 提交时写 `git commit --fixup <目标提交>`，之后 `git rebase -i --autosquash <目标提交>` 会**自动**把 `fixup!` 提交排到目标之后并标记为 `fixup`，你连编辑器都不用改。整理一堆 review 修正时极其高效。

> [!warning] 这同样是改写历史
> rebase 会把被压的提交变成新哈希。==**只对未推送/未共享的提交做**==，铁律同 [[Rebase]]。

## 四、对比一览

| 方式 | 作用范围 | 结果 | 记录合并关系 | 典型用途 |
|---|---|---|---|---|
| `git merge --squash` | 跨分支 | 单父普通提交 | ❌ 不记录 | 分支合并后即废弃 |
| `rebase -i` 的 `squash` | 分支内 | 合并多个提交、保留信息 | — | 整理自己的开发历史 |
| `rebase -i` 的 `fixup` | 分支内 | 合并多个提交、丢弃信息 | — | 抹掉笔误类提交 |
| `git commit --amend` | 最近一个 | 改写最近提交 | — | 只补最后一次 |

## 五、什么时候该用

> [!success] 适合
> - 特性分支开发完、准备合并前，**内部**整理成一到几个干净提交。
> - 把"修笔误""改 review 意见"这类噪音压掉。
> - 工具/平台侧要求"一个 PR 一个提交"时。

> [!warning] 不适合 / 要小心
> - **已推送到共享分支**的历史：压缩＝改写，会给协作者添乱。
> - **需要保留独立回滚点**的提交：压了就回不去了。
> - 依赖 `--squash` 合并后，**别再拿原分支去二次合并**（关系没被记录）。

## 六、常见困惑

> [!question] `merge --squash` 和 `rebase -i` 压缩，选哪个？
> - 想保留对方分支的"合并语义"，但输出成一个提交 → 但注意 `--squash` **不留语义**；要留语义就用 `--no-ff`。
> - 想整理**自己分支内部**的提交 → `rebase -i`。
> 一句话：**跨分支用 `merge --squash`，分支内用 `rebase -i`**。

> [!question] 压完为什么 `git branch -d` 删不掉原分支？
> 因为 `--squash` 没记录合并关系，Git 认为它"还没合并"。确认无误后用 `git branch -D` 强删，或在合并前就决定好策略。

> [!question] 压缩会改变代码内容吗？
> 不会。压的是**提交记录**，最终文件内容一致（前提是冲突解决正确）。改的是历史形状和哈希。

> [!question] 已经 push 的小提交能压吗？
> 技术上能（rebase + 强推），但除非这是你独占的分支，否则别做。见 [[Rebase]] 的黄金法则。

> [!question] 压过头了想拆开？
> 可以，但麻烦：需要重写历史把内容重新拆成多个提交。所以==**压缩前想清楚：这个节点将来看得出、还需要吗？**==

---

> [!quote] 一句话记忆
> **Squash = 多个提交 → 一个提交**。跨分支用 `git merge --squash`（但**不记录合并关系**），分支内用 `rebase -i` 的 `squash`/`fixup`。==**压缩是为读者服务：让历史只说结论，不记流水账。**==
