# 层缓存

Docker 逐层构建，每层带着父层的 ID。某条指令执行前，builder 会算一个缓存键：父层 ID、指令本身，以及这条指令引用的文件内容。键没变就直接复用，后面的层继续比对；一旦有一层没命中，后面全部重建。

所以顺序就是性能：变化少的放前面，变化多的放后面。

反例：

```dockerfile
FROM node:20
WORKDIR /app
COPY . .
RUN npm ci
CMD ["node", "server.js"]
```

改一行 `index.js`，`COPY . .` 的校验和就变了，`npm ci` 跟着重跑，几分钟没了。调换两步：

```dockerfile
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
```

只有依赖清单变化时才重装依赖，日常改代码几乎立刻完成。构建日志里对应层显示 `CACHED`，这是判断有没有命中的直接依据。

`RUN` 的缓存键只看命令字符串，不看命令执行时从网络拉了什么。所以 `RUN apt-get update` 单独一层、安装放另一层，是很典型的坑：过几周 `update` 层还在缓存里，索引已经过期，安装就会 404。要么合并成 `RUN apt-get update && apt-get install -y ... && rm -rf /var/lib/apt/lists/*`，要么定期 `--no-cache`。

基础镜像也一样。`FROM node:20` 在本地缓存了就不会主动去拉新的，上游打了安全补丁你也不知道。想强制更新用 `docker build --pull`。

## BuildKit 缓存挂载

包管理器的下载目录每次构建都从零开始，即使依赖层命中不了。BuildKit 的 cache mount 把这类目录单独持久化，不进入镜像层：

```dockerfile
RUN --mount=type=cache,target=/root/.npm,sharing=locked \
    npm ci --omit=dev
```

`target` 是容器内的缓存目录，`sharing=locked` 让并发构建串行访问，避免 npm 缓存损坏。Go 项目对应两个目录：

```dockerfile
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -o /out/app ./cmd/app
```

缓存存在 builder 本地，`docker builder prune` 会清掉。CI 里 builder 每次都是新的，本地缓存用不上，需要把缓存导出到镜像仓库：

```bash
docker buildx build \
  --cache-from type=registry,ref=registry.example.com/my-app:cache \
  --cache-to type=registry,ref=registry.example.com/my-app:cache,mode=max \
  -t my-app:1.0 --push .
```

`mode=max` 会导出中间层的缓存，代价是推送体积变大；`mode=min` 只导出最终层。私有仓库记得配置认证，否则缓存拉取失败时构建会安静地退回全量。

> [!warning] 缓存骗人的几种情况
> 锁文件没变但依赖源上的包被重新发布、`RUN` 里 `git clone` 了浮动分支，这些都不会让缓存键变化；`ADD` 远程 URL 会看 HTTP 的 ETag/Last-Modified，源站不返回这些头时同样可能拿到旧内容。CI 每周跑一次 `--no-cache` 构建，能提前暴露问题。
