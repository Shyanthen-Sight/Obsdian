# 相关子查询 —— 逐行重算的子查询

> [!abstract] 一句话
> 相关子查询（correlated subquery）==**引用了外层查询的列**==，因此它**不能独立运行**：外层每处理一行，就要把内层子查询**带着这一行的值重新算一遍**，像"逐行绑定参数的函数"。
> 代价就在这句"逐行"里——==**它是"每次都能写对、但可能很慢"的典型。**==

> [!info] 与其它笔记的分工
> [[嵌套查询]] 讲子查询的**全景与非相关**形态；本篇专讲**相关**的那一类：==**相关在哪、执行模型、四类经典场景、以及性能优化**==。
> `EXISTS` 的基本语法在 [[嵌套查询]] 第八节，本篇重点在它的**相关本质**与实战用法。

---

> [!example] 本篇示例数据
> 与 [[嵌套查询]]、`连接查询/` 各篇**共用同一套 `dept` / `emp` 表**。
> 孙七 `dept_id` 为 NULL，会在"比本部门平均"这类相关查询里**自动落选**——是个天然的反例。

```sql
CREATE TABLE dept (
    dept_id   INT PRIMARY KEY,
    dept_name VARCHAR(20)
);

CREATE TABLE emp (
    emp_id   INT PRIMARY KEY,
    emp_name VARCHAR(20),
    dept_id  INT,              -- 允许 NULL：孙七没有部门
    salary   DECIMAL(10,2)
);

INSERT INTO dept VALUES (1001, '研发部'), (1002, '销售部'), (1003, '财务部');

INSERT INTO emp VALUES (1, '张三', 1001, 12000),
                       (2, '李四', 1001, 15000),
                       (3, '王五', 1002,  9000),
                       (4, '赵六', 1002,  8500),
                       (5, '孙七', NULL,  7000);
```

```
-- dept（3 行）                       -- emp（5 行）
dept_id | dept_name                 emp_id | emp_name | dept_id | salary
--------+----------                 -------+----------+---------+--------
   1001 | 研发部                        1 | 张三     |    1001 |  12000
   1002 | 销售部                        2 | 李四     |    1001 |  15000
   1003 | 财务部  <-- 没人               3 | 王五     |    1002 |   9000
                                      4 | 赵六     |    1002 |   8500
                                      5 | 孙七     |    NULL |   7000  <-- 没部门
```

## 一、"相关"到底相关在哪

**非相关子查询**：内层自成一体，不碰外层的列 → **只算一次**。

```sql
-- 非相关：内层 (SELECT AVG(salary) FROM emp) 与外层无关，先算出一个 10300
SELECT emp_name FROM emp WHERE salary > (SELECT AVG(salary) FROM emp);
```

**相关子查询**：内层**引用了外层的列**（如 `e.dept_id`）→ 脱离外层就报"未知列"，**必须逐行绑定**。

```sql
-- 相关：内层 WHERE 里的 e.dept_id 来自外层 emp e
SELECT emp_name, salary
FROM emp e
WHERE salary > (SELECT AVG(x.salary) FROM emp x WHERE x.dept_id = e.dept_id);
```

> [!important] 一眼识别相关与否
> 把内层的 `SELECT` **单独拎出来跑一遍**——跑得通 = 非相关；报"Unknown column 'e.xxx'" = 相关。
> 关键看内层有没有引用**外层别名**（这里是 `e.dept_id`）。

## 二、执行模型：一次 vs 逐行

| | 非相关子查询 | 相关子查询 |
| --- | --- | --- |
| 与外层关系 | 独立 | 引用外层列 |
| 执行次数 | **1 次**（算完缓存） | **外层每行 1 次** |
| 类比 | 一个常量 | 一个"带参数的函数" |
| 代价 | 低 | 与外层行数 × 每行内层代价成正比 |

> [!note] 相关子查询的伪代码
> ```text
> for 外层每一行 r:
>     result = 执行内层子查询(用 r 的值作参数)
>     if 条件成立: 输出 r
> ```
> 外层 5 行，内层就跑 5 次；外层 100 万行，内层就跑 100 万次——**这就是它慢的根源**。

```sql
-- 看执行计划：内层通常显示为 DEPENDENT SUBQUERY（依赖子查询）
EXPLAIN SELECT emp_name FROM emp e
WHERE salary > (SELECT AVG(x.salary) FROM emp x WHERE x.dept_id = e.dept_id);
```

## 三、经典场景 1：比本部门平均工资高

最标准的相关标量子查询——"组内比较"：

```sql
SELECT e.emp_name, e.dept_id, e.salary,
       (SELECT AVG(x.salary) FROM emp x WHERE x.dept_id = e.dept_id) AS dept_avg
FROM emp e
WHERE e.salary > (SELECT AVG(x.salary) FROM emp x WHERE x.dept_id = e.dept_id);
```

各组的 avg：研发 `(12000+15000)/2 = 13500`、销售 `(9000+8500)/2 = 8750`。

```
emp_name | dept_id | salary | dept_avg
---------+---------+--------+---------
李四     |    1001 |  15000 |   13500    <-- 15000 > 13500 ✅
王五     |    1002 |   9000 |    8750    <-- 9000 > 8750 ✅
```

> [!warning] 孙七为什么不在结果里
> 孙七 `dept_id IS NULL`，内层 `WHERE x.dept_id = NULL` **匹配不到任何行** → `AVG` 返回 `NULL` → 外层 `7000 > NULL` = `UNKNOWN` → **落选**。
> 相关子查询里，凡内层引用的那列是 NULL，该行基本都会被静默排除——**不是被显式过滤，而是被判为"未知"**。

## 四、经典场景 2：`EXISTS` / `NOT EXISTS`

`EXISTS` 的内层几乎总是相关子查询（要用外层列建立关联）：

```sql
-- 找出"有员工"的部门（相关 EXISTS）
SELECT d.dept_name FROM dept d
WHERE EXISTS (SELECT 1 FROM emp e WHERE e.dept_id = d.dept_id);
-- → 研发部、销售部

-- 找出"没员工"的部门（相关 NOT EXISTS，NULL 安全）
SELECT d.dept_name FROM dept d
WHERE NOT EXISTS (SELECT 1 FROM emp e WHERE e.dept_id = d.dept_id);
-- → 财务部
```

> [!tip] `EXISTS` 天生适合"存在性"判断
> - **短路特性**：内层找到第一行就返回 `TRUE`，不再往下扫——所以"有没有"这类问题它很快。
> - **NULL 安全**：不像 `NOT IN` 会被 NULL 搞成空集（见 [[嵌套查询]] 第三章）。
> 找缺失、找"至少有一个"的写法，`NOT EXISTS` / `EXISTS` 是首选。

```sql
-- 等价写法对照（找"没员工的部门"）
-- ① NOT EXISTS（推荐）
WHERE NOT EXISTS (SELECT 1 FROM emp e WHERE e.dept_id = d.dept_id)
-- ② LEFT JOIN + IS NULL（反连接，也很常用）
FROM dept d LEFT JOIN emp e ON e.dept_id = d.dept_id WHERE e.emp_id IS NULL
-- ③ NOT IN + IS NOT NULL（要记得滤 NULL）
WHERE d.dept_id NOT IN (SELECT dept_id FROM emp WHERE dept_id IS NOT NULL)
```

> [!note] `EXISTS` 的"返回值"其实无所谓
> 内层写 `SELECT 1` / `SELECT *` / `SELECT NULL` 都一样，因为 `EXISTS` 只看"有没有行"，不看列。写 `SELECT 1` 是最省事、最不易错的约定。

## 五、经典场景 3：组内极值（每组最高工资的人）

"每个部门工资最高的人"是相关比较的另一个高频形态：

```sql
SELECT e.emp_name, e.dept_id, e.salary
FROM emp e
WHERE e.salary = (SELECT MAX(x.salary) FROM emp x WHERE x.dept_id = e.dept_id);
```

```
emp_name | dept_id | salary
---------+---------+--------
李四     |    1001 |  15000    <-- 研发部最高
王五     |    1002 |   9000    <-- 销售部最高
```

（孙七因 `dept_id` 为 NULL、内层 `MAX` 返回 `NULL` 而被排除。）

> [!note] "每组最大"的另外两种写法
> - 相关子查询：本节的写法，易读但**逐行执行**。
> - 窗口函数（8.0+）：`RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) = 1`，**一次扫描**完成。
> - 自连接：见 [[SELF JOIN]]，用 `a.salary < b.salary` 反查，可读性较差。
> 数据量大时优先窗口函数。

## 六、经典场景 4：`SELECT` 列表里的相关计数

相关子查询放在 `SELECT` 列表里，可以为每行算一个"随行变化"的附加值——比如"工资不高于我的人数"（一种排名）：

```sql
SELECT e.emp_name, e.salary,
       (SELECT COUNT(*) FROM emp x WHERE x.salary <= e.salary) AS 名次
FROM emp e
ORDER BY e.salary DESC;
```

```
emp_name | salary | 名次
---------+--------+------
李四     |  15000 |    5
张三     |  12000 |    4
王五     |   9000 |    3
赵六     |   8500 |    2
孙七     |   7000 |    1
```

> [!warning] 这其实是"轮子"——8.0 有窗口函数
> 上面的排名用 `RANK()` 一行搞定，且**只需扫一遍**：
> ```sql
> SELECT emp_name, salary, RANK() OVER (ORDER BY salary DESC) AS 名次 FROM emp;
> ```
> `SELECT` 列表里的相关子查询是"逐行执行"的典型，能用窗口函数就别手写。

## 七、性能：为什么慢，怎么优化

> [!danger] 相关子查询的代价 = 外层行数 × 内层代价
> 它天然是"外层每行都要跑一次内层"。外层 10 万行，内层哪怕每次 1ms，也是**100 秒**。

优化三招：

| 招式 | 做法 | 效果 |
| --- | --- | --- |
| ① 内层关联列**建索引** | `ALTER TABLE emp ADD INDEX idx_dept (dept_id)` | 内层从全表扫变成索引查找 |
| ② 改写成 `JOIN` | 相关子查询 → 派生表 + `JOIN` | 一次算完，避免逐行 |
| ③ 用**窗口函数** | `RANK() / AVG() OVER (...)` | 单次扫描，8.0+ 首选 |

把第三章的例子改写成 `JOIN`：

```sql
-- 相关子查询版（逐行）
SELECT e.emp_name FROM emp e
WHERE e.salary > (SELECT AVG(x.salary) FROM emp x WHERE x.dept_id = e.dept_id);

-- JOIN 版（一次性算出每组均值，再连）
SELECT e.emp_name
FROM emp e
JOIN (SELECT dept_id, AVG(salary) AS avg_sal FROM emp GROUP BY dept_id) t
  ON t.dept_id = e.dept_id
WHERE e.salary > t.avg_sal;
```

两者结果一致，但 `JOIN` 版**每组均值只算一次**。

> [!info] 优化器有时会替你"去相关"
> MySQL 优化器可能把某些 `EXISTS` / `IN` 相关子查询**改写成半连接（semi-join）**，效果接近手写 `JOIN`。
> 但**这不能指望**：一旦出现 `DEPENDENT SUBQUERY`（`EXPLAIN` 可见），就是真的逐行。**先 `EXPLAIN`，再决定要不要改写。**

## 八、相关子查询 vs `JOIN` vs 窗口函数

| 维度 | 相关子查询 | `JOIN` | 窗口函数（8.0+） |
| --- | --- | --- | --- |
| 可读性 | 贴近"逐行思考"，易写对 | 需想清连接/分组 | 声明式，最简洁 |
| 执行 | 外层每行 1 次 | 一次扫描（配合索引） | 一次扫描 |
| 适合规模 | 小表 | 中大表 | 中大表 |
| 典型用途 | 存在性、组内比较 | 取多列、批量关联 | 排名、组内均值、累计 |

> [!tip] 选择决策
> 1. 只是"有没有 / 是不是"→ `EXISTS` / `NOT EXISTS`（相关，短路快）。
> 2. 要"取另一张表的多列" → `JOIN`。
> 3. "组内排名 / 组内均值比较" → 优先**窗口函数**，其次相关子查询。
> 4. 拿不准就看 `EXPLAIN` 有没有 `DEPENDENT SUBQUERY`。

## 九、常见错误合集

> [!failure] 内层忘了引用外层列 → 变成非相关
> ```sql
> -- ❌ 本意"比本部门平均高"，却写成全表平均（内层没引用 e.dept_id）
> SELECT emp_name FROM emp e WHERE salary > (SELECT AVG(salary) FROM emp);
> ```
> 少写一个关联条件，语义从"组内"悄悄变成"全局"，**结果对不上却不报错**。

> [!failure] 引用的外层列是 NULL → 整行静默落选
> 孙七那类 `dept_id IS NULL` 的行，内层 `= NULL` 匹配不到 → 聚合得 `NULL` → 比较为 `UNKNOWN` → 被排除。需要保留时用 `IFNULL` 或单独处理。

> [!failure] `SELECT` 列表里塞相关子查询当"性能重灾区"
> 看着像加一列，实则逐行执行。取关联列用 `JOIN`，做排名用窗口函数。

> [!failure] 用 `NOT IN` 代替 `NOT EXISTS`
> 子查询含 NULL 时 `NOT IN` 恒为空集。见 [[嵌套查询]] 第三章。

## 十、速查表

| 需求 | 写法 |
| --- | --- |
| 判断相关与否 | 内层是否引用外层别名（能独立跑=非相关） |
| 组内比较 | `WHERE x > (SELECT AVG(..) FROM t WHERE t.g = outer.g)` |
| 存在性（有） | `WHERE EXISTS (SELECT 1 FROM t WHERE t.g = outer.g)` |
| 存在性（无） | `WHERE NOT EXISTS (...)` |
| 每组极值 | `WHERE x = (SELECT MAX(..) FROM t WHERE t.g = outer.g)` |
| 逐行附加值 | `SELECT (SELECT .. WHERE t.g = outer.g)`（慎用，考虑窗口函数） |
| 提速三招 | 建索引 / 改 `JOIN` / 用窗口函数 |
| 看是否逐行 | `EXPLAIN` 里是否有 `DEPENDENT SUBQUERY` |
