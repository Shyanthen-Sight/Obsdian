> 一句话：沙箱是==**给程序划出的一块"只能在这里折腾"的隔离区**==——代码在里面可以随便跑，但碰不到外面的文件、网络和系统。

## 是什么

- 英文 **sandbox**（也译作"沙盒"），名字来自小孩玩的沙坑：四周围一圈，随便挖，但沙子出不了圈
- 在计算机里，它指一种**隔离机制**：把程序以及它派生出的进程、文件、网络访问，限制在一个受控范围内
- 它要解决的核心问题只有一个：**这段代码不可信，但我又不得不让它跑**

### 沙箱的"围栏"到底管什么

一个沙箱通常从下面几个维度同时下手，任何一维漏了都可能被突破：

| 维度 | 限制方式 | 举例 |
| --- | --- | --- |
| 文件系统 | 只能看到 / 写入指定目录 | chroot、容器挂载、App 私有目录 |
| 网络 | 禁止联网，或只允许指定地址 | 离线分析、防火墙规则、代理白名单 |
| 系统调用 | 只放行白名单里的 syscall | seccomp、gVisor |
| 资源用量 | 限制 CPU、内存、磁盘、进程数 | cgroups、ulimit |
| 权限 | 降权运行，丢掉 root | 以 `nobody` 运行、capabilities |
| 生命周期 | 用完即毁，或快照回滚 | 一次性容器、虚拟机快照 |

- 一个合格的沙箱 = **隔离（isolate）+ 限制（restrict）+ 可观察 / 可回滚（observe / rollback）**
- 目标不是"让程序不能干坏事"，而是**"就算它干了坏事，也影响不到宿主"**

## 为什么需要沙箱

- **来源不可信**：下载的 exe、网页里的 JavaScript、用户上传的文件、第三方插件
- **恶意软件分析**：把样本放进去跑，观察它改了哪些文件、连了哪些地址，而分析机自己不会中招
- **软件测试 / 开发**：环境被弄脏了，删掉重来即可
- **多租户**：同一台机器上跑很多用户、很多应用，彼此不能看见
- **在线执行陌生人代码**：在线判题（OJ）、在线 IDE、AI 生成的代码要执行时
- **浏览器**：每个标签页都可能加载任意网站，天然需要把渲染进程关起来

## 沙箱的分层实现（从轻到重）

沙箱不是某一种具体技术，而是一类思路。按隔离发生在哪一层，可以分为下面几档：

| 层级 | 代表技术 | 隔离强度 | 开销 |
| --- | --- | --- | --- |
| 语言 / 运行时级 | JS 引擎、WebAssembly、JVM 安全管理器 | 弱 ~ 中 | 最小 |
| 进程 / 系统调用级 | seccomp、capabilities、chroot、macOS Seatbelt | 中 | 小 |
| 操作系统 / 容器级 | namespaces + cgroups、Docker、gVisor | 中 ~ 强 | 中 |
| 虚拟化级 | KVM、VirtualBox、VMware、Firecracker | 强 | 大 |
| 物理隔离 | 独立机器、气隙网络 | 最强 | 最大 |

### 语言 / 运行时级沙箱

- **浏览器**：JavaScript 本身拿不到文件系统 API；同源策略（Same-Origin Policy）限制跨站读取；`<iframe sandbox>` 属性可以进一步禁用脚本、表单、弹窗
- **WebAssembly**：代码跑在线性内存里，不能直接发起系统调用，一切能力都要由宿主显式导入
- **JVM**：曾经有 `SecurityManager` 做权限检查，但因设计缺陷已在 Java 17 标记废弃、Java 24 永久禁用
- **特点**：最轻量，启动几乎无成本；但围栏建立在运行时自己的正确性上——**解释器 / 引擎一个漏洞，围栏就整体失效**

### 操作系统 / 容器级沙箱

- **chroot**：把进程的"根目录"换到某个子树，让它看不到外面的文件
  - 注意：chroot 本身**不是安全边界**，有 root 权限的进程可以逃出去，它更多是"改变视角"
- **Linux namespaces**：让进程看到独立的 PID、网络、挂载点、用户、主机名等"世界"
  - 常见的有 `mnt`、`pid`、`net`、`ipc`、`uts`、`user`、`cgroup`、`time`
- **cgroups**：限制一组进程能用多少 CPU、内存、IO
- **seccomp / seccomp-bpf**：给系统调用装白名单，只允许程序真正需要的那几个
- **capabilities**：把 root 的全能权限拆成很多小块，按需授予
- **容器**：Docker / LXC 本质上就是 **namespaces + cgroups + 文件系统镜像** 的组合
  - 关键局限：**所有容器共享宿主机内核**，内核漏洞或配置失误都可能导致逃逸
- **移动端**：Android 每个应用一个独立 UID + SELinux；iOS 用 Seatbelt 沙箱 + entitlements 授权
- **桌面端**：Windows Sandbox、macOS App Sandbox、Flatpak（bubblewrap）、Snap（AppArmor）

### 虚拟化级沙箱

- 跑一台完整虚拟机，客户机里有自己的内核，与宿主机之间隔着 Hypervisor
- 恶意软件分析几乎都用这一层：**Cuckoo Sandbox**、在线沙箱（VirusTotal、Any.Run、Joe Sandbox 等）
- 配合**快照**：样本跑完，直接回滚到干净状态，反复分析
- 代价：启动慢、占资源多，但隔离强度明显高于容器
- 折中方案：**microVM**（Firecracker）和 **用户态内核**（gVisor、Kata Containers）——想要容器的轻量，又想要接近虚拟机的隔离

### 物理隔离

- 最彻底的沙箱：单独一台机器，甚至不接网络（气隙）
- 用来分析最危险的样本，或运行最不能出事的系统
- 缺点显而易见：贵、笨重、难以规模化

## 沙箱 vs 虚拟机 vs 容器

这三个词经常被混着用，关键差别在**隔离边界画在哪**：

| | 沙箱 | 容器 | 虚拟机 |
| --- | --- | --- | --- |
| 本质 | 一类"限制访问"的思路 | 共享宿主机内核的隔离进程组 | 完整模拟一台计算机 |
| 隔离边界 | 视实现而定 | 内核（namespace / cgroup） | Hypervisor / 硬件 |
| 是否共享内核 | 视实现而定 | **是** | 否 |
| 启动速度 | 快 | 秒级 | 数十秒 |
| 隔离强度 | 弱 ~ 强 | 中 | 强 |
| 典型用途 | 运行不可信代码 | 部署应用 | 跑不同操作系统、强隔离 |

- 关系不是并列的：**容器和虚拟机都可以被当作沙箱来用**，但"容器"强调打包部署，"虚拟机"强调完整模拟
- 判断一个东西是不是"沙箱"，看的不是它叫什么，而是**它限制了哪些能力、边界在哪**

## 沙箱逃逸：围栏也会被撞破

- **沙箱逃逸（sandbox escape）**：沙箱里的代码突破隔离，触碰到宿主系统
- 常见途径：
  1. **内核漏洞**：容器共享内核，内核提权漏洞 = 直接逃逸
  2. **运行时漏洞**：浏览器 JS 引擎的 bug，配合提权链突破渲染进程沙箱
  3. **配置错误**：`--privileged`、挂载 `docker.sock`、把宿主目录可写挂进容器——等于自己拆了围栏
  4. **侧信道**：Spectre / Meltdown 一类 CPU 漏洞，能跨隔离读到不该读的内存
  5. **沙箱软件自身的漏洞**：隔离层也是代码，也会写错
- 结论：**沙箱是"降低风险"，不是"消除风险"**
- 高风险场景的正确做法是**纵深防御**：沙箱 + 最小权限 + 网络隔离 + 快照回滚 + 监控告警，多层叠加

## 常见误区

- **"容器就是沙箱，所以绝对安全"** —— 容器共享宿主机内核，隔离强度取决于配置，默认配置并不等于安全边界
- **"用了沙箱就不用管权限了"** —— 沙箱内部仍应遵循最小权限，否则逃逸后的破坏面会更大
- **"沙箱 = 备份 / 快照"** —— 快照是沙箱常用的一种手段，但沙箱的核心是访问限制
- **"浏览器 sandbox 属性 = 完整安全"** —— 它只是限制 iframe 的部分能力，不等于进程级沙箱
- **"沙箱能挡住所有恶意代码"** —— 它提高的是攻击成本，不是提供绝对保证

## "沙箱"这个词的其他含义

同一个词在不同语境下指代不同东西，读文档时要注意区分：

- **支付 / 第三方 API 沙箱**：一套模拟环境，用假数据联调，不碰真实资金和用户
- **开发沙箱环境**：与生产隔离的测试环境
- **游戏沙箱（sandbox game）**：开放世界、自由玩法的游戏类型，和"隔离"已经关系不大
- **AI 代码执行沙箱**：让模型生成的代码在受限容器里运行，防止误伤宿主

## 一句话记忆

- 沙箱的本质：**画一个圈，让不可信的代码在圈里跑**
- 圈的强度取决于边界画在哪：运行时 < 系统调用 < 容器 < 虚拟机 < 物理隔离
- 圈再结实也可能被撞破，所以真正可靠的是**多层防御 + 最小权限**
