# 命名空间

宿主机上 `ps -ef` 能看到容器进程，它们和普通进程没区别，只是挂在不同命名空间里。命名空间是内核对全局资源的包装：同一类资源被拆成多份，每个进程只看到自己所属的那份。它改的是“视野”，不是“权限”。

内核里每个进程通过 `nsproxy` 指向自己所属的一组命名空间。`clone()` 带上 `CLONE_NEW*` 标志会为新进程新建命名空间，`unshare()` 则把当前进程移进新的命名空间。Docker 调用的就是这两个系统调用，封装在 runc 里。

## 八种命名空间

| 类型 | 隔离的内容 | 引入版本 | Docker 默认 | Docker 开关 |
| --- | --- | --- | --- | --- |
| mnt | 挂载点表、根目录 | 2.4.19 | 是 | 无单独开关；`--privileged` 可绕过 |
| pid | 进程号、`/proc` 里的进程视图 | 2.6.24 | 是 | `--pid=host`、`--pid=container:web` |
| net | 网卡、路由表、端口、iptables | 2.6.24 | 是 | `--network=host`、`--network=container:web`、`--network=none` |
| ipc | SysV 共享内存、信号量、消息队列 | 2.6.19 | 是 | `--ipc=host`、`--ipc=container:web` |
| uts | hostname、domainname | 2.6.19 | 是 | `--hostname`、`--uts=host` |
| user | UID/GID 映射 | 2.6.23 | 否（rootless、userns-remap 时启用） | `--userns=host`、rootless |
| cgroup | cgroup 根路径视图 | 4.6 | cgroup v2 下是 | `--cgroupns=host` / `private` |
| time | 系统时钟偏移 | 5.6 | 否 | 无（CRIU 等场景用） |

“默认”指的是常规 Linux 上的 Docker Engine；rootless、Docker Desktop 和 Kubernetes 的配置可能不同，以 `lsns` 的实际输出为准。

## 怎么观察

```bash
lsns | head -4
#        NS TYPE  NPROCS   PID USER COMMAND
# 4026531836 pid      214     1 root /sbin/init
# 4026532320 net        3  9341 root nginx: master process
```

同一 TYPE 下编号不同就说明不共享。也可以直接看进程的 `ns` 目录：

```bash
PID=$(docker inspect -f '{{.State.Pid}}' web)
ls -l /proc/1/ns /proc/"$PID"/ns
readlink /proc/"$PID"/ns/net
```

`/proc/<pid>/ns/*` 里的数字是命名空间 inode。两个进程的同一项 inode 相同，就说明它们共享该命名空间；不同则说明隔离。容器进程的 net、mnt、uts、ipc、pid 编号通常都和宿主机 1 号进程不同；user 命名空间要 rootless 或 `--userns-remap` 才会分叉。

## 手动隔离一次

```bash
sudo unshare --fork --pid --mount-proc bash
ps -ef
#   1 root 0:00 bash
#   2 root 0:00 ps -ef
echo $$        # 1
exit

sudo unshare -n sh -c 'ip link set lo up; ip addr'
# 只有 lo，且刚创建时是 down 的
sudo unshare -u sh -c 'hostname demo; hostname'    # demo
unshare --user --map-root-user id                  # uid=0(root)，仅在这个命名空间里
```

- `--fork` 先进新命名空间再 fork，否则 bash 仍是原 PID。
- `--mount-proc` 重挂 `/proc`，`ps` 才只看得到新空间里的进程；不重挂会读到旧的 `/proc`，看到宿主机全部进程。
- `unshare -n` 的 lo 默认是 down 的，要 `ip link set lo up`。
- `--user --map-root-user` 不需要 root 就能建用户命名空间，但部分发行版默认禁用非特权 user namespace，遇到 `Operation not permitted` 先查 `sysctl kernel.unprivileged_userns_clone`。

## PID：1 号进程就是应用

PID 命名空间让容器里的进程只看到同一空间内的进程，所以入口命令拿到了 PID 1。宿主机上它仍然是普通 PID，`docker top` 看到的是宿主机视角：

```bash
docker run -d --name web nginx
docker top web
# UID  PID   PPID  CMD
# root 9341  9320  nginx: master process
```

两个直接后果：

- **1 号进程不享受普通进程的信号默认行为**。内核只把带处理函数的信号投递给 PID 1，默认动作（终止、终止并 core）会被忽略。应用没装 SIGTERM 处理器时，`docker stop` 会一直等到超时，最后被 SIGKILL，退出码 137。
- **1 号进程要负责回收孤儿进程**。应用不处理 `SIGCHLD` 时，孙进程退出后会堆成 `<defunct>`。用 `docker run --init` 会插入 tini/dumb-init 当 PID 1，由它转发信号并回收。

`--pid=host` 让容器看到宿主机进程列表，排查网络、抓包、看 `ps` 时方便，但等于拆掉一层隔离，不建议用在长期运行的服务上。`--pid=container:web` 则加入另一个容器的 PID 空间，适合 sidecar 观察主容器。

从宿主机可以对容器进程直接发信号，因为调度和信号都发生在同一个内核里：

```bash
kill -TERM "$(docker inspect -f '{{.State.Pid}}' web)"
sudo nsenter -t "$PID" -p ps -ef
```

## NET：每个容器一套网络栈

NET 命名空间给容器独立的网卡、路由表、端口空间和 iptables 视图。Docker 默认的 bridge 网络会给每个容器建一对 veth：一端在容器里（通常叫 `eth0`），另一端挂在宿主机的 `docker0` 网桥上。

```bash
docker network inspect bridge --format '{{json .Containers}}' | jq
ip link show docker0
```

端口映射不是“容器直接监听宿主机端口”，而是转发：

```bash
docker run -d -p 8080:80 nginx
sudo ss -lntp | grep 8080     # 通常看到 docker-proxy，而不是 nginx
sudo iptables -t nat -L DOCKER -n
```

实现上通常有两条路径：iptables/nftables 的 DNAT 规则负责多数流量，`docker-proxy` 负责本机访问和 hairpin NAT 等边角情况。所以排查端口问题时，既要看容器内 `ss -lntp`，也要看宿主机规则和防火墙（`DOCKER-USER` 链）。

几个常用模式：

- `--network=host`：容器直接复用宿主机网络栈，省掉 NAT，性能好一点；代价是端口冲突，且 `-p` 会被忽略。
- `--network=container:web`：共享另一个容器的网络栈，适合 sidecar；两个容器不能各自再发布同一端口。
- `--network=none`：只有 loopback，适合离线任务和沙箱实验。
- 自定义 bridge：自带内嵌 DNS `127.0.0.11`，容器之间可以用服务名互相访问；默认 bridge 没有这个能力。

在 Docker Desktop 上，容器访问宿主机用 `host.docker.internal`，因为中间隔着一层 Linux 虚拟机；Linux 上则可以直接用 `--network=host` 或网关地址。

## MNT：根文件系统和挂载表

MNT 命名空间给容器独立的挂载点表。容器启动时，runc 把镜像层叠加成 rootfs，用 `pivot_root` 把进程的根切过去，再把旧根卸载。之后 Docker 还会挂入一批东西：

- `/proc`、`/sys`、`/dev`、`/dev/pts`、`/dev/mqueue`、`/dev/shm`
- `/etc/hosts`、`/etc/resolv.conf`、`/etc/hostname`（从宿主机文件绑定）
- 只读的 `/proc/sys`、`/proc/sysrq-trigger`、`/proc/kcore` 等敏感路径（masked / read-only paths）

```bash
PID=$(docker inspect -f '{{.State.Pid}}' web)
sudo cat /proc/"$PID"/mountinfo | head
sudo nsenter -t "$PID" -m findmnt | head
```

挂载传播默认是 `rprivate`：容器里新挂的东西不会传播回宿主机，宿主机新挂的也不会进容器（除非显式配置 `rshared`）。绑定挂载是把宿主机目录直接挂进容器的挂载表，绕过了 overlay，所以性能接近原生，也让容器能改宿主机文件。

`docker exec` 能“进容器”，靠的是 `setns` 进入目标进程的 mnt、pid、net、ipc、uts 命名空间再 fork 一个进程；它不新建命名空间，也不改容器的 rootfs。`--privileged` 则相反，它会去掉大部分限制，允许容器挂载宿主机目录、访问设备，隔离基本失效。

## UTS 与 IPC

UTS 命名空间只管 `hostname` 和 `domainname`：

```bash
docker run --rm --hostname demo alpine hostname    # demo
```

`--uts=host` 让容器共享宿主机 hostname，容器里改 hostname 会影响宿主机，一般只在特殊调试时用。

IPC 命名空间隔离 SysV 共享内存、信号量和消息队列，也隔离 `/dev/shm`。Docker 默认给 `/dev/shm` 64MB，PostgreSQL、Chrome、部分机器学习库会报共享内存不足：

```bash
docker run --rm --shm-size=1g postgres:16 df -h /dev/shm
docker run --rm --ipc=host alpine ipcs
```

`--ipc=container:web` 让两个容器共享 IPC，适合主容器和 sidecar 通过共享内存通信；`--ipc=host` 则直接暴露宿主机的 IPC 资源。

## USER：UID 映射

默认情况下 Docker **不启用** user 命名空间，容器里的 uid 0 在宿主机上也是 uid 0。之所以看起来“没那么危险”，是因为 capabilities、seccomp 和挂载限制收紧了它能做的事，而不是因为 uid 被映射走了。

启用之后，映射关系写在 `/proc/<pid>/uid_map`：

```bash
cat /proc/"$PID"/uid_map
#          0       1000          1
```

两种常见形态：

- **userns-remap**：dockerd 配置 `"userns-remap": "default"`，容器 uid 0 映射到宿主机 subordinate UID（通常是 100000 起）。绑定挂载的文件属主会显示成 `100000:100000`，宿主机普通用户反而改不了。
- **rootless**：整个 dockerd 跑在一个用户命名空间里，容器 uid 0 映射到当前用户自己的 uid，其他 UID 用 `/etc/subuid` 分配。文件属主通常还是你自己，但网络、端口、cgroup 权限都受限制。

代价要提前算：卷的属主、NFS 挂载、需要特权的镜像、`ping` 所需的 `ping_group_range`、以及依赖 `CAP_SYS_ADMIN` 的工具，都可能出问题。收益是容器逃逸后拿到的不是宿主 root，而是无特权用户。

## Cgroup 与 time

cgroup 命名空间只影响“能看到哪棵 cgroup 树”。cgroup v2 下 Docker 默认给容器私有视图，容器里读 `/sys/fs/cgroup` 看到的是自己的子树，而不是宿主机整棵树；在容器里跑 systemd 时通常需要 `--cgroupns=host`，否则 systemd 找不到预期的层级。

time 命名空间允许调整进程看到的时钟偏移（`/proc/<pid>/timens_offsets`），主要用于 CRIU 做检查点恢复和测试时间相关逻辑。Docker 默认不启用，普通容器里不需要关心。

## docker exec 和 nsenter

`docker exec` 的底层是 `setns`：进入目标容器的命名空间，再执行命令。所以它看到的是容器的进程树、网卡和根目录，而不是宿主机的。

不使用 Docker CLI 时，可以用 `nsenter` 达到同样效果：

```bash
PID=$(docker inspect -f '{{.State.Pid}}' web)
sudo nsenter -t "$PID" -n ss -lntp          # 只看网络命名空间
sudo nsenter -t "$PID" -m -p -n sh          # 进入 mnt、pid、net
sudo nsenter -t "$PID" -a sh                # 进入全部命名空间
```

排查网络时这个组合最有用：宿主机上 `ss` 看不到容器内监听端口，`nsenter -n` 进去就能看到；反过来，容器里看不到宿主机的连接，也是同一原因。

> [!warning] 隔离不是安全边界
> 命名空间只改“看得见什么”，不改权限模型。`--privileged`、挂载宿主目录、暴露 `/var/run/docker.sock`、共享 PID 命名空间，都可能让容器拿到宿主机 root 或等价能力。真正要跑不可信代码，还要配合 user 命名空间、capabilities 裁剪、seccomp/AppArmor，必要时直接用虚拟机、gVisor 或 Kata。详见 [[02-运行时安全|运行时安全]]。

## 常见现象对照

| 现象 | 原因 | 验证方式 |
| --- | --- | --- |
| 容器里 `ps` 只有几个进程 | PID 命名空间隔离 | `lsns -p <PID>` |
| 容器里连不上宿主机的服务 | NET 命名空间独立，`localhost` 指容器自己 | `nsenter -n ss -lntp`，或用 `host.docker.internal` |
| 宿主机 `ss` 看不到容器监听端口 | 端口在容器的 NET 命名空间里 | `nsenter -t <PID> -n ss -lntp` |
| 端口映射不生效 | NAT 规则、防火墙、`--network=host` 忽略 `-p` | `docker port`、`iptables -t nat -L` |
| 容器 hostname 和宿主机不同 | UTS 命名空间 | `hostname`、`--uts=host` |
| `/dev/shm` 太小导致数据库报错 | IPC 命名空间默认 64MB | `--shm-size=1g` |
| 容器里 root 能改宿主文件 | user 命名空间默认未启用 | `cat /proc/<PID>/uid_map` |
| `docker exec` 进去看不到某个进程 | 该进程在另一个 PID 命名空间 | `--pid=container:<name>` 或 `nsenter` |
| 容器里 systemd 起不来 | cgroup 命名空间或 cgroup v2 限制 | `--cgroupns=host`，检查 cgroup 版本 |
