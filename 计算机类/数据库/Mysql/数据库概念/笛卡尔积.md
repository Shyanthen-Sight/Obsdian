# 笛卡尔积（Cartesian Product）

> [!abstract] 一句话
> 笛卡尔积就是==两张表所有行的"两两组合"==，行数是**相乘**不是相加（m × n），列数是两表列数之和。
> 它是连接运算的**原材料**——内连接 = 笛卡尔积 + 筛选，而"漏写连接条件"就是让笛卡尔积直接暴露在结果里的灾难。

---

## 一、数学定义

设 A、B 是两个集合，则笛卡尔积：
```
A × B = { (a, b) | a ∈ A, b ∈ B }
```


- 结果是一个==有序对==的集合，每个 `a` 与每个 `b` 恰好配对一次
- ==元素个数 = |A| × |B|==（相乘）
- **不满足交换律**：`A × B ≠ B × A`（有序对不同），但元素个数相同
- 命名来自笛卡尔（Descartes），本质是"坐标"思想：A 是 x 轴、B 是 y 轴，所有交叉点就是全部组合

> [!example] 小例子
> A = `{ 1, 2 }`，B = `{ x, y, z }`
> A × B = `{ (1,x), (1,y), (1,z), (2,x), (2,y), (2,z) }` → 2 × 3 = **6 个**

---

## 二、数据库中的笛卡尔积

在关系数据库里，一张表就是元组的集合，所以两张表直接"拼"起来就是笛卡尔积：

> [!important] 两个公式
> - **结果行数** = 表1行数 **×** 表2行数
> - **结果列数** = 表1列数 **+** 表2列数

沿用 [[Join]] 里的 `dept`（3 行 2 列）和 `emp`（5 行 4 列）举例：

```sql
SELECT * FROM dept CROSS JOIN emp;

-- 完全等价的老写法（逗号连接，不写任何条件）
SELECT * FROM dept, emp;
```

结果 = 3 × 5 = **15 行**、2 + 4 = **6 列**，每个部门 × 每个员工的全部组合：

```
dept_id | dept_name | emp_id | emp_name | dept_id | salary
--------+-----------+--------+----------+---------+--------
   1001 | 研发部    |      1 | 张三     |    1001 |  12000
   1001 | 研发部    |      2 | 李四     |    1001 |  15000
   1001 | 研发部    |      3 | 王五     |    1002 |   9000
   1001 | 研发部    |      4 | 赵六     |    1002 |   8500
   1001 | 研发部    |      5 | 孙七     |    NULL |   7000
   1002 | 销售部    |      1 | 张三     |    1001 |  12000
   1002 | 销售部    |      2 | 李四     |    1001 |  15000
   ...（共 15 行，1001 / 1002 / 1003 各 5 行）
```

> [!warning] 大部分行是"无意义"的
> 上面 15 行里，只有 `dept.dept_id = emp.dept_id` 的那 **4 行**有真实语义（张三、李四 → 研发部；王五、赵六 → 销售部）。
> 剩下 11 行只是纯粹的组合——==它们是连接的"中间产物"，正常情况下必须被连接条件筛掉==。

## 三、什么时候会"意外"产生笛卡尔积（危险）

| 写法                                 | 结果     | 报错吗                            |
| ---------------------------------- | ------ | ------------------------------ |
| `FROM a CROSS JOIN b`              | 笛卡尔积   | ❌ 不报错（**故意的**）                 |
| `FROM a, b`（逗号连接，不写 `WHERE`）       | 笛卡尔积   | ❌ 不报错（**漏了**）                  |
| `FROM a JOIN b`（不写 `ON`）           | 笛卡尔积   | ❌ 不报错（MySQL 允许 `JOIN` 省略 `ON`） |
| `FROM a JOIN b ON a.x = b.y`（字段写错） | 接近笛卡尔积 | ❌ 不报错（**写错了**）                 |

> [!danger] 最坑的一点：全部**静默通过**
> 上面四种语法**全都合法**，只有结果行数暴涨。==行数是唯一的警报信号==——一旦看到结果行数明显多于预期，第一反应就该是"回去检查连接条件"。

## 四、笛卡尔积与连接的关系（本节最重要）

这是理解笛卡尔积价值的关键角度：

> [!important] 关系代数里的定义
> **内连接（θ 连接）= 笛卡尔积 + 选择（筛选）**
>
> ```
> R ⋈_θ S = σ_θ ( R × S )
> ```
> 先把 `R × S` 的**全部组合**算出来，再按条件 `θ` 挑出满足的行。

于是有这条链：

```
笛卡尔积（15 行）  ── 按连接条件筛选 ──▶  内连接（4 行）
```

由此推出三条结论：

- 隐式连接 `FROM a, b WHERE a.x = b.y` 是**字面照做**这个定义：先乘、再筛
- 显式 `JOIN ... ON` 只是**语法糖 + 优化**，语义完全相同（见 [[Join]] 第三章）
- ==连接条件一旦不写，得到的就是那个没被筛选的、原始的笛卡尔积==

## 五、危害：为什么必须避免

> [!danger] 行数是指数级爆炸，不是线性增长
> 两表相乘，多表连乘：

| 组合 | 行数 |
| --- | --- |
| 表 A（1 万行） | 10,000 |
| 表 A × 表 B（各 1 万行） | ==1 亿== |
| 表 A × B × C（各 1 万行） | ==1 万亿== |

具体后果：

1. **结果错误**：数据完全不是业务要的语义，直接污染报表和分析结论
2. **性能崩塌**：中间结果集巨大，内存 / 磁盘临时表被撑爆，`join_buffer` 装不下
3. **拖垮数据库**：一条 SQL 把 IO、CPU、内存吃满——==生产环境"一条慢查询打挂库"的经典事故==
4. **难以察觉**：小表测试时（3 × 5 = 15）看着"还行"，一上大数据量表就雪崩

> [!warning] 三表全表连接的典型翻车
> `SELECT * FROM a, b, c WHERE a.id = b.aid;`
> 漏了 `b` 与 `c` 的连接条件，`c` 直接被卷进笛卡尔积，行数从预期几万**变成上亿**。

## 六、什么时候**故意**用笛卡尔积

笛卡尔积本身只是个运算，**不是错误**，用对地方很有价值：

| 场景 | 做法 |
| --- | --- |
| **生成组合 / 骨架** | 日期表 × 部门表 → "每个部门 × 每一天"，再 LEFT JOIN 真实数据补 0 |
| **枚举数字序列** | `digits`(0~9) 自交叉两次 → 0~99，三次 → 0~999 |
| **造测试数据** | 小表 × 小表，快速生成一大批样本 |
| **交叉表 / 矩阵报表** | 行维度 × 列维度 |
| **求两表全部差异** | 严格说这是 FULL OUTER JOIN 的用途（见 [[Join]] 第八章） |

> [!tip] 关键词：**做骨架**
> 正经用法几乎都是"**先用笛卡尔积造出一个"完备的骨架"，再用 `LEFT JOIN` 把真实数据填进去**"。
> 例：最近 30 天 × 10 个门店的销售报表，要保证"没卖货的店 / 没开张的天"也能出现在表里。

---

## 七、怎么避免 / 排查

> [!success] 五条实用准则
> 1. **禁止逗号连接**：一律显式 `JOIN ... ON`，团队规范里最常见的一条
> 2. **`JOIN` 必须写 `ON`**：MySQL 允许省略，但那是灾难，很多团队用 SQL 规范工具（如 SQLFluff）卡住
> 3. **核对结果行数**：查询前先估一下预期量级
> 4. **写复杂查询前先画连接图**：确认每张表都是"通过某个字段"接到链上的，没有孤立参与的表
> 5. **`EXPLAIN` 看 `rows` 列**：若某步估算行数是两表行数的乘积量级，说明连接条件失效了

> [!question] 面试常问
> **Q：怎么判断一条 SQL 产生了笛卡尔积？**
> > 看结果行数是否等于参与连接各表行数的**乘积**；看是否有表**没有连接条件**；`EXPLAIN` 里 `type=ALL` 且 `rows` 异常大。
>
> **Q：笛卡尔积和交叉连接（`CROSS JOIN`）是一回事吗？**
> > 是的。`CROSS JOIN` 就是显式的笛卡尔积运算，两者在关系代数里是同一个东西。
>
> **Q：为什么 NULL 匹配不上，容易产生多余行？**
> > `NULL = 任何值` 结果是 `NULL`（未知），连接条件只认 `TRUE`，所以外键为 NULL 的行在等值连接里**永远匹配不上**——这是三值逻辑的必然结果（见 [[Join]]）。

## 八、速查

| 问题      | 答案                                     |     |
| ------- | -------------------------------------- | --- |
| 结果行数    | 表1行数 **×** 表2行数（n 张表就连乘）               |     |
| 结果列数    | 各表列数 **之和**                            |     |
| 数学符号    | `R × S`                                |     |
| 对应 SQL  | `CROSS JOIN` / 逗号连接 / 漏写 `ON` 的 `JOIN` |     |
| 与内连接的关系 | ==内连接 = 笛卡尔积 + 筛选==（`σ_θ(R × S)`）      |     |
| 危害      | 行数指数爆炸、结果错误、拖垮数据库                      |     |
| 正确用途    | 造骨架、枚举序列、造测试数据                         |     |
| 如何避免    | ==显式 `JOIN` + 必须写 `ON` + 核对行数==        |     |
