

> [!abstract] 一句话定义
> QA 思维是一种==以风险为导向、以证伪为目标、从用户与系统视角审视产品==的思考方式。它的起点不是"我觉得这里没问题"，而是"**如果这里有问题，会是什么问题？**"

---

## 一、测试思维 vs 开发思维

| 维度 | 开发思维 | 测试思维 |
|---|---|---|
| 目标 | 让功能**能工作** | 找出功能**在什么情况下不工作** |
| 路径 | 正向、happy path | 逆向、边界、异常、破坏 |
| 假设 | 输入合法、环境正常 | 输入可能非法、环境可能异常 |
| 抽象 | 抽取共性、复用 | 关注差异、特例、组合 |
| 成功标准 | 代码跑通、需求实现 | 风险被覆盖、缺陷被发现 |
| 心态 | 建设性 | 批判性 + 建设性 |

> [!note] 不是对立，而是互补
> 开发思维帮助系统被**构建出来**，测试思维帮助系统被**信任**。好的测试人员也要有开发思维，否则设计不出可执行的验证；好的开发也要有测试思维，否则写不出可测、健壮的代码。

## 二、六个核心思维

### 1. 证伪思维（Falsification）

波普尔：**一个理论无法被证实，只能被证伪**。测试同理：

- 测试通过 ≠ 没有缺陷，只说明"在这组输入和环境下没发现缺陷"。
- 测试的价值在于**不断尝试推翻"系统是正确的"这一假设**。
- 因此要问：**什么样的输入最可能让它失败？**

### 2. 风险思维

资源永远有限，测试不是"全都测一遍"，而是**把有限的资源投向最可能出问题、出问题代价最大的地方**。

- **可能性**：复杂度、变更频率、新技术、依赖、历史缺陷。
- **影响**：业务价值、用户量、资金、安全、合规、不可逆性。
- 详见 [[测试优先级分配]]。

### 3. 用户思维（同理心）

- 用户不会按你的用例操作：会误点、会重复提交、会断网、会用奇怪的数据。
- 问：**谁会用？在什么场景用？他真正想完成什么？**
- 关注**任务完成**，而非仅仅"按钮能点"。

### 4. 系统思维

- 不只看单个功能，还要看**数据流、状态、依赖、时序、并发、失败传播**。
- 一个功能"单独测没问题"，组合起来可能出问题。
- 关注：上下游契约、缓存、异步、重试、幂等、事务、权限边界。

### 5. 批判性思维

- 需求文档可能自相矛盾、遗漏、不可测试。
- 开发说"这是框架行为"不等于"这是正确行为"。
- 对**假设**保持敏感：默认值、时区、字符集、精度、权限、排序稳定性。

### 6. 经济思维

- 测试是投资，存在**边际收益递减**。
- 不是所有缺陷都值得修，也不是所有路径都值得测。
- 目标是"**足够好**"，而非"数学意义上的完备"。

## 三、可操作的思考习惯（启发式）

### 3.1 从六个维度扫描（SFDPOT）

| 维度 | 问什么 | 例子 |
|---|---|---|
| **S**tructure 结构 | 系统由什么组成？ | 模块、接口、数据表、依赖 |
| **F**unction 功能 | 它能做什么？ | 增删改查、计算、导入导出 |
| **D**ata 数据 | 处理什么数据？ | 空值、超长、特殊字符、精度、编码 |
| **P**latform 平台 | 跑在什么环境？ | 浏览器、系统、设备、数据库版本 |
| **O**perations 操作 | 用户如何操作？ | 重复点击、刷新、回退、并发 |
| **T**ime 时间 | 时间相关行为？ | 超时、时区、夏令时、定时任务、跨天 |

### 3.2 边界与极值

- 0、1、多；空、满、超限。
- 最小/最大值、刚好越界、类型边界、长度边界。
- 空字符串 vs null vs 全空格；负数、零、小数、超大数。

### 3.3 状态与时序

- 合法状态迁移 / 非法状态迁移。
- 重复提交、乱序到达、中途取消、超时重试、并发修改。
- 刷新/后退/多标签页/多端同时操作。

### 3.4 异常与失败路径

- 依赖不可用、网络抖动、磁盘满、权限不足、第三方超时。
- **部分成功**如何处理？是否可重试？是否幂等？是否留下脏数据？

### 3.5 组合与交互

- 单因素都正常，组合起来是否正常？
- 参数组合爆炸时用**成对测试/正交实验**（见 [[测试方法]]）。

### 3.6 "测试四问"

面对任何功能，至少问：

1. **如果……会怎样？**（异常、极端、非法）
2. **谁会用、怎么用？**（真实场景）
3. **它在什么条件下不成立？**（假设与前提）
4. **最坏情况是什么？**（影响与恢复）

### 3.7 其他常用启发式

- **HICCUPPS**：History（历史）、Image（品牌形象）、Comparable products（竞品）、Claims（宣称）、User expectations（用户预期）、Product（产品自身一致性）、Purpose（目的）、Standards（标准/法规）。
- **3 的法则**：0、1、多。
- **CRUD**：增删改查是否都覆盖。
- **黄金路径 + 替代路径 + 异常路径**。

## 四、常见思维偏差

| 偏差 | 表现 | 对策 |
|---|---|---|
| 确认偏误 | 只找支持"没问题"的证据 | 主动设计反例；红队评审 |
| 乐观偏差 | "这个很简单，不会出错" | 用检查表强制覆盖异常路径 |
| 正常化偏差 | 看到异常但觉得"一直这样" | 记录并追问预期行为 |
| 权威偏差 | 开发/文档说的就是对的 | 以实际行为与需求为准 |
| 可得性偏差 | 只测熟悉、容易想到的场景 | 用启发式清单扩展视角 |
| 锚定效应 | 被第一版用例框住 | 换人、换视角重设计 |
| 后见之明 | 出事后觉得"早就该想到" | 复盘时关注流程而非个人 |
| 群体思维 | 团队都认为没问题 | 引入外部评审、独立测试 |

## 五、如何训练

1. **刻意练习**：拿一个简单功能（登录、搜索、购物车），限时列出 30 个可能的失败场景。
2. **缺陷模式库**：积累自己遇到的 bug，归纳成检查表。
3. **读需求时提问**：把每条需求改写成"在什么条件下会失败"。
4. **探索性测试**：固定时间盒，边学习边设计边执行，记录发现。
5. **复盘**：每个线上问题都问"哪个测试思维缺口导致它逃逸？"
6. **跨界学习**：看用户支持记录、运维事故、竞品缺陷。
7. **结对测试**：两个人不同视角，互相挑战假设。

> [!tip] 思维的产物是"问题"
> 好的 QA 思维最终会表现为一串高质量的问题：**这个字段为空会怎样？并发提交两次会怎样？依赖超时会怎样？权限边界在哪里？数据删除了还能恢复吗？**

## 六、思维与方法的区别

- **思维**决定"**测什么、为什么测、优先测哪里**"。
- **方法**决定"**怎么设计用例、怎么执行、怎么判定**" → [[测试方法]]。
- 没有思维的方法只是机械执行；没有方法的思维无法落地。
