# Fast-Forward vs Non-FF —— 合并出来的历史长什么样

> [!abstract] 一句话
> ==合并分支时，Git 有两个选择：**直接把指针往前挪（Fast-forward）**，还是**生成一个双父的合并提交（Non-FF / 三方合并）**==。前者让历史变成一条直线、看不出分叉；后者在历史里留下一个"合并节点"，看得出一条分支曾被并进来。选哪个，本质是"历史要好看，还是要好读"。

> [!note] 先读这篇的前提
> 合并的**方向、冲突、基本命令**见 [[合并基础]]。本篇只聚焦一件事：**为什么同样的 `merge`，有时产生新提交、有时不产生**，以及如何用选项和配置去控制它。

---

## 一、一张图看懂两种形态

```text
【Fast-forward（快进）】—— 没有分歧

    A ── B ── C          A ── B ── C
              ↑      →            ↑
             main              main, feature
            （feature 领先）    （main 直接追上，无新提交）

【Non-FF / 三方合并】—— 各有各的提交

    A ── B ── C          A ── B ── C ── M
    │            →       │            /
    D ── E               D ── E ─────
   （两条线分叉）        （M 是双父的合并提交）
```

> [!info] 判定的唯一标准
> 站在当前分支看：**当前分支有没有"目标分支没有的提交"**？
> - 没有（只是落后）→ 能快进 → 默认快进，**不产生新提交**。
> - 有（真的分叉了）→ 必须三方合并 → **产生合并提交**。

---

## 二、Fast-forward（快进）

### 2.1 发生的条件

当前分支是目标分支的**祖先**：目标分支在分叉后一路前进，当前分支原地没动。此时合并"只是把标签往前移一格"。

```bash
git switch main
git merge feature        # 若 main 上没有独有提交 → 输出 "Fast-forward"
```

输出会明确写着：

```text
Updating a1b2c3d..e4f5g6h
Fast-forward
 file.txt | 2 ++
```

### 2.2 优点与代价

| | 说明 |
|---|---|
| ✅ 历史是**直线**，`git log` 清爽无分叉 | |
| ✅ 不产生额外提交，节点数最少 | |
| ❌ **看不出"这里曾有过一条 feature 分支"** | 分叉和汇合被抹平了 |
| ❌ 想**整体回滚**这次合并时，没有单一节点可 revert | 得逐个 revert 那批提交 |

> [!warning] 快进会"丢失"分支存在的痕迹
> 快进之后，`feature` 和 `main` 指向同一个提交，你完全看不出中间曾经并行开发过。
> 对"想知道某功能是哪次合并进来的"这种诉求，快进是不利的。

---

## 三、Non-FF（三方合并）

### 3.1 发生的条件

当前分支和目标分支**各自都有对方没有的提交**（真的分叉了）。Git 找到共同祖先，做三方合并，生成一个**有两个父提交**的新提交 `M`：

```text
      A ── B ── C ── M   ← main（新提交）
      │            /
      D ── E ─────        ← feature
```

### 3.2 合并提交的特殊之处

- `M` 的 parent 有**两个**哈希（`C` 和 `E`），这是它区别于普通提交的唯一标志。详见 [[提交]]。
- `M` **本身不引入任何代码改动**（除非解决冲突时你手动改了），它只是把两条线"缝"在一起。
- 因为留了节点，`git log --graph` 能画出那个分叉口；**整体回滚**时 `git revert -m 1 M` 一行搞定。

> [!tip] 为什么团队偏爱它
> 有了 `M`，历史变成"主干 + 一个个功能汇入点"的故事。想理解某功能、想回滚某功能，都从 `M` 入手，不用在长长一串提交里翻找。

## 四、控制形态的三个选项

```bash
git merge feature            # 默认：能快进就快进（受 merge.ff 配置影响）
git merge --ff feature       # 显式要求：能快进就快进
git merge --no-ff feature    # ★ 即使能快进，也强制生成合并提交
git merge --ff-only feature  # 只允许快进；若有分歧则报错退出，绝不自动合并
```

> [!info] 三个选项的语义
> - `--ff`（默认）：有快进就快进，否则三方合并。
> - `--no-ff`：**永远产生合并提交**——这才是"我要在历史里留下这条分支"的表达。
> - `--ff-only`：**拒绝三方合并**。适合"我确信应该快进，若不是就说明我漏拉了"的场合，出错即停，避免意外合并。

```bash
# --ff-only 的典型用法：更新本地 main 时，宁可报错也不要莫名分叉
git switch main
git pull --ff-only
```

## 五、把偏好写进配置：merge.ff

不想每次敲 `--no-ff`，可以设默认值：

```bash
git config --global merge.ff false   # 默认等同 --no-ff：每次合并都留节点
git config --global merge.ff true    # 默认等同 --ff（出厂默认）
git config --global merge.ff only    # 默认等同 --ff-only
```

> [!note] 配置只是"默认值"
> 命令行选项**永远覆盖**配置。设了 `merge.ff false` 后，偶尔想要快进仍可 `git merge --ff feature`。

## 六、怎么选：一张决策表

| 场景 | 推荐 | 理由 |
|---|---|---|
| 个人小项目、追求线性历史 | 默认（快进） | 历史干净、节点少 |
| 团队协作、功能分支合并 | `--no-ff` | 看得出每次合并、易整体回滚、易做 code review 溯源 |
| 更新本地主干、确信应快进 | `--ff-only` | 若报错说明有意外分叉，及时暴露问题 |
| 想把一团提交压成一个 | `--squash` | 见 [[Squash]] |

> [!question] 是"能不能快进"的问题，还是"要不要快进"的问题？
> 记住两层：
> 1. **能不能**快进，由历史结构客观决定（有无分歧）。
> 2. **要不要**快进，由你/团队的主观选择决定（`--no-ff` 可以否决掉能快进的情况）。

## 七、合并后的历史怎么自查

```bash
git log --oneline --graph --all -15   # 画分叉图：有 M 就有"分叉+汇合"
git log --merges --oneline            # 只看合并提交——非快进合并都会出现在这里
git merge-base main feature           # 找共同祖先，理解为什么是快进/三方
```

> [!success] 成功判据
> - 快进：`git log` 是一条直线，查不到合并提交。
> - `--no-ff`：`git log --merges` 里能找到那个节点，`--graph` 里能看到分叉汇合。

## 八、常见困惑

> [!question] 为什么我明明合并了，`git log --graph` 却没有分叉？
> 因为你这次是**快进**：没有分歧就不需要分叉，指针直接前移。想要分叉，用 `--no-ff`。

> [!question] 快进合并需要用 `revert` 回滚吗？
> 快进没有单一合并节点，`git revert` 只能针对被引入的那批提交逐个来。想整体回滚，`--no-ff` 更省事。

> [!question] `--no-ff` 会不会多出一堆没用的提交？
> 每次合并只多**一个**节点（合并提交），换来的是历史可读性与可回溯性。绝大多数团队认为值得。

> [!question] `--ff-only` 报错是不是坏了？
> 不是。它是在告诉你"当前分支有对方没有的提交，无法快进"。要么先处理分叉（pull/rebase），要么改用普通合并（去掉 `--ff-only`）。

> [!question] 这和 rebase 有什么区别？
> 快进/三方合并都用 **merge** 保留分叉；**rebase** 是把提交搬到对方顶端、重写成直线，**完全不留分叉**。想"看起来像从未分叉过"，那才是 rebase 的场景，见 [[Rebase]]。

---

> [!quote] 一句话记忆
> **能快进就快进**＝历史直线、无节点、看不出分支；**`--no-ff`**＝每次都留一个"合并节点"、看得见汇入。==**想让历史讲故事，就 `--no-ff`；想让历史最简，就让 Git 快进**==。
