# 容器

容器不是"小虚拟机"，本质上是一个被限制了视野的进程。它有自己的文件系统视图、网络栈、PID 空间和主机名，但和宿主机共用同一个内核。理解这句话，很多现象就不用死记。

## 镜像与容器

镜像只读，容器是镜像跑起来的实例。类似类和对象：一个镜像能起很多容器，每个容器在镜像之上多一层可写层。写文件时走 copy-on-write，改的是可写层，镜像纹丝不动；容器删掉，可写层一起没。

所以"进容器改配置"只在当前容器有效，重建就回到镜像状态。要持久，用卷，见 [[01-临时文件系统|临时文件系统]]；要固化，改 Dockerfile 重新构建。

## 一次 run 发生了什么

```bash
docker run -d --name web -p 8080:80 nginx:1.27
docker ps
docker exec -it web sh
curl -I http://localhost:8080
```

`docker run` 依次做几件事：本地找镜像，没有就从仓库拉；在镜像上创建可写层；建命名空间、配 cgroups 和网络；启动镜像里的主进程。`-d` 让它后台运行，`-p 8080:80` 把宿主 8080 转到容器 80。`docker exec` 不是"登录虚拟机"，而是往已有容器的命名空间里再塞一个进程，所以看到的文件系统和网络和主进程完全一样。

容器里的 PID 1 就是主进程，可以验证：

```bash
docker run --rm --name p1 nginx:1.27 sh -c 'echo $$'
```

## 容器为什么会退出

容器只在主进程活着时运行。主进程退出，容器就 Exited，退出码很关键：

- `0`：正常结束，一次性任务常见
- `1`：应用报错，先看 `docker logs`
- `137`：被 SIGKILL，常见于 `docker kill` 或内存超限
- `143`：收到 SIGTERM 后退出，`docker stop` 的正常结果

`docker ps -a` 能看到退出码。区分 OOM 和手动杀：

```bash
docker inspect web --format '{{.State.OOMKilled}} {{.State.ExitCode}}'
```

如果应用把日志写进容器里的文件而不是 stdout，`docker logs` 会空空如也，先确认日志配置，再去 `docker exec` 或挂载目录里找。

> [!tip] 排障顺序
> 先问三件事：进程还在吗（`docker ps -a`）、日志说什么（`docker logs`）、隔离和挂载对不对（`docker inspect`）。镜像里缺工具通常不是第一嫌疑人。
