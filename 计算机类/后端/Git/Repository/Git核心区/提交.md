# 提交 —— Commit

> [!abstract] 一句话
> ==一次提交（Commit）是仓库在**某个瞬间的完整快照**==，外加作者、时间、说明和指向父提交的指针。它是 Git 历史里**最小的、不可变的**单位——一旦生成，内容就冻结，你能做的只有"在它之上再叠一个新提交"。

---

## 一、提交在"三棵树"里的位置

```text
 ①工作目录            ②暂存区                ③仓库(提交)
 Working Directory     Staging Area / Index   Repository / HEAD
┌──────────────┐      ┌──────────────┐       ┌──────────────┐
│  你编辑的文件  │ ──①──│ 待提交的清单  │ ──②──│  永久历史快照  │
│              │ add  │  .git/index  │commit │ .git/objects │
└──────────────┘      └──────────────┘       └──────────────┘
        ▲                                              │
        └──────────────── checkout / restore ──────────┘
```

`git commit` 做的事：**把暂存区当前的样子打包成一个快照，写进 `.git/objects`**，然后让当前分支指针往前挪一格。

> [!info] 提交不是"文件差异"，是"快照"
> 很多人以为 Git 存的是"每次改动的 diff"。**错。**
> Git 每次提交都保存**全部被追踪文件在当时的样子**（能存在一起的重复内容会被去重复用，所以并不浪费）。
> 你在 `git log -p` 里看到的 diff 是**临时算出来的**，不是存下来的。

## 二、一次提交里装了什么

```text
commit 对象（用 SHA-1 哈希命名，如 a1b2c3d...）
├── tree      → 指向一棵目录树，记录本次快照里所有文件与目录
├── parent    → 指向父提交（首个提交没有这行；合并提交有多个）
├── author    → 作者 + 时间（你写的代码）
├── committer → 提交者 + 时间（把它放进仓库的人）
└── message   → 提交说明
```

真实样子（`git cat-file -p HEAD`）：

```text
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent 1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b
author 张三 <zs@example.com> 1717200000 +0800
committer 张三 <zs@example.com> 1717200000 +0800

feat: 新增 utils 工具
```

> [!note] `author` 和 `committer` 可以不同
> 你 `cherry-pick` 或 `rebase` 别人的提交时，**作者仍是原作者**，但 committer 变成你。
> 时间戳同理分两套。日常自己提交时两者相同。

> [!warning] 哈希由内容算出，改一个字就全变
> 提交的 SHA-1 是"tree + parent + author + message"等内容一起算出来的。
> 所以**改提交信息、改作者、改父提交**，都会得到一个**全新的哈希**——这正是 `--amend`、`rebase` 会"改写历史"的根源。

## 三、HEAD 与分支指针

提交之后，"我在哪"靠 `HEAD` 指路：

```text
HEAD → refs/heads/main → <最新提交>
                          ↓ parent
                       <上一个提交>
                          ↓
                       <更早的提交>  …… 
```

| 名词 | 含义 |
| --- | --- |
| **HEAD** | "当前所在位置"，通常指向某个分支，分支再指向某个提交 |
| **detached HEAD** | HEAD **直接**指向某个提交、不指向分支（检出旧提交后进入此状态） |
| **分支指针** | 只是个可移动的标签，永远指向该分支**最新**的提交 |

> [!tip] 提交就是"让当前分支往前走一步"
> 所谓"提交到 main 分支"，本质是：`main` 这个指针从旧提交**移到**你刚建的新提交上。
> 这也解释了 `git reset --hard HEAD~1` 为什么能"撤销提交"——它只是把指针**挪回去**，新提交变成"没人指向的孤儿"，迟早被垃圾回收。

> [!warning] detached HEAD 时提交要当心
> 如果你不在任何分支上（`git switch --detach` 或检出旧提交），此时提交**不属于任何分支**。
> 一旦切走，这些提交会**变得难以找回**（短期内还能靠 `git reflog` 补救）。
> 想留下它们，先 `git switch -c <新分支名>`。

## 四、常用的提交方式

### 4.1 标准流程

```bash
git add <挑好的改动>          # 先精挑细选进暂存区
git commit -m "fix: 修复登录态失效"
```

### 4.2 变体

```bash
git commit                    # 打开编辑器，写多行说明（推荐写正文）
git commit -m "标题" -m "正文" # 多段消息，第一段是标题，其余是正文
git commit -a -m "..."        # 自动 add 所有"已追踪"文件的改动后再提交（不含新文件）
git commit --amend            # ★修改最近一次提交（内容/信息），不改数量
git commit --amend --no-edit  # 只补内容进去，提交信息不变
git commit --allow-empty      # 提交一个空快照（触发 CI 等专用）
```

> [!warning] `--amend` 是"重写"，不是"追加"
> 它**替换**掉最后一次提交，生成一个**新哈希**。
> - 还没 `push` 的提交：随便 amend。
> - **已经 `push` 且被他人拉取过的提交**：不要 amend，否则别人的历史会对不上，只能强推（`--force-with-lease`）并让队友受罪。
>
> 口诀：**公共历史不可改，私人历史随便改。**

### 4.3 提交信息的写法

一次好的提交信息，第一行就是"给未来的自己看的一句话"：

```text
<类型>: <做了什么>

（可选）为什么这么做、涉及哪些权衡
```

常用类型前缀（Conventional Commits）：

| 前缀 | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修复 bug |
| `docs` | 文档 |
| `style` | 格式（不影响逻辑） |
| `refactor` | 重构（非新功能、非修 bug） |
| `test` | 测试 |
| `chore` | 构建/工具/杂务 |

> [!tip] 写清楚"为什么"，不只是"做了什么"
> `git log` 里 `改了什么` 从 diff 就能看懂，**真正会失传的是"为什么这么改"**。
> 把决策理由写进正文，半年后你会感谢自己。

## 五、完整示例

```bash
# 1. 挑好要提交的改动
git add src/login.js
git diff --staged                # 提交前确认清单

# 2. 提交（标题 + 正文说清动机）
git commit -m "fix: 修复登录态在刷新后失效" -m "原因是 token 只在内存里保存，改为持久化到 localStorage。"

# 3. 发现漏了一个文件 → 补进同一次提交
git add src/auth.js
git commit --amend --no-edit     # 内容补进去，信息不变

# 4. 回看结果
git log --oneline -3
git show HEAD --stat
```

> [!success] 成功标志
> `git log --oneline` 能打出你刚写的提交；`git status` 显示 `working tree clean`。
> 若 `git log` 里还是空的、`status` 显示 `No commits yet`，说明 `add`/`commit` 漏了。

## 六、常见困惑

> [!question] 提交之后文件还在，那我提交了个啥？
> 提交**不移动、不删除**你的文件。它只是把当时的快照**复制**进 `.git/objects`，工作目录原封不动。
> 所以 `commit` 一个已保存的文件后，你继续编辑，磁盘上一切照旧。

> [!question] 不小心 `commit` 了大文件 / 密码怎么办？
> - 只是**最近一次**、还没推：`git rm --cached <文件>` → 加进 `.gitignore` → `git commit --amend`。
> - 已在历史深处：历史里**始终留着**它，需要 `git filter-repo` 之类的工具重写历史，**并且立即更换泄露的密钥**。
> 教训：**提交前 `git diff --staged` 看一眼，比事后清理便宜一万倍。**

> [!question] 提交能"撤销"吗？
> "撤销"有不同的含义，对应不同命令：
> | 想做的事 | 命令 | 影响范围 |
> | --- | --- | --- |
> | 撤销提交，改动保留在暂存区 | `git reset --soft HEAD~1` | 仅本地历史 |
> | 撤销提交，改动退回工作目录 | `git reset HEAD~1`（默认 mixed） | 仅本地历史 |
> | ⚠️ 彻底丢弃提交与改动 | `git reset --hard HEAD~1` | 不可逆 |
> | 安全地"反向提交"抵消它 | `git revert HEAD` | **推荐用于已推送的历史** |
> 详见 [[查看commit历史]]。

> [!question] 提交里的时间是"我电脑的时间"吗？
> 是。Git 记录的是**你本机的时区 + 时间戳**。所以服务器时区、双系统时间不同步，都可能让提交时间看起来"穿越"。提交后改不了（除非 amend / rebase，且那会换哈希）。

---

> [!quote] 一句话记忆
> **提交 = 给项目拍一张不可篡改的照片**：暂存区是取景框，`commit` 是按下快门；照片一旦拍下，你只能**在后面接着拍**，不能修改底片（除非重写历史）。
