# 镜像

镜像命令的日常核心是两件事：把镜像弄到本地，把本地镜像送出去。剩下的多半是在查它到底是什么。

## 基本流转

```bash
docker pull nginx:1.27.3
docker images
docker tag my-app:1.0 registry.example.com/team/my-app:1.0
docker push registry.example.com/team/my-app:1.0
docker rmi registry.example.com/team/my-app:1.0
```

`tag` 不改内容，只是给同一个 image ID 再贴一个名字。推送前必须让仓库地址成为标签的一部分，否则 `push` 不知道往哪送。

没有仓库可用时，`save` / `load` 保留镜像的完整结构：层、标签、配置都在。`export` / `import` 只导出容器文件系统，会丢掉历史和元数据，别混用：

```bash
docker save my-app:1.0 | gzip > my-app.tar.gz
docker load < my-app.tar.gz
```

## 看清楚一个镜像

`docker images` 默认字段有限，用 `--format` 自己排版：

```bash
docker images --format 'table {{.Repository}}\t{{.Tag}}\t{{.ID}}\t{{.Size}}'
docker images --filter dangling=true
# REPOSITORY   TAG   IMAGE ID       SIZE
# my-app       1.0   4f2c1a8b9d3e   182MB
```

`inspect -f` 能直接取字段，排障时很好用：

```bash
docker inspect -f '{{.Config.User}}' my-app:1.0          # 空表示 root
docker inspect -f '{{index .RepoDigests 0}}' my-app:1.0  # 固定 digest 用
docker inspect -f '{{len .RootFS.Layers}}' my-app:1.0    # 层数
docker inspect -f '{{json .Config.Env}}' my-app:1.0      # 环境变量
```

层数多不一定是坏事，但每层都增加体积和管理成本。`docker history` 看每层由哪条指令产生：

```bash
docker history --no-trunc --format '{{.CreatedBy}}\t{{.Size}}' my-app:1.0
```

`--no-trunc` 很关键，默认会截断 `RUN` 命令，看不到完整内容。

## 磁盘与清理

```bash
docker system df -v
docker image prune          # 悬空镜像
docker image prune -a       # 所有没被容器使用的镜像
```

`system df -v` 会列出每个镜像的大小以及是否共享层，比 `docker images` 的 SIZE 更接近真实占用。`prune -a` 连尚未推送的本地构建一起删，执行前先看一眼列表。

> [!warning] 删镜像不等于删容器
> 容器仍引用镜像时 `rmi` 会报错。先删容器，或者确认它只是 stopped；`prune -a` 同样会跳过被任何容器引用的镜像。

## 常见问题

拉取报 `manifest unknown`，通常是 tag 写错，或该架构没有对应 manifest，用 `docker buildx imagetools inspect` 看仓库里到底有哪些平台。被限流会返回 `toomanyrequests`，登录 Docker Hub 或换镜像源。`docker images` 里出现 `<none>`，是构建失败或被新 tag 顶掉的悬空镜像，按 ID 删除即可。
