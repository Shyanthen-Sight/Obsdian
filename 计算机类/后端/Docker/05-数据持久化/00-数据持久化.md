# 数据持久化

容器是个一次性的东西：删掉重建，可写层里的改动就全部归零。数据库文件、用户上传的图片、审计日志，生命周期比容器长，得放在容器外面。

这一阶段要解决的就是“数据放哪”。三个位置，边界很清楚：

| 位置 | 谁管理 | 容器重建后 | 适合 |
| --- | --- | --- | --- |
| 可写层 | 容器自己 | 丢失 | 缓存、临时文件 |
| 命名卷 | Docker | 保留 | 数据库、上传目录 |
| 绑定挂载 | 宿主 | 保留 | 源码、配置文件 |

先看一个最小对比：

```bash
# 写进可写层：--rm 删除容器后，文件一起消失
docker run --rm alpine sh -c 'echo hi > /data.txt'

# 写进命名卷：容器删除，卷里的内容还在
docker run --rm -v demo-data:/data alpine sh -c 'echo hi > /data.txt'
docker volume inspect demo-data
```

`--rm` 只删容器，不删卷；第二条命令里 `/data` 背后是 Docker 管理的卷，`inspect` 能看到它在宿主上的实际路径。这个对比能解释大部分“为什么我的数据没了”的问题。

阅读顺序按这个来：先看 [[01-临时文件系统|临时文件系统]]，搞清楚为什么不能把数据留在容器里；再看 [[02-卷挂载|卷挂载]]，这是默认答案；最后看 [[03-绑定挂载|绑定挂载]]，它解决开发时的问题，也带来路径和权限的麻烦。

一个经验法则：如果这份数据在 `docker compose down` 之后还要在，就别让它待在容器里。开发机上用绑定挂载图方便没问题，但上线前要确认生产环境用的是卷或者外部存储。

还有一个容易混的点：`docker compose down` 默认删容器和网络，保留命名卷；加 `-v` 才会连卷一起删。第一次丢数据的人，多半是习惯性敲了 `down -v`。

学完这节，应该能回答几个具体问题：为什么 `docker rm` 之后数据没了，而 `docker restart` 之后还在；卷被误删了怎么恢复；容器里的进程以 UID 1000 写宿主目录，为什么文件属主变成了 1000。容器里 `df -h` 的数字和宿主对不上，也是这里要解释的现象。
