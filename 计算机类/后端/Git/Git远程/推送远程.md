# 推送远程 —— git push

> [!abstract] 一句话
> ==`git push` 是把**本地提交送进远程仓库**==，方向与 `fetch` / `pull` 正好相反（本地 → 远程）。它做的其实很"物理"：比较两边的分支指针，把对方缺少的那些**提交对象**传上去，然后更新远程分支指针。所以它只会"增加"提交，永远不会替你删掉别人的东西——除非你显式让它强推。

---

## 一、先记住方向

```text
        本地                             远程·
   main ──→ ────────── push ──────────→  main
          ←────────── fetch / pull ──────
```

> [!warning] push 是"送到哪"，不是"拿到手"
> `push` 只往外送。想从远程取回更新，用 [[fetch跟pull]]。
> 两个方向搞反，是新手最常见的心智混淆。

---

## 二、最常用：首次推送与 `-u`

```bash
git push                    # ① 推当前分支到它的"上游"（若已设）
git push -u origin main     # ★ 首次推送：推送并顺带设好上游
git push origin main        # 推 main 到 origin/main（不设上游）
```

> [!tip] `-u` 是"一次设置，永久省事"
> `-u` 是 `--set-upstream` 的简写。执行 `git push -u origin main` 后，
> 这条本地 `main` 就记住了"我的上游是 `origin/main`"。
> 以后你**只敲 `git push`** 即可，Git 自动知道送去哪。
> 反向的 `git pull` 同理受益。上游关系可在 `git branch -vv` 里看到。

> [!info] 不设上游就 `git push` 会怎样？
> 若 `push.default` 为默认的 `simple`，且当前分支没有上游，Git 会拒绝并给提示：
> ```text
> fatal: The current branch main has no upstream branch.
> To push the current branch and set the remote as upstream, use
>     git push --set-upstream origin main
> ```
> 按提示补上 `-u` 即可。

---

## 三、完整语法与"本地:远程"

```bash
git push <远程名> <本地分支>:<远程分支>
git push origin main:main            # 本地 main → 远程 main
git push origin feature:release      # 本地 feature → 远程 release（名字可不同）
git push origin HEAD                 # HEAD 指向的分支 → 远程同名分支
```

> [!info] 冒号两边分别是什么
> `本地:远程`。左边是你**有的**（数据源），右边是远程上**要更新的**（目标指针）。
> 省略冒号和右边时（`git push origin main`），默认"同名对同名"。

> [!tip] 推送"当前分支"的最短写法
> `git push origin HEAD` 不必记分支名，特别适合脚本或分支名很长的场合。

---

## 四、推送标签

`git push` **默认不推标签**——标签得单独推：

```bash
git push origin v1.2.0         # 推单个标签
git push origin --tags         # 推所有本地标签
git push --follow-tags         # ★ 推提交时，顺带推"本次可达的注释标签"
```

> [!warning] 轻量标签 vs 注释标签
> `--follow-tags` 只推**注释标签**（`git tag -a` 创建的），轻量标签（`git tag v1`）不带过去。
> 团队约定发布用注释标签，正是为了配合这个选项。详见 [[查看commit历史]] 中关于 tag 的讨论。

> [!note] 标签同名的坑
> 若远程已存在同名标签但内容不同，推送会被拒绝，需要显式 `git push origin <tag> --force`。
> 标签代表发布点，**强推标签要非常慎重**，改历史前先和团队打招呼。

---

## 五、删除远程分支

```bash
git push origin --delete <分支名>     # ★ 推荐，语义清晰
git push origin :<分支名>             # 老写法：推一个"空"到该分支 = 删掉它
```

> [!warning] 影响所有协作者
> 远程分支是共享成果，删除会让别人的 `origin/xxx` 变 `[gone]`。
> 删前确认 PR 已合并、无人在用。详见 [[删除分支]]、[[查看分支]]。

---

## 六、强推：`--force` 与更安全的 `--force-with-lease`

当你**改写了历史**（`rebase`、`commit --amend`、`reset`）后，本地与远程的提交对不上，普通 push 会被拒。此时才需要强推：

```bash
git push --force              # 危险：无条件覆盖远程
git push --force-with-lease   # ★ 安全：只有当远程还是我上次见到的样子才覆盖
```

> [!danger] `--force` 会覆盖别人的提交
> 如果在你不知情时同事往这条远程分支推了东西，`--force` 会**把它们原地抹掉**，且很难察觉。
> 只要是**多人共享**的分支，==默认永远不要用裸 `--force`==。

> [!success] 为什么 `--force-with-lease` 更安全
> 它带着"租约"：只有远程分支仍停在**你本地记录的 `origin/xxx` 位置**（说明没人插队）时才允许覆盖；
> 一旦发现别人推过新提交，它就**拒绝**。几乎总是应该用它替代 `--force`。

> [!tip] 强推前先确认只影响自己
> ```bash
> git fetch
> git log --oneline origin/main..main   # 只列"我要覆盖掉的远程？"——再看清
> git push --force-with-lease
> ```
> 一个经验：**只对"自己独占的 feature 分支"强推**；`main` / `develop` 等公共分支，改历史前先商量。

## 七、被拒绝：`non-fast-forward`

```text
! [rejected]  main -> main (non-fast-forward)
error: failed to push some refs
hint: Updates were rejected because the remote contains work that you do not have locally.
```

> [!info] 为什么会被拒
> 推送要求是**快进（fast-forward）**：你在远程现有提交的基础上**只增不减**。
> 若远程有你**没有**的提交（别人先推了），你的推送就不是快进，Git 拒绝，**保护你不覆盖别人的工作**。

> [!success] 正确处置：先取回，再推
> ```bash
> git pull --rebase          # 把远程新提交接进来（rebase 让历史保持直线）
> # 若有冲突：解决、git add、git rebase --continue
> git push
> ```
> 或先 `git fetch`、看清差异、手动 `merge` / `rebase` 后再推（见 [[fetch跟pull]]）。
> ==绝不推荐用 `--force` 来"解决"这个拒绝==——那正是它要防的事。

## 八、完整示例

```bash
# 场景一：新分支首次推送
git switch -c feature/login          # 见 [[创建分支]]
git add .
git commit -m "feat: 登录模块"
git push -u origin feature/login     # 首次推送并设上游

# 场景二：之后日常推送
git push                             # 因为上游已设，一条搞定

# 场景三：推送被拒（别人先推了）
git pull --rebase                    # 接住远程新提交
git push

# 场景四：本地 rebase 后，力推自己的 feature 分支
git push --force-with-lease origin feature/login

# 场景五：发布标签
git tag -a v1.0.0 -m "首个正式版"
git push origin v1.0.0
```

> [!success] 成功标志
> 输出里出现 `main -> main` 或 `+ abc1234...def5678 main -> main (forced update)`；
> 随后 `git branch -vv` 显示 `[origin/main]` 与本地**同步**（无 `ahead`）。

## 九、常见困惑

> [!question] `git push` 会不会把我所有分支都推上去？
> 默认只推**当前分支**（`simple` 模式）。想一次推多个，可设
> `git config --global push.default current`，或用 `git push --all`（推全部本地分支）/ `--tags`（推全部标签）。

> [!question] `git push` 会把标签一起推吗？
> 默认**不会**。要么显式 `--tags`，要么用 `--follow-tags`（推荐，只带注释标签）。见第四节。

> [!question] 我 push 完，同事那边会自动更新吗？
> 不会。push 只是把数据放上服务器，同事必须自己 `git pull` / `git fetch` 才看得到。
> 这是 Git "分布式"的代价与优点：**没人被强制同步**。

> [!question] 推送成功但远程页面没刷新？
> 多半是平台缓存或你看的是旧的分支。确认推的是哪条分支、哪个远程（`git push -v` 有详细过程）。

> [!question] 误用 `--force` 覆盖了别人的提交，能救吗？
> 若被覆盖的提交**还在某人本地**或**还能在服务器 reflog 找到**，有机会恢复；
> 但这是抢救，不是日常。==所以强推前一定要用 `--force-with-lease` 并先 `fetch`。==

> [!question] `push` 和 `fetch` 都能"同步分支指针"，为何一个要认证一个不用？
> `fetch` 是**读**远程，多数配置下匿名即可；`push` 是**写**远程，必须有写权限（SSH 密钥或令牌）。
> 这也是为什么 HTTPS 下 push 常要输令牌。

---

> [!quote] 一句话记忆
> **push 是"本地 → 远程"的传送**：首次 `-u` 设上游，之后 `git push` 一条走天下；被拒（`non-fast-forward`）说明==远程有新东西，先 pull 再推==；只有改写历史才强推，且**优先 `--force-with-lease`**。
