# MCP 详解

> 一句话：MCP 是 **Model Context Protocol（模型上下文协议）**——一套让 LLM 用统一标准接入外部数据和能力的"USB-C 接口"。

## 一、什么是 MCP

### 1. 概念

拆开名字看，三个词各司其职：

| 词 | 含义 |
| --- | --- |
| **Model** | 强调服务主体是 LLM |
| **Context** | 强调其信息枢纽功能 |
| **Protocol** | 凸显信息交互的**标准化**特性 |

MCP 如同 USB-C 接口般，==通过统一协议实现 LLM 与外部能力的**高效互联**。==

作为算力核心的 LLM==，既需要调用本地数据（如磁盘存储），也需对接远程服务（如邮件服务器==），
==而 MCP 正是实现这种多源能力整合的**转换器**。==

其价值在于：通过标准化协议广泛接入外部资源，让 LLM 在完成训练后还能突破固有的能力边界。MCP 官网展示的最经典案例——接入气象数据接口后，LLM 就能准确回答"明天会下雨吗"这类即时性问题。

### 2. 组成

MCP 采用经典的**客户端-服务器架构**，通常包含三个部分：

#### MCP Host

能够通过 MCP 集成外部能力的主体。

- 通常承担**最终用户交互界面**的角色
- 既可以是独立的 LLM Desktop，也可以是基于 LLM 构建的生产力工具（==如 IDE==）
- 代表的是**需求方**，是 MCP Client 的运行时环境，负责协调用户、LLM 与外部资源之间的交互

#### MCP Client

Host 内部负责与 MCP Server 交互的组件。

- 由 Host 创建，与 Server 建立**一对一的有状态会话**
- 将 Host 的请求转换为符合 MCP 标准的消息发送给 Server
- 再将 Server 的响应解析为 Host 可以理解的格式

#### MCP Server

==LLM 需要的外部能力的**具象化**。==

- 能力可以是读取本地磁盘文件、写入本地数据库、查询天气/股票价格等等
- 但 **Server 不是能力/资源本身**——==它是通过统一标准协议将能力对外暴露的**代理**==

- ![[Pasted image 20260920123347.png|687]]

#### Server 对外暴露的三种能力

MCP Server 是为 LLM 赋能的关键，其暴露的能力分为三类：

| 能力 | 定位 | 说明 | 类比 |
| --- | --- | --- | --- |
| **Resources** | 可供加工的数据 | 一般是静态或半动态的原始数据，可直接被 LLM 理解并放入上下文用于推理，比如日志或配置等基础信息 | 只读的文件或数据库 |
| **Tools** | 执行一个具体的任务 | LLM 将用户需求拆分为多个子步骤时，可调用 Tools 实现其中一步或多步。可以是写数据库、基于敏感信息计算后输出脱敏信息、或调用另一个没提供 MCP 接口的系统 | 菜刀 |
| **Prompts** | 可复用的 LLM 提示模板 | 处理私域场景时需要的特化逻辑（输入/输出格式、上下文片段等）可固化为 Prompts 保存在 Server 中 | 偏好 |

> 通常一个 Server 中的 Tools 具有**相关性**，它们在一起描述了这个服务拥有的所有能力。

#### 做饭的比喻

用做饭来比喻：

- **Resources** = 各种未处理/预处理的**食材**
- **Tools** = 定义了"**菜刀**"
- **Prompts** = 定义了**偏好**

当我向一个基于 LLM 扮演厨师的 Agent 提出想吃"凉拌黄瓜"时：

1. Agent 基于 LLM 理解了做饭的流程
2. 通过 Prompts 知道了成品**一定要放香菜**
3. 通过 Resources 得到了**老家产的黄瓜**
4. 调用了**多次 Tools** 切出黄瓜块

> ⚠️ **注意**：与 MCP Server 的哪些资源/能力进行交互，是 **LLM 自己判断并选择的**，因此对资源/能力的描述要**准确无误**。
> 如果提供了"黄瓜牌西红柿"，也是有可能得到"凉拌西红柿"的。

## 二、直观体验

MCP 包含 Host/Client 和 Server 两大部分：前者代表具备**通用能力**的 LLM 应用，后者代表具备**专项能力**的外部模块。

### 案例：用通义灵码查 12306 车票

演示环境：VS Code 中的**通义灵码**插件（集成了 MCP Client）。

**安装步骤**：依次点击 `MCP 工具` → `MCP 广场` → `12306-MCP车票查询工具`，即可为一个编码 Agent 安装查询 12306 车票的 MCP Server。

> 注意：这里要将通义灵码从默认的"智能问答"切换到"**智能体**"模式。

安装成功后可以在"我的服务"里看到 `12306-mcp`。MCP 协议支持 LLM 查询服务器提供了哪些方法，LLM 会在解决相关问题时**自主选择**执行哪些 Tools（因此通常需要为 Tools 提供 LLM 可以理解的精准描述）。

**提问 1**："周末想从上海去北京玩，帮我随便找几班快点的车次"

→ 通义灵码依次调用了**四次** MCP 工具，分别查看：

1. 当前的时间
2. 出发城市的车站代码
3. 目标城市的车站代码
4. 出发到目的之间的车票信息

在得到基础信息后，LLM 基于已有的通用能力判断出哪班车次的速度更快并进行推荐。

**提问 2**："有没有哪班车还有二等座的票"

→ 虽然 `12306-mcp` 中**没有定义**哪个方法可以过滤无票的车次，但 LLM 在获得信息后**自己实现了筛选**，并且延续了前面对车次速度的要求进行推荐。

**反例**：如果询问与 MCP Server 提供的 Tools 无关的问题，LLM 也不会"迂腐"地强行调用。

### 自建一个简单的 MCP Server

目前实现 MCP Server 的编程语言主要是 **Node.js、Python 和 Java**，分别对应了前后端一体化开发、开发友好性和生产环境友好性。（作者体验了 Node.js 和 Python，**个人更喜欢后者**。）

示例：一个非常简单的 MCP Server，里面定义了一个 **1+1=3** 的 Tool。

**接入方式**：点击通义灵码插件右上角的用户名称，选择 `个人设置` → `MCP 服务` → 右上角的 ➕ 号，即可选择手动/配置文件添加。

这个例子主要想展示 MCP Server 对 LLM 基础能力的一种"**侵入型**"表现——LLM 理解 1+1 不等于 3，但还是会选择执行对应的 Tool 并输出。

> 生产环境因为历史遗留问题，总会有一些看起来奇奇怪怪但是"不遵循就会爆炸"的规则，**能够遵循这些规则本身也是生产力的一种表现**。

## 三、MCP 的意义是什么

讲 MCP 肯定会提及 **Function Calling**。23 年 OpenAI 发布的 GPT Function Calling 也可以实现类似的功能：通过指定的格式将外部工具传给 LLM 用于扩展其能力边界。

但两者的关键差异在于：

| | Function Calling | MCP |
| --- | --- | --- |
| 本质 | **模型能力**，而非标准协议 | **统一的标准协议** |
| 兼容性 | 不同供应商的 LLM 支持格式**各不相同** | 一套协议，低成本接入 |
| 成本 | 适配一个外部平台同一类工作可能要**重复多遍**，还有隐含的调优成本 → 产品化成本高昂 | 统一协议让低成本接入成为可能 |

**结论**：当一种成本被快速降低时，想象力的空间就会急速上升。无论是 Function Calling 还是 MCP，落脚点都是**为 LLM 提供更多的业务理解**。在已经初步具备与人相近理解能力的基础上，再赋予其足够多、足够广的业务能力，智能体就能脱离于个人展现出**通用的生产力**——这才是 MCP 如此广泛被讨论的原因。
