# 容器

容器不是"小虚拟机"，本质上是一个被限制了视野的进程。它有自己的文件系统视图、网络栈、PID 空间和主机名，但和宿主机共用同一个内核。理解这句话，很多现象就不用死记。

## 镜像与容器

镜像只读，容器是镜像跑起来的实例。类似类和对象：一个镜像能起很多容器，每个容器在镜像之上多一层可写层。写文件时走 copy-on-write，改的是可写层，镜像纹丝不动；容器删掉，可写层一起没。

所以"进容器改配置"只在当前容器有效，重建就回到镜像状态。要持久，用卷，见 [[01-临时文件系统|临时文件系统]]；要固化，改 Dockerfile 重新构建。

## 一次 run 发生了什么

```bash
docker run -d --name web -p 8080:80 nginx:1.27
docker ps
docker exec -it web sh
curl -I http://localhost:8080
```

`docker run` 依次做几件事：本地找镜像，没有就从仓库拉；在镜像上创建可写层；建命名空间、配 cgroups 和网络；启动镜像里的主进程。`-d` 让它后台运行，`-p 8080:80` 把宿主 8080 转到容器 80。`docker exec` 不是"登录虚拟机"，而是往已有容器的命名空间里再塞一个进程，所以看到的文件系统和网络和主进程完全一样。

容器里的 PID 1 就是主进程，可以验证：

```bash
docker run --rm --name p1 nginx:1.27 sh -c 'echo $$'
```

## 容器为什么会退出

容器只在主进程活着时运行。主进程退出，容器就 Exited，退出码很关键：

- `0`：正常结束，一次性任务常见
- `1`：应用报错，先看 `docker logs`
- `137`：被 SIGKILL，常见于 `docker kill` 或内存超限
- `143`：被 SIGTERM 终止（128+15），常见于 `docker stop` 后应用没有接管信号

`docker ps -a` 能看到退出码。区分 OOM 和手动杀：

```bash
docker inspect web --format '{{.State.OOMKilled}} {{.State.ExitCode}}'
```

如果应用把日志写进容器里的文件而不是 stdout，`docker logs` 会空空如也，先确认日志配置，再去 `docker exec` 或挂载目录里找。

> [!tip] 排障顺序
> 先问三件事：进程还在吗（`docker ps -a`）、日志说什么（`docker logs`）、隔离和挂载对不对（`docker inspect`）。镜像里缺工具通常不是第一嫌疑人。

## 镜像、可写层、卷：数据到底放在哪

容器里写文件，位置不同，命运完全不同。先把五种位置摆在一起：

| 位置 | 谁写 | 生命周期 | 容器删除后 | 典型用途 |
| --- | --- | --- | --- | --- |
| 镜像只读层 | 构建时 | 跟镜像 | 保留 | 代码、依赖、默认配置 |
| 容器可写层 | 运行时 | 跟容器 | 消失 | 临时文件、运行期改动 |
| 命名卷 | 容器 | 独立于容器 | 保留 | 数据库、上传目录 |
| 绑定挂载 | 容器或宿主 | 跟宿主目录 | 保留 | 开发源码、配置文件 |
| tmpfs | 容器 | 跟容器内存 | 消失 | 缓存、临时密钥 |

可写层用的是 copy-on-write：读文件时直接读只读层，第一次写某个文件时，才把整个文件复制到可写层再改。注意是“整个文件”，不是按块复制，所以改一个几百 MB 的日志文件，第一次写就会复制几百 MB。删除文件也不是真删，而是在可写层放一个 whiteout 标记，把下层同名文件遮住。

这带来两个直接结论：

- 容器里改配置、装软件，只影响当前容器的可写层，镜像纹丝不动；`docker diff` 能看到改了哪些文件。
- 可写层跟着容器生命周期走，`docker rm` 之后一起消失；想留住数据，必须用卷或绑定挂载。

`docker commit` 能把可写层固化成新镜像，但它和 Dockerfile 是两回事：

| 对比 | `docker commit` | Dockerfile |
| --- | --- | --- |
| 可复现 | 否，取决于当时容器里发生过什么 | 是，构建步骤可审查 |
| 构建记录 | 没有 | 有，能进版本库 |
| 体积 | 容易把临时文件和缓存一起固化 | 可以分层清理、多阶段控制 |
| 适用场景 | 临时实验、抢救现场 | 正式交付 |

所以“进容器改完再 commit”只能救急。要长期维护，把改动写回 Dockerfile，重新构建。

## exec 不是登录虚拟机

`docker exec` 经常被当成“ssh 进容器”，但三者的进程关系完全不同：

| 对比   | `docker run`      | `docker exec` | ssh 进虚拟机          |
| ---- | ----------------- | ------------- | ----------------- |
| 进程关系 | 创建新容器，入口命令是 PID 1 | 往已有容器里再塞一个进程  | 登录已有系统，起一个新 shell |
| 文件系统 | 镜像 + 新的可写层        | 和主进程共用同一个可写层  | 虚拟机的根磁盘           |
| 网络   | 默认新建网络命名空间        | 和主进程共享网络命名空间  | 虚拟机的网络栈           |
| 生命周期 | 主进程退出，容器结束        | 命令退出，容器继续运行   | shell 退出，系统继续运行   |
| 前提   | 镜像存在              | 容器正在运行        | 虚拟机已启动且网络可达       |

关键在“共享命名空间”：`exec` 进去看到的 `/`、网卡、进程列表，和主进程看到的是同一套。所以 exec 里改的文件会影响这个容器（落在可写层），但不会影响镜像；exec 里 `curl localhost` 访问的是容器自己，不是宿主机。容器处于 `Exited` 状态时 `exec` 会直接报错，因为命名空间已经没了。

另外，`exec` 默认不分配 TTY，交互式排查要写 `-it`；它也不会加载登录 shell 的 profile，环境变量以容器主进程的配置为准。

## 退出码逐条看

容器退出码不是随便定的，`128 + 信号编号` 是惯例：

| 退出码 | 含义 | 常见来源 | 先看什么 |
| --- | --- | --- | --- |
| `0` | 进程正常结束 | 一次性任务跑完、应用主动退出 | 任务本身是否真的成功 |
| `1` | 应用级错误 | 未捕获异常、配置错误 | `docker logs` |
| `2` | 用法错误 | shell 内建命令参数不对 | 启动命令和参数 |
| `125` | Docker 自身失败 | 参数非法、daemon 异常 | `docker run` 的报错文本 |
| `126` | 命令不可执行 | 没有执行权限、格式不兼容 | 文件权限、CPU 架构 |
| `127` | 命令找不到 | 入口命令拼错、镜像里没这个程序 | `ENTRYPOINT`/`CMD` |
| `130` | 收到 SIGINT | 前台运行时按了 Ctrl-C | 操作记录 |
| `137` | 收到 SIGKILL（128+9） | `docker kill`、`stop` 超时、OOM | `OOMKilled` 和事件 |
| `143` | 收到 SIGTERM（128+15） | `docker stop` 正常停止 | 应用是否处理了优雅退出 |

`137` 最容易被误判。先查 OOM：

```bash
docker inspect web --format '{{.State.OOMKilled}} {{.State.ExitCode}}'
```

`true` 是 cgroup 内存超限，去看 `docker stats` 和应用的堆配置；`false` 再区分是手动 `docker kill`、`docker stop` 等满 10 秒后被 SIGKILL，还是宿主 OOM killer 动的手。`143` 表示进程被 SIGTERM 终止：可能是 `docker stop` 发出后应用没装处理器，直接按默认动作退出；如果应用捕获信号并正常收尾，退出码可能是 0。

## stop、kill、rm、pause 的区别

| 命令             | 发的信号                   | 是否等待               | 容器状态              | 适用场景        |
| -------------- | ---------------------- | ------------------ | ----------------- | ----------- |
| `docker stop`  | 先 SIGTERM，宽限期后 SIGKILL | 默认等 10 秒，可 `-t` 调整 | 停止，仍可用 `start` 拉起 | 正常停机        |
| `docker kill`  | 默认 SIGKILL，可 `-s` 指定   | 不等待                | 停止                | 进程卡死、必须立刻中断 |
| `docker rm`    | 无                      | 无                  | 删除                | 清理已停止的容器    |
| `docker rm -f` | SIGKILL                | 不等待                | 直接删除              | 清理运行中的容器    |
| `docker pause` | 冻结 cgroup（类似 SIGSTOP）  | 无                  | 暂停，进程还在           | 临时冻结，保留内存状态 |

`docker stop` 的 10 秒是给应用收尾的窗口：停止接新请求、处理完手头的、关闭连接池。应用如果没把 SIGTERM 接住，或者 PID 1 是 shell 而信号没转发，就会等到超时被 SIGKILL，退出码从 143 变成 137。这也是 [[04-Shell 脚本|Shell 脚本]] 里强调 `exec "$@"` 的原因。

## 在容器里看到的进程，不是宿主机的全部

`docker exec` 进去跑 `ps` 只看到一两个进程，是因为 PID 命名空间把宿主进程藏起来了，不是因为宿主机上真的只有这些。要看全貌有两个方向：

```bash
docker top web                 # 在宿主机上看这个容器的进程
ps -ef | grep <进程名>          # 在宿主机上看全部进程
```

同理，容器里的 `localhost` 是容器自己，`ip addr` 是容器的网卡，`hostname` 是容器 ID（或 `--hostname` 指定的名字）。排查“为什么连不上”时，先确认自己站在哪个命名空间里，再谈网络配置。
