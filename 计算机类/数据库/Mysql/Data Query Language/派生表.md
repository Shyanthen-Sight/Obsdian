# 派生表 —— 子查询当表用

> [!abstract] 一句话
> 派生表（derived table，也叫表子查询）就是==**写在 `FROM` / `JOIN` 后面、用括号包起来的 `SELECT`**==：先算出一个中间结果集，再把它当成一张"临时表"交给外层查询。
> 两条铁律：==**必须起别名**==（否则 `ERROR 1248`）；==**外层只能通过这个别名访问它的列**==。

> [!info] 与其它笔记的分工
> - 子查询的整体分类（标量 / 列 / 行 / 表）见 [[嵌套查询]]
> - `FROM` 的基础语法与多表来源见 [[From]]
> - 引用外层列、逐行执行的子查询见 [[相关子查询]]
> - 物化、`EXPLAIN` 的通用分析方法见 [[查询优化]]
>
> 本篇只讲一件事：**把一条 SELECT 当成表来用**。

---

> [!example] 本篇示例数据
> 与 [[嵌套查询]]、[[相关子查询]] 以及连接查询各篇**共用同一套 `dept` / `emp` 表**。
> 两个"不匹配"继续有用：**财务部没人**、**孙七没部门**（`dept_id IS NULL`）。

```sql
CREATE TABLE dept (
    dept_id   INT PRIMARY KEY,
    dept_name VARCHAR(20)
);

CREATE TABLE emp (
    emp_id   INT PRIMARY KEY,
    emp_name VARCHAR(20),
    dept_id  INT,              -- 允许 NULL：孙七没有部门

);

INSERT INTO dept VALUES (1001, '研发部'), (1002, '销售部'), (1003, '财务部');

INSERT INTO emp VALUES (1, '张三', 1001, 12000),
                       (2, '李四', 1001, 15000),
                       (3, '王五', 1002,  9000),
                       (4, '赵六', 1002,  8500),
                       (5, '孙七', NULL,  7000);
```

```
-- dept（3 行）                  -- emp（5 行）
dept_id | dept_name            emp_id | emp_name | dept_id | salary
--------+----------            -------+----------+---------+--------
   1001 | 研发部                   1 | 张三     |    1001 |  12000
   1002 | 销售部                   2 | 李四     |    1001 |  15000
   1003 | 财务部  <-- 没人          3 | 王五     |    1002 |   9000
```

## 一、语法与最小例子

```sql
SELECT 外层列
FROM (
    SELECT 内层列
    FROM 表
    WHERE 内层条件
) AS 别名
WHERE 别名.列 外层条件;
```

把一个聚合结果套进派生表，再在外层过滤：

```sql
SELECT t.dept_id, t.avg_sal
FROM (
    SELECT dept_id, ROUND(AVG(salary), 2) AS avg_sal
    FROM emp
    GROUP BY dept_id
) AS t
WHERE t.avg_sal > 9000;
```

派生表 `t` 算出来的内容（3 个组）：

```
dept_id | avg_sal
--------+---------
   1001 | 13500.00
   1002 |  8750.00
   NULL |  7000.00    <-- 孙七单独成组
```

外层 `WHERE` 过滤后只剩一行：

```
dept_id | avg_sal
--------+---------
   1001 | 13500.00
```

> [!important] 执行顺序：逻辑上"先里后外"
> 非 `LATERAL` 的派生表**先独立算完**，外层再拿它的结果继续过滤 / 连接。
> 所以外层 `WHERE` 在语义上作用在"已经聚合好的结果"上——这正是它能把 `AVG(salary)` 的别名当普通列用的原因。
> 物理执行未必如此：优化器可能把派生表**合并**进外层，见第六章。

> [!tip] 写法习惯
> - 括号、缩进各占一块：内层 `SELECT` 往里缩一层，一眼看出"这是一张临时表"
> - 右括号后**立刻**写 `AS 别名`，别等写完了再补
> - 内层列**全部起别名**：`AVG(salary) AS avg_sal`，外层用 `t.avg_sal` 更清楚

## 二、别名与作用域：四条硬规则

### 2.1 派生表必须有别名

```sql
-- ❌
SELECT * FROM (SELECT 1 AS n);
-- ERROR 1248 (42000): Every derived table must have its own alias

-- ✅
SELECT * FROM (SELECT 1 AS n) AS t;
```

> [!danger] 1248 是 MySQL 的硬性要求
> 没有别名，外层就没法引用这张"临时表"的列。`AS` 本身可以省（`FROM (...) t` 也合法），但**别名不能省**。
> 养成"右括号 + AS 别名"连写的肌肉记忆，这类报错就再也不会出现。

### 2.2 内层别名不会跑出去

派生表里面的表别名、列别名有各自的作用域：

```sql
-- ❌ e 是内层别名，外层不认识
SELECT e.emp_name
FROM (SELECT emp_name, salary FROM emp AS e) AS t;
-- ERROR 1054 (42S22): Unknown column 'e.emp_name' in 'field list'

-- ✅ 外层只认派生表别名 t
SELECT t.emp_name
FROM (SELECT emp_name, salary FROM emp AS e) AS t;
```

| 别名 | 写在哪 | 谁能看见 |
| --- | --- | --- |
| 派生表别名 `t` | 右括号之后 | **外层**（以及更外层） |
| 内层表别名 `e` | 内层 `FROM` | 只在括号内 |
| 内层列别名 `avg_sal` | 内层 `SELECT` | 变成派生表的**列名**，外层通过 `t.avg_sal` 访问 |

### 2.3 列名：内层起什么名，外层就叫什么

派生表对外暴露的列名 = 内层 `SELECT` 列表的列名。表达式必须起别名：

```sql
-- ⚠️ 列名变成 "salary * 12"，外层只能写反引号，极难读
SELECT t.`salary * 12` FROM (SELECT salary * 12 FROM emp) AS t;

-- ✅ 内层起好名
SELECT t.annual FROM (SELECT salary * 12 AS annual FROM emp) AS t;
```

### 2.4 列名必须唯一

```sql
-- ❌ 两列都叫 dept_id
SELECT * FROM (
    SELECT e.dept_id, d.dept_id
    FROM emp AS e JOIN dept AS d ON e.dept_id = d.dept_id
) AS t;
-- ERROR 1060 (42S21): Duplicate column name 'dept_id'
```

```sql
-- ✅ 在派生表内部就把重名列区分开
SELECT * FROM (
    SELECT e.dept_id AS emp_dept_id,
           d.dept_id AS dept_dept_id
    FROM emp AS e JOIN dept AS d ON e.dept_id = d.dept_id
) AS t;
```

> [!warning] 派生表不是真的表
> 它没有索引、没有统计信息、不能直接 `UPDATE`，也**不能在同一个语句里被引用两次**：
> ```sql
> FROM (SELECT ...) AS t JOIN (SELECT ...) AS t ON ...  -- ERROR 1066 Not unique table/alias
> ```
> 需要复用同一个中间结果时，要么把子查询**重复写一遍**，要么用 8.0 的 **CTE**（见第五章）。

## 三、五个典型用途

### 3.1 先聚合，再过滤（`WHERE` 不能写聚合）

```sql
-- ❌ 聚合函数不能出现在 WHERE
SELECT dept_id, AVG(salary) AS avg_sal
FROM emp
WHERE AVG(salary) > 9000
GROUP BY dept_id;
-- ERROR 1111 (HY000): Invalid use of group function
```

`WHERE` 执行时还没分组，"组成员的平均值"根本不存在。把聚合放进派生表，外层就能当普通列过滤：

```sql
-- ✅ 派生表版本
SELECT t.dept_id, t.avg_sal
FROM (
    SELECT dept_id, ROUND(AVG(salary), 2) AS avg_sal
    FROM emp
    GROUP BY dept_id
) AS t
WHERE t.avg_sal > 9000;
```

它和 `HAVING` 是**等价**的：

```sql
-- ✅ HAVING 版本（更短）
SELECT dept_id, ROUND(AVG(salary), 2) AS avg_sal
FROM emp
GROUP BY dept_id
HAVING AVG(salary) > 9000;
```

| 场景 | 推荐写法 | 原因 |
| --- | --- | --- |
| 只是"分组后筛一筛" | `HAVING` | 少一层嵌套，优化器路径最短 |
| 聚合结果还要**继续 JOIN / 再加工** | 派生表 | 中间结果要当"表"用 |
| 想在外层 `WHERE` 用**列别名** | 派生表 | `WHERE` 认派生表列名 |
| 团队规范要求"过滤统一用 `WHERE`" | 派生表 | 统一心智模型 |

> [!note] 二者不是对错之分，是**表达能力**之分
> `HAVING` 只能"筛完就结束"；派生表把聚合结果变成一张可继续操作的表，能再连接、再聚合、再套一层。
> 能写 `HAVING` 的简单场景，优先 `HAVING`；一旦中间结果要被复用或再连接，就轮到派生表。

### 3.2 先聚合，再连接：拿"组值"和明细行比

需求：找出**工资高于本部门平均**的员工。

```sql
-- ❌ 相关子查询：外层每行都要重算一次部门均值
SELECT e.emp_name, e.salary
FROM emp AS e
WHERE e.salary > (
    SELECT AVG(x.salary) FROM emp AS x WHERE x.dept_id = e.dept_id
);

-- ✅ 派生表：每组均值只算一次，再 JOIN
SELECT e.emp_name, e.salary, t.avg_sal
FROM emp AS e
JOIN (
    SELECT dept_id, AVG(salary) AS avg_sal
    FROM emp
    WHERE dept_id IS NOT NULL
    GROUP BY dept_id
) AS t ON e.dept_id = t.dept_id
WHERE e.salary > t.avg_sal
ORDER BY e.emp_id;
```

```
emp_name | salary | avg_sal
---------+--------+---------
李四     |  15000 | 13500.00
王五     |   9000 |  8750.00
```

（研发部均值 13500：张三 12000 不够；销售部均值 8750：赵六 8500 不够；孙七没部门，`JOIN` 直接落选。）

> [!tip] 这是"相关子查询 → 派生表 + JOIN"的固定改写
> 判断标准：内层是否引用了外层列、是否每行重算。需要逐行 → [[相关子查询]]；能一次算完 → 派生表 + `JOIN`。
> 改写思路的完整版见 [[相关子查询]] 第七章。

### 3.3 让 `WHERE` 用上 `SELECT` 别名

`WHERE` 执行在 `SELECT` 之前，别名还没诞生，直接引用报 `ERROR 1054`。套一层派生表，别名就成了"真实的列"：

```sql
-- ❌ Unknown column 'annual' in 'where clause'
SELECT emp_name, salary * 12 AS annual
FROM emp
WHERE annual > 100000;

-- ✅ 派生表：先算出 annual，外层再过滤
SELECT t.emp_name, t.annual
FROM (
    SELECT emp_name, salary * 12 AS annual
    FROM emp
) AS t
WHERE t.annual > 100000
ORDER BY t.annual DESC;
```

```
emp_name | annual
---------+--------
李四     | 180000
张三     | 144000
王五     | 108000
赵六     | 102000
```

> [!info] 原理
> 派生表把"计算列"固化成了结果集的**列名**，外层 `WHERE` 看到的是 `t.annual` 这个列，不再是一条待求值的表达式。
> 这是 [[Where]] 第七章"别名不能用在 WHERE"里"方案二"的展开版。

### 3.4 先排序 / 限量，再参与连接

先取工资最高的 3 个人，再补上部门名：

```sql
SELECT t.emp_name, t.salary, d.dept_name
FROM (
    SELECT emp_name, salary, dept_id
    FROM emp
    ORDER BY salary DESC
    LIMIT 3
) AS t
LEFT JOIN dept AS d ON t.dept_id = d.dept_id
ORDER BY t.salary DESC;
```

```
emp_name | salary | dept_name
---------+--------+----------
李四     |  15000 | 研发部
张三     |  12000 | 研发部
王五     |   9000 | 销售部
```

> [!warning] 派生表里的 `ORDER BY` 只有配 `LIMIT` 才有意义
> 不带 `LIMIT` 的 `ORDER BY`，优化器**可以直接丢掉**——因为外层关系的行顺序本来就不保证。想控制最终顺序，**必须在外层写 `ORDER BY`**。
> 即使内层带了 `LIMIT`，它也只保证"选中的是哪几行"，不保证外层拼接后的顺序。

> [!tip] "每组 Top-N" 不能用普通派生表
> 普通派生表只算一次，没法"每个部门各取前 2 名"。需要：
> - 8.0.14+ 用 **`LATERAL`**（第七章）
> - 或窗口函数 `ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC)` 再过滤 `rn <= 2`

### 3.5 绕开 `ERROR 1093`：`UPDATE` / `DELETE` 引用目标表

```sql
UPDATE emp SET salary = salary + 100
WHERE salary < (SELECT AVG(salary) FROM emp);
-- ERROR 1093 (HY000): You can't specify target table 'emp' for update in FROM clause
```

MySQL 不允许在改目标表的子查询里再读目标表。套一层派生表**强迫物化**，就能绕过：

```sql
-- ✅ 绕法一：派生表包一层
UPDATE emp
SET salary = salary + 100
WHERE salary < (
    SELECT avg_sal FROM (
        SELECT AVG(salary) AS avg_sal FROM emp
    ) AS tmp
);

-- ✅ 绕法二：改成 JOIN，语义更清楚
UPDATE emp AS e
JOIN (
    SELECT AVG(salary) AS avg_sal FROM emp
) AS t ON TRUE
SET e.salary = e.salary + 100
WHERE e.salary < t.avg_sal;
```

> [!danger] 这层派生表不是"可有可无的装饰"
> 它存在的目的就是**阻止优化器把子查询合并回外层**，逼 MySQL 先把平均值算成一个独立结果集。去掉 `AS tmp` 别名还会直接报 1248。
> 完整讨论见 [[Update|Update]]。

## 四、多层嵌套：从里往外读

派生表里还能再套派生表。读法永远是**最内层先算**：

```sql
SELECT s.dept_id, s.avg_sal
FROM (
    SELECT base.dept_id, AVG(base.salary) AS avg_sal
    FROM (
        SELECT dept_id, salary
        FROM emp
        WHERE dept_id IS NOT NULL
    ) AS base
    GROUP BY base.dept_id
) AS s
WHERE s.avg_sal > 9000;
```

执行顺序：

| 步骤 | 做什么 | 结果 |
| --- | --- | --- |
| ① 最内层 `base` | 去掉孙七（`dept_id IS NULL`） | 4 行 |
| ② 中层 `s` | 按部门求平均 | 2 行：1001 → 13500、1002 → 8750 |
| ③ 外层 `WHERE` | 筛 `avg_sal > 9000` | 只剩 1001 |

```
dept_id | avg_sal
--------+---------
   1001 | 13500.00
```

> [!warning] 别把作用域和嵌套层次搞混
> - 最内层别名 `base` **只能在中层用**，外层 `s` 看不到
> - 中层别名 `s` 才能被最外层引用
> - 每多一层，就多一个别名空间；起名统一用 `t1` / `t2` 或语义名，比 `t` 套 `t` 清晰得多

> [!tip] 嵌套超过两层就该考虑换了
> 三层以上的派生表**可读性急剧下降**，排错时几乎无法一眼看出哪个条件属于哪层。此时优先：
> - 8.0+ 改用 **CTE**（`WITH a AS (...), b AS (...) SELECT ...`），从上往下读
> - 中间结果很大时**落地成临时表**并建索引
> - 把逻辑拆成多条语句，交给应用层编排

## 五、派生表 vs 子查询 / 视图 / 临时表 / CTE

先把几个容易混的概念摆在一起：

| 形态 | 写法 | 生命周期 | 一个语句里能引用几次 | MySQL 版本 |
| --- | --- | --- | --- | --- |
| **标量 / 列子查询** | `WHERE x IN (SELECT ...)` | 语句内 | 每次都要重写 | 一直有 |
| **派生表** | `FROM (SELECT ...) AS t` | 语句内 | ❌ 一次（重写才行） | 一直有 |
| **CTE** | `WITH t AS (SELECT ...)` | 语句内 | ✅ 多次 | **8.0+** |
| **视图** | `CREATE VIEW v AS SELECT ...` | 持久（只存定义） | ✅ 跨语句 | 一直有 |
| **临时表** | `CREATE TEMPORARY TABLE ...` | 会话 | ✅ | 一直有 |

> [!info] 一句话区分
> - **子查询**回答"值 / 集合是多少"，派生表回答"这张表长什么样"
> - **视图 = 有名字、存起来的派生表；派生表 = 一次性的视图**
> - **CTE = 可以起名、可以被引用多次的派生表**（还能递归）
> - **临时表 = 真正落了地、能建索引的中间结果**

### 5.1 CTE：8.0 之后的"更好写法"

同样的需求，用 CTE 写：

```sql
WITH dept_avg AS (
    SELECT dept_id, AVG(salary) AS avg_sal
    FROM emp
    WHERE dept_id IS NOT NULL
    GROUP BY dept_id
)
SELECT e.emp_name, e.salary, a.avg_sal
FROM emp AS e
JOIN dept_avg AS a ON e.dept_id = a.dept_id
WHERE e.salary > a.avg_sal;
```

CTE 的三个优势：

1. **可读性**：定义在前，使用在后，从上往下读
2. **可复用**：同一个 `dept_avg` 可以在后面的 `JOIN`、`UNION` 里多次引用，派生表做不到
3. **可递归**：`WITH RECURSIVE` 能展开任意深度的树（见 [[SELF JOIN]]）

> [!warning] CTE 不是"性能银弹"
> 它和派生表遵循**同一套合并 / 物化规则**（第六章）。`WITH` 只是语法糖，不会自动让查询变快；有时 MySQL 还会把 CTE 物化，反而比内联子查询多一步。
> 5.7 及更早版本不支持 CTE，只能写派生表。

### 5.2 什么时候用哪个

```sql
-- 同一个中间结果要用两次 → 只能 CTE（或临时表）
WITH t AS (SELECT dept_id, AVG(salary) AS avg_sal FROM emp GROUP BY dept_id)
SELECT * FROM t WHERE avg_sal > 10000
UNION ALL
SELECT * FROM t WHERE avg_sal < 8000;
```

| 需求 | 选择 |
| --- | --- |
| 一次性中间结果 | 派生表 / 子查询 |
| 同一结果引用多次、层级多 | CTE（8.0+） |
| 跨多条语句复用 | 视图或临时表 |
| 中间结果大、要反复 JOIN | 临时表 + 索引 |
| 递归层级 | 递归 CTE |

## 六、性能：合并还是物化

派生表有两条执行路径，性能差异很大：

| 路径 | 触发条件 | 怎么执行 | 代价 |
| --- | --- | --- | --- |
| ==**合并**（merge）== | 派生表足够简单 | 直接把内层 `SELECT` **展开**进外层，条件可下推、索引可用 | 低 |
| ==**物化**（materialize）== | 含聚合、`GROUP BY`、`HAVING`、`DISTINCT`、`LIMIT`、`UNION`、窗口函数等 | 先算出一个**临时结果集**，外层再扫它 | 高 |

> [!important] 合并的条件
> MySQL **5.7.6+** 引入 `derived_merge` 优化（默认开启）。满足以下条件时，派生表会被合并：
> - 内层是**简单 SELECT**：没有聚合函数、`GROUP BY`、`HAVING`、`DISTINCT`、`LIMIT`、`UNION`、窗口函数
> - 没有用户变量赋值等副作用
> - 外层没有阻止合并的结构（如某些外连接、`STRAIGHT_JOIN` 等）
>
> 合并后，外层 `WHERE` 能**下推到基表**，索引才有机会用上。

> [!danger] 物化之后，索引可能是断的
> 一旦派生表被物化成临时表：
> - 临时表通常**没有业务索引**，外层连接只能全扫（优化器偶尔会自动建临时索引，但不能依赖）
> - 没有统计信息，优化器**估不准行数**，可能选错连接顺序
> - 中间结果可能很大，内存放不下就落盘，慢一个数量级
>
> 这就是"派生表写得好好的，`EXPLAIN` 一看 `<derived2>` + `type=ALL`"的由来。

### 6.1 怎么看出来

```sql
EXPLAIN
SELECT t.dept_id, t.avg_sal
FROM (
    SELECT dept_id, AVG(salary) AS avg_sal
    FROM emp
    GROUP BY dept_id
) AS t
WHERE t.avg_sal > 9000;
```

```
id | select_type | table      | type | key  | rows | Extra
---+-------------+------------+------+------+------+-----------------
 1 | PRIMARY     | <derived2> | ALL  | NULL |    3 | Using where
 2 | DERIVED     | emp        | ALL  | NULL |    5 | Using temporary
```

| 信号 | 含义 |
| --- | --- |
| `table` 列出现 `<derivedN>` | 派生表**被物化**了（合并的话会直接看到基表） |
| `select_type = DERIVED` | 这一行是派生表的内部查询 |
| `FORMAT=JSON` 里的 `materialized_from_subquery` | 确认走了物化 |
| `type = ALL` 且 `key = NULL` | 临时表没有可用索引 |

```sql
-- 排查时临时关闭合并，观察物化的真实代价（只建议会话级）
SET SESSION optimizer_switch = 'derived_merge=off';
```

> [!info] 8.0.22 起：物化也能条件下推
> 较早版本里，物化了的派生表是"黑盒"，外层 `WHERE` 进不去；MySQL **8.0.22** 增加了**派生表条件下推**（derived condition pushdown），能把外层条件塞进内层 `WHERE`，减少物化行数。
> 但它**仍然改变不了临时表无索引**的事实——它只减少行数。

### 6.2 写派生表的性能习惯

| 做法 | 原因 |
| --- | --- |
| **过滤条件尽量写在内层** | 减少物化行数；即使优化器能下推，明确写出来也更稳 |
| **只 `SELECT` 需要的列** | 临时表按列宽占用内存，`SELECT *` 会把无用列一起物化 |
| **不带 `LIMIT` 就别写 `ORDER BY`** | 排序会被丢弃，白写 |
| **大结果反复用 → 临时表 + 索引** | 派生表没有索引，临时表可以自己建 |
| **复杂多层 → 改 CTE** | 可读性优先；物化规则相同 |
| **上线前 `EXPLAIN` 一眼** | 看有没有 `<derivedN>`、`type=ALL` |

> [!tip] 什么时候物化反而更好
> 物化不总是坏事：当派生表**结果很小、外层要反复探测**时，物化成一张小临时表再连接，可能比把复杂子查询展开进每一行更快。
> 判断标准仍然是 `EXPLAIN` 的实际行数，而不是"派生表一定慢"的直觉。

## 七、`LATERAL` 派生表（8.0.14+）

普通派生表是**独立**的：写在内层的查询**不能引用同一 `FROM` 里前面的表**：

```sql
-- ❌ 不写 LATERAL：内层看不到 d，即使 8.0.14+ 也一样报错
SELECT d.dept_name, t.emp_name
FROM dept AS d
JOIN (
    SELECT emp_name FROM emp WHERE dept_id = d.dept_id
) AS t ON TRUE;
-- ERROR 1054 (42S22): Unknown column 'd.dept_id' in 'where clause'
```

`LATERAL` 打开这个口子：内层可以**逐行引用外层表**，于是能做"每组的 Top-N"：

```sql
SELECT d.dept_name, t.emp_name, t.salary
FROM dept AS d
JOIN LATERAL (
    SELECT e.emp_name, e.salary
    FROM emp AS e
    WHERE e.dept_id = d.dept_id
    ORDER BY e.salary DESC
    LIMIT 2
) AS t ON TRUE
ORDER BY d.dept_id, t.salary DESC;
```

```
dept_name | emp_name | salary
----------+----------+--------
研发部    | 李四     |  15000
研发部    | 张三     |  12000
销售部    | 王五     |   9000
销售部    | 赵六     |   8500
```

（财务部没人，`JOIN` 直接不产生行；要保留它得写 `LEFT JOIN LATERAL ... ON TRUE`。）

> [!important] `LATERAL` 的语义
> - 加在派生表前面：`JOIN LATERAL (...) AS t ON TRUE`
> - 内层**每处理外层一行就跑一次**，本质是"相关派生表"
> - 必须接 `ON TRUE`（或用逗号连接），因为它不是按等值条件关联
> - MySQL **8.0.14+** 才支持

> [!tip] 没有 `LATERAL` 怎么办
> - **窗口函数**（8.0+）：先 `ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC)` 再筛 `rn <= 2`
> - **相关子查询**：`SELECT (SELECT ... LIMIT 1)` 逐行取值，但只能取单值、性能差
> - **自连接 + 计数**：老式"组内排名"写法，可读性差，不推荐

## 八、常见报错与坑

> [!failure] ERROR 1248：Every derived table must have its own alias
> 派生表忘写别名。右括号后立刻补 `AS t`。

> [!failure] ERROR 1054：Unknown column
> 三种典型：
> - 外层引用了**内层表别名**（`e.emp_name`）→ 改成派生表别名 `t.emp_name`
> - 列名拼错 / 内层表达式没起别名
> - 想在内层引用外层表（非 `LATERAL`）→ 见第七章

> [!failure] ERROR 1060：Duplicate column name
> 派生表内部出现了**重名列**（常见于 `JOIN` 两张表都取 `dept_id`）。在派生表内部用 `AS` 区分开。

> [!failure] ERROR 1066：Not unique table/alias
> 同一个语句里给两个派生表起了**相同别名**，或自连接没区分别名。

> [!failure] ERROR 1093：You can't specify target table ...
> `UPDATE` / `DELETE` 的子查询引用了目标表。套一层派生表强迫物化，或改 `JOIN`（第三章 3.5）。

> [!warning] 不报错但结果不对：`ORDER BY` 被丢弃
> 派生表里的 `ORDER BY` 不配 `LIMIT` 时，优化器可以合法地删掉它。**要顺序就在最外层写 `ORDER BY`**。

> [!warning] 不报错但很慢：物化 + 无索引
> `EXPLAIN` 出现 `<derivedN>` 和 `type=ALL` 就要警惕。先看能否把过滤写进内层、减少列、去掉对排序的依赖，再考虑临时表。

## 九、速查表

| 需求 | 写法 |
| --- | --- |
| 聚合结果再过滤 | `FROM (SELECT 组键, AVG(...) AS avg FROM ... GROUP BY 组键) AS t WHERE t.avg > ...` |
| 组值和明细行比 | `JOIN (SELECT 组键, AVG(...) ...) AS t ON ... WHERE 明细 > t.avg` |
| 让 `WHERE` 用列别名 | 把计算列放进派生表，外层引用 `t.别名` |
| 先取前 N 再连接 | 内层 `ORDER BY ... LIMIT n`，外层再 `JOIN` |
| 绕开 `1093` | 子查询外再套一层派生表，或改 `JOIN` |
| 每组 Top-N | 8.0.14+ `JOIN LATERAL (... ORDER BY ... LIMIT n) ON TRUE` |
| 同一中间结果用多次 | 8.0+ CTE `WITH t AS (...)` |
| 中间结果大、反复用 | 临时表 + 索引 |
| 检查是否物化 | `EXPLAIN` 看 `<derivedN>` / `FORMAT=JSON` 的 `materialized_from_subquery` |

判断流程：

| 问自己 | 答 | 结论 |
| --- | --- | --- |
| 这个中间结果要当"表"再查吗？ | 是 | 用派生表 / CTE |
| 同一结果要引用多次吗？ | 是 | CTE（8.0+）或临时表 |
| 每行结果不同（要引用外层列）吗？ | 是 | `LATERAL`（8.0.14+） |
| 只是分组后筛一下吗？ | 是 | 直接用 `HAVING`，不必套派生表 |

> [!question] 自测三连
> 1. 派生表为什么必须起别名？漏写报哪个错误码？
> 2. 内层 `SELECT` 里的列别名，和外层怎么对应？内层的表别名 `e` 外层能用吗？
> 3. 什么情况下派生表会被物化？物化后为什么可能突然变慢？怎么在 `EXPLAIN` 里看出来？

---

> [!quote] 一句话记忆
> **派生表 = 写在 `FROM` 里的 `SELECT`，用完就扔的临时表**：必须别名（1248），外层只认别名；聚合结果先落地再过滤 / 连接；简单派生表会被**合并**，带聚合 / `LIMIT` / `UNION` 的会被**物化**——物化后没索引，写之前先 `EXPLAIN`。
