# 查询优化 —— 从慢查询到执行计划

> [!abstract] 一句话
> 查询优化有固定套路：**先定位慢 SQL → 再看执行计划 → 再改索引或 SQL → 最后验证**。
> 跳过前两步直接"凭感觉加索引"，通常越优化越慢。

> [!info] 和 [[管理索引]] 的分工
> [[管理索引]] 讲"索引怎么建、怎么查、怎么维护"；
> 本篇讲"**查询为什么慢、优化器为什么不用索引、怎么改**"。

---

## 一、优化流程

| 步骤 | 做什么 | 常用工具 |
| --- | --- | --- |
| ① 定位 | 找出**最慢、最频繁、扫描行数最多**的 SQL | 慢查询日志、`performance_schema`、`sys` 库 |
| ② 分析 | 看优化器**打算怎么执行** | `EXPLAIN`、`EXPLAIN ANALYZE`、`optimizer_trace` |
| ③ 改造 | 加/改索引、重写 SQL、调整表结构 | `ALTER TABLE`、SQL 改写 |
| ④ 验证 | 对比**扫描行数、耗时、执行计划** | `EXPLAIN ANALYZE`、监控、压测 |

> [!warning] 优化的第一原则：**先测量，再动手**
> 没有 `EXPLAIN` 的优化都是猜测。
> 同一个 SQL 在不同数据量、不同统计信息下可能走完全不同的计划，"我本地很快"说明不了任何问题。

## 二、先定位：慢查询从哪里来

### 2.1 慢查询日志

```sql
-- 运行时开启（重启失效，永久配置写 my.cnf）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;                 -- 超过 1 秒记录
SET GLOBAL log_queries_not_using_indexes = ON;  -- 记录未走索引的语句

SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';
```

`my.cnf` 持久配置：

```ini
[mysqld]
slow_query_log = 1
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 1
log_queries_not_using_indexes = 1
log_throttle_queries_not_using_indexes = 10
```

> [!warning] `log_queries_not_using_indexes` 会刷屏
> 小表全表扫描本来就很正常，这个开关会把它们全部记下来，日志迅速膨胀。
> 生产环境建议配合 `log_throttle_queries_not_using_indexes` 限流，或者只在排查期临时开启。

常用分析工具：

```bash
# 按总耗时排序，取前 10 条
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log

# 更强大的聚合分析（Percona Toolkit）
pt-query-digest /var/log/mysql/slow.log
```

### 2.2 `performance_schema`：按 SQL 指纹聚合

```sql
SELECT DIGEST_TEXT,
       COUNT_STAR                                   AS exec_count,
       ROUND(SUM_TIMER_WAIT / 1e12, 2)              AS total_sec,
       ROUND(AVG_TIMER_WAIT / 1e12, 4)              AS avg_sec,
       SUM_ROWS_EXAMINED                            AS rows_examined,
       SUM_ROWS_SENT                                AS rows_sent,
       SUM_NO_INDEX_USED                            AS no_index_used,
       SUM_CREATED_TMP_TABLES                       AS tmp_tables,
       SUM_SORT_ROWS                                AS sort_rows
  FROM performance_schema.events_statements_summary_by_digest
 ORDER BY SUM_TIMER_WAIT DESC
 LIMIT 10;
```

> [!tip] 重点看两个比值
> - **`rows_examined / rows_sent`**：扫描很多行却只返回几行 → 索引或过滤条件有问题
> - **`no_index_used` / `tmp_tables` / `sort_rows`**：频繁全表扫描、临时表、排序 → 重点优化对象
>
> 耗时高但扫描行数少，可能是锁等待、I/O 抖动或返回数据量太大，不一定是索引问题。

### 2.3 当前会话与锁

```sql
-- 正在执行的语句
SHOW FULL PROCESSLIST;

SELECT ID, USER, HOST, DB, COMMAND, TIME, STATE, INFO
 FROM information_schema.PROCESSLIST
 WHERE COMMAND <> 'Sleep'
 ORDER BY TIME DESC;

-- 锁等待
SELECT * FROM sys.innodb_lock_waits\G

-- InnoDB 整体状态（锁、事务、死锁）
SHOW ENGINE INNODB STATUS\G
```

常见 `STATE` 与含义：

| `STATE` | 通常意味着 |
| --- | --- |
| `Sending data` | 正在扫描/读取并发送结果，可能是大扫描 |
| `Copying to tmp table` | 正在写临时表，常见于 `GROUP BY` / `DISTINCT` / `UNION` |
| `Sorting result` | 正在排序，常见于 `ORDER BY` 无索引 |
| `Locked` | 等行锁 |
| `Waiting for table metadata lock` | 等元数据锁，常见于 DDL 被长事务阻塞 |

### 2.4 `sys` 库：开箱即用的诊断视图

```sql
SELECT * FROM sys.statement_analysis LIMIT 10;              -- 综合慢 SQL
SELECT * FROM sys.statements_with_full_table_scans LIMIT 10; -- 全表扫描
SELECT * FROM sys.statements_with_sorting LIMIT 10;          -- 排序
SELECT * FROM sys.statements_with_temp_tables LIMIT 10;      -- 临时表
```

> [!note] `sys` 库是 `performance_schema` 的"人话版"
> 底层还是 `performance_schema`，只是帮你把常用分析写成了视图。用之前确认 `performance_schema = ON`。

### 2.5 Handler 计数器：判断到底扫了多少

```sql
FLUSH STATUS;

SELECT * FROM student WHERE name = '张三';

SHOW SESSION STATUS LIKE 'Handler_read%';
```

| 变量 | 含义 |
| --- | --- |
| `Handler_read_key` | 通过索引键读取的次数，越高说明索引用得多 |
| `Handler_read_next` | 按索引顺序读下一行，范围扫描/索引扫描 |
| `Handler_read_first` | 读索引第一行，常见于全索引扫描 |
| `Handler_read_rnd_next` | **按数据页顺序读下一行**，很高通常意味着**全表扫描** |

> [!tip] `Handler_read_rnd_next` 是最直观的"全表扫描计数器"
> 优化前后各跑一次，对比这个值，比只看耗时更稳定。

## 三、EXPLAIN 详解

### 3.1 三种用法

```sql
-- 最常用：看优化器的执行计划（不真正执行）
EXPLAIN SELECT * FROM student WHERE class_id = 1;

-- JSON 格式：能看到成本、join buffer、使用的算法
EXPLAIN FORMAT=JSON SELECT * FROM student WHERE class_id = 1;

-- 8.0.18+：真正执行，并输出实际耗时/行数（主要用于 SELECT）
EXPLAIN ANALYZE SELECT * FROM student WHERE class_id = 1;
```

> [!note] `EXPLAIN` 也能用于写语句
> `EXPLAIN` 支持 `SELECT` / `DELETE` / `INSERT` / `REPLACE` / `UPDATE`。
> 但 `EXPLAIN ANALYZE` 主要用于 `SELECT`，不要拿它去"真跑"一条 `DELETE`。

### 3.2 输出列速查

| 列 | 含义 | 重点 |
| --- | --- | --- |
| `id` | SELECT 的编号 | 相同 `id` 通常是同一个查询块；`id` 越大越先执行 |
| `select_type` | 查询类型 | `SIMPLE` / `PRIMARY` / `SUBQUERY` / `DERIVED` / `UNION` 等 |
| `table` | 当前访问的表 | 别名会显示在这里 |
| `partitions` | 命中的分区 | 分区裁剪是否生效 |
| `type` | **访问类型** | **最重要**：看是否全表扫描 |
| `possible_keys` | 可能用到的索引 | 只是"候选"，不代表真的用 |
| `key` | **实际使用的索引** | `NULL` = 没走索引 |
| `key_len` | 索引使用的字节数 | 判断联合索引用了几列 |
| `ref` | 索引比较的对象 | `const`、列名、函数结果 |
| `rows` | **估算扫描行数** | 越小越好，注意是估算 |
| `filtered` | 过滤后剩余百分比 | `rows × filtered%` ≈ 传给下一步的行数 |
| `Extra` | 额外信息 | `Using index` / `Using filesort` / `Using temporary` 等 |

### 3.3 `type` 访问类型：从好到坏

| 等级 | `type` | 含义 | 典型场景 |
| --- | --- | --- | --- |
| 🟢 最好 | `system` | 表只有一行 | 系统表/常量表 |
| 🟢 | `const` | 最多一行命中 | 主键 / 唯一索引等值查询 |
| 🟢 | `eq_ref` | 联表时每行只匹配一行 | 被驱动表用主键/唯一索引关联 |
| 🟢 | `ref` | 非唯一索引等值匹配 | 普通索引 `WHERE col = ?` |
| 🟡 | `fulltext` | 全文索引 | `MATCH ... AGAINST` |
| 🟡 | `ref_or_null` | `ref` + `IS NULL` | 索引列等值或为空 |
| 🟡 | `index_merge` | 合并多个索引 | `OR` 多列、`IN` 组合 |
| 🟡 | `unique_subquery` | `IN` 子查询用唯一索引 | `IN (SELECT pk ...)` |
| 🟡 | `index_subquery` | `IN` 子查询用普通索引 | `IN (SELECT key ...)` |
| 🟡 | `range` | 索引范围扫描 | `> < BETWEEN IN LIKE 'x%'` |
| 🔴 | `index` | **全索引扫描** | 扫描整棵索引树，通常要优化 |
| 🔴 最差 | `ALL` | **全表扫描** | 没走索引，大表上最危险 |

> [!warning] `type=index` 不等于"好"
> 它表示"扫描整棵索引树"，只是比全表扫描少读一些列。
> 大表上看到 `index`，和看到 `ALL` 一样要警惕：**用了索引 ≠ 用对了索引**。

> [!tip] 判断顺序
> 1. 大表上出现 `ALL` / `index` → 优先查索引
> 2. `possible_keys` 有、`key` 为 `NULL` → 优化器主动放弃了索引
> 3. `key` 不对 → 索引设计或统计信息有问题
> 4. `rows` 很大、`filtered` 很低 → 索引选择性不足或条件无法下推

### 3.4 `key_len`：联合索引用了几列

`key_len` 是**索引使用的字节数**，不是字符数。常见计算：

| 类型 | 字节数 |
| --- | --- |
| `TINYINT` | 1 |
| `SMALLINT` | 2 |
| `MEDIUMINT` | 3 |
| `INT` | 4 |
| `BIGINT` | 8 |
| `FLOAT` | 4 |
| `DOUBLE` | 8 |
| `DATE` | 3 |
| `DATETIME(0)` | 5 |
| `TIMESTAMP(0)` | 4 |
| `CHAR(n)` | `n × 字符集最大字节数` |
| `VARCHAR(n)` | `n × 字符集最大字节数 + 2` |

> [!important] 两个附加规则
> - **可空列 +1 字节**（用于存 NULL 标记）
> - `utf8mb4` 每字符最多 **4 字节**，`utf8` 最多 3 字节，`latin1` 1 字节
>
> 例：`VARCHAR(20) NOT NULL` 的 `utf8mb4` 列 = `20 × 4 + 2 = 82` 字节
> 例：`VARCHAR(20) NULL` 的 `utf8mb4` 列 = `20 × 4 + 2 + 1 = 83` 字节

假设索引 `idx_class_age (class_id INT NULL, age TINYINT NULL)`：

| 查询条件 | `key_len` | 说明 |
| --- | --- | --- |
| `WHERE class_id = 1` | `5` | `INT` 4 + 可空 1 |
| `WHERE class_id = 1 AND age = 18` | `7` | `5 + (TINYINT 1 + 可空 1)` |
| `WHERE age = 18` | — | `key` 为 `NULL`，最左前缀不满足 |

> [!tip] `key_len` 是最容易被忽略的排查利器
> 你以为用了联合索引的三列，`key_len` 一看只用了第一列——问题立刻暴露。
> 注意：`key_len` 不包含排序、索引页开销等，只能用来**估算用了几列**。

### 3.5 `Extra` 常见值

| `Extra` | 含义 | 要不要紧张 |
| --- | --- | --- |
| `Using index` | **覆盖索引**，不回表 | ✅ 好事 |
| `Using where` | 存储引擎取回行后，Server 层再过滤 | 🟡 看情况 |
| `Using index condition` | **索引条件下推（ICP）**，在索引层过滤 | ✅ 通常好事 |
| `Using filesort` | 无法用索引排序，需要额外排序 | 🟡 结果集大时要注意 |
| `Using temporary` | 使用了临时表 | 🟡 常见于 `GROUP BY` / `DISTINCT` / `UNION` |
| `Using join buffer (hash join)` | 使用哈希连接（8.0.18+） | 🟡 无索引等值连接 |
| `Using join buffer (Block Nested Loop)` | 使用块嵌套循环连接（旧版/非等值） | 🟡 通常说明被驱动表缺索引 |
| `Using MRR` | 多范围读，先排序再批量回表 | ✅ 通常好事 |
| `Using index for group-by` | 松散索引扫描优化 `GROUP BY` | ✅ 好事 |
| `Using index for skip scan` | 8.0.13+ 跳跃扫描 | ✅ 好事 |
| `Select tables optimized away` | 优化器直接从索引算出结果 | ✅ 好事 |
| `Impossible WHERE` | 条件恒假，不会执行 | ✅ 好事（但可能是 SQL 写错） |
| `Distinct` | 优化 `DISTINCT` | 🟡 看情况 |
| `Not exists` | 反连接优化 | ✅ 通常好事 |
| `Start temporary` / `End temporary` | 半连接物化 | 🟡 看情况 |
| `FirstMatch` | 半连接策略：找到第一条就停 | ✅ 通常好事 |
| `LooseScan` | 半连接策略：松散扫描 | ✅ 通常好事 |
| `Range checked for each record` | 每行都要重新选索引 | 🔴 通常说明缺合适索引 |

> [!warning] `Using filesort` 和 `Using temporary` 不是"死刑"
> 结果集只有几十行时，内存排序/临时表非常快，不值得为它大动干戈。
> 真正要优化的是：**大结果集 + `filesort` / `temporary` + 高并发**。

## 四、索引失效的常见场景

> [!abstract] 先纠正一个说法
> 很多"索引失效"并不是索引坏了，而是：
> 1. 写法让索引**在语法上无法使用**；
> 2. 优化器评估后认为**走索引更贵**，主动选择全表扫描。
>
> 两种情况处理方式不同：前者改 SQL，后者改索引/统计信息/数据分布。

### 4.1 函数或运算作用在索引列上

```sql
-- ❌ 索引列被函数包住
SELECT * FROM orders WHERE YEAR(created_at) = 2026;
SELECT * FROM student WHERE id + 1 = 100;

-- ✅ 把函数从列上拿掉，改成范围
SELECT * FROM orders
 WHERE created_at >= '2026-01-01'
   AND created_at <  '2027-01-01';

SELECT * FROM student WHERE id = 99;

-- ✅ 或者建函数索引（8.0.13+）
CREATE INDEX idx_created_year ON orders ((YEAR(created_at)));
```

> [!tip] 原则：**索引列要"裸奔"**
> 列上不要套函数、不要做算术、不要拼接字符串。把计算放到常量那一侧。

### 4.2 隐式类型转换

```sql
-- phone 是 VARCHAR(20)
-- ❌ 数字常量：MySQL 把列值转成数字比较，索引失效
SELECT * FROM user WHERE phone = 13800138000;

-- ✅ 字符串常量
SELECT * FROM user WHERE phone = '13800138000';
```

> [!important] 转换方向决定索引生死
> | 列类型 | 比较值 | MySQL 怎么做 | 索引 |
> | --- | --- | --- | --- |
> | `VARCHAR` | 数字 | **列转数字** | ❌ 失效 |
> | `INT` | 字符串 | **常量转数字** | ✅ 通常仍可用 |
> | `VARCHAR` | 字符串 | 直接比较 | ✅ |
>
> 结论：**类型对上，别让 MySQL 帮你转。** 最常见的坑就是手机号、身份证、订单号存成 `VARCHAR`，查询时忘了加引号。

### 4.3 前导通配符 `LIKE '%xxx'`

```sql
SELECT * FROM student WHERE name LIKE '张%';    -- ✅ 前缀匹配，能用索引
SELECT * FROM student WHERE name LIKE '%三';    -- ❌ 前导 %
SELECT * FROM student WHERE name LIKE '%三%';   -- ❌ 前后都 %
```

> [!tip] 必须做"包含搜索"怎么办？
> - 数据量中等：`FULLTEXT` 全文索引
> - 数据量大、要相关性排序：Elasticsearch / OpenSearch
> - 业务允许：改成前缀搜索、拼音首字母、标签等可索引的方案

### 4.4 `OR` 连接不同列

```sql
-- ❌ 两个列各有索引，也未必能用好；可能全表扫描
SELECT * FROM student WHERE class_id = 1 OR name = '张三';

-- ✅ 拆成 UNION ALL（注意去重语义）
SELECT * FROM student WHERE class_id = 1
UNION ALL
SELECT * FROM student WHERE name = '张三' AND class_id <> 1;

-- ✅ 或者建联合索引，让一个索引同时覆盖两列
KEY idx_class_name (class_id, name);
```

> [!note] `OR` 不总是失效
> - 同一列：`WHERE a = 1 OR a = 2` → 可以转成 `a IN (1,2)` 的范围扫描
> - 不同列但都有索引 → 可能走 `index_merge`
> - 不同列且有一个没索引 → 大概率全表扫描
>
> 用 `EXPLAIN` 看 `type` 和 `key`，不要凭直觉。

### 4.5 违反联合索引最左前缀

```sql
-- 索引 idx_class_age (class_id, age)
SELECT * FROM student WHERE age = 18;                 -- ❌ 跳过 class_id
SELECT * FROM student WHERE class_id = 1 AND age = 18; -- ✅
```

> [!tip] 补救方式
> - 给 `age` 单独建索引（如果它确实高频）
> - 或调整联合索引顺序为 `(age, class_id)`（看哪个查询更常见）
> - 或建 `(class_id, age)` + `(age)` 两个索引，但要权衡写入成本

### 4.6 范围条件之后的列

```sql
-- 索引 (class_id, age)
SELECT * FROM student WHERE class_id > 1 AND age = 18;
```

`class_id` 是范围条件，索引扫描到多个 `class_id` 区间；在每个区间内 `age` 虽然有序，但**无法用 `age` 继续缩小整体扫描范围**。
`Extra` 可能显示 `Using index condition`（ICP 在索引层过滤），但这不等于"用 `age` 做了范围定位"。

> [!tip] 如果 `age = 18` 很高频
> 考虑把索引改成 `(age, class_id)`，让等值列在前、范围列在后。

### 4.7 `!=` / `<>` / `NOT IN` / `NOT LIKE`

```sql
SELECT * FROM student WHERE status != 1;
SELECT * FROM student WHERE class_id NOT IN (1, 2, 3);
SELECT * FROM student WHERE name NOT LIKE '张%';
```

> [!warning] 不是语法上不能用，而是"通常不划算"
> 这类条件往往命中大部分行，优化器评估"走索引再回表"比"直接全表扫描"更贵，于是主动放弃索引。
> 如果确实只排除少量值，可以改写成 `IN` 正向列表，或调整索引让条件更有选择性。

### 4.8 `IS NULL` / `IS NOT NULL`

```sql
SELECT * FROM student WHERE class_id IS NULL;      -- ✅ 通常能用索引
SELECT * FROM student WHERE class_id IS NOT NULL;  -- 🟡 常全表扫描
```

索引里会存 `NULL` 值，所以 `IS NULL` 可以用索引。
`IS NOT NULL` 命中行太多时，优化器通常选择全表扫描。

### 4.9 区分度太低

```sql
-- gender 只有 M/F/U 三个值
SELECT * FROM student WHERE gender = 'M';
```

即使建了 `idx_gender`，优化器也可能算出来"走索引要回表一半的行，不如全表扫描"，于是 `key` 显示 `NULL`。

> [!tip] 低区分度列的正确用法
> 不要单独建索引；把它作为**联合索引的一部分**，和高区分度列组合：
> ```sql
> KEY idx_gender_class (gender, class_id)
> ```

### 4.10 统计信息过期

```sql
-- 大量导入/删除后
ANALYZE TABLE student;

-- 看统计信息相关参数
SHOW VARIABLES LIKE 'innodb_stats_persistent';
SHOW VARIABLES LIKE 'innodb_stats_auto_recalc';
```

统计信息失真时，优化器会低估/高估行数，选错索引甚至放弃索引。
`EXPLAIN` 的 `rows` 明显离谱，就是信号。

> [!tip] 数据分布倾斜时用直方图（8.0+）
> ```sql
> ANALYZE TABLE student UPDATE HISTOGRAM ON class_id WITH 32 BUCKETS;
> SELECT * FROM information_schema.COLUMN_STATISTICS
>  WHERE TABLE_NAME = 'student';
> ```
> 直方图帮助优化器理解"某些值特别多"的倾斜分布，但它**不能替代索引**。

### 4.11 字符集 / 排序规则不一致

```sql
-- t1.c 是 utf8mb4_general_ci，t2.c 是 utf8mb4_0900_ai_ci
SELECT * FROM t1 JOIN t2 ON t1.c = t2.c;
```

联表字段的**字符集或排序规则不一致**时，MySQL 需要转换，可能导致索引无法使用。

> [!warning] 联表三一致
> 类型一致、字符集一致、排序规则一致。
> 建表时统一 `utf8mb4` + 统一 `COLLATE`，能省掉大量隐性性能问题。

### 4.12 `SELECT *` 与覆盖索引

```sql
-- 索引 idx_class_score (class_id, score)
SELECT class_id, score FROM student WHERE class_id = 1;  -- ✅ Using index
SELECT *               FROM student WHERE class_id = 1;  -- 🟡 需要回表
```

`SELECT *` 本身不会让索引"失效"，但它会让覆盖索引失效，增加回表、网络传输和临时表开销。

> [!tip] 只取需要的列
> 这是成本最低、收益最稳定的优化之一。

### 4.13 混合排序方向（8.0 之前）

```sql
-- 索引 (a, b)，都是升序
SELECT * FROM t ORDER BY a ASC, b DESC;  -- 8.0 前无法用索引避免 filesort
```

MySQL 8.0 支持真正的降序索引：

```sql
CREATE INDEX idx_a_b ON t (a ASC, b DESC);
```

### 4.14 对索引列使用表达式排序

```sql
-- ❌ 排序表达式无法直接用索引
SELECT * FROM student ORDER BY UPPER(name);

-- ✅ 如果业务必须，建函数索引
CREATE INDEX idx_upper_name ON student ((UPPER(name)));
```

## 五、EXPLAIN 实战

### 5.1 统一示例表

```sql
CREATE TABLE student (
    id         BIGINT       NOT NULL AUTO_INCREMENT,
    stu_no     CHAR(10)     NOT NULL,
    name       VARCHAR(50)  NOT NULL,
    gender     CHAR(1)      DEFAULT 'U',
    age        TINYINT,
    class_id   INT,
    score      DECIMAL(5,2),
    created_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_stu_no (stu_no),
    KEY idx_class_age (class_id, age),
    KEY idx_class_score (class_id, score),
    KEY idx_created_at (created_at),
    KEY idx_name (name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE class (
    id   INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(30) NOT NULL,
    UNIQUE KEY uk_name (name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 5.2 等值查询：`const`

```sql
EXPLAIN SELECT * FROM student WHERE stu_no = '2026000001';
```

| id | select_type | table | type | key | key_len | rows | filtered | Extra |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | SIMPLE | student | `const` | `uk_stu_no` | 40 | 1 | 100.00 | `NULL` |

`CHAR(10)` + `utf8mb4` = 40 字节；唯一索引等值查询最多一行，`type=const`，非常理想。

### 5.3 联合索引：最左前缀

```sql
-- ✅ 两列都用上
EXPLAIN SELECT * FROM student WHERE class_id = 1 AND age = 18;
```

| type | key | key_len | rows | Extra |
| --- | --- | --- | --- | --- |
| `ref` | `idx_class_age` | 7 | 少量 | `NULL` |

`class_id INT NULL` = 5，`age TINYINT NULL` = 2，合计 7。

```sql
-- ❌ 跳过最左列
EXPLAIN SELECT * FROM student WHERE age = 18;
```

| type | key | key_len | rows | Extra |
| --- | --- | --- | --- | --- |
| `ALL` | `NULL` | `NULL` | 全表行数 | `Using where` |

### 5.4 范围查询：`range`

```sql
EXPLAIN SELECT * FROM student WHERE class_id = 1 AND age > 16;
```

| type | key | key_len | rows | Extra |
| --- | --- | --- | --- | --- |
| `range` | `idx_class_age` | 7 | 部分行 | `Using index condition` |

`class_id` 等值 + `age` 范围，联合索引正好适配。`Using index condition` 表示 ICP 在索引层先过滤掉不满足 `age > 16` 的索引项，减少回表。

### 5.5 排序：有没有 `filesort`

```sql
EXPLAIN SELECT id, name, score
  FROM student
 WHERE class_id = 1
 ORDER BY score DESC
 LIMIT 10;
```

有 `idx_class_score (class_id, score)` 时：

| type | key | rows | Extra |
| --- | --- | --- | --- |
| `ref` | `idx_class_score` | 少量 | `NULL`（或 `Using where`，视版本而定） |

排序由索引顺序直接满足，**没有 `Using filesort`**。

如果没有 `idx_class_score`，只有 `idx_class_age`：

| type | key | Extra |
| --- | --- | --- |
| `ref` | `idx_class_age` | `Using where; Using filesort` |

`class_id` 等值后，索引顺序是 `age`，不是 `score`，所以必须额外排序。

### 5.6 覆盖索引：`Using index`

```sql
EXPLAIN SELECT class_id, score
  FROM student
 WHERE class_id = 1
 ORDER BY score DESC
 LIMIT 10;
```

| type | key | Extra |
| --- | --- | --- |
| `ref` | `idx_class_score` | `Using index` |

查询列 `class_id`、`score` 全在索引里，主键 `id` 也在二级索引叶子中，**不需要回表**。

```sql
-- 多查一个 name，就无法覆盖
EXPLAIN SELECT class_id, score, name
  FROM student
 WHERE class_id = 1
 ORDER BY score DESC
 LIMIT 10;
-- Extra 不再有 Using index，需要回表取 name
```

### 5.7 联表查询

```sql
EXPLAIN SELECT s.name, c.name
  FROM student s
  JOIN class c ON s.class_id = c.id
 WHERE c.name = '高一1班';
```

期望计划：

| id | table | type | key | rows | Extra |
| --- | --- | --- | --- | --- | --- |
| 1 | `c` | `const` / `ref` | `uk_name` | 1 | `NULL` |
| 1 | `s` | `ref` | `idx_class_age` | 少量 | `NULL` |

- 先通过 `uk_name` 定位班级（驱动表）
- 再用 `idx_class_age` 的第一列 `class_id` 找学生（被驱动表）
- 被驱动表的关联列**必须有索引**，否则会退化成全表扫描 / BNL / hash join

> [!tip] 联表优化三件事
> 1. 被驱动表的 `JOIN` 列有索引
> 2. 两边字段类型、字符集、排序规则一致
> 3. 尽量让小结果集做驱动表（最终由优化器按成本决定）

### 5.8 子查询

```sql
EXPLAIN SELECT *
  FROM student
 WHERE class_id IN (SELECT id FROM class WHERE name = '高一1班');
```

MySQL 8.0 可能把它改写成**半连接（semi-join）**，常见策略：

| `Extra` / 策略 | 含义 |
| --- | --- |
| `FirstMatch` | 外表每行只要在内表找到第一条匹配就停 |
| `LooseScan` | 利用索引松散扫描去重 |
| `Start temporary` / `End temporary` | 物化内表结果 |
| `Materialize` | 物化子查询 |

> [!tip] 不要背"`IN` 一定比 `EXISTS` 快"或反过来
> MySQL 8.0 的优化器会做半连接改写，两者经常被优化成同一个计划。
> 正确做法：**两种写法都 `EXPLAIN` 一下，看 `rows` 和 `Extra`。**

### 5.9 深分页

```sql
-- ❌ 越往后越慢
EXPLAIN SELECT * FROM student ORDER BY id LIMIT 1000000, 10;
```

| type | key | rows | Extra |
| --- | --- | --- | --- |
| `index` | `PRIMARY` | 约 1000010 | `NULL` |

它要沿着主键索引**扫描前 1,000,010 行**，再把前 1,000,000 行丢掉。

```sql
-- ✅ 方案一：延迟关联，先在索引里取 10 个 id，再回表
SELECT s.*
  FROM student s
  JOIN (
      SELECT id FROM student ORDER BY id LIMIT 1000000, 10
  ) t ON s.id = t.id;

-- ✅ 方案二：游标分页，记住上一页最后一条 id
SELECT * FROM student WHERE id > 1000000 ORDER BY id LIMIT 10;
```

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 延迟关联 | 兼容 `OFFSET` 语义，回表少 | 仍需扫描偏移量之前的索引 |
| 游标分页 | 稳定 O(1) 定位，最快 | 不能随机跳页，要求排序键稳定唯一 |

> [!warning] 深分页的根因不是 `LIMIT`，是 `OFFSET`
> `LIMIT 1000000, 10` 的语义就是"数到第 100 万行再取 10 行"。
> 只要还用大 `OFFSET`，就没有真正的"瞬间完成"。

### 5.10 函数导致索引失效

```sql
-- ❌ 全表扫描
EXPLAIN SELECT * FROM student WHERE YEAR(created_at) = 2026;

-- ✅ 改成范围，走 idx_created_at
EXPLAIN SELECT * FROM student
 WHERE created_at >= '2026-01-01'
   AND created_at <  '2027-01-01';

-- ✅ 或建函数索引
CREATE INDEX idx_created_year ON student ((YEAR(created_at)));
```

## 六、SQL 改写清单

### 6.1 深分页

见 §5.9。优先用**游标分页**，其次**延迟关联**。

### 6.2 `COUNT` 查询

```sql
SELECT COUNT(*) FROM student;           -- ✅ 统计行数
SELECT COUNT(1) FROM student;           -- ✅ 与 COUNT(*) 基本等价
SELECT COUNT(score) FROM student;       -- ⚠️ 只统计 score 非 NULL 的行
```

> [!info] `COUNT(*)` 为什么"看起来快"
> InnoDB 不保存精确行数，`COUNT(*)` 也要扫描，但优化器会**选择最小的二级索引**来扫，减少 I/O。
> 它**不是 O(1)**，大表上仍然会慢。
>
> - 精确计数：`COUNT(*)`
> - 近似计数：`SHOW TABLE STATUS` / `EXPLAIN` 的 `rows`（估算，不准）
> - 高频计数：单独维护计数表（注意事务和并发）

> [!warning] `SQL_CALC_FOUND_ROWS` 已废弃
> 它会在分页查询时顺便算总数，但代价很高。改用两条 SQL：一条 `COUNT(*)`，一条分页查询。

### 6.3 `ORDER BY` / `GROUP BY`

```sql
-- ✅ 索引顺序与排序一致
SELECT id, name FROM student ORDER BY created_at DESC LIMIT 10;
-- 需要 idx_created_at

-- ✅ 分组列有索引
SELECT class_id, COUNT(*) FROM student GROUP BY class_id;
-- 需要 idx_class_age / idx_class_score 的最左列 class_id

-- ✅ 先 WHERE 再 GROUP BY
SELECT class_id, AVG(score)
  FROM student
 WHERE class_id = 1
 GROUP BY class_id;
```

> [!note] MySQL 8.0 不再隐式排序 `GROUP BY`
> 5.7 及以前，`GROUP BY` 可能附带排序；8.0 去掉了隐式排序。
> 如果业务依赖分组后的顺序，**必须显式写 `ORDER BY`**。

### 6.4 `HAVING` 能下推就下推

```sql
-- ❌ 先分组再过滤
SELECT class_id, AVG(score)
  FROM student
 GROUP BY class_id
HAVING class_id = 1;

-- ✅ 先过滤再分组
SELECT class_id, AVG(score)
  FROM student
 WHERE class_id = 1
 GROUP BY class_id;
```

`WHERE` 在分组前过滤行，`HAVING` 在分组后过滤组。能放 `WHERE` 的条件不要放 `HAVING`。

### 6.5 `UNION` → `UNION ALL`

```sql
-- ❌ UNION 会去重，可能产生临时表 + 排序
SELECT name FROM student WHERE class_id = 1
UNION
SELECT name FROM student WHERE class_id = 2;

-- ✅ 业务允许重复时用 UNION ALL
SELECT name FROM student WHERE class_id = 1
UNION ALL
SELECT name FROM student WHERE class_id = 2;
```

### 6.6 `NOT IN` 的 NULL 陷阱

```sql
-- 如果子查询返回 NULL，整个 NOT IN 可能返回空结果
SELECT * FROM student
 WHERE class_id NOT IN (SELECT id FROM class WHERE name IS NOT NULL);

-- ✅ 更稳的写法：NOT EXISTS
SELECT * FROM student s
 WHERE NOT EXISTS (
     SELECT 1 FROM class c WHERE c.id = s.class_id
 );

-- ✅ 或 LEFT JOIN ... IS NULL
SELECT s.*
  FROM student s
  LEFT JOIN class c ON s.class_id = c.id
 WHERE c.id IS NULL;
```

> [!danger] `NOT IN` + `NULL` 是经典坑
> `x NOT IN (1, NULL)` 的结果不是 `TRUE`，而是 `UNKNOWN`，`WHERE` 会把它当假处理。
> 用 `NOT EXISTS` 或 `LEFT JOIN ... IS NULL` 更安全。

### 6.7 `EXISTS` vs `IN`

```sql
-- 外表小、内表大：EXISTS 通常更自然
SELECT * FROM class c
 WHERE EXISTS (SELECT 1 FROM student s WHERE s.class_id = c.id);

-- 内表结果集小：IN 通常更自然
SELECT * FROM student WHERE class_id IN (1, 2, 3);
```

> [!tip] 不要背口诀
> MySQL 8.0 会把很多 `IN` 子查询改写成半连接，和 `EXISTS` 计划趋同。
> **看 `EXPLAIN` 的 `rows`、`Extra`，不要看句式。**

### 6.8 `SELECT *` → 明确列

```sql
-- ❌ 多读列、无法覆盖索引、增加网络和临时表开销
SELECT * FROM student WHERE class_id = 1;

-- ✅
SELECT id, name, score FROM student WHERE class_id = 1;
```

### 6.9 `ORDER BY RAND()` → 可控随机

```sql
-- ❌ 全表扫描 + 随机排序，大表上极慢
SELECT * FROM student ORDER BY RAND() LIMIT 10;

-- ✅ 按随机 id 近似取（id 有空洞时可能不足 10 条）
SELECT *
  FROM student
 WHERE id >= (SELECT FLOOR(RAND() * (SELECT MAX(id) FROM student)))
 ORDER BY id
 LIMIT 10;
```

> [!note] 随机取数的本质
> "随机"和"快速"天然矛盾。数据量很大时，通常用**预生成随机键**、**应用层随机 offset**，或接受"近似随机"。

### 6.10 批量操作代替循环

```sql
-- ❌ 循环 10000 次，每次一个事务/一次网络往返
-- INSERT INTO student (name) VALUES ('A');
-- INSERT INTO student (name) VALUES ('B');
-- ...

-- ✅ 批量插入
INSERT INTO student (name) VALUES ('A'), ('B'), ('C');

-- ✅ 大批量包在事务里
START TRANSACTION;
-- ... 分批 INSERT ...
COMMIT;
```

> [!tip] 批量操作的三条边界
> - 单条 SQL 别超过 `max_allowed_packet`（默认 64MB）
> - 每批 500~1000 行，分批提交
> - 大事务会长时间持锁、撑大 undo，未必比小批量快

## 七、Join 算法与驱动表

### 7.1 三种常见连接算法

| 算法 | 触发条件 | `Extra` | 特点 |
| --- | --- | --- | --- |
| **NLJ / INLJ**（嵌套循环） | 被驱动表关联列有索引 | 无特殊标记 | 外表每行去内表做索引查找，最理想 |
| **BNL**（块嵌套循环） | 被驱动表无索引，旧版本 | `Using join buffer (Block Nested Loop)` | 用 join buffer 批量比较，8.0.20 起等值连接被 hash join 取代 |
| **Hash Join** | 等值连接、无可用索引，8.0.18+ | `Using join buffer (hash join)` | 对小表建哈希表，再扫描大表探测 |
| **BKA**（批量键访问） | 有索引 + MRR | `Using join buffer (Batched Key Access)` | 批量回表，减少随机 I/O |

> [!info] 8.0.20 之后的变化
> 等值连接没有索引时，MySQL 优先使用 **hash join**，不再使用 BNL。
> 看到 `Using join buffer (hash join)` 不一定是坏事，但通常说明**被驱动表缺索引**；如果数据量不大，hash join 往往比补索引更划算。

### 7.2 驱动表怎么选

```sql
EXPLAIN SELECT ...
```

- `id` 相同的多行，**从上到下**就是连接顺序
- 第一行通常是**驱动表（外表）**
- 优化器按成本选择：小结果集、过滤后行数少的表更容易成为驱动表
- 需要强制顺序时用 `STRAIGHT_JOIN`（谨慎，数据变化后可能变慢）

> [!tip] 驱动表选择的原则
> - 被驱动表的**关联列必须有索引**
> - 驱动表的结果集**尽量小**
> - 但最终以 `EXPLAIN` 的实际计划为准，不要凭"小表驱动大表"的口号硬套

### 7.3 联表常见问题

| 问题 | 后果 | 解决 |
| --- | --- | --- |
| 关联列无索引 | 全表扫描 / hash join / BNL | 给被驱动表关联列建索引 |
| 类型不一致 | 隐式转换，索引失效 | `BIGINT` 对 `BIGINT`，别 `INT` 对 `BIGINT` |
| 字符集/排序规则不一致 | 无法用索引 | 统一 `utf8mb4` 和 `COLLATE` |
| 关联列套函数 | 索引失效 | 把函数移到常量侧 |
| 联表太多 | 中间结果爆炸 | 拆分查询、减少列、加索引、必要时反范式 |
| 大表 JOIN 大表 | 无论怎么优化都慢 | 分批、预聚合、宽表、离线计算 |

## 八、优化器、统计信息与 Hint

### 8.1 统计信息

```sql
ANALYZE TABLE student;   -- 更新索引统计信息
SHOW INDEX FROM student; -- 看 Cardinality
```

| 参数 | 作用 |
| --- | --- |
| `innodb_stats_persistent` | 统计信息持久化，重启不丢 |
| `innodb_stats_auto_recalc` | 数据变化超阈值时自动重算 |
| `innodb_stats_persistent_sample_pages` | 采样页数，越大越准、越慢 |

> [!warning] 优化器不是神
> 它依赖**估算**：`rows`、`filtered`、`Cardinality` 都可能失真。
> 数据倾斜、统计信息过期、关联列类型不一致，都会让它选错计划。

### 8.2 `optimizer_trace`：看优化器怎么想的

```sql
SET optimizer_trace = 'enabled=on';

SELECT * FROM student WHERE class_id = 1 AND age = 18;

SELECT * FROM information_schema.OPTIMIZER_TRACE\G

SET optimizer_trace = 'enabled=off';
```

输出里能看到：

- 候选索引及成本
- 为什么选了某个索引
- 是否做了条件下推、物化、半连接改写
- 最终选择的 join order

> [!tip] `optimizer_trace` 输出很长
> 只看 `considered_execution_plans`、`chosen_plan`、`rows_estimation` 这几段即可，不要从头啃到尾。

### 8.3 优化器开关

```sql
SELECT @@optimizer_switch;

-- 临时关闭/开启某个特性（会话级）
SET SESSION optimizer_switch = 'index_condition_pushdown=on';
SET SESSION optimizer_switch = 'mrr=on';
SET SESSION optimizer_switch = 'batched_key_access=on';
SET SESSION optimizer_switch = 'hash_join=on';
```

常见开关：

| 开关 | 作用 |
| --- | --- |
| `index_condition_pushdown` | 索引条件下推，减少回表 |
| `mrr` | 多范围读，批量回表 |
| `batched_key_access` | BKA，配合 MRR |
| `hash_join` | 哈希连接（8.0.18+） |
| `block_nested_loop` | 块嵌套循环 |
| `derived_merge` | 派生表合并 |
| `semijoin` | 半连接优化 |
| `materialization` | 子查询物化 |

> [!danger] 不要全局乱关优化器特性
> 这些开关是给排查问题用的。全局关闭可能让所有查询变慢，且很难回溯。
> 先在会话级验证，再评估是否值得改。

### 8.4 索引 Hint 与 `FORCE INDEX`

```sql
-- 推荐优化器使用指定索引
SELECT * FROM student FORCE INDEX (idx_class_score)
 WHERE class_id = 1 ORDER BY score DESC LIMIT 10;

-- 8.0 优化器 Hint（更细粒度）
SELECT /*+ INDEX(student idx_class_score) */ *
  FROM student
 WHERE class_id = 1;

SELECT /*+ NO_INDEX(student idx_class_age) */ *
  FROM student
 WHERE class_id = 1;
```

> [!warning] `FORCE INDEX` 是最后的止痛药
> 数据分布变化后，强制索引可能从"救命"变成"致命"。
> 优先修正索引设计、统计信息、SQL 写法；确实需要时，记录原因并定期复查。

## 九、执行计划之外：还可能慢在哪

> [!abstract] SQL 优化不是全部
> 执行计划很好，查询仍然慢，问题可能在锁、I/O、数据量、架构或应用层。

| 层面 | 常见问题 | 排查/解决 |
| --- | --- | --- |
| **锁** | 行锁等待、MDL 等待、长事务 | `sys.innodb_lock_waits`、`SHOW ENGINE INNODB STATUS` |
| **事务** | 大事务、未提交事务、undo 膨胀 | 缩短事务、分批提交 |
| **I/O** | 磁盘慢、buffer pool 不足、刷脏页 | 监控 I/O、增大 `innodb_buffer_pool_size` |
| **数据量** | 单表过大、历史数据不归档 | 分区、归档、冷热分离 |
| **表结构** | 字段过宽、类型不当、过度范式/反范式 | 精简字段、选对类型、适度冗余 |
| **应用层** | N+1 查询、循环查库、重复查询 | 批量查询、缓存、预加载 |
| **架构** | 单库扛不住读/写 | 读写分离、缓存、分库分表 |
| **硬件** | CPU/内存/磁盘瓶颈 | 升级配置、SSD、独立磁盘 |

> [!tip] 优化顺序
> **SQL / 索引 → 表结构 → 架构（缓存、读写分离、分库分表）→ 硬件**
> 不要一上来就分库分表。大多数"数据库性能问题"其实是一条缺索引的 SQL。

### 9.1 N+1 查询

```java
// ❌ 先查 100 个班级，再为每个班级查一次学生：1 + 100 次查询
for (Class c : classes) {
    List<Student> students = query("SELECT * FROM student WHERE class_id = ?", c.id);
}

// ✅ 一次批量查
List<Student> all = query(
    "SELECT * FROM student WHERE class_id IN (?, ?, ...)", ids);
```

> [!tip] N+1 是应用层最常见的"数据库慢"
> 数据库本身很快，但被调用了几百次。用批量查询、`JOIN`、缓存或 ORM 的预加载解决。

### 9.2 缓存

- 热点数据放 Redis / 本地缓存
- 注意缓存一致性、穿透、雪崩、击穿
- 缓存不是"先上再说"，要先确认数据访问模式

### 9.3 读写分离与分库分表

- 读多写少 → 读写分离（注意主从延迟）
- 单表过大 → 分区 / 归档 / 分表
- 单库写入瓶颈 → 分库分表（引入分布式事务、跨分片查询等复杂度）

> [!warning] 分库分表是最后手段
> 它会显著增加开发、运维、事务、查询的复杂度。
> 先把索引、SQL、表结构、缓存做到位，再考虑分片。

## 十、查询优化自查清单

- [ ] 已开启慢查询日志，或能从 `performance_schema` / `sys` 找到慢 SQL
- [ ] 已看 `rows_examined / rows_sent` 比值
- [ ] 已用 `EXPLAIN` 看 `type`、`key`、`key_len`、`rows`、`filtered`、`Extra`
- [ ] `type` 不是大表上的 `ALL` / `index`
- [ ] `key` 是预期索引，`key_len` 说明联合索引列用对了
- [ ] 高频查询没有 `Using filesort` / `Using temporary`（或结果集很小）
- [ ] 高频查询尽量 `Using index`（覆盖索引）
- [ ] 没有函数、隐式转换、前导 `%`、`OR` 等索引失效写法
- [ ] 联表字段类型、字符集、排序规则一致，关联列有索引
- [ ] 深分页已改写为游标分页或延迟关联
- [ ] 没有不必要的 `SELECT *`
- [ ] 统计信息不过期，必要时 `ANALYZE TABLE`
- [ ] 没有长事务、锁等待、MDL 阻塞
- [ ] 优化前后有对比数据（耗时、扫描行数、`Handler_read_*`）
- [ ] 已评估是否需要缓存、归档、读写分离、分库分表

## 十一、常见面试问答

> [!question] Q1：一条 SQL 很慢，你怎么排查？
> 1. 看慢查询日志 / `performance_schema`，确认慢在哪条 SQL、执行频率、扫描行数
> 2. `EXPLAIN` 看 `type`、`key`、`rows`、`Extra`
> 3. 判断是"没走索引""走错索引""回表太多""排序/临时表""锁等待"还是"数据量太大"
> 4. 针对性加/改索引、重写 SQL、更新统计信息
> 5. `EXPLAIN ANALYZE` 或监控对比优化前后
> 6. 仍不够再考虑表结构、缓存、归档、读写分离、分库分表

> [!question] Q2：`EXPLAIN` 里你最关注哪些字段？
> **`type`**（访问类型）、**`key`**（实际索引）、**`key_len`**（联合索引用了几列）、**`rows`**（估算扫描行数）、**`filtered`**（过滤比例）、**`Extra`**（覆盖索引/排序/临时表/ICP）。
> `possible_keys` 只作参考，`key` 才是实际选择。

> [!question] Q3：`type` 的性能等级怎么排？
> `system > const > eq_ref > ref > fulltext > ref_or_null > index_merge > unique_subquery > index_subquery > range > index > ALL`
> 大表上重点避免 `index` 和 `ALL`；`const` / `eq_ref` / `ref` / `range` 通常可接受。

> [!question] Q4：`Using filesort` 和 `Using temporary` 是什么意思？
> - `Using filesort`：无法利用索引顺序完成排序，需要额外排序（内存或磁盘）
> - `Using temporary`：需要临时表，常见于 `GROUP BY`、`DISTINCT`、`UNION`、复杂子查询
>
> 两者不一定慢，要看结果集大小；大结果集 + 高并发时才需要重点优化。

> [!question] Q5：哪些情况会导致索引失效？
> 常见：
> - 索引列上套函数/做运算
> - 隐式类型转换（`VARCHAR` 列和数字比较）
> - `LIKE '%xxx'` 前导通配符
> - 违反联合索引最左前缀
> - `OR` 连接不同列
> - 范围条件之后的列无法继续用于缩小范围
> - 低区分度列，优化器主动放弃索引
> - 统计信息过期
> - 联表字符集/排序规则不一致
>
> 注意：有些不是"失效"，而是优化器认为走索引不划算。

> [!question] Q6：深分页怎么优化？
> - **游标分页**：`WHERE id > 上一页最后一条 ORDER BY id LIMIT 10`，最快，但不能随机跳页
> - **延迟关联**：子查询先取 10 个 id，再回表取整行
> - 避免大 `OFFSET`；业务上考虑限制最大页数或改用搜索
> - 覆盖索引 + 稳定排序键

> [!question] Q7：`COUNT(*)` 为什么比 `COUNT(col)` 快？
> `COUNT(*)` 只统计行数，优化器会选择**最小的二级索引**扫描；
> `COUNT(col)` 还要判断 `col IS NOT NULL`，且不一定能选到最小索引。
> 但 `COUNT(*)` 在 InnoDB 里**不是 O(1)**，大表仍然要扫描。

> [!question] Q8：Join 的驱动表怎么选？
> 优化器按成本选择，通常会选**过滤后结果集小**的表做驱动表。
> 被驱动表的关联列必须有索引；否则会走 hash join / BNL / 全表扫描。
> 需要强制顺序时可用 `STRAIGHT_JOIN`，但要谨慎，数据变化后可能变慢。

> [!question] Q9：什么是覆盖索引？怎么判断？
> 查询需要的所有列都能从二级索引中拿到，不需要回表。
> `EXPLAIN` 的 `Extra` 出现 **`Using index`** 就是覆盖索引。
> 注意二级索引叶子包含索引列 + 主键，所以查主键和索引列通常可以覆盖。

> [!question] Q10：什么是最左前缀原则？
> 联合索引 `(a, b, c)` 只能从最左列开始连续使用：
> `(a)`、`(a,b)`、`(a,b,c)` 可以；`(b)`、`(b,c)`、`(a,c)` 不行（`a,c` 中 `c` 无法用于缩小范围）。
> 另外，某列用了范围条件后，右边的列通常无法继续用于范围定位。

> [!question] Q11：什么是索引下推（ICP）？
> MySQL 5.6+ 把 `WHERE` 中能用索引列判断的条件下推到存储引擎层，在**索引遍历时**就过滤，减少回表。
> `EXPLAIN` 的 `Extra` 显示 `Using index condition`。
> 它不能替代最左前缀，只是减少无效回表。

> [!question] Q12：Hash Join 和 Nested Loop Join 有什么区别？
> - **NLJ / INLJ**：外表每行去内表查找；内表关联列有索引时最快
> - **Hash Join**：对小表建哈希表，再扫描大表探测；适合**无索引的等值连接**，8.0.18+ 支持
> - **BNL**：旧版无索引连接方案，8.0.20 起等值连接被 hash join 取代
>
> 看到 `Using join buffer (hash join)` 说明没有走索引连接，数据量大时考虑补索引。

> [!question] Q13：为什么不要 `SELECT *`？
> - 多读不需要的列，增加 I/O 和网络传输
> - 无法使用覆盖索引，强制回表
> - 表结构变化时结果集不稳定
> - 容易让临时表/排序占用更多内存
>
> 明确列出需要的列，是最便宜的优化之一。

> [!question] Q14：统计信息为什么会过期？怎么办？
> InnoDB 通过采样估算 `Cardinality` 和 `rows`，大量增删改后估算会失真。
> 解决：`ANALYZE TABLE`；数据分布倾斜时用 8.0 的直方图；检查 `innodb_stats_auto_recalc` 和采样页数。
> 最终仍以 `EXPLAIN` / `EXPLAIN ANALYZE` 的实际计划为准。

---

> [!quote] 一句话记忆
> **先慢日志定位，再 EXPLAIN 看计划；type 看访问方式，key 看有没有走索引，key_len 看用了几列，rows 看扫了多少行，Extra 看排序/临时表/覆盖。**
> **索引列别套函数，类型别乱转，联合索引别跳列，深分页别用大 OFFSET。**
