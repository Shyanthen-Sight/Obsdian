# 命令行工具

有些工具只是偶尔用一下：aws-cli、kubectl、ffmpeg、jq、数据库客户端。为它们在宿主机装一堆依赖，版本还互相打架，不划算。用容器跑，用完就删，环境保持干净。

```bash
docker run --rm -it \
  -v "$(pwd)":/work -w /work \
  amazon/aws-cli s3 ls
```

`--rm` 让容器退出后自动删除，不然跑几次就攒一堆 Exited 容器。`-v "$(pwd)":/work` 把当前目录映射进去，工具就能读写本地文件；`-w` 指定工作目录，省得每条命令都写绝对路径。

需要凭据的工具，把宿主配置目录只读挂进去：

```bash
docker run --rm -it \
  -v "$HOME/.kube":/root/.kube:ro \
  bitnami/kubectl get pods -A
```

`:ro` 很重要。工具默认以 root 跑，可写挂载意味着容器里的进程能改你的 kubeconfig、aws 凭据。只读挂载至少挡住了误写。

用非 root 镜像或者需要生成属主正确的文件时，显式指定 UID：

```bash
docker run --rm -u "$(id -u):$(id -g)" \
  -v "$(pwd)":/src -w /src \
  golang:1.22 go build -o app ./cmd/app
```

不加 `-u` 的话，编译产物在宿主上属主是 root，后面想删还得 sudo。有些镜像没有对应用户，指定 UID 后可能找不到 `$HOME`，需要额外加 `-e HOME=/tmp`。

工具需要访问宿主上的服务（比如本地跑着的数据库）时，Linux 上可以加 `--network host`；macOS/Windows 的 Docker Desktop 里 `host.docker.internal` 更可靠。这个区别经常让“本地能连、容器里连不上”的排查走弯路。

> [!tip] 别名比记长命令靠谱
> 把常用调用写进 shell 配置：
> ```bash
> alias aws='docker run --rm -it -v "$PWD":/work -w /work -v "$HOME/.aws":/root/.aws:ro amazon/aws-cli'
> ```
> 代价是每次都要启动容器，冷启动比原生工具慢；高频工具还是本地装更合适。

容器跑 CLI 还有个隐性成本：镜像本身不小，`kubectl` 镜像几百 MB，第一次拉取要等。网络差的环境里，本地装一个二进制反而更快。
