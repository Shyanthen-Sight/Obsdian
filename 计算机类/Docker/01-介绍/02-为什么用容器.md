# 为什么用容器

"本地能跑，线上跑不起来"通常不是代码问题，而是依赖版本、系统库、环境变量不一致。容器把应用和它的运行环境一起打包，换台机器还是同一套东西。

一个常见的例子：开发机装的是 Python 3.12，服务器还是 3.8，`numpy` 版本也不一样。用镜像把版本写死：

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "main.py"]
```

`python:3.12-slim` 固定了解释器和基础库，`requirements.txt` 固定第三方依赖。构建出来的镜像有 digest，测试环境和线上跑的是同一份字节。出了问题也能直接回滚到上一个 tag，而不是"把服务器上的包降个版本试试"。镜像推到仓库后，测试、预发、生产引用同一个 digest，也就没有"部署时又装了一遍依赖"这种事。

## 收益不止环境一致

| 原来头疼的事 | 容器带来的变化         | 代价      |
| ------ | --------------- | ------- |
| 环境漂移   | 镜像不可变，回滚就是换 tag | 要维护构建流程 |
| 交付慢    | 镜像推拉替代手工部署      | 要有仓库和网络 |
| 机器利用率低 | 一台机器塞多个容器       | 需要编排和监控 |
| 扩容靠加机器 | 起容器是秒级          | 应用得无状态  |

镜像还能像代码一样打标签、进仓库、回滚。配合 CI，构建、测试、推送可以串成一条流水线，具体做法见 [[04-持续集成|持续集成]]。

## 启动快、密度高

容器不引导操作系统，启动时间通常几十毫秒到几秒；虚拟机要引导内核和 init，往往几十秒。这个差距在扩容时很直观：流量上来，起 20 个容器可能几秒钟，起 20 台 VM 要等几分钟。

密度也是同理。同样 8C16G 的机器，跑十几个虚拟机内存就满了，跑几十个容器还有余量，因为每个容器只带应用自己的开销。

## 代价也要算

数据默认跟着容器走，删了就没了，得上卷；网络多一层命名空间，排查比宿主机麻烦；共享内核意味着隔离弱于虚拟机，不可信负载要谨慎。镜像构建本身也有学习成本：层缓存、多阶段、体积控制，都得踩一遍。

> [!warning] 别为了容器而容器
> 一个静态页面、一个单机定时脚本，直接部署可能更省事。容器适合的是需要一致环境、需要频繁交付、需要横向扩容的场景，收益要和运维复杂度一起算。

## 逐条拆开收益与代价

前面那张收益表每一行都值得展开，因为“收益”和“代价”往往是一体两面。

**环境漂移 → 镜像不可变。** 传统部署里，同一份代码在开发机、测试机、生产机上依赖不同，问题只在最后一刻暴露。镜像把“代码 + 运行时 + 系统库 + 配置默认值”固化成不可变产物，部署变成“换一个 digest”，回滚也变成“换回上一个 digest”。代价是必须维护构建流程：基础镜像要定期更新，依赖要锁版本，构建失败要有人管。镜像不是自动保鲜的，`latest` 标签尤其不可靠。

**交付慢 → 推拉镜像。** 手工部署要登机器、拷文件、装依赖、改配置，步骤多且不可复现。镜像推到仓库后，测试、预发、生产拉同一份字节，省掉“在目标机上再装一遍”的环节。代价是仓库和网络成为交付链的一部分：仓库挂了、网络不通、认证过期，都会卡住发布；镜像体积大时，拉取时间也会成为瓶颈。

**机器利用率低 → 多容器混部。** 一台 8C16G 的机器如果只跑一个服务，大部分资源是闲置的。容器把多个服务塞到同一台机器上，靠 cgroups 限制各自用量，靠命名空间隔离视图。代价是混部之后需要编排、监控和资源规划：谁和谁可以放一起、CPU 超卖多少、内存 OOM 先杀谁，都得有答案。

**扩容靠加机器 → 秒级起容器。** 容器启动不引导操作系统，扩容粒度从“一台机器”变成“一个进程”，调度器可以在几秒内起几十个副本。代价是应用必须无状态：会话、上传文件、本地缓存、定时任务状态都不能留在容器里，否则新副本接不住流量，旧副本一删状态就丢。

这四行合起来就是一句话：容器把“环境”变成了可交付的软件产物，但把复杂度从“部署时”挪到了“构建时和运行时”。

## 容器、虚拟机、裸机、Serverless 怎么比

“为什么用容器”本质上是在选部署单元，把几种常见形态放在一起更清楚：

| 形态 | 部署单元 | 启动 | 隔离 | 状态管理 | 适合什么 |
| --- | --- | --- | --- | --- | --- |
| 裸机 | 一台物理机 | 分钟级 | 无（靠进程权限） | 本地磁盘 | 高性能、特殊硬件、长期稳定负载 |
| 虚拟机 | 一台 VM | 十几秒到分钟 | 硬件级 | 虚拟磁盘 | 强隔离、多租户、非 Linux、内核定制 |
| 容器 | 一个进程 | 毫秒到秒 | 内核级 | 卷 + 外部服务 | 微服务、Web、CI、频繁交付 |
| Serverless 容器 | 一个请求/任务 | 毫秒到秒（含冷启动） | microVM 或沙箱 | 外部服务 | 突发流量、事件驱动、不想管节点 |

容器不是所有维度的最优解：裸机的性能损耗最小，虚拟机的隔离最强，Serverless 的运维负担最轻。容器的优势集中在“交付一致 + 启动快 + 密度高”这三件事上，离开这些场景，收益就要重新算。

## “无状态”到底要求什么

扩容那一行的前提是应用无状态，但“无状态”不是“应用里不能有变量”，而是“任何实例被删掉，状态都不丢”。按状态类型拆开看：

| 状态 | 常见位置 | 容器化后放哪 | 不处理会怎样 |
| --- | --- | --- | --- |
| 会话 | 进程内存、本地文件 | Redis、数据库、签名 Cookie | 实例一换，用户掉线 |
| 上传文件 | 容器本地目录 | S3、MinIO、NFS | 容器删了文件没 |
| 本地缓存 | 容器内存 | Redis、进程内缓存（可重建） | 缓存丢失可接受，但要能回源 |
| 日志 | 容器内文件 | stdout，交给日志驱动 | 日志随容器消失 |
| 定时任务 | 容器内 cron | 外部调度器、分布式锁 | 多副本重复执行 |
| 数据库 | 容器内数据目录 | 托管数据库、命名卷 | 数据随容器删除 |

判断标准很简单：容器随时可能被 kill、被调度到另一台机器、被新版本替换。凡是“换一个实例就找不到”的东西，都要外置。

## 什么时候不该用容器

- **单机定时脚本、一次性工具**：直接放 cron 或 systemd 更简单，引入镜像构建和运行时只是多一层。
- **静态页面**：对象存储 + CDN 往往更便宜、更快，容器反而要维护 Web 服务器和证书。
- **需要特定内核、内核模块、驱动的负载**：容器共享宿主内核，加载不了模块，也改不了全局参数，这类负载应该用虚拟机。
- **强隔离多租户**：跑不可信代码时，普通容器的内核攻击面太大，应该上 VM、microVM 或 gVisor。
- **GUI、遗留桌面软件**：容器基本只跑 Linux 无头服务，桌面环境、图形驱动、专有许可软件通常更适合虚拟机。
- **团队还没有基础运维能力**：镜像仓库、构建流水线、日志收集、监控告警，任何一环缺失都会让容器变成负担。容器化一个单机脚本只要半小时，但后面要维护基础镜像、构建流程、漏洞扫描和运行时升级，收益要和这些长期成本一起算。
