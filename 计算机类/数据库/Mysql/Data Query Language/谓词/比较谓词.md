# 比较谓词 —— `=`、`<>`、`>`、`>=`、`<`、`<=`

> [!abstract] 一句话
> 比较谓词用==**六个比较运算符**==把两个值放在一起比大小或比相等，结果是 `TRUE` / `FALSE` / `UNKNOWN`。
> 它是最基础、最常用、也最容易因==**隐式类型转换**==而"静默比错"的一类谓词。

> [!info] 与其它笔记的分工
> 本篇讲 `=`、`<>`、`!=`、`>`、`>=`、`<`、`<=` 这六个"普通比较"。
> NULL 安全的 `<=>` 单独成篇，见 [[安全等于]]；判空见 [[空值谓词]]。
> `WHERE` 子句的整体执行位置见 [[Where]]。

---

## 一、六个运算符

| 运算符 | 含义 | 示例 | 备注 |
| --- | --- | --- | --- |
| `=` | 等于 | `age = 18` | 不是赋值 |
| `<>` | 不等于 | `age <> 18` | 标准写法 |
| `!=` | 不等于 | `age != 18` | ==与 `<>` 完全等价== |
| `>` | 大于 | `salary > 10000` | |
| `>=` | 大于等于 | `salary >= 10000` | 包含边界 |
| `<` | 小于 | `salary < 10000` | |
| `<=` | 小于等于 | `salary <= 10000` | 包含边界 |

> [!tip] `<>` 和 `!=` 选哪个
> 两者在 MySQL 里**完全等价**，执行计划和结果都一样。
> 建议统一写 `<>`：它是 SQL 标准写法，换到别的数据库也不用改。

---

## 二、基本用法

```sql
-- 数值
SELECT * FROM emp WHERE salary > 10000;
SELECT * FROM emp WHERE salary >= 10000 AND salary <= 15000;

-- 字符串（必须加引号）
SELECT * FROM student WHERE name = '张三';
SELECT * FROM student WHERE gender <> 'M';

-- 日期（字符串会被转成日期比较）
SELECT * FROM `order` WHERE created_at >= '2026-09-01';
```

> [!warning] 字符串和日期一定要加引号
> `WHERE name = 张三` 会被 MySQL 当成"拿 `name` 列和 `张三` 列比较"，报：
> `ERROR 1054 (42S22): Unknown column '张三' in 'where clause'`
> 日期同理：`WHERE created_at >= '2026-09-01'`。

## 三、NULL：比较的"黑洞"

> [!danger] 任何与 NULL 的普通比较，结果都是 UNKNOWN
> ```sql
> SELECT NULL = 1;      -- NULL
> SELECT NULL <> 1;     -- NULL
> SELECT NULL = NULL;   -- NULL（不是 1！）
> SELECT NULL <> NULL;  -- NULL
> SELECT 1 = NULL;      -- NULL
> ```
> `WHERE` 只保留 `TRUE`，所以这些条件**一行都查不出来**。

```sql
-- ❌ 永远 Empty set，哪怕表里真有 name 为 NULL 的行
SELECT * FROM student WHERE name = NULL;
SELECT * FROM student WHERE name <> NULL;

-- ✅ 正确：判空用 IS NULL / IS NOT NULL
SELECT * FROM student WHERE name IS NULL;
SELECT * FROM student WHERE name IS NOT NULL;

-- ✅ 或者用 NULL 安全等于 <=>
SELECT * FROM student WHERE name <=> NULL;
```

> [!important] 记住这条
> **普通比较谓词遇到 NULL，一律返回 UNKNOWN；UNKNOWN 在 `WHERE` 里等于"不通过"。**
> 这不是 bug，是 SQL 三值逻辑的规定。详见 [[空值谓词]] 与 [[安全等于]]。

## 四、隐式类型转换：最容易静默出错的地方

MySQL 在比较**不同类型的值**时，会先做隐式转换，再比较。规则不直观，坑很多。

### 4.1 数字 vs 字符串

```sql
SELECT 1 = '1';        -- 1（TRUE）
SELECT 1 = '1.0';      -- 1（TRUE）
SELECT 1 = '1abc';     -- 1（TRUE，伴随 warning：字符串被截成 1）
SELECT 0 = 'abc';      -- 1（TRUE！'abc' 转数字得 0）
SELECT '' = 0;         -- 1（TRUE！空串转数字得 0）
```

> [!danger] `'abc' = 0` 竟然是 TRUE
> 当字符串和数字比较时，MySQL 会把**字符串转成数字**：
> `'abc'` → `0`，`'1abc'` → `1`（截断到第一个非数字字符），并产生 warning。
> 于是 `WHERE code = 0` 可能把一堆"非数字字符串"也查出来。
> **写 SQL 时保证比较两边类型一致**，别依赖隐式转换。

### 4.2 字符串列 vs 数字

```sql
-- phone 是 VARCHAR，却拿数字比
SELECT * FROM user WHERE phone = 13812345678;
```

这会让 `phone` 列被转成数字再比较，**索引很可能失效**（无法按字符串前缀定位），而且前导 0 会丢失。

```sql
-- ✅ 类型对齐，能走索引
SELECT * FROM user WHERE phone = '13812345678';
```

> [!tip] 经验法则
> **列是什么类型，就用什么类型的字面量去比。**
> 字符串加引号，日期用 `'YYYY-MM-DD'`，数字不加引号。

### 4.3 日期 vs 字符串

```sql
-- 字符串会按日期解析
SELECT * FROM `order` WHERE created_at >= '2026-09-01';

-- ⚠️ 但别在列上套函数，否则索引失效
SELECT * FROM `order` WHERE DATE(created_at) = '2026-09-29';
```

日期范围的标准写法是**半开区间**：

```sql
SELECT * FROM `order`
WHERE created_at >= '2026-09-01'
  AND created_at <  '2026-10-01';
```

这样既能走索引，又不会漏掉月末最后一天的任何时刻。

## 五、字符串比较：大小写、尾随空格、排序规则

字符串比较的结果取决于**排序规则（collation）**：

| 排序规则 | 大小写 | 示例 |
| --- | --- | --- |
| `utf8mb4_0900_ai_ci`（MySQL 8 默认） | 不敏感 | `'A' = 'a'` → TRUE |
| `utf8mb4_bin` | 敏感 | `'A' = 'a'` → FALSE |
| `utf8mb4_general_ci` | 不敏感 | `'A' = 'a'` → TRUE |

```sql
SELECT 'A' = 'a';                    -- 取决于 collation
SELECT BINARY 'A' = 'a';             -- 0（强制按字节比较）
SELECT 'A' = 'a' COLLATE utf8mb4_bin; -- 0
```

> [!warning] 尾随空格也可能被忽略
> 在部分 `PAD SPACE` 排序规则下，`'abc' = 'abc   '` 为 TRUE。
> 如果业务要求"严格相等"，用 `BINARY` 或二进制排序规则。
> 更稳妥的做法是**在应用层先 trim**，而不是指望数据库的比较规则。

## 六、链式比较的陷阱

数学里可以写 `1 < age < 10`，SQL 里**不能**：

```sql
-- ❌ 不会报错，但语义完全错了
SELECT * FROM student WHERE 1 < age < 10;
```

它会被解析成：

```text
(1 < age) < 10
```

`1 < age` 先得到一个 `0` 或 `1`，再和 `10` 比较，`0 < 10` 和 `1 < 10` **永远为 TRUE**——结果就是全表返回。

```sql
-- ✅ 正确：用 AND 拆开
SELECT * FROM student WHERE age > 1 AND age < 10;
```

## 七、比较谓词与索引

| 写法 | 索引 | 说明 |
| --- | --- | --- |
| `col = 值` | ✅ | 等值查找 |
| `col > 值` / `>=` / `<` / `<=` | ✅ | 范围扫描 |
| `col BETWEEN a AND b` | ✅ | 本质是范围 |
| `col <> 值` | ⚠️ | 否定条件，选择性差时全表扫 |
| `col = 值 OR col = 值` | ✅ | 同一列可用索引合并 |
| `col1 = 1 OR col2 = 2` | ⚠️ | 不同列可能 Index Merge，也可能全表 |
| `DATE(col) = 值` | ❌ | 列被函数包住 |
| `col + 1 = 值` | ❌ | 列参与运算 |
| `varchar_col = 数字` | ⚠️ | 隐式转换可能失效 |

> [!important] 核心原则
> **索引列上不要做运算、不要套函数、保持比较两边类型一致。**
> B+ 树存的是列的原始值，你一旦改变了参与比较的"形态"，树上的顺序就对不上，只能逐行算。

## 八、常见错误合集

> [!failure] `= NULL` 查不出数据
> 应写 `IS NULL` 或 `<=> NULL`。见 [[空值谓词]]。

> [!failure] 字符串忘了引号
> `WHERE name = 张三` → `Unknown column '张三'`。数字型的字符串（手机号、邮编、身份证）尤其容易漏。

> [!failure] `'abc' = 0` 为 TRUE
> 隐式转换把非数字字符串转成 0。比较前确保类型一致。

> [!failure] 链式比较 `1 < age < 10`
> SQL 逐个运算符求值，结果恒为 TRUE。必须用 `AND`。

> [!failure] 在索引列上套函数
> `DATE(created_at) = ...` 会让索引失效，改成范围查询。

> [!failure] 大小写预期错误
> 默认 collation 多半大小写不敏感，`'A' = 'a'` 可能为 TRUE。需要严格区分时用 `BINARY`。

## 九、速查表

| 需求 | 写法 |
| --- | --- |
| 等于 | `col = 值` |
| 不等于 | `col <> 值`（`!=` 等价） |
| 范围 | `col >= a AND col <= b` 或 `col BETWEEN a AND b` |
| 日期范围 | `col >= '2026-09-01' AND col < '2026-10-01'` |
| 判空 | `col IS NULL` / `col IS NOT NULL` |
| NULL 安全相等 | `col <=> 值` |
| 大小写敏感比较 | `BINARY col = 'A'` |
| 避免隐式转换 | 字符串加引号、类型对齐 |

> [!question] 自测三连
> 1. `NULL = NULL` 的结果是什么？为什么 `WHERE name = NULL` 查不出数据？
> 2. `'abc' = 0` 为什么是 TRUE？这会带来什么业务风险？
> 3. `WHERE 1 < age < 10` 为什么恒为真？正确写法是什么？

---

> [!quote] 一句话记忆
> **比较谓词遇 NULL 一律 UNKNOWN；判空用 `IS NULL`，NULL 安全相等用 `<=>`；字符串加引号、类型要对齐，索引列不套函数，链式比较必须拆成 `AND`。**
