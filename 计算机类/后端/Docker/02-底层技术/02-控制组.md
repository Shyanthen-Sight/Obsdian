# 控制组

cgroups 决定容器能用多少 CPU、内存、IO 和进程数。它和命名空间正交：可以给容器独立视野却不限资源，也可以限死资源但让它共享网络。

## cgroup v2 的树

v2 把所有控制器收进一棵树，挂在 `/sys/fs/cgroup`。每个进程只属于一个 cgroup，父节点通过 `cgroup.subtree_control` 把控制器下放给子节点：

```bash
cat /sys/fs/cgroup/cgroup.controllers
# cpuset cpu io memory hugetlb pids rdma misc
cat /sys/fs/cgroup/cgroup.subtree_control
# cpuset cpu io memory pids
```

有子 cgroup 的节点不能再放进程，systemd 因此把每个容器塞进独立 scope。用 systemd cgroup driver 时，容器目录是：

```bash
CID=$(docker inspect -f '{{.Id}}' web)
ls /sys/fs/cgroup/system.slice/docker-$CID.scope/
# cpu.max  cpu.weight  memory.current  memory.events  memory.max  pids.max
```

driver 是 `cgroupfs` 或 cgroup v1 时，路径和文件名都不一样，排查前先用 `docker info` 确认版本。

## 内存限制怎么生效

```bash
docker run -d --name hog --memory=128m --memory-swap=128m \
  python:3.12-alpine python -c 'x = bytearray(256 * 1024 * 1024); print(len(x))'

docker inspect hog -f '{{.State.OOMKilled}} {{.State.ExitCode}}'
# true 137
cat /sys/fs/cgroup/system.slice/docker-<容器ID>.scope/memory.events
# oom 1
# oom_kill 1
```

退出码 137 是 128 + 9，进程收到 SIGKILL。`--memory` 写进 `memory.max`，进程触碰页面超过上限时内核先回收缓存，回收不动就触发 cgroup OOM，杀掉组内进程。`--memory-swap=128m` 表示内存加 swap 总共 128MB，等于禁用 swap；不写这个参数时，Docker 默认给 `--memory` 的两倍，也就是允许用掉一半 swap。

## CPU 是配额不是绑核

```bash
docker run -d --name api --cpus=1.5 --cpu-shares=512 --cpuset-cpus=0-1 nginx
cat /sys/fs/cgroup/system.slice/docker-<容器ID>.scope/cpu.max
# 150000 100000
```

`--cpus=1.5` 翻译成 quota 150000、period 100000，即每个 100ms 周期最多跑 150ms，允许短时用到 1.5 个核，但不保证在哪个核上。`--cpu-shares` 只在争抢时按权重分配，空闲时不限制。要减少跨核缓存失效或跑 DPDK 这类场景，才用 `--cpuset-cpus` 真正绑核。

其他限制：`--pids-limit` 防 fork 炸弹，`--device-read-bps` 限磁盘带宽，`--blkio-weight` 调 IO 权重。

## 容易踩的坑

运行时不一定认 cgroup 限制。JDK 10 以前默认按宿主机内存算堆，容器里会申请过多然后被 OOM，需要 `-XX:+UseContainerSupport -XX:MaxRAMPercentage=75`；Node 的默认老生代上限也和宿主机有关，要显式 `--max-old-space-size`。

`docker stats` 里的 MEM USAGE 包含 page cache，看起来比 `--memory` 涨得快，不代表泄漏，看 `memory.stat` 里的 `anon` 更准。`--memory` 只是上限不是预留，节点超卖时多个容器仍会互相挤压。
