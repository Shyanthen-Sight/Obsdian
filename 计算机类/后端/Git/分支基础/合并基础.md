# 合并基础 —— git merge

> [!abstract] 一句话
> ==合并（merge）就是把**另一条分支的工作并入当前分支**==。Git 先找两边的共同祖先，再把各自的改动拼到一起：能自动拼就自动完成；拼不拢（同一处两边都改）就叫**冲突**，交给你手动裁决。合并产生的新提交有**两个父提交**，这就是"分叉又汇合"的痕迹。

---

## 一、先搞清方向：合到谁里面

```bash
git switch main            # 先站在"接收方"分支上
git merge feature          # 把 feature 合进 main
```

> [!warning] 永远把"当前分支"当成接收方
> `git merge X` 的意思是 ==**"把 X 合进我现在所在的分支"**==，不是"把我合进 X"。
> 合错方向很常见：先在 `git branch` 里看清 `*` 落在哪，再敲 `merge`。

---

## 二、两种合并形态

### 2.1 快进合并（Fast-forward）

当**当前分支没有任何独有提交**、只是落后于目标分支时，Git 只需把当前分支指针**直接挪过去**：

```text
合并前:   C1 ── C2 ── C3   ← feature
                    ↑
                   main

合并后:   C1 ── C2 ── C3   ← main, feature
```

> [!info] 快进 = 不产生新提交
> 因为两边没有分歧，历史是**一条直线**，Git 只是"把标签往前移"。
> 好处是历史干净；代价是**看不出"这里曾有过一条分支"**。

### 2.2 三方合并（Three-way merge）

当两条线**各有各的新提交**，就必须真正"缝合"，Git 会生成一个**合并提交**：

```text
合并前:
      A ── B ── C     ← main
      │
      D ── E          ← feature

合并后:
      A ── B ── C ── M   ← main
      │            /
      D ── E ─────
```

> [!info] 合并提交的两个父
> `M` 的 `parent` 字段有**两个**哈希（分别是 `C` 和 `E`），这是它和普通提交的唯一区别。
> 它记下了"这次合并来自哪两条线"，所以 `git log --graph` 能画出那个分叉口。详见 [[提交]]。

## 三、控制合并形态的选项

```bash
git merge feature              # 默认：能快进就快进
git merge --no-ff feature      # ★ 即使能快进，也强制生成合并提交
git merge --ff-only feature    # 只允许快进，否则报错退出（保证历史不乱合）
git merge --squash feature     # 把 feature 的改动压成"未提交的改动"，你自己再 commit
git merge --abort              # 冲突搞不定时，放弃本次合并、回到合并前的状态
git merge --continue           # 解决冲突并 git add 之后，继续完成合并
```

> [!tip] `--no-ff` 是团队常用的策略
> 它让每次合并都留下一个"合并提交"，于是 `git log --graph` 里 ==**清清楚楚能看出"某个 feature 是一次合并进来的"**==。
> 代价是多一个提交；收益是历史可读、易于整体回滚。很多团队对 feature 分支坚持 `--no-ff`。

> [!note] `--squash` 不记录合并关系
> 它把对方**所有提交的效果**一次性放到你的暂存区，你 `commit` 出来仍是一个**普通单父提交**。
> 好处：历史极简；坏处：Git **不认为那条分支被合并过**，之后 `git branch -d` 会拒绝删它（见 [[删除分支]]）。

## 四、冲突：同一处两边都改了

### 4.1 长什么样

合并中断时，`git status` 会显示 `Unmerged paths`，冲突文件里被插入记号：

```text
要合进来的分支的版本
```

> [!info] 记号怎么读
> - `<<<<<<< HEAD` 之下、`=======` 之上：==**你这边**==的内容
> - `=======` 之下、`>>>>>>> feature` 之上：==**对方**==的内容
>
> 你的任务就是：**把这一整段替换成你想要的最终样子**（保留一边、另一边，或二者融合），并删掉那三行记号。

### 4.2 解决流程

```bash
git status                            # 1. 看哪些文件冲突（Unmerged paths）
git diff --name-only --diff-filter=U  #    只想看冲突文件清单
# 2. 打开每个冲突文件，编辑成最终内容，删掉 <<<< ==== >>>> 记号
git add <解决好的文件>                  # 3. 标记为"已解决"
git merge --continue                  # 4. 完成合并（会弹编辑器让你确认合并信息）
# 也可以直接 git commit —— 效果一样
```

> [!success] 成功标志
> `git status` 不再有 `Unmerged paths`；`git log --graph` 出现那个合并提交。
> 中途想放弃：`git merge --abort`，一切完整回到 merge 之前。

### 4.3 借助工具与快捷取舍

```bash
git mergetool                  # 用配置好的图形化工具逐个解决
git checkout --ours  <文件>     # 直接采用"我这边"的整份文件
git checkout --theirs <文件>    # 直接采用"对方"的整份文件
```

> [!warning] `--ours` / `--theirs` 在 merge 与 rebase 里意思相反
> **合并（merge）时**：`--ours` = 当前分支（接收方），`--theirs` = 被合进来的分支。
> **rebase 时**：这两个词的含义会**反过来**，千万别凭记忆混用。

> [!tip] 冲突不是坏事
> 冲突恰恰说明"同一处被两边认真改过"，是 Git 不敢替你拍板的地方。
> 解法没有标准答案，关键是**读懂两边的意图**再决定，而不是无脑选一边。

## 五、完整示例

```bash
# 场景：feature/hello 开发完了，要合回 main
git switch main                  # 1. 站到接收方
git pull                         # 2. 确保 main 是最新的
git merge --no-ff feature/hello  # 3. 合并，并留下一个合并提交

# 若有冲突：
git status                       #    看冲突文件
#    编辑文件、删掉记号……
git add <文件>
git merge --continue

git log --oneline --graph -5     # 4. 确认出现"分叉 + 汇合"
git branch -d feature/hello      # 5. 收尾，删掉已合并的分支
```

> [!success] 成功标志
> `--graph` 里能看到两条线并成一条；`git branch -d` 能顺利删掉 feature 分支（说明确实已合并）。

## 六、常见困惑

> [!question] 合并后原来的分支还在吗？
> 在。`merge` **不删除**任何分支，它只是在当前分支上叠加对方的改动。
> 删除是另一回事，见 [[删除分支]]。

> [!question] 合并会把我的改动覆盖掉吗？
> 不会"悄悄覆盖"：两边都改了同一处 → 冲突，交给你裁决；只有一边改了 → 采用改动的那边。
> 真正会**丢工作**的是 `merge` 之外的操作（`reset --hard`、`clean`），不是 merge 本身。

> [!question] fast-forward 和 `--no-ff` 到底选哪个？
> - 想要**线性、干净**的历史，个人小项目 → 默认（能快进就快进）。
> - 想要**看得出每次合并**、便于整体回滚，团队协作 → `--no-ff`。
>
> 这更多是**团队约定**问题，开工前对齐即可。

> [!question] 冲突解决到一半想推倒重来？
> `git merge --abort`。它把你完整地送回 merge 之前的状态，工作区、暂存区都还原。

> [!question] merge 和 rebase 有什么区别？
> 一句话：==**merge 保留分叉、生成合并提交；rebase 把提交"搬"到另一条线顶端、重写历史变成直线**==。
> 改公开历史有风险，rebase 的规矩是"只 rebase 别人没拉过的提交"。本笔记只讲 merge。

> [!question] 合并时提示 `Already up to date.` 是出错了吗？
> 不是。它表示目标分支的提交**已经全部在你的历史里**，无需合并——通常是两分支本来就一致。

---

> [!quote] 一句话记忆
> **merge = 把两条线拧成一股**：没分歧就快进（指针一挪），有分歧就生一个"双父提交"把两边缝上；缝不拢的地方，Git 把它摊在你面前，==**由你当裁判**==。
