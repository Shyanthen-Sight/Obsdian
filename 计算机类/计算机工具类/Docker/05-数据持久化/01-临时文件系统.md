# 临时文件系统

容器里的 `/` 看起来是一个完整的文件系统，实际上是镜像的若干只读层叠起来，最上面盖一层可写层。所有新建、修改、删除都落在可写层，镜像本身不动。这就是联合文件系统和写时复制在起作用，细节见 [[03-联合文件系统|联合文件系统]]。

写时复制的行为值得亲手看一遍。改一个镜像里已有的大文件时，Docker 先把它从只读层复制到可写层，再改副本；原文件还在镜像里躺着。所以容器里 `du` 看到的占用，和 `docker ps -s` 里可写层的大小不是一回事。

```bash
docker run -d --name demo alpine sh -c 'echo hello > /data.txt; sleep 600'
docker diff demo
# A /data.txt
docker rm -f demo

docker run --rm alpine cat /data.txt
# cat: can't open '/data.txt': No such file or directory
```

`docker diff` 里的 `A` 是新增、`C` 是修改、`D` 是删除，排查“容器里到底改了什么”时很好用。第二条命令说明可写层跟着容器一起没了。

`docker restart` 和 `docker rm` 要分清楚：重启只是把进程停掉再拉起来，可写层还在；删掉容器再 `docker run`，就是全新的可写层。compose 里 `up --force-recreate` 也会重建容器。

有人用 `docker commit` 把可写层固化成镜像当备份。能跑通，但不可复现，还会把临时文件、日志、甚至调试时写进去的密钥一起打包，生产环境不要这么干。

磁盘被吃满时，`docker system df` 能分开看镜像、容器可写层、卷和构建缓存各占多少，比盲目 `prune` 安全。

不想落盘的数据可以放内存：

```bash
docker run --rm --tmpfs /tmp:size=64m,noexec alpine \
  sh -c 'dd if=/dev/zero of=/tmp/f bs=1M count=10'
```

`--tmpfs` 挂的是内存文件系统，容器停止即清空，适合放会话缓存、临时解压目录。`size` 要设上限，否则容器可能把宿主内存吃光。

> [!warning] 判断标准只有一句
> 容器重建后这份数据还需不需要？需要就挂出来，别赌自己不会手滑 `docker rm -f`。
