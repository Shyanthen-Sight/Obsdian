# 镜像标签

标签只是指向某份镜像 manifest 的名字，本质是可变的指针。`my-app:1.4` 今天和明天完全可能对应不同 digest：CI 重复构建、基础镜像更新、有人手动重新推送，都会让标签移动。digest 由内容计算得出，镜像内容不变，digest 就不会变。

## tag 和 digest

```bash
docker inspect --format '{{index .RepoDigests 0}}' my-app:1.4
# my-app@sha256:4f1c8d...e9a2

docker pull my-app@sha256:4f1c8d...e9a2
```

对已经推送或拉取过的镜像，`RepoDigests` 里记录着它在仓库中的 digest。用 `image@sha256:...` 拉取时 Docker 会校验内容，哪怕同名标签已经被覆盖，拿到的也是同一份东西。生产部署、回滚记录、事故复盘都适合记 digest；给人看的发布说明里再写版本号。

## 一次构建打多个标签

```bash
VERSION=1.4.2
SHA=$(git rev-parse --short HEAD)

docker build -t my-app:$VERSION -t my-app:1.4 -t my-app:1 -t my-app:sha-$SHA .
docker push my-app:$VERSION
docker push my-app:1.4
docker push my-app:1
docker push my-app:sha-$SHA
```

| 标签 | 用途 | 可变性 |
| --- | --- | --- |
| `1.4.2` | 精确版本，发布和回滚用 | 不应覆盖 |
| `1.4` / `1` | 跟随小版本、大版本 | 会移动 |
| `sha-abc1234` | 对应一次提交，排查用 | 不变 |
| `latest` | 不写标签时的默认值 | 随意变动 |

语义化版本要守规矩：`1.4.2` 只包含补丁修复，`1.4` 指向该系列最新的补丁，`1` 指向最新的小版本。如果 `1.4.2` 被重新推成不同内容，所有基于它的回滚都会失真，这比不打标签更糟。

Git SHA 标签的好处是可追溯，CI 日志里看到 `sha-abc1234` 就能定位到提交；缺点是不直观，所以一般和版本号并存，而不是二选一。

## latest 不是“最新”

`latest` 只是“没写标签时的默认值”，很多项目根本不更新它，或者只在主干推送时更新。Kubernetes 里用 `latest` 还会让 `imagePullPolicy` 默认变成 `Always`，每次启动都去拉一次。

## 钉 digest 的代价

```yaml
services:
  api:
    image: ghcr.io/acme/api@sha256:4f1c8d...e9a2
```

完全可复现，但升级要改 digest，发布流程里得有个步骤把 tag 解析成 digest 再写进部署文件。折中做法是部署文件用版本 tag，发布系统在写入时解析并记录 digest，回滚时按记录来。

> [!warning] 别拿环境名当唯一标签
> `prod`、`staging` 这类标签一旦被覆盖，回滚就找不到上一版。真要用，也保留一份带版本号或 digest 的记录。
