# 网络

容器启动时，Docker 给它一套独立的网络栈：自己的网卡、IP、路由表，外加 iptables 里的 NAT 规则。连不上时，先怀疑这层栈没对上，而不是容器坏了。

## 几种网络模式

| 模式 | 网络栈 | 用途 | 限制 |
| --- | --- | --- | --- |
| bridge | 独立，接 Docker 网桥 | 单机多容器，默认 | 不能跨主机 |
| host | 直接用宿主 | 高性能、特殊网络需求 | 端口冲突，隔离弱 |
| none | 只有 lo | 离线批处理 | 需手动配网 |
| overlay | 独立，跨主机隧道 | Swarm、多机通信 | 依赖 Swarm，注意 MTU |
| macvlan | 独立，接物理网段 | 需要二层可见的设备型容器 | 宿主默认访问不到，二层配置受限 |
| ipvlan | 独立，共用宿主 MAC | 大量容器、DHCP 受限 | 对网络环境要求高 |

`docker run` 默认进 `bridge`。默认网桥 docker0 能通，但不按名字解析。自己 `docker network create` 出来的 bridge 才有内嵌 DNS，容器 `/etc/resolv.conf` 里的 `127.0.0.11` 负责把容器名、网络别名解析成 IP。

```bash
docker network create app-net
docker run -d --name db --network app-net postgres:16
docker run -d --name api --network app-net -p 3000:3000 my-api
```

`api` 连数据库写 `db:5432`，不用知道 IP。compose 默认把服务名注册进 DNS。

## 发布端口和 EXPOSE

`EXPOSE 3000` 只是镜像元数据，声明程序默认监听 3000，不会打开端口。真正映射到宿主的是 `-p`（compose 的 `ports`）。同网络的其他容器访问服务时用容器端口，跟有没有 `-p` 无关。

```bash
docker run -d --name web -p 127.0.0.1:8080:80 nginx
docker port web
```

`127.0.0.1:8080:80` 只监听宿主回环，适合本地调试；写成 `8080:80` 会监听 `0.0.0.0`，暴露到局域网。

高频坑：应用在容器里监听 `127.0.0.1:3000`。容器回环只属于容器自己，宿主 DNAT 过来的流量进不去，现象是“端口映射了但 curl 不通”。把监听地址改成 `0.0.0.0`。

## 排障顺序

按“有没有网 → 名字能不能解析 → 端口有没有人听 → 包到没到”走，通常三步内定位。

```bash
docker inspect -f '{{range $k, $v := .NetworkSettings.Networks}}{{$k}}={{$v.IPAddress}} {{end}}' api
docker exec api getent hosts db          # 验证内嵌 DNS
docker exec api ss -lntp                 # 看监听地址
docker run --rm --net container:db nicolaka/netshoot \
  tcpdump -i eth0 -nn port 5432          # 在目标网络栈抓包
```

`docker network inspect app-net` 能看到接了哪些容器、IP 和别名，排查接入问题先看它。`getent hosts` 走系统解析链；Alpine 没有 `getent` 时改用 `nslookup db 127.0.0.11`。`ss -lntp` 里 `-l` 是监听、`-n` 不解析、`-p` 带进程。抓包用 netshoot，通过 `--net container:` 共享目标网络栈。

host 网络没有 NAT，`-p` 会被忽略；overlay 跨主机时先确认 Swarm 节点和 4789/UDP、7946/TCP 是否放行。

> [!warning] 防火墙与 Docker 的 iptables
> Docker 自己写 `DOCKER` 链做 DNAT，常常绕过 ufw/firewalld 的默认拒绝规则。以为只开了 22 和 80，`-p 5432:5432` 的数据库却已经暴露在公网。发布前先想清楚绑定地址，云主机再配安全组兜底。
