# 镜像大小与安全

镜像越小，拉取和冷启动越快，攻击面也越小。一个动辄 1GB 的镜像，里面通常躺着编译器、包管理器缓存和整份构建工具链，运行时一个都用不上。

先看基础镜像的取舍：

| 基础镜像 | 体积 | 适合 | 代价 |
| --- | --- | --- | --- |
| `scratch` | 0 | 静态编译的 Go/Rust | 没有 shell、CA 证书、时区数据，全要自己拷 |
| `distroless` | 2–20MB | 编译型服务 | 没有 shell，进不去容器排障 |
| `alpine` | ~5MB | 通用，需要 shell | musl libc，部分预编译二进制不兼容 |
| `debian-slim` | ~75MB | 依赖 glibc 的应用 | 比 alpine 大一个数量级 |

Alpine 的坑很具体：Python 的 manylinux wheel、某些 Node 原生模块、Oracle 客户端，都是按 glibc 编译的，装到 musl 上要么找不到 `.so`，要么运行时直接段错误。遇到这种就退回 `debian-slim`，别硬折腾。

多阶段构建是瘦身的主力：

```dockerfile
FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
```

第一个阶段装全部依赖并打包，第二个阶段只拿走 `dist`。最终镜像里没有 node、没有源码、没有 `node_modules`，通常从 1GB 降到几十 MB。

非 root 运行是另一条底线。镜像里没有现成用户就自己建：

```dockerfile
FROM alpine:3.20
RUN addgroup -S app && adduser -S -G app app
WORKDIR /app
COPY --chown=app:app app /app/app
USER app
ENTRYPOINT ["/app/app"]
```

`--chown` 让文件属主正确，否则非 root 用户读不了。`USER` 之后的指令都以该用户执行，需要 root 的操作要放在它前面。运行时不改镜像也能覆盖：`docker run --user 1000:1000 my-app`。

密钥千万别进层。`COPY .env` 再 `RUN rm .env` 是无效的，`rm` 只在新层里删了引用，前一层还能被 `docker history` 和镜像导出翻出来。用 BuildKit secret：

```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci --omit=dev
```

```bash
docker build --secret id=npmrc,src="$HOME/.npmrc" -t my-app:1.0 .
```

secret 只在构建时挂载，不写入任何层。同理，`ARG` 传密钥也会留在 `docker history` 里，只适合传版本号这类非敏感值。

构建完扫一遍：

```bash
docker scout cves my-app:1.0
trivy image --severity HIGH,CRITICAL --ignore-unfixed my-app:1.0
docker history --no-trunc my-app:1.0 | head -20
```

`docker scout` 是 Docker 自带入口，trivy 的规则和输出更适合接 CI。`docker history` 看每层大小和命令，找“哪一步把镜像撑大了”很快。

> [!warning] 固定到 digest
> `FROM node:20` 会随上游更新漂移，同一份 Dockerfile 今天和下周构建出的镜像可能不同。生产镜像用 `node:20@sha256:...` 固定，配合定期更新。
