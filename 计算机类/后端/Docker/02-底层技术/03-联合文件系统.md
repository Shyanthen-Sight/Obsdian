# 联合文件系统

镜像分层不是 Docker 造的格式，底层是内核的联合挂载。Linux 上默认用 overlay2，把多个只读目录和一个可写目录合成一个 merged 视图。

## 四个目录

OverlayFS 的四个关键位置：

- `lowerdir`：一个或多个只读层，冒号分隔，最左边优先级最高；
- `upperdir`：可写层，所有修改都落在这里；
- `workdir`：内核内部用的工作目录，必须为空、和 upperdir 在同一个文件系统；
- `merged`：挂载点，进程看到的就是它。

手动挂一次最直观：

```bash
mkdir -p /tmp/ovl/{lower,upper,work,merged}
echo "base image" > /tmp/ovl/lower/a.txt
echo "v1" > /tmp/ovl/lower/b.txt

sudo mount -t overlay overlay \
  -o lowerdir=/tmp/ovl/lower,upperdir=/tmp/ovl/upper,workdir=/tmp/ovl/work \
  /tmp/ovl/merged

cat /tmp/ovl/merged/a.txt            # base image
echo "v2" > /tmp/ovl/merged/b.txt    # 触发 copy-up
echo "new" > /tmp/ovl/merged/c.txt
ls /tmp/ovl/upper                    # b.txt  c.txt

rm /tmp/ovl/merged/a.txt
ls -la /tmp/ovl/upper                # c--------- ... a.txt  <- whiteout
```

改 lower 文件，内核会先把整个文件复制到 upperdir，再在副本上修改，这叫 copy-up，大文件第一次写入会明显卡顿。删文件不动 lower，而是在 upper 里放一个 whiteout（字符设备 0/0），merged 视图里就看不见了。

## Docker 里的对应关系

```bash
docker inspect web -f '{{json .GraphDriver.Data}}' | jq
# {
#   "LowerDir": "/var/lib/docker/overlay2/l/ABC...:/var/lib/docker/overlay2/l/DEF...",
#   "UpperDir": "/var/lib/docker/overlay2/xxx/diff",
#   "WorkDir": "/var/lib/docker/overlay2/xxx/work"
# }
```

`LowerDir` 每一项对应一层镜像，最左边是最上面的层；容器的可写层就是 `UpperDir`。多个容器用同一个镜像时，LowerDir 指向同一批目录，磁盘上只有一份，这是一个 nginx 镜像起十个容器不占多少空间的原因。`docker diff web` 输出的 A/C/D 就是 upperdir 相对镜像层的变化。

构建镜像同理，两种写法体积差很多：

```dockerfile
# 差：下载物留在第一层，第二层删掉也不减体积
RUN curl -fsSL https://example.com/tool.tar.gz -o /tmp/tool.tar.gz
RUN tar -xzf /tmp/tool.tar.gz -C /usr/local/bin && rm /tmp/tool.tar.gz

# 好：下载、解压、清理在同一层完成
RUN curl -fsSL https://example.com/tool.tar.gz -o /tmp/tool.tar.gz && \
    tar -xzf /tmp/tool.tar.gz -C /usr/local/bin && \
    rm /tmp/tool.tar.gz
```

后者没有中间产物进入已提交层；前者即使后面删了文件，前一层字节仍随镜像分发。

## 注意

overlay2 要求底层文件系统支持 `d_type`，xfs 需要 `ftype=1`，NFS 之类通常不行。层数太多会消耗 inode，合并 RUN 和定期 `docker image prune` 能缓解。容器的可写层随容器删除一起消失，需要保留的数据放 [[02-卷挂载|卷]] 或 [[03-绑定挂载|绑定挂载]]，它们不经过 overlay。`docker commit` 会把可写层固化成新层，调试方便，但不该进正式流程。
