# SQL 集合运算符

> 集合运算把**多个查询结果纵向拼接**（加行），是"表之间的加减法"。
> 与 `JOIN`（横向扩列）方向正好相反，两者解决的问题不同，不能互相替代。
>
> 一句话抓住本质：==**`UNION` 是并集，`INTERSECT` 是交集，`EXCEPT` 是差集，`ALL` 后缀保留重复。**==

---

## 一、运算符总览

| 运算符             | 名称       | 是否去重 | 结果含义          |
| --------------- | -------- | ---- | ------------- |
| `UNION`         | 并集       | ✅ 去重 | A 或 B 中的所有行   |
| `UNION ALL`     | 并集（保留重复） | ❌    | A 的全部 + B 的全部 |
| `INTERSECT`     | 交集       | ✅ 去重 | 同时在 A 和 B 中   |
| `INTERSECT ALL` | 交集（保留重复） | ❌    | 取重复次数的**较小值** |
| `EXCEPT`        | 差集       | ✅ 去重 | 在 A 中但不在 B 中  |
| `EXCEPT ALL`    | 差集（保留重复） | ❌    | 重复次数**相减**    |


```sql
-- 通用语法：把若干 SELECT 用集合运算符串起来
SELECT 列列表 FROM A
UNION [ALL]
SELECT 列列表 FROM B
[ORDER BY ...] [LIMIT ...];     -- 排序/分页只能写在【最后】，作用于合并后的整体
```

**记忆锚点**：`UNION` / `INTERSECT` / `EXCEPT` 三者都**默认去重**（等价于 `DISTINCT`），
加 `ALL` 就变成"纯拼接 / 计数运算"，**性能也更好**。

## 二、三条硬性规则

### 列数必须相同 

```sql
SELECT id, name FROM a
UNION
SELECT id FROM b;
-- ERROR 1222 (21000): The used SELECT statements have a different number of columns
```

**补救**：少的凑 `NULL` 占位（注意要给占位列起名，见规则 3）。

```sql
SELECT id, name FROM a
UNION ALL
SELECT id, NULL FROM b;      -- 用 NULL 补齐列数
```

###  对应列的类型必须"兼容"

不要求完全相同，MySQL 会把各分支的同序号列**聚合**成一个兼容类型再比较/合并。

```sql
SELECT 1      UNION SELECT '1';      # 1 行 ← int 1 被聚合为字符串 '1'，与 '1' 重复
SELECT 1      UNION SELECT '1 ';     # 2 行 ← 字符串比较，"1" 与 "1 " 不等
```

> 危险在于：**类型聚合可能让本该不同的行被判为相同，也可能让字符串截断**。
> 规范做法：分支里显式 `CAST` 成同一类型。

```sql
SELECT CAST(id AS CHAR) AS id FROM a
UNION ALL
SELECT CAST(id AS CHAR) FROM b;
```

### 结果列名 / 只写一个 `ORDER BY`

- **列名取第一个 `SELECT` 的别名**，后面分支的别名对结果没影响（但建议保持一致便于阅读）。
- `ORDER BY` / `LIMIT` 只能出现在**整个语句的最后**，且只能引用**第一个分支的列名或序号**。

```sql
SELECT id AS pid, name FROM a
UNION ALL
SELECT id, name FROM b
ORDER BY pid;                 # ✅ 用第一分支的别名
-- ORDER BY b.id             # ❌ Unknown column 'b.id'
```

**想让每个分支各自排序/取前 N，必须加括号**：

```sql
(SELECT * FROM a ORDER BY id LIMIT 3)
UNION ALL
(SELECT * FROM b ORDER BY id LIMIT 3)
ORDER BY id;
```

## 三、`UNION` 与 `UNION ALL`的差异

`UNION` 去重 = 建临时表 + **唯一索引去重**（或排序去重），CPU 与磁盘代价都高；
`UNION ALL` 只是顺次写入临时表，**不做任何比较**。

```sql
CREATE TABLE a (id INT, name VARCHAR(10));
CREATE TABLE b (id INT, name VARCHAR(10));
INSERT INTO a VALUES (1,'A'), (2,'B'), (2,'B');    -- 注意 a 内部就有重复
INSERT INTO b VALUES (2,'B'), (3,'C');

SELECT * FROM a UNION ALL SELECT * FROM b;
# 1,A / 2,B / 2,B / 2,B / 3,C     共 5 行 ← 重复行原样保留（含 a 内部的重复）

SELECT * FROM a UNION SELECT * FROM b;
# 1,A / 2,B / 3,C                 共 3 行 ← 全局去重
```

**结论：能确定"不需要去重"或"分支本身互不重叠"时，无脑用 `UNION ALL`。**

```sql
# 分表/分库汇总：各表主键天然不冲突，UNION 的去重完全是无用开销
SELECT * FROM orders_2024
UNION ALL
SELECT * FROM orders_2025;

# 需要去重时，UNION 的等价写法（可读性更好，本质一样）
SELECT DISTINCT * FROM (
  SELECT * FROM a UNION ALL SELECT * FROM b
) t;
```

> 去重代价举例：两个 500 万行的表做 `UNION`，MySQL 要建一个 1000 万行的临时表并维护唯一索引，
> 落盘后可能慢 10 倍以上；而 `UNION ALL` 是流式写入。

## 四、`INTERSECT` / `EXCEPT`

**MySQL 5.7 / 8.0.30 及以前不支持这两个关键字**，
只能用 `JOIN` / `IN` / `EXISTS` 模拟（见第七节）。
Oracle 里差集叫 **`MINUS`**，不叫 `EXCEPT`。

```sql
-- 沿用第三节的表
SELECT * FROM a INTERSECT SELECT * FROM b;
# 2,B                             1 行（去重）

SELECT * FROM a EXCEPT SELECT * FROM b;
# 1,A                             1 行 —— 方向敏感！b EXCEPT a 会是 3,C
```

### `ALL` 后缀：重复次数的算术

| 运算 | 重复次数规则（以同一行在两边的出现次数 m、n 计） |
|---|---|
| `INTERSECT ALL` | 输出 `min(m, n)` 次 |
| `EXCEPT ALL` | 输出 `max(m - n, 0)` 次 |

```sql
-- a 中 (2,'B') 出现 2 次，b 中出现 1 次
SELECT * FROM a INTERSECT ALL SELECT * FROM b;
# 2,B                             1 行 = min(2,1)

SELECT * FROM a EXCEPT ALL SELECT * FROM b;
# 1,A / 2,B                       2 行：(1,A) 是 1-0=1 次，(2,B) 是 2-1=1 次
```

> 这三个运算符**方向性不同**：`UNION`、`INTERSECT` 满足交换律；
> **`EXCEPT` 不满足**——`A EXCEPT B ≠ B EXCEPT A`，写之前先想清楚"谁减谁"。

## 五、NULL 的语义：与 `=` 完全不同（重点）

集合运算**把 `NULL` 当作一个普通值来比较**：两个 NULL 在 `UNION` 去重、`INTERSECT`、`EXCEPT` 中**视为相等**。
这与 `WHERE a = b`（NULL 得 `UNKNOWN`）的规则是两套逻辑。

```sql
SELECT NULL UNION SELECT NULL;        # 1 行 ← 去重时 NULL = NULL
SELECT NULL INTERSECT SELECT NULL;    # 1 行
SELECT NULL EXCEPT SELECT NULL;       # 0 行（空集）
SELECT 1 WHERE NULL = NULL;           # 0 行 ← 普通比较里 NULL = NULL 是 UNKNOWN
```

**这直接导致 `NOT IN` 的著名陷阱——`EXCEPT` 能救你：**

```sql
CREATE TABLE t1 (v INT);  INSERT INTO t1 VALUES (1), (NULL), (2);
CREATE TABLE t2 (v INT);  INSERT INTO t2 VALUES (1), (NULL);

SELECT v FROM t1 WHERE v NOT IN (SELECT v FROM t2);
# 空集！因为 t2 里有 NULL，比较结果变 UNKNOWN，整条 WHERE 全部不成立
#   期望答案本应是 2

SELECT v FROM t1 EXCEPT SELECT v FROM t2;
# 2   ✅ 正确：NULL 被当成值，只有 2 真的不在 t2 中
```

**`NOT EXISTS` 与 `EXCEPT` 也不等价**（NULL 行会漏出去）：

```sql
SELECT v FROM t1 x WHERE NOT EXISTS (SELECT 1 FROM t2 y WHERE y.v = x.v);
# 2 / NULL  ← NULL 行也被返回：y.v = NULL 永远不为真，导致 NOT EXISTS 成立
```

| 写法 | NULL 处理 | 语义 |
|---|---|---|
| `NOT IN` | 集合含 NULL → **整条失效**（返回空集） | 最危险 |
| `NOT EXISTS` | NULL 行**会被返回** | 偏"宽松" |
| `EXCEPT` | NULL 视为值，正确参与比较 | 最符合直觉 |

> 结论：**涉及 NULL 的差集，优先用 `EXCEPT`**（若版本支持）；用 `NOT IN` 时务必先 `WHERE col IS NOT NULL` 过滤子查询。

## 六、优先级与括号

MySQL 8.0.31+ 中：**`INTERSECT` 优先级高于 `UNION` 和 `EXCEPT`**；`UNION` 与 `EXCEPT` 同级、**左结合**。

```sql
-- 不加括号极易误读：
SELECT 1 UNION SELECT 2 INTERSECT SELECT 2;
# 等价于 SELECT 1 UNION (SELECT 2 INTERSECT SELECT 2) → 结果 1, 2

-- 想得到 (1 UNION 2) INTERSECT 2 的效果，必须显式加括号：
(SELECT 1 UNION SELECT 2) INTERSECT SELECT 2;
# 2
```

> 实战铁律：**只要超过一个集合运算符，就加括号**。读代码的人不该去翻优先级表。

## 七、与 `JOIN` 的辨析 + 等价改写

```sql
-- JOIN：横向扩列（把 B 的列贴到 A 的右边）
SELECT a.id, a.name, b.amount
FROM a JOIN b ON a.id = b.id;          # 结果列数 = 两表列数之和

-- UNION：纵向加行（把 B 的行接在 A 的下面）
SELECT id, name FROM a
UNION ALL
SELECT id, name FROM b;                # 结果列数 = 单表列数
```

**这是新手最常见的方向性错误**：
"要查两张表的用户" → 用 `UNION`；"要查用户和他们的订单" → 用 `JOIN`。

**交集/差集的等价改写（老版本 MySQL 必须这么写）：**

| 需求 | 集合运算 | 等价改写 | NULL 语义是否一致 |
|---|---|---|---|
| 交集 | `INTERSECT` | `INNER JOIN ON 所有列相等` 或 `IN` / `EXISTS` | ❌ JOIN 的 `=` 不匹配 NULL |
| 差集 | `EXCEPT` | `NOT EXISTS` | ❌ NULL 行会被错误返回 |
| 并集去重 | `UNION` | `UNION ALL` + `DISTINCT` | ✅ 一致 |

```sql
-- INTERSECT 的替代写法（多列交集）
SELECT a.* FROM a
WHERE EXISTS (SELECT 1 FROM b WHERE b.id = a.id AND b.name = a.name);

-- 8.0.31 之前做 "差集" 的安全写法：先滤掉 NULL
SELECT v FROM t1
WHERE v IS NOT NULL
  AND v NOT IN (SELECT v FROM t2 WHERE v IS NOT NULL);
```

> `INTERSECT` 与 `INNER JOIN` 的差异常被忽略：
> 若 `id` 列有 NULL，`INTERSECT` 会把两边的 NULL 判为同一行 → 有输出；
> `ON a.id = b.id` 匹配不到 NULL → 无输出。**默认列可为 NULL 时别用 JOIN 模拟交集。**

## 八、实际场景举例

### 1. 多表 / 分表汇总（最常用）

```sql
SELECT '2024' AS src, id, amount FROM orders_2024
UNION ALL
SELECT '2025',       id, amount FROM orders_2025
ORDER BY id;
```

> 加一列 `src` 常量做**来源标记**，是合并报表的标准手法（否则数据混在一起无法溯源）。

### 2. 用 `UNION ALL` 替代 `OR` 提升索引命中率

```sql
-- 慢：OR 两边通常只能走一条索引（或直接全表扫描）
SELECT * FROM t WHERE a = 1 OR b = 2;

-- 快：拆成两支，各自走自己的索引，再合并行（注意：这里不会有重复行则用 ALL）
SELECT * FROM t WHERE a = 1
UNION
SELECT * FROM t WHERE b = 2;      # 若 a、b 条件可能命中同一行，需要去重
```

### 3. 数据对账 / 增量同步

```sql
-- 找出"源表多了哪些、目标表多了哪些"
SELECT '仅在源' AS diff_type, * FROM src EXCEPT SELECT '仅在源', * FROM dst
UNION ALL
SELECT '仅在目标', * FROM dst EXCEPT SELECT '仅在目标', * FROM src;
```

```sql
-- 增量同步：只插入目标表没有的行
INSERT INTO dst (id, name)
SELECT s.id, s.name FROM src s
LEFT JOIN dst d ON d.id = s.id
WHERE d.id IS NULL;
```

### 4. 权限并集（角色越多权限越全）

```sql
SELECT perm_code FROM role_permission WHERE role_id = 1
UNION                                   -- 多角色可能重叠，必须去重
SELECT perm_code FROM role_permission WHERE role_id = 2;
```

### 5. A/B 实验分组合并

```sql
SELECT 'A' AS grp, user_id FROM exp_a
UNION ALL
SELECT 'B',        user_id FROM exp_b;
```

### 6. 全量维度汇总（把多张结构相同的维表拼成一张宽表）

```sql
SELECT 'province' AS level, name, code FROM dim_province
UNION ALL
SELECT 'city',      name, code FROM dim_city
UNION ALL
SELECT 'district',  name, code FROM dim_district;
```

## 九、常见坑清单

### 坑 1：`WHERE` 只作用于紧挨着它的那一个分支

```sql
-- 本意：只取 id > 10 的数据
SELECT * FROM a
UNION ALL
SELECT * FROM b WHERE id > 10;        # ❌ 只过滤了 b！a 的行全部进来了

-- 正确：每个分支各自过滤
SELECT * FROM a WHERE id > 10
UNION ALL
SELECT * FROM b WHERE id > 10;
```

`FROM ... WHERE ...` 是**绑定在单个 SELECT 上的**，集合运算符只是把这些 SELECT 串起来。
这也意味着：能在分支里过滤的，**别留到最外层**（外层过滤等于先生成巨大中间结果再筛）。

### 坑 2：把 `ORDER BY` 写进分支却不加括号

```sql
SELECT * FROM a ORDER BY id UNION ALL SELECT * FROM b;
-- ❌ MySQL 语法错误（ORDER BY 被视为要作用于整个 UNION，但位置不在最后）
```

### 坑 3：以为 `UNION` 会按第一分支的列排序

```sql
SELECT id FROM a UNION SELECT id FROM b;
# 输出顺序【不保证】！MySQL 8.0 常按去重临时表的唯一索引顺序返回，看起来"像排好序"，
# 但 5.7 或换版本/加 UNION ALL 后顺序就会变。要顺序就必须显式 ORDER BY。
```

### 坑 4：用 `UNION` 去重代替 `DISTINCT` 却带来额外开销

单表去重直接用 `SELECT DISTINCT`；`UNION` 去重只在"多结果集合并"时才必要。

### 坑 5：`LIMIT` 写在了错误的位置

```sql
-- 这是"整体取前 10 行"，不是"每支取 10 行"
SELECT * FROM a UNION ALL SELECT * FROM b LIMIT 10;

-- 每支各取 10 行
(SELECT * FROM a LIMIT 10) UNION ALL (SELECT * FROM b LIMIT 10);
```

### 坑 6：分支里列的顺序错位

```sql
-- a 是 (id, name)，b 是 (name, id) —— 列数都是 2，类型也兼容，不会报错！
SELECT id, name FROM a
UNION ALL
SELECT name, id FROM b;        # ❌ 静默错位，数据全乱
```

> 集合运算**按列位置对应**，不按列名匹配。约定：分支一律写相同的列顺序与别名。

## 十、跨数据库差异

| 行为 | MySQL | PostgreSQL | SQL Server | Oracle |
|---|---|---|---|---|
| `UNION (ALL)` | ✅ | ✅ | ✅ | ✅ |
| `INTERSECT` | ==8.0.31+== | ✅ | ✅ | ✅ |
| `EXCEPT` | ==8.0.31+== | ✅ | ✅ | ❌ 叫 **`MINUS`** |
| `INTERSECT ALL` / `EXCEPT ALL` | ✅ 8.0.31+ | ✅ | ❌ 不支持 | ❌ 不支持 |
| 分支各自 `ORDER BY` / `LIMIT` | 需加括号（8.0 起更规范） | 需加括号 | 需加括号，`TOP` 写在分支内 | 需加括号 |
| 结果列名来源 | 第一个 SELECT | 第一个 SELECT | 第一个 SELECT | 第一个 SELECT |

> 跨库移植提醒：**写 `EXCEPT` 的 SQL 拿到 Oracle 会直接报错**，改为 `MINUS`；
> 反过来若目标库可能是 MySQL 5.7，则整段 `INTERSECT` / `EXCEPT` 都要改写成 `JOIN` / `EXISTS`。

## 十一、速查小结

1. **`UNION` 纵向加行，`JOIN` 横向扩列**，方向相反，别混用。
2. 三条硬规则：**列数相同、类型兼容、`ORDER BY` 唯一且在最末**（列名取第一分支）。
3. 默认**全部去重**；`UNION ALL` / `INTERSECT ALL` / `EXCEPT ALL` 保留重复且**更快**。
4. `ALL` 的重复次数：交集取 `min(m,n)`，差集取 `max(m-n,0)`。
5. **`NULL` 在集合运算中被视为相等**，这是它比 `NOT IN`（易失效）、`NOT EXISTS`（会漏 NULL）更可靠的原因。
6. `INTERSECT` 优先级高于 `UNION` / `EXCEPT`，**超过一个运算符就加括号**。
7. `WHERE` 只属于它所在的那个分支；分支里过滤优于外层过滤。
8. `EXCEPT` 有方向性；`MINUS` 是 Oracle 的叫法；MySQL 需 **8.0.31+** 才支持。
9. 输出顺序**不保证**，要顺序必须显式 `ORDER BY`。

## 十二、常见面试题

**Q1：`UNION` 和 `UNION ALL` 的区别？什么时候必须用 `UNION`？**
> `UNION` 会去重（内部建临时表并去重），`UNION ALL` 直接拼接、保留重复且不排序，性能更好。
> 只有"结果中重复行必须消除"时才用 `UNION`，例如多角色权限并集；
> 分表汇总、带来源标记的合并报表、A/B 分组这类场景，重复行要么不可能出现要么应保留，一律用 `UNION ALL`。

**Q2：为什么 `UNION` 里 `ORDER BY` 只能写一个？想每个分支各自排序怎么办？**
> 集合运算是"先合并成一张结果集，再排序"，所以排序的对象只能是合并后的整体，且只能引用第一个分支的列名。
> 若需要分支内排序/限量，用括号把每个 `SELECT` 包起来：`(SELECT ... ORDER BY ... LIMIT 3) UNION ALL (...)`。

**Q3：`SELECT id FROM a UNION SELECT id FROM b` 结果有序吗？**
> 不保证。MySQL 8.0 的去重临时表恰好按唯一索引顺序返回，容易让人误以为"天然有序"，
> 但这是实现细节，换版本、加 `ALL`、或加并行后顺序就变。要顺序必须显式 `ORDER BY`。

**Q4：`NOT IN` 子查询结果为空，为什么？**
> 子查询结果里含 `NULL`。`x NOT IN (1, NULL)` 展开为 `x<>1 AND x<>NULL`，后半段恒为 `UNKNOWN`，
> 整个 `WHERE` 不成立 → 一行都查不出。修复方式：子查询加 `IS NOT NULL`、
> 改用 `NOT EXISTS`，或用集合运算 `EXCEPT`（它把 NULL 当值比较，语义正确）。

**Q5：`EXCEPT` 和 `NOT EXISTS` 有什么区别？**
> 二者在数据无 NULL 时结果相同，但涉及 NULL 时不同：
> `NOT EXISTS (... WHERE y.v = x.v)` 中 `y.v = NULL` 永不成立，导致左表的 NULL 行被当作"不存在于右表"而返回；
> `EXCEPT` 认为两边的 NULL 相等，NULL 行会被正确剔除。因此对 NULL 敏感的差集，优先用 `EXCEPT`。

**Q6：`A INTERSECT B` 和 `A JOIN B ON 所有列相等` 结果一样吗？**
> 无 NULL 且去重后一致；但两点不同：
> ① `JOIN` 用 `=` 比较，NULL 行匹配不上，而 `INTERSECT` 认为 NULL 相等；
> ② `JOIN` 若某列在多行中重复会**放大行数**（笛卡尔），`INTERSECT` 永远只输出去重后的唯一行。
> 所以"求交集"语义上应该用 `INTERSECT`，用 `JOIN` 只是老版本下的权宜之计。

**Q7：什么场景下 `UNION ALL` 反而比 `OR` 更快？**
> 当 `OR` 连接的两个条件各自有索引时，优化器往往无法同时利用两个索引，退化为全表扫描；
> 拆成两个分支后每个分支都能走自己的索引，再用 `UNION ALL` 合并结果，通常快数倍。
> 代价是 SQL 变长，且若两个条件可能命中同一行，需改用 `UNION` 去重。
