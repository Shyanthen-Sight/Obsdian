# WebGL

> 一句话：WebGL 是==**让浏览器直接调用显卡（GPU）画 2D / 3D 图形的 JavaScript API**==——网页里那些流畅的 3D 模型、粒子特效、数据可视化，底层大多是它。

## 是什么

- 全称 **Web Graphics Library**（Web 图形库），是浏览器里的一套 **JavaScript API**
- 作用：==**不装任何插件**==，用 JS 直接操作 GPU，把 2D / 3D 图形画到网页的 `<canvas>` 画布上
- 出身：由 **Khronos Group**（OpenGL 的制定组织）维护，本质是 **OpenGL ES 2.0 的浏览器版**
  - 也就是说，它把已经成熟的图形 API "搬"进了浏览器
- 两个版本：
  - **WebGL 1.0**：2011 年发布，基于 OpenGL ES 2.0
  - **WebGL 2.0**：2017 年发布，基于 OpenGL ES 3.0，功能更多（如更好的纹理、实例化渲染）
- 现在所有主流浏览器（Chrome / Edge / Firefox / Safari）都默认支持，写代码不用引任何库就能用

### 它长什么样（最小示例）

WebGL 的一切都发生在一块 **`<canvas>`** 上，拿到"绘图上下文"就能开始画：

```html
<canvas id="glcanvas" width="640" height="480"></canvas>
<script>
  // 1. 拿到画布，向它要一个 WebGL 上下文（所有 WebGL 调用都从它出发）
  const canvas = document.getElementById('glcanvas');
  const gl = canvas.getContext('webgl2'); // 老浏览器用 'webgl'

  // 2. 之后的活基本是：写着色器 → 传数据 → 下达绘制命令
  gl.clearColor(0.0, 0.0, 0.0, 1.0); // 背景设为黑色
  gl.clear(gl.COLOR_BUFFER_BIT);     // 清屏
</script>
```

- 这一小段就是 WebGL 的"骨架"：拿到 `gl` 对象后，一切绘制都靠调它的方法

### 核心：着色器（Shader）

WebGL 和普通 Canvas 画图最大的不同——**你写的不是"画一个圆"这种命令，而是"每个像素 / 每个顶点怎么算"的小程序**，这类小程序叫**着色器**，用类似 C 的语言 **GLSL** 编写，跑在 GPU 上。

| 着色器 | 管什么 |
| --- | --- |
| **顶点着色器**（Vertex Shader） | 每个"顶点"跑一次，决定顶点的**位置**（以及颜色等数据） |
| **片元着色器**（Fragment Shader） | 每个"像素"跑一次，决定最终**颜色** |

- 两者**并行**运行——GPU 有成千上万个小核心同时算，这正是它适合图形的根本原因
- 这也是 WebGL "难"的地方：你得用图形学的思路去思考，而不是像调 CSS 那样描述结果

### 它**不是**什么（新手最容易混的点）

- 不是 3D 引擎 —— 引擎是 **Three.js / Babylon.js** 这类"帮你干脏活"的库，WebGL 是它们脚下的**底层**
- 不是 HTML/CSS 的一部分 —— 它是独立的 JS API，借助 `<canvas>` 这个 HTML 元素来显示
- 不是 Canvas 2D —— 同在 `<canvas>` 上，但 `getContext('2d')` 是画 2D 图（简单、CPU 风格），`getContext('webgl')` 才是走 GPU 的 WebGL
- 不是 "HTML5 的新功能" —— 它是**独立于 HTML5 标准**的 Web 标准，只是恰好和 HTML5 一起火起来
- 不是通用的计算 API —— 它专为画图设计（想拿 GPU 做通用计算，有后辈 **WebGPU / WebCL**）

## 产生原因（为什么会有 WebGL）

要理解它为什么出现，得看当年网页 3D 的窘境。

### 前传：插件的天下

- 2000 年代想在网页里做 3D，基本只有两条路：**Flash** 或 **Java Applet**
- 问题很明显：
  1. **要装插件**，用户不装就白屏
  2. **安全隐患**，插件是浏览器外的独立程序
  3. **性能差、体验割裂**，和网页本身融不到一起
- 移动端兴起后，插件方案更是全线崩溃（iOS 直接不支持 Flash）

### 转折：把 OpenGL ES "搬进" 浏览器

- 图形硬件这边，**OpenGL ES**（嵌入式设备版 OpenGL）已经很成熟，手机上跑 3D 游戏靠的就是它
- 于是思路很自然：**既然设备都有 GPU，为什么不给 JS 开一扇直接调用它的门？**
- 2009 年前后，Khronos 提出 **WebGL**，把 OpenGL ES 2.0 的能力用 JS 暴露出来；2011 年 WebGL 1.0 正式发布
- 浏览器厂商（Mozilla、Google、Apple 等）陆续支持，**不装插件**就能跑 3D

### WebGL 的解法

| 当年网页 3D 的问题 | WebGL 的解法 |
| --- | --- |
| 要装 Flash / Java 插件 | 浏览器**原生**能力，开箱即用 |
| 插件安全风险大 | 跑在浏览器沙箱里，受同源、跨域等规则约束 |
| 全靠 CPU 软件渲染，卡顿 | 直接调 **GPU**，并行计算，性能大幅提升 |
| 各家方案各搞一套 | 统一的**开放标准**（Khronos），跨浏览器一致 |
| 移动端不支持 | 手机浏览器同样支持，天生跨平台 |

### 后来呢

- 2017 年 **WebGL 2.0** 发布，对标 OpenGL ES 3.0
- WebGL 也暴露了一些时代局限（状态繁琐、不支持通用计算等），于是有了继任者 —— **WebGPU**（更现代、贴近 Vulkan/Metal/DX12，还能跑计算任务），目前正逐步铺开
- 生态成熟：**Three.js / Babylon.js / PixiJS** 等库把底层封装好，让写 3D 网页的门槛大幅降低

## 作用

一句话概括：**让网页能实时画出高质量的 2D / 3D 图形**。具体能干这些事：

### 1. 3D 网页内容

- 产品 3D 展示（可旋转、缩放的模型）、在线 3D 配置器
- 网页游戏、互动场景、数字孪生
- 典型：小米 / 苹果产品页的 3D 展示，很多 Web 版小游戏

### 2. 数据可视化

- 海量点的散点图、地理轨迹、关系图谱（几万几十万个元素，Canvas 2D 早就卡死）
- 医学 / 科学可视化、分子结构、流体模拟

### 3. 特效与滤镜

- 图片 / 视频的实时 GPU 滤镜、粒子特效、背景动画
- 视频编辑器的实时预览（WebGL 做滤镜比 CPU 快几个量级）

### 4. 高性能图形计算的基础

- 很多库（Three.js、地图引擎如 Mapbox GL、图表引擎）底层都是 WebGL
- 一句话：**凡是"网页要画得又快又多"，答案往往就是 WebGL**

### 渲染流水线（它到底怎么画出来的）

理解这条"流水线"，就理解了 WebGL 的干活方式：

```
顶点数据 → [顶点着色器] → 图元装配 → 光栅化 → [片元着色器] → 帧缓冲 → 屏幕
  ↑ 你传的       ↑ 你写的              ↑ 自动        ↑ 你写的       ↑ 输出
```

- 前两步是你主要负责的：**准备数据 + 写两个着色器**
- 中间"装配、光栅化"由管线自动完成
- 最终结果画进缓冲区，显示到 `<canvas>` 上

### 会不会用不当？当然

| 场景 | 更适合 | 原因 |
| --- | --- | --- |
| 普通 2D 图表、简单图形 | **Canvas 2D** | WebGL 上手成本高，杀鸡用牛刀 |
| 矢量图标、交互式矢量图 | **SVG** | 天然矢量可缩放，用 DOM 就能操控 |
| 大量元素 / 3D / 实时滤镜 | **WebGL** | 只有走 GPU 才扛得住 |

## 跟什么类似

### ① 网页绘图三兄弟：SVG / Canvas 2D / WebGL

| | SVG | Canvas 2D | **WebGL** |
| --- | --- | --- | --- |
| 本质 | 矢量，用 XML 描述图形 | 位图，用 JS 逐笔绘制 | 位图，用 JS 调 **GPU** |
| 谁在算 | 浏览器排版引擎 | **CPU** | **GPU** |
| 操控方式 | 每个图形是一个 DOM 节点 | 画上去就没了，只能整体重绘 | 写着色器 + 下达绘制命令 |
| 适合 | 图标、地图、可交互矢量图 | 简单 2D 图表、小游戏 | **3D、海量元素、实时特效** |
| 上手难度 | 低 | 低 | **高**（要懂图形学） |

- 性能记忆点：元素一多，**SVG 卡 DOM**、**Canvas 2D 卡 CPU**，只有 **WebGL 靠 GPU 扛得住**
- 它们不能互相替代，而是**按场景选**

### ② 与它同层的图形 API（不只是浏览器）

| 领域 | API | 说明 |
| --- | --- | --- |
| 桌面 / 移动原生 | **OpenGL / OpenGL ES** | WebGL 就是从 OpenGL ES 来的"亲爹" |
| Windows | DirectX (Direct3D) | 微软阵营的图形 API |
| 新一代跨平台 | **Vulkan / Metal** | 更底层、更能榨性能，对应网页版的 **WebGPU** |
| **浏览器** | **WebGL / WebGPU** | 网页里调用 GPU 的两代标准 |

- 关系：**WebGL ≈ 浏览器里的 OpenGL ES**；**WebGPU ≈ 浏览器里的 Vulkan 那一档**
- 换句话说，WebGL 不是孤立的，它是整个 GPU 图形 API 家族里的"网页分店"

### ③ 上层库：别裸写 WebGL

实际开发几乎不直接写 WebGL，而是用封装好的库：

| 库 | 定位 | 一句话 |
| --- | --- | --- |
| **Three.js** | 最流行的 3D 库 | "写 3D 网页的默认答案"，生态最大、资料最多 |
| **Babylon.js** | 功能全的 3D 引擎 | 游戏化、企业级功能强 |
| **PixiJS** | 高性能 2D 库 | 拿 WebGL 加速 2D，做小游戏 / 动画很爽 |
| **regl / twgl** | 轻量封装 | 想贴近原生 WebGL 又不想太啰嗦 |

- 层级关系：**WebGL（底层 API）← Three.js（上层库）← 你的项目**
- 类比：WebGL 像"汇编"，Three.js 像"Python"——大多数人不写汇编照样能做出东西

### ④ 生活化类比

- **WebGL = 直接指挥一支画师军团**：
  - 你（JS）不用一个个像素去点，而是把"每个点在哪、每个像素什么颜色"的**规则**（着色器）交出去
  - GPU 里成千上万个画师**同时**照着规则画，所以快
- **Canvas 2D = 你一个人拿画笔一笔一笔画**：简单但慢，画多了手就酸（CPU 忙不过来）
- **Three.js = 请一个美术总监**：你说"来个球体、打个光"，他帮你把指挥画师的脏活全干了
- 一句话：**WebGL 之于网页 3D ≈ GLS 之于浏览器里的 OpenGL ES ≈ 直接调用 GPU 的那扇门**

## 常见问题（新手）

- **要不要直接学 WebGL 再学 Three.js**：不一定要。想快速做东西 → 直接上 Three.js；想搞懂原理 / 做底层优化 → 再回头啃 WebGL
- **为什么 WebGL 代码这么长、这么绕**：因为它是**底层 API**，状态管理、缓冲、着色器都要自己管。这也是 Three.js 存在的意义
- **画不出来 / 黑屏**：先看控制台有没有着色器编译错误；再看 canvas 尺寸、`clearColor` 和是否真的调了 `drawArrays / drawElements`；跨域贴图也会导致失败
- **手机上很卡**：GPU 性能有限，注意减少绘制调用（draw call）、复用几何体和纹理、降分辨率
- **`getContext('webgl')` 返回 `null`**：说明浏览器 / 设备不支持，或显卡驱动被禁；可先降级到 Canvas 2D 或给个提示
- **WebGL 和 WebGPU 选哪个**：目前大部分项目仍是 **WebGL（生态成熟、兼容好）**；追求新特性和性能可关注 WebGPU，但要注意浏览器支持度
- **能做 AI 计算吗**：可以用 WebGL 做点 GPU 计算（如 TensorFlow.js 的 WebGL 后端），但这属于"将就"，正经通用计算应看 **WebGPU / WebCL**
