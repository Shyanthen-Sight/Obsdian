# 自动编译

> [!abstract] 一句话
> "自动编译"就是==让编译器盯着源文件、你一保存就自动重编==，省掉"改一行 → 手动敲 `tsc` → 再运行"的重复循环。最基本的是 `tsc --watch`；想连"重编后自动重启"一起要，用 `nodemon` / `ts-node-dev` / `tsx watch`；现代前端项目则把这一步交给打包器的 watch 模式（Vite / esbuild / webpack）。

---

## 一、先看它替代了什么

不自动编译时，每改一次代码都要重走一遍手工程序：

```text
手动：  改代码 → 存盘 → npx tsc → node dist/index.js    （每轮都敲一遍）
自动：  改代码 → 存盘 → ──── 编译器盯着，自动重编 ────▶ 产物已更新
                              ↑ 终端里这条常驻进程一直开着
```

> [!info] 它省的是"手速"，不是"编译"
> 自动编译并没有让编译本身更快（[[tsc]] 全量类型检查依旧慢），只是把**触发时机**从"你敲命令"变成"文件一变动"。
> 真正的提速靠**增量编译**（`--incremental` / `.tsbuildinfo`）与 **watch 常驻内存的编译程序**——两者常配合使用。

---

## 二、最基础：`tsc --watch`

```bash
npx tsc --watch                      # 简写 -w：常驻，改动即重编
npx tsc -w -p tsconfig.build.json    # 指定用哪份配置
```

启动后终端停在这一行等文件变化，不退出：

```text
[12:00:01] Starting compilation in watch mode...
[12:00:02] Found 0 errors. Watching for file changes.

[12:03:15] File change detected. Starting incremental compilation...
[12:03:15] Found 0 errors. Watching for file changes.
```

> [!tip] 常驻一条 `npm run watch`
> 写进 `package.json` 后就不必记参数：
> ```json
> { "scripts": { "watch": "tsc --watch" } }
> ```
> 之后 `npm run watch` 开一个终端挂着即可。

> [!note] watch 模式为什么每次重编都很快
> 它把上次的**编译程序（Program）留在内存里**，文件一变只重编受影响的文件，而不是从零全量编译。
> 也就是说**它已经天然"增量"了**，不必再额外依赖 `.tsbuildinfo`（那是给一次性的 `--incremental` / 构建模式用的，见 [[解析产物说明]]）。

## 三、三种"自动"的层次

"自动编译"在 TypeScript 生态里其实分三层，需求的终点决定你选哪层：

| 层次 | 触发后发生什么 | 典型工具 | 适用 |
| --- | --- | --- | --- |
| ① 自动**重编** | 存盘 → 重新产出 `.js` | `tsc --watch` | 后端脚本、Node 服务、发布前 |
| ② 自动**重启** | 存盘 → 重编 → 重启 Node 进程 | `nodemon`、`ts-node-dev`、`tsx watch` | Node 服务开发 |
| ③ 自动**热更新** | 存盘 → 增量替换浏览器里的模块 | Vite、webpack-dev-server | 前端应用 |

> [!info] 一句话选型
> **只要产物更新** → `tsc -w`；**还要进程跟着重启** → 第五节；**前端要热更新** → 直接用打包器的 dev server，类型检查另开一条 `tsc --noEmit -w`。

## 四、`watchOptions`：调监听行为

`tsc --watch` 的监听细节可在 `tsconfig.json` 里用 `watchOptions` 精细控制——常见于**网络盘 / 虚拟机 / 大仓库**里监听失灵时。

```jsonc
{
  "watchOptions": {
    // 单个文件的监听策略
    "watchFile": "useFsEvents",
    // 目录的监听策略
    "watchDirectory": "useFsEvents",
    // 系统文件事件不可用时的回退轮询策略
    "fallbackPolling": "dynamicPriority",
    // 目录事件是否同步触发（网络文件系统上可减少延迟）
    "synchronousWatchDirectory": false,
    // 显式排除，进一步减少监听负担
    "excludeDirectories": ["**/node_modules", "temp"],
    "excludeFiles": ["temp/generated.ts"]
  }
}
```

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `watchFile` | `useFsEvents`（默认）/ `useFsEventsOnParentDirectory` / `fixedPollingInterval` / `priorityPollingInterval` / `dynamicPriorityPolling` | 单个文件怎么盯 |
| `watchDirectory` | `useFsEvents`（默认）/ `fixedPollingInterval` / `dynamicPriorityPolling` | 目录怎么盯 |
| `fallbackPolling` | `fixedPollingInterval` / `priorityPollingInterval` / `dynamicPriorityPolling` | 原生事件用不了时改走轮询 |

> [!warning] "文件改了却不重编"多半是监听方式的问题
> 在 Docker / WSL / 共享网络盘 / 某些 NAS 上，原生文件事件常常收不到。把 `watchFile` / `watchDirectory` 改成 `dynamicPriorityPolling`（走轮询）通常能救。
> 代价是 CPU 占用升高——轮询本质是"定时去问文件变了没"。

> [!tip] `--preserveWatchOutput`：别让屏幕反复清空
> 默认 watch 每次重编会清屏、只看得到最新一次；想保留历史输出加 `--preserveWatchOutput`，排查"改了哪次生效"时有用。

## 五、连"重启"一起自动：Node 服务的开发循环

`tsc -w` 只更新磁盘上的 `.js`，**已在运行的 Node 进程不会自己加载新代码**。Node 服务开发还要多一层"重启"，或干脆跳过产物、用执行器直接跑 `.ts`（详见 [[ts-node]]）。

```bash
# ① 编译 + 重启：tsc -w 一个终端，nodemon 盯产物另一个终端
npx nodemon --watch dist dist/index.js

# ② 直接在 TS 层面监听并重启
nodemon --watch src --ext ts --exec "ts-node -T src/index.ts"

# ③ ts-node-dev：内置监听 + 重启，专为此场景而生
npx ts-node-dev --respawn --transpile-only src/index.ts

# ④ tsx：现代首选，开箱即带 watch
npx tsx watch src/index.ts
```

> [!tip] 选哪个
> 新项目直接 `tsx watch`，几乎零配置、CJS/ESM 都能跑；已有 ts-node 体系就用 `ts-node-dev --respawn`；需要复杂监听规则的用 `nodemon`。
> 注意：这些工具**默认不做类型检查**（`-T` / `--transpile-only`），类型把关交给编辑器或 `tsc --noEmit -w`。

## 六、前端项目：watch 交给打包器

前端里 TS 只是"一种源语言"，真正的 watch / 重编 / 热更新由**打包器**负责，其 TS 转译通常用 esbuild（极快，但不报类型错）：

```bash
npx vite                                        # Vite：dev server 自带 HMR，改 TS 即时生效
npx webpack serve                               # webpack-dev-server：走 ts-loader / babel / swc
npx esbuild src/index.ts --bundle --outfile=dist/bundle.js --watch
```

> [!warning] 打包器不替你做类型检查
> esbuild / swc / babel 都是**只转译、不检查类型**——为了让 watch 足够快，它们直接忽略类型错误。
> 所以前端项目里常见这个组合：**打包器负责 watch 与热更新，再另开一个 `tsc --noEmit --watch` 专门盯类型**。两条线各司其职，谁都不拖慢谁。

```json
{
  "scripts": {
    "dev": "vite",
    "typecheck": "tsc --noEmit --watch"
  }
}
```

## 七、编辑器里要不要"保存即编译"

- **VS Code 内置的 TS 支持**已经**实时**算好类型错误、提示、跳转——但它**只服务编辑体验，不把 `.js` 写到磁盘**。
- 想"保存就产出文件"，别指望编辑器，**改用 `tsc -w` 常驻**：语义与命令行完全一致，也便于和团队 / CI 对齐。
- 老式的 `"compileOnSave": true`（tsconfig 顶层字段）只有少数旧 IDE 认，**自 TypeScript 5.0 起已被废弃**，不建议使用。

> [!info] 编辑器的"红线"和 `tsc` 的红线是同一套吗
> 是同一套 TypeScript 语言服务，但**编辑器用的是它内存里的配置**（含 `tsconfig.json`）。若编辑器不报错而 `tsc --noEmit` 报错，多半是**打开的文件不在同一个 tsconfig 范围**里，或编辑器还没重新加载配置。

## 八、常见问题

> [!question] `tsc --watch` 改了文件没反应？
> 先确认改的文件**在编译范围内**（`include` / `files` 覆盖到它），且没被 `exclude` 掉。若在 Docker / 网络盘 / WSL 上，多半是原生文件事件收不到——按第四节把 `watchFile` / `watchDirectory` 换成 `*Polling*`。

> [!question] 改了 `tsconfig.json` 要重启 watch 吗？
> 多数情况下 `tsc --watch` 会**自动检测配置变化并重启编译**；但涉及 `include` / `exclude` / 插件等结构性改动时，稳妥起见手动 `Ctrl+C` 重启一次。

> [!question] watch 模式下新增的文件会被编进去吗？
> 会，只要新文件落在 `include` 范围里。但**被 import 却没匹配任何 include** 的文件是例外——那属于 `rootDir` / `include` 对不上的老问题，去查这两项（见 [[tsc]]）。

> [!question] 自动编译很吃 CPU / 风扇狂转？
> watch 本身不贵，贵的是**每次类型检查**。可：确认是真正的增量 watch、把 `node_modules` 排除出监听（`excludeDirectories`）、关掉不必要的项目，或开发期改用 `tsx` / esbuild 这类不做类型检查的快工具。

> [!question] Node 服务里 `tsc -w` 生效了，为什么运行结果没变？
> 因为**运行中的进程不会自动加载新的 `.js`**。得配 `nodemon` / `ts-node-dev` / `tsx watch` 做重启（第五节）。

> [!question] 生产环境能一直挂着 `--watch` 吗？
> 不能。watch 是**开发期**的便利：进程常驻、监听文件、占内存。生产用一次性的 `tsc` 编出 `.js` 再 `node dist/index.js`，或交给 CI/CD 构建。
