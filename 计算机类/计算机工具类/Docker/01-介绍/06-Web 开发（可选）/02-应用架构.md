# 应用架构

容器化会逼着应用往"无状态、可替换"的方向改。容器随时可能被销毁、重建、调度到另一台机器，任何落在本地磁盘的状态都会丢，任何绑在主机的会话都会断。

## 十二条里最相关的几条

- 配置从环境变量进来，不写死在镜像里：`DATABASE_URL`、`REDIS_URL`、`LOG_LEVEL`
- 日志写 stdout/stderr，交给 `docker logs` 或日志驱动收集，别自己切文件
- 进程无状态，会话放 Redis，上传文件放 S3/MinIO
- 端口从环境变量读，别假设固定 8080
- 优雅退出：收到 SIGTERM 后停止接新请求，处理完手头的再退出

一个 compose 片段能把这些串起来：

```yaml
services:
  api:
    image: registry.example.com/shop-api:1.8.3
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/shop
      REDIS_URL: redis://cache:6379/0
      LOG_LEVEL: info
    depends_on:
      db:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/healthz"]
      interval: 10s
      timeout: 3s
      retries: 3
```

`environment` 把配置外置；`depends_on` 的 `service_healthy` 只保证启动顺序，不保证应用真的可用，应用自己仍要有重试；`healthcheck` 让编排层知道实例是否该接流量。

## 无状态到底要求什么

“无状态”不是“应用里不能有变量”，而是“任何实例被销毁，状态都不丢”。容器随时可能被 kill、被调度到另一台机器、被新版本替换，所以要把状态分成“可以丢的”和“不能丢的”：

| 状态 | 常见位置 | 留在容器里的后果 | 推荐位置 |
| --- | --- | --- | --- |
| 会话 | 进程内存、本地文件 | 实例一换用户掉线，多副本不一致 | Redis、数据库、签名 Cookie |
| 上传文件 | 容器本地目录 | 容器删除即丢，多副本看不到 | S3、MinIO、NFS |
| 本地数据库 | SQLite、内嵌 H2 | 无法多副本，备份和迁移困难 | 托管数据库 |
| 配置 | `.env`、配置文件 | 镜像绑定环境，易泄漏 | 环境变量、ConfigMap、Secret |
| 定时任务 | 容器内 cron | 多副本重复执行 | 外部调度器、分布式锁、队列 |
| 本地缓存 | 进程内缓存 | 丢失可接受，但要能回源 | Redis，或进程内缓存 + 失效策略 |
| 日志 | 容器内文件 | 随容器消失，无法集中检索 | stdout/stderr，交给日志驱动 |
| 分布式锁 | 本地文件锁 | 多副本下完全失效 | Redis、数据库、etcd |

判断标准很简单：**这个实例被删掉，另一个实例能不能无缝接住？** 不能，就说明有状态没外置。

无状态带来的直接好处是“牲畜化”：实例坏了不用救，直接换一个。代价是应用要接受“任何依赖都可能暂时不可用”，要有重试、超时、降级和幂等。无状态不是免费的性能优化，而是一套故障模型。

## 一个容器一个进程

不是绝对规则，但尽量遵守。一个容器塞 web、cron、worker，日志混在一起，健康检查说不清，重启一个把另一个也带走了。需要多个服务协作，用 compose 或编排工具拆开。

把几种组织方式放在一起看：

| 方式 | 进程隔离 | 日志 | 健康检查 | 生命周期 | 适用 |
| --- | --- | --- | --- | --- | --- |
| 单进程容器 | 容器级 | 清晰 | 明确 | 独立 | 默认选择 |
| 同容器多进程 | 无 | 混在一起 | 说不清 | 耦合 | 紧密耦合的遗留应用 |
| Sidecar（同 Pod） | 进程级 | 各自独立 | 各自定义 | 独立 | 日志收集、代理、证书注入 |
| Init container | 进程级 | 各自独立 | 一次性 | 启动前执行 | 初始化、迁移、等待依赖 |

同容器多进程的问题不是“跑不起来”，而是运行之后的事：

- **信号**：PID 1 只有一个，SIGTERM 发给谁、怎么转发给其他进程，要自己实现。
- **日志**：多个进程都写 stdout，行与行交错，难以区分来源。
- **健康检查**：一个进程健康不代表另一个健康，`HEALTHCHECK` 只能给一个退出码。
- **重启**：PID 1 崩了，容器退出，其他进程跟着被带走；非 PID 1 进程崩了，容器可能还在，但半个服务已经不可用。
- **资源**：cgroup 限额是整个容器的，无法按进程细分。

例外是“主进程 + 辅助进程”紧密耦合的场景，比如 nginx + php-fpm、应用 + 本地日志转发。可以用 supervisor、s6-overlay 或 dumb-init 管理，但要接受排障复杂度上升。能拆成 sidecar 的，优先拆：sidecar 共享网络和卷，但进程、日志、健康检查、生命周期都是独立的。

## 配置外置

配置和镜像分开，是“同一份镜像跑遍所有环境”的前提。常见方式对比：

| 方式 | 例子 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 构建期 `ARG`/`ENV` | 镜像里写死默认值 | 简单 | 环境绑定，改配置要重建 | 非敏感默认值 |
| 运行时环境变量 | `-e`、compose `environment`、K8s `env` | 符合 12-factor，易覆盖 | 明文可见，数量多难管理 | 大多数配置 |
| 挂载配置文件 | ConfigMap、Secret volume、`config.yaml` | 结构清晰，可挂多个文件 | 权限、重载逻辑要处理 | 复杂配置、证书 |
| 配置中心 | Consul、etcd、Nacos | 集中管理，可动态更新 | 多一个依赖，启动时要能连上 | 微服务、多环境 |
| 命令行参数 | `command:`、`args` | 显式，适合一次性覆盖 | 不适合大量配置 | 调试、临时覆盖 |

几条实践：

- 镜像里只放“所有环境都成立”的默认值；环境相关的 `DATABASE_URL`、`REDIS_URL`、`LOG_LEVEL` 从运行时注入。
- 密钥不要写进镜像，也不要写进 `.env` 再 `COPY` 进去；用 Secret 挂载或密钥管理服务。`docker inspect` 能看到环境变量，别把密码放 `ENV`。
- 配置变更后应用能不能热加载，要明确设计。不能热加载就滚动重启，别假装支持。
- 配置缺失要早失败：启动时校验必填项，给出清晰错误，而不是运行到一半才 `KeyError`。

## 启动与关闭

应用启动时数据库可能还没准备好，别在启动瞬间就崩。带退避的重试比 `sleep 10` 可靠。

### 健康检查与启动顺序

`depends_on` 有两种语义，差别很大：

- 默认的 `depends_on: [db]` 只保证“先启动 db 容器，再启动 api 容器”，不保证 db 已经能接受连接。
- `condition: service_healthy` 会等 db 的 `healthcheck` 通过，才启动 api；但仍然只保证启动顺序，不保证 api 启动后 db 一直健康。

健康检查本身也有坑：

- 镜像里必须有检查命令。`distroless` 没有 `curl`，`healthcheck: ["CMD", "curl", ...]` 会一直失败；可以用应用自带的健康端点配合一个静态二进制，或者改用 TCP 检查。
- `start_period` 给应用留启动时间，避免刚开始就被判死；`interval`、`timeout`、`retries` 决定判定节奏。
- liveness 检查应用自己是否卡死，应该轻量、只看本地状态；readiness 检查是否该接流量，可以依赖外部服务；startup 检查只用于启动慢的应用。三者混用会导致“数据库抖一下，所有 Pod 一起重启”的雪崩。
- 健康检查不要调用昂贵的接口，也不要每次查数据库全表。

应用侧的重试策略：

- 只对瞬时错误重试（连接拒绝、超时、503），配置错误、认证失败不要重试。
- 用指数退避加抖动，避免所有副本同时重连打爆数据库。
- 设置总超时，别无限重试；启动失败就退出，让编排层重启或报警，比挂死更容易发现。

### 优雅退出

收到 SIGTERM 后，应用应该按顺序做：

1. 停止接受新请求（从负载均衡摘除、关闭监听 socket）。
2. 处理完手头的请求，或者给它们一个截止时间。
3. 关闭数据库连接池、消息队列消费者、后台任务。
4. 刷新日志和指标，正常退出（退出码 0）。

Python 里可以注册信号处理器：

```python
signal.signal(signal.SIGTERM, lambda *_: server.shutdown())
```

Node 用 `process.on('SIGTERM', ...)`，Java 用 shutdown hook，Go 用 `signal.NotifyContext`。关键是入口命令要 `exec` 成应用，让信号真正到达，而不是停在 shell 上。

Kubernetes 里还要考虑两段时间：

- `preStop`：在发 SIGTERM 前执行，常用来 `sleep` 几秒等 Endpoint 摘除，或者主动从注册中心下线。
- `terminationGracePeriodSeconds`：默认 30 秒，超时后 SIGKILL。应用收尾时间必须小于这个值，否则会被硬杀。

`docker stop -t 30` 对应的是单机场景的宽限期。长任务要在收到信号后 checkpoint，消息队列消费者要在处理完当前消息后再 ack，避免“进程死了但消息已确认”。

### 日志

容器世界里的标准接口是 stdout/stderr：应用把日志打到标准输出，Docker 的日志驱动负责收集、轮转、转发。这样做的好处是应用不需要知道日志最终去哪，本地开发用 `docker logs`，生产接 Loki/ELK/CloudWatch。

实践要点：

- 用结构化日志（JSON），至少包含时间、级别、服务名、请求 ID；排查时能按字段过滤。
- 日志要行缓冲或立即刷新。Python 加 `-u` 或 `PYTHONUNBUFFERED=1`，否则 `docker logs` 可能延迟甚至丢尾部。
- 不要在日志里打密码、token、完整信用卡号；环境变量和请求体尤其容易泄漏。
- 配置日志轮转：Docker 默认 `json-file` 驱动会无限增长，设置 `--log-opt max-size=10m --log-opt max-file=3`，或者用 `local`/`journald` 驱动。
- 多进程容器里日志会交错，尽量一个容器一个进程；确实要多进程，用带前缀的日志或 sidecar 分流。

> [!tip] 别把日志写文件再挂卷
> 除非有明确的轮转和采集方案，否则这是给自己找麻烦。stdout 是容器世界里的标准接口。
