# 热重载

热重载要解决的事很具体：宿主上保存文件，几百毫秒后容器里的进程已经用上新代码。做法不是反复 build，而是把源码目录绑定挂载进容器，让容器里的文件监听器自己触发重启或热更新。

```bash
docker run --rm -it --name dev \
  -p 3000:3000 -p 5173:5173 \
  -v "$(pwd)":/app \
  -v /app/node_modules \
  -w /app \
  -e CHOKIDAR_USEPOLLING=true \
  node:20 npm run dev
```

两个 `-v` 的顺序有讲究：第一个把项目目录盖到 `/app`，第二个再挂一个匿名卷到 `/app/node_modules`，把宿主的依赖目录挡住。这样容器用自己安装的依赖，宿主也不会被写入文件污染。前端的 `dist`、`.next`，Java 的 `target` 也常这样处理。

## 监听器与轮询

文件监听依赖内核的 inotify。Linux 上绑定挂载就是普通目录，事件完整；macOS 和 Windows 的 Docker Desktop 中间隔着一层虚拟机文件共享，事件可能丢或延迟，监听器于是提供了轮询开关：

| 工具 | 轮询配置 |
| --- | --- |
| nodemon | `--legacy-watch` 或 `CHOKIDAR_USEPOLLING=true` |
| Vite | `server.watch.usePolling: true` |
| webpack-dev-server | `watchOptions.poll: 1000` |
| uvicorn | `--reload --reload-dir /app`（配合 watchfiles） |
| Spring Boot DevTools | 监听 classpath，重启比完整启动快 |

轮询稳，但 CPU 和磁盘 IO 会上去。先确认默认监听可用，真丢了事件再开轮询，间隔从 500ms 到 1s 试。

## 用 compose 管住开发配置

手写 `docker run` 很快会漏参数，开发环境一般落在 `compose.yaml` 里：

```yaml
services:
  api:
    build:
      context: .
      target: dev          # 多阶段构建里的开发阶段
    command: npm run dev
    ports:
      - "127.0.0.1:3000:3000"
      - "127.0.0.1:9229:9229"
    volumes:
      - .:/app
      - /app/node_modules
    environment:
      NODE_ENV: development
      CHOKIDAR_USEPOLLING: "true"
    develop:
      watch:
        - action: sync
          path: ./src
          target: /app/src
          ignore:
            - node_modules/
        - action: rebuild
          path: package.json
```

`develop.watch` 是 Compose 2.22 之后的能力，`docker compose watch` 启动后按规则同步：`sync` 只拷变化的文件，`rebuild` 在依赖清单变化时重建镜像。它比整目录挂载更精细，适合源码和依赖混在一起的仓库。`target: dev` 要求 Dockerfile 里有对应的构建阶段，生产阶段不要装 devDependencies，也不要带 watcher。

## 容易踩的坑

容器里以非 root 用户跑、宿主目录又属于你的 UID 时，监听器可能没权限读文件；反过来，容器写出的文件在宿主上变成 root 所有。开发镜像里把 UID/GID 对齐，或用 `user: "1000:1000"`。Linux 上项目文件多时还会撞到 `fs.inotify.max_user_watches` 上限，报 “ENOSPC”，调大 sysctl 或改用轮询。

生成代码、日志、数据库文件落在被监听目录里，会触发重启循环。把 `node_modules`、`.git`、`tmp`、`*.log` 放进 ignore。热重载只是开发手段，生产镜像里不要保留 `npm run dev` 和源码挂载。
