

> [!abstract] 一句话定义
> 测试优先级分配是在**时间、人力、环境都有限**的前提下，决定"先测什么、重点测什么、可以少测或不测什么"的过程。它的本质是==基于风险的资源投资决策==，而不是给用例随便贴个高/中/低标签。

---

## 一、为什么必须分优先级

1. **穷尽测试不可能**：输入、路径、环境组合是无限的。
2. **缺陷分布不均**：经验上大量缺陷集中在少数模块（近似帕累托分布）。
3. **越晚发现越贵**：缺陷从需求到上线，修复成本呈数量级上升。
4. **回归规模会膨胀**：功能越加越多，全量回归越来越慢。
5. **发布窗口固定**：版本不会因为测试没做完而无限延期。
6. **资源有限**：人、环境、数据、第三方依赖都不是无限的。

> [!important] 优先级的本质
> 优先级不是"这个用例重不重要"的主观感受，而是：**如果只能测 30%，应该测哪 30% 才能把剩余风险降到可接受水平？**

---

## 二、核心：风险 = 可能性 × 影响

最常用的优先级模型就是风险模型：

```
风险 = 发生缺陷的可能性 × 缺陷发生后的影响
```

### 2.1 影响"可能性"的因素

| 因素 | 说明 |
|---|---|
| 复杂度 | 逻辑分支多、状态多、算法复杂、并发多 |
| 变更程度 | 新功能、重构、频繁修改、hotfix |
| 技术风险 | 新技术、新框架、不熟悉的领域 |
| 依赖数量 | 依赖第三方、跨服务、跨团队 |
| 缺陷历史 | 历史上 bug 多的模块往往还会继续出 bug |
| 代码质量 | 耦合高、缺少测试、技术债重 |
| 团队经验 | 新人开发、交接频繁 |
| 环境差异 | 测试环境与生产环境不一致 |

### 2.2 影响"影响程度"的因素

| 因素 | 说明 |
|---|---|
| 业务价值 | 是否核心收入/核心流程 |
| 用户规模 | 影响多少用户 |
| 使用频率 | 高频功能出问题影响更大 |
| 资金/交易 | 支付、退款、结算、对账 |
| 安全与隐私 | 越权、数据泄露、合规 |
| 不可逆性 | 删除、转账、发布后难以回滚 |
| 法规/合同 | 合规要求、SLA、审计 |
| 品牌与舆情 | 对外可见、容易被传播 |
| 恢复成本 | 出问题后修复/补偿的代价 |
| 数据完整性 | 数据丢失、错乱、污染 |

### 2.3 风险矩阵

用 5×5 矩阵快速定位：

| 可能性 \ 影响 | 很低 | 低 | 中 | 高 | 很高 |
|---|---|---|---|---|---|
| **很高** | 中 | 高 | 高 | 极高 | 极高 |
| **高** | 中 | 中 | 高 | 极高 | 极高 |
| **中** | 低 | 中 | 中 | 高 | 高 |
| **低** | 低 | 低 | 中 | 中 | 高 |
| **很低** | 低 | 低 | 低 | 中 | 中 |

> [!tip] 风险矩阵的价值
> 它强迫团队把"感觉很重要"拆成两个可讨论的维度：**多大概率出问题**、**出了问题多严重**。讨论过程本身往往比最终分数更有价值。

## 三、影响优先级的具体因素清单

设计用例优先级时，可以逐项打分（1–5 分）：

1. **业务关键路径**：下单、支付、登录、核心查询。
2. **使用频率/用户量**：高频入口优先。
3. **功能复杂度**：分支、状态、并发、计算。
4. **本次变更范围**：新增、修改、重构、依赖升级。
5. **历史缺陷密度**：过去出问题多的地方。
6. **不可逆操作**：删除、扣款、发布、审批。
7. **安全与权限**：认证、授权、越权、注入。
8. **数据一致性**：事务、幂等、对账、迁移。
9. **集成与依赖**：第三方、跨服务、消息、缓存。
10. **法规/合规/合同**：必须满足的硬约束。
11. **可恢复性**：出问题能否快速回滚/补偿。
12. **用户可见性**：UI、文案、错误提示。
13. **可测试性**：难以测试的地方反而要提前设计。
14. **环境/平台覆盖**：浏览器、设备、系统版本。

## 四、优先级分级体系

### 4.1 用例优先级（P0–P4）

| 级别 | 定义 | 典型内容 | 执行时机 | 是否自动化 |
|---|---|---|---|---|
| **P0** | 阻断级：不通过则版本不可测/不可发 | 登录、核心主流程、冒烟 | 每次构建/提测 | 必须 |
| **P1** | 核心级：主要业务功能 | 下单、支付、关键查询 | 每次迭代/每日 | 强烈建议 |
| **P2** | 重要级：一般功能与常见异常 | 次要功能、常见边界 | 每轮回归 | 建议 |
| **P3** | 一般级：边缘场景、低频功能 | 罕见组合、兼容性 | 版本发布前/抽测 | 可选 |
| **P4** | 低优先级：可延后 | 极端场景、历史遗留 | 有空再测/不测 | 一般不 |

> [!warning] 优先级膨胀
> 如果 80% 的用例都是 P0，那等于没有优先级。合理的分布应呈金字塔形，例如 P0 5–10%、P1 20–30%、P2 40–50%、P3/P4 其余。**P0 应该少而硬**。

### 4.2 三种"优先级"不要混淆

| 概念 | 对象 | 回答的问题 |
|---|---|---|
| 需求优先级 | 产品需求/故事 | 先做哪个功能？ |
| 测试用例优先级 | 测试用例 | 先执行哪条用例？ |
| 缺陷优先级 | 已发现的缺陷 | 先修哪个 bug？ |

三者相关但不等价。一个低优先级需求可能包含高风险技术点；一个高优先级用例可能发现低优先级缺陷。

## 五、用例优先级排序策略（TCP）

**测试用例优先级排序（Test Case Prioritization, TCP）** 的目标通常是：在有限执行预算下，**尽早发现缺陷**或**尽早覆盖高价值目标**。

### 5.1 常见策略

| 策略 | 思想 | 适用 |
|---|---|---|
| **风险优先** | 风险高的先测 | 通用，最常用 |
| **业务/需求优先** | 核心业务先测 | 发布前验收 |
| **覆盖优先** | 优先覆盖新变更/未覆盖代码 | 回归、增量开发 |
| **历史失败优先** | 最近/经常失败的用例先跑 | 快速反馈 |
| **客户/利益相关者优先** | 客户最关心的先测 | 验收、定制项目 |
| **成本效益优先** | 单位执行成本发现缺陷最多者优先 | 回归预算紧 |
| **依赖约束** | 前置用例必须先执行 | 有数据/状态依赖 |
| **随机/轮换** | 避免长期只测同一批 | 补充手段 |

### 5.2 覆盖策略：Total vs Additional

- **Total 覆盖**：按"该用例覆盖的代码总量"排序，覆盖多者先跑。
- **Additional 覆盖**：每次选择"能带来最多新增覆盖"的用例，动态更新。

> [!note] 研究结论
> 一般情况下，**Additional 策略**通常优于 Total 策略，因为它避免重复覆盖已被覆盖的部分。但实际工程中还要考虑执行成本、稳定性、依赖关系。

### 5.3 回归测试选择（RTS）

不是所有用例都要回归。常见做法：

- **变更影响分析**：改了哪些文件/模块 → 找出受影响的用例。
- **代码覆盖映射**：用例覆盖了哪些代码 → 变更代码 → 相关用例。
- **依赖图**：服务/模块依赖关系传播。
- **风险兜底**：无论影响分析结果如何，P0 冒烟必跑。

> [!warning] 安全的回归选择
> 影响分析可能漏掉隐式依赖（反射、配置、动态调用、数据库触发器）。因此通常保留一个"安全子集"（P0/P1）无条件执行。

## 六、测试金字塔与分层优先级

测试资源不应平均分布在所有层次。典型分层：

```
        /\        E2E / UI（少量，关键链路）
       /  \
      /----\      集成/契约（适量）
     /      \
    /--------\    单元测试（大量，快速）
```

- **底层优先**：逻辑、边界、异常尽量在单元测试覆盖，反馈快、定位准。
- **中层**：接口契约、数据库、消息、缓存。
- **顶层**：只保留核心用户旅程，避免端到端用例过多导致慢和脆弱。

> [!note] 比例不是教条
> "70/20/10"只是经验参考。微服务、前端、算法、嵌入式系统的合理比例差异很大。原则是：**能在低成本层验证的，不要放到高成本层**。

## 七、量化方法

### 7.1 加权评分

给每个因素分配权重，逐项打分：

| 因素 | 权重 | 模块 A | 模块 B | 模块 C |
|---|---|---|---|---|
| 业务价值 | 30% | 5 | 3 | 4 |
| 使用频率 | 20% | 5 | 2 | 4 |
| 复杂度 | 20% | 4 | 5 | 2 |
| 变更程度 | 15% | 5 | 4 | 1 |
| 历史缺陷 | 10% | 4 | 3 | 2 |
| 安全/合规 | 5% | 3 | 2 | 5 |
| **加权得分** | | **4.60** | **3.25** | **3.05** |

计算：A = 0.3×5 + 0.2×5 + 0.2×4 + 0.15×5 + 0.1×4 + 0.05×3 = 4.60。

> [!tip] 权重怎么定
> 权重应由产品、开发、测试、运维共同确认，并随业务阶段调整。例如金融/医疗系统会显著提高安全与合规权重。

### 7.2 FMEA / RPN

FMEA（失效模式与影响分析）用三个维度评估：

```
RPN = S（严重度）× O（发生度）× D（可探测度）
```

- **S**：后果多严重（1–10）。
- **O**：多容易发生（1–10）。
- **D**：多难被发现（1–10，越难发现分数越高）。

RPN 越高，越应优先测试/优先改进。

> [!note] 测试视角的调整
> 传统 FMEA 的 D 是"失效被探测到的难度"；在测试优先级中，也可以理解为"该缺陷若存在，现有手段多难发现"，从而指导我们加强预言机和测试设计。

### 7.3 MoSCoW

- **M**ust have：必须满足。
- **S**hould have：应该满足。
- **C**ould have：可以满足。
- **W**on't have：本次不做。

适合需求/范围层面的优先级沟通，也常用于验收标准。

### 7.4 期望损失法

```
期望损失 = 缺陷发生概率 × 损失金额
```

适合有明确业务数据的场景（支付、交易、SLA 赔偿）。用它排序比纯主观打分更有说服力。

## 八、动态调整

优先级不是一次性标签，而是**随上下文变化的动态决策**。

需要重新评估的触发点：

- 新版本/新迭代开始。
- 需求变更、架构调整、依赖升级。
- 线上事故、客诉、缺陷趋势异常。
- 测试发现某模块缺陷密集。
- 发布窗口压缩或资源变化。
- 新功能上线后的观察期（通常需要提高回归优先级）。
- 环境/平台变化（新浏览器、新系统版本）。

> [!important] 定期复审
> 建议每个迭代或每个发布周期复审一次用例优先级；长期不更新的优先级表会逐渐失真。

## 九、常见误区

| 误区 | 问题 | 改进 |
|---|---|---|
| 按开发顺序测 | 先写完的未必最重要 | 按风险/业务排序 |
| 全部标 P0 | 等于没有优先级 | 控制 P0 比例，定义硬标准 |
| 只测新功能 | 回归缺失导致旧功能被破坏 | 变更影响分析 + P0 回归 |
| 只测 happy path | 异常路径才是缺陷高发区 | 边界、异常、并发、权限 |
| 平均分配资源 | 高风险区投入不足 | 风险加权 |
| 只看功能，忽略非功能 | 性能/安全/兼容问题上线才爆 | 把非功能纳入风险模型 |
| 用严重程度代替优先级 | 两者维度不同 | 分开评估（见下） |
| 忽略依赖和环境 | 用例无法执行或结果失真 | 前置条件、环境矩阵 |
| 优先级定完就不管 | 上下文变化后失真 | 定期复审 |
| 只凭个人感觉 | 难以解释、难以复用 | 评分表 + 团队评审 |

## 十、严重程度（Severity）vs 优先级（Priority）

这是缺陷管理中极易混淆的一对概念：

| 维度 | 严重程度 Severity | 优先级 Priority |
|---|---|---|
| 回答 | 缺陷对系统/业务的**影响有多大** | 缺陷**多紧急需要修** |
| 视角 | 技术/质量 | 业务/项目管理 |
| 决定者 | 测试/开发 | 产品/项目经理（测试提供建议） |
| 示例 | 崩溃、数据丢失 = 高 | 老板明天要看 = 高 |

四象限：

| | 高优先级 | 低优先级 |
|---|---|---|
| **高严重度** | 核心功能崩溃、支付失败 → 立即修 | 罕见路径崩溃、极端环境问题 → 排期修 |
| **低严重度** | 首页文案错误、Logo 错位 → 尽快修 | 边缘体验问题 → 有空再修 |

> [!example] 经典案例
> - **高严重度 + 低优先级**：某罕见机型在特定系统版本下崩溃，但该机型用户占比 0.01%。
> - **低严重度 + 高优先级**：官网首页把公司名称写错，影响品牌形象。
>
> 所以**严重程度高不等于优先级高**，反之亦然。

## 十一、落地模板

### 11.1 用例优先级评估表

| 字段 | 说明 |
|---|---|
| 用例编号 | 唯一标识 |
| 所属模块/需求 | 便于追溯 |
| 风险等级 | 高/中/低（由可能性 × 影响得出） |
| 优先级 | P0–P4 |
| 优先级依据 | 一句话说明为什么 |
| 自动化状态 | 已自动化/待自动化/手工 |
| 最后执行结果 | 通过/失败/阻塞 |
| 复审日期 | 下次复审时间 |

### 11.2 发布前检查清单

- [ ] P0 冒烟全部通过。
- [ ] P1 核心用例全部通过。
- [ ] 本次变更影响范围内的用例已覆盖。
- [ ] 已知高严重度缺陷已修复或有明确规避方案。
- [ ] 性能/安全/兼容性关键项已评估。
- [ ] 回滚方案与监控告警已就绪。

> [!quote] 一句话总结
> 优先级分配的本质，是在"测不完"的现实下回答：==哪些风险必须现在被覆盖，哪些可以接受、延后或明确不测。==
