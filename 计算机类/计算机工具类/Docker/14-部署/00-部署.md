# 部署

镜像构建完，剩下的事是怎么把它稳定地跑在服务器上。这一阶段不纠结某个工具的按钮在哪，而是帮你判断：什么规模该用什么方案，各方案的边界又在哪。

部署方式大致分三档：

- 托管 PaaS：推镜像或连 Git 就上线，节点、TLS、日志、扩缩容都不用自己管。适合早期产品和不想养运维的团队。
- 单机编排：一台机器上用 compose 或 systemd 管几个容器，够用、好排查。流量上来后前面加一层反向代理。
- 集群编排：[[02-Docker Swarm|Docker Swarm]]、[[01-Nomad|Nomad]]、[[03-Kubernetes|Kubernetes]]，解决多机调度、副本维持、滚动发布和服务发现。

建议按 PaaS → Swarm/Nomad → K8s 的顺序了解，不必每个都学。先把 [[00-运行容器|运行容器]] 里的端口映射、重启策略，以及 [[00-网络|网络]] 里的 bridge/host 模式弄熟，再看编排会轻松很多——编排器干的事，本质是把这些单机操作分发到多台机器上并保持状态。

单机部署先把 compose 跑稳：

```bash
docker compose -f compose.prod.yaml up -d
docker compose ps
docker compose logs -f --tail=100 api
```

生产用的 compose 文件把镜像固定到版本或 digest，端口只绑需要的地址，数据目录换成命名卷；这些做到之后，再考虑多机编排。

学完这一阶段，你应该能回答几个具体问题：当前项目该不该上 K8s；滚动发布时旧副本什么时候下线；`ImagePullBackOff` 该从哪一层查；PaaS 账单为什么会在某个月突然翻倍。

选型先看团队规模和维护意愿。三个人以内的团队自建 K8s，经常一半时间在修集群而不是写业务。反过来，已经有平台团队、需要多租户和细粒度权限时，PaaS 很快就不够用。中间地带才是大多数项目的真实位置：一台或几台机器，加上一个足够简单的编排工具。
