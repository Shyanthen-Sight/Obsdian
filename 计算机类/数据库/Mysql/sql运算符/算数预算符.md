# SQL 算术运算符

> 算术运算符只能用于**数值运算**，SQL 里**没有字符串拼接**（MySQL 用 `CONCAT()`）。

---

## 一、运算符总览

| 运算符         | 名称     | 示例        | 结果       | 说明                                      |
| ----------- | ------ | --------- | -------- | --------------------------------------- |
| `+`         | 加      | `5 + 3`   | `8`      | 一元 `+` 无实际作用                            |
| `-`         | 减      | `5 - 3`   | `2`      | 一元 `-` 取负：`-(-5)=5`                     |
| `*`         | 乘      | `5 * 3`   | `15`     |                                         |
| `/`         | 除      | `5 / 2`   | `2.5000` | ==结果恒为小数（DECIMAL）==                     |
| `DIV`       | 整除     | `5 DIV 2` | `2`      | 丢弃小数部分，**向零截断**                         |
| `%` 或 `MOD` | 取模（余数） | `5 % 2`   | `1`      | 三种写法等价：`a % b` = `a MOD b` = `MOD(a,b)` |

```sql
SELECT 5 + 3, 5 - 3, 5 * 3, 5 / 2;   # 8  2  15  2.5000
SELECT 10 DIV 3, 10 MOD 3, 10 % 3;   # 3  1  1
SELECT MOD(10, 3);                   # 1  函数写法
```

## 二、重点：`/`、`DIV`、`%` 三者辨析

这是三种"除法"最容易混淆的地方。

```sql
SELECT 7 / 2;      # 3.5000  —— 真除法，保留小数
SELECT 7 DIV 2;    # 3       —— 整除，砍掉小数
SELECT 7 % 2;      # 1       —— 只要余数

SELECT -7 / 2;     # -3.5000
SELECT -7 DIV 2;   # -3      —— 向零截断，不是 FLOOR(-3.5)=-4
SELECT -7 % 2;     # -1      —— 符号跟随【被除数】
SELECT 7 % -3;     #  1      —— 同上，不是 -2
```

**关键点：**

1. **`/` 永远返回小数**，即使能整除：`SELECT 3 / 1` → `3.0000`。MySQL 的除法结果类型是 `DECIMAL`，默认保留 4 位小数（由系统变量 `div_precision_increment` 控制，默认 4）。
2. **`DIV` 向零截断**，与 `FLOOR()` 不同：
   - 向下取整用 `FLOOR(-7/2)` = `-4`
   - 整除用 `-7 DIV 2` = `-3`
3. **取模的符号跟随被除数**（和 C/Java 一致，和 Python 相反）。

```sql
# 想要"Python 式"取模（结果永远非负）：
SELECT (a % b + b) % b;
# 例：SELECT (-7 % 3 + 3) % 3;  -> 2
```

## 三、NULL 传播：最大的陷阱

==任何算术运算只要有一个操作数是 `NULL`，结果就是 `NULL`==（不是 0）。这与聚合函数忽略 NULL 的行为完全不同。

```sql
SELECT 100 + NULL;          # NULL
SELECT NULL * 0;            # NULL  ← 不是 0！
SELECT 5 / NULL;            # NULL

# 表中有 NULL 时，整列计算全部塌陷：
CREATE TABLE t(id INT, price DECIMAL(10,2), qty INT);
INSERT INTO t VALUES (1, 10.00, 3), (2, NULL, 3);

SELECT id, price * qty AS amount FROM t;
# 1 -> 30.00
# 2 -> NULL     ← 期望 0 或忽略，实际是 NULL
```

**两种修复思路（语义不同，别混用）：**

```sql
# 思路 A：把 NULL 当 0 参与计算（如"运费未填按 0 算"）
SELECT id, IFNULL(price, 0) * IFNULL(qty, 0) AS amount FROM t;
# 也可以用 COALESCE(price, 0)（标准 SQL，支持多参数）

# 思路 B：把 NULL 当"缺失"，整行结果仍为 NULL，交给上层过滤
SELECT id, price * qty AS amount FROM t WHERE price IS NOT NULL;
```

> **对比记忆**：`SELECT SUM(price * qty) FROM t;` 因为 `SUM` 会**跳过 NULL**，所以结果是 `30.00` 而不是 `NULL`。
> 但 `AVG(price * qty)` 只对 1 行求平均 → 也是 `30.00`，分母被"悄悄缩小"了，这是统计口径错误的常见来源。

## 四、隐式类型转换

MySQL 在数值上下文里把字符串**按前缀转数字**，转不动就当 0，并且**只给 warning 不报错**——静默错误的重灾区。

```sql
SELECT '10' + 5;        # 15     纯数字字符串
SELECT '3.5' + 2;       # 5.5
SELECT '10abc' + 5;     # 15     ← 截取前缀 10，抛 warning
SELECT 'abc' + 5;       # 5      ← 当成 0，抛 warning
SELECT '' + 5;          # 5
SELECT '1e2' + 0;       # 100    科学计数法可识别
```

**日期字符串的坑（重点）：**

```sql
SELECT '2024-01-01' + 0;   # 2024   ← 字符串只取数字前缀，不是日期！
```

所以要算日期加减，**必须用日期函数或 `INTERVAL` 关键字**，见下一节。

**建议**：跨类型运算一律显式转换，避免"能跑但结果错"。

```sql
SELECT CAST('3.5' AS DECIMAL(10,2)) + 2;   # 5.50
SELECT CAST('abc' AS UNSIGNED);            # 0（严格模式下 INSERT 才报错）
```

## 五、日期时间参与运算

`+` / `-` 可以直接配合 `INTERVAL` 使用，这是日期运算的**唯一推荐写法**：

```sql
SELECT '2024-01-01' + INTERVAL 1 DAY;      # 2024-01-02
SELECT '2024-01-01' - INTERVAL 1 DAY;      # 2023-12-31
SELECT NOW() + INTERVAL 7 DAY;             # 一周后
SELECT NOW() - INTERVAL 3 MONTH;           # 三个月前
SELECT DATE_ADD('2024-01-01', INTERVAL 2 MONTH);  # 函数写法，等价
SELECT DATE_SUB('2024-01-01', INTERVAL 2 MONTH);
```

**反面教材（三个都会得到错误结果，但都不报错）：**

```sql
SELECT '2024-01-02' - '2024-01-01';   # 0    ← 两个字符串都取前缀 2024，相减为 0
SELECT '2024-01-01' + 1;              # 2025 ← 把日期当数字 2024 加 1
SELECT NOW() + 1;                     # 20240922123456 + 1，毫无意义
```

**要算"相差多少天"，用 `DATEDIFF`，不要用减号：**

```sql
SELECT DATEDIFF('2024-01-02', '2024-01-01');   # 1（只算日期部分）
SELECT TIMESTAMPDIFF(HOUR, '2024-01-01 00:00:00', '2024-01-02 03:00:00');  # 27
```

> 一个历史遗留写法：对 `DATE` 类型的**列**执行 `+ 0`，会得到 `YYYYMMDD` 的数值（如 `20240101`），
> 且 `date_col - other_date_col` 会变成整数相减。**别依赖这个行为**，语义不清晰、跨库不通用。

## 六、整数溢出与精度

**1. 整数溢出会直接报错**（MySQL 会检测）：

```sql
SELECT 9223372036854775807 + 1;
# ERROR 1690 (22003): BIGINT value is out of range in '(... + 1)'
```

同理，`UPDATE` 让某列超出其类型范围（如 `TINYINT` 加到 128）在严格模式下也会报错，而不是静默回绕。这是好事——能保护数据；但批量更新时要注意**分批次或改用更大类型（`BIGINT`）**。

**2. 浮点精度：金额绝不能用 `FLOAT` / `DOUBLE`**

```sql
SELECT 0.1 + 0.2 = 0.3;      # 1（true）
# 原因：MySQL 中带小数点的字面量是 DECIMAL（精确小数），不是 DOUBLE

SELECT 0.1E0 + 0.2E0 = 0.3E0;  # 0（false）—— 强制成 DOUBLE 就露馅了
# 0.1E0 + 0.2E0 = 0.30000000000000004

CREATE TABLE bad (amount DOUBLE);   INSERT INTO bad VALUES (0.1), (0.2);
SELECT SUM(amount) FROM bad;        # 0.30000000000000004  ← 金额表禁止用 DOUBLE
```

> 结论：**金额字段一律 `DECIMAL(m,2)`**，运算结果也是精确的；只有在需要科学计算的场景才用 `DOUBLE`。

## 七、运算符优先级

从高到低（只列常用部分）：

| 优先级 | 运算符 |
|--------|--------|
| 1 | `INTERVAL` |
| 2 | `BINARY`、`COLLATE` |
| 3 | `!`、一元 `-`、`~` |
| 4 | `^` |
| 5 | `*`、`/`、`DIV`、`%`、`MOD`  ← 注意 `DIV`/`MOD` 与乘除**同级** |
| 6 | `-`、`+`（二元） |
| 7 | `<<`、`>>` |
| 8 | `&`、`\|` |
| 9 | 比较运算 `=`、`>`、`<`、`LIKE`、`IN`、`IS` … |
| 10 | `BETWEEN`、`CASE` |

要点：**乘除模同级、加减同级、同级从左到右**。

```sql
SELECT 2 + 3 * 4;      # 14   先乘后加
SELECT (2 + 3) * 4;    # 20   括号优先
SELECT 10 % 3 * 2;     # 2    (10%3)=1，再 *2  —— 从左到右
SELECT 10 - 3 - 2;     # 5    左结合，(10-3)-2
SELECT 1 + 2 * 3 % 4;  # 3    (2*3)=6，6%4=2，1+2=3
```

> 实战建议：**表达式超过两个运算符就加括号**。可读性比"我知道优先级"更值钱。

## 八、实际场景举例

### 1. 计算订单金额

```sql
SELECT
  o.id,
  SUM(i.price * i.qty)                     AS goods_amount,
  ROUND(SUM(i.price * i.qty) * 0.85, 2)    AS discount_amount,   # 85 折
  ROUND(SUM(i.price * i.qty) * 0.85 + 10, 2) AS final_amount     # 再加 10 元运费
FROM order_item i
JOIN orders o ON o.id = i.order_id
GROUP BY o.id;
```

### 2. 计算百分比 / 占比（跨库必踩的坑）

```sql
# MySQL：/ 结果就是小数，直接乘 100 即可
SELECT
  dept,
  ROUND(SUM(CASE WHEN gender = '男' THEN 1 ELSE 0 END) / COUNT(*) * 100, 2) AS male_pct
FROM employee GROUP BY dept;

# 保险写法（任何数据库都对）：乘 1.0 强制浮点
SELECT ROUND(SUM(...) * 1.0 / COUNT(*) * 100, 2);
```

> 在 **PostgreSQL / SQLite** 中，两个整数相除是**整数除法**：`1/2 = 0`，必须写 `1.0/2`。
> 在 MySQL 里 `1/2 = 0.5000`。同一段 SQL 换库就"少了一半数据"，多半是这个原因。

### 3. 求平均时的除法陷阱

```sql
# 用 AVG 而不是 SUM/COUNT（AVG 自动忽略 NULL，口径一致）
SELECT AVG(salary) FROM employee;

# 若要自己算，注意 COUNT(*) 与 COUNT(col) 的差异
SELECT SUM(salary) / COUNT(*)     AS avg_all,     # 分母含 salary 为 NULL 的行
       SUM(salary) / COUNT(salary) AS avg_valid    # 分母不含 NULL 行
FROM employee;
```

### 4. 取模的两个经典用途

```sql
# ① 分片 / 分组：按 id 取模均匀切分
SELECT * FROM orders WHERE MOD(id, 4) = 0;      # 每 4 条取 1 条

# ② 判断奇偶、轮询分配
SELECT id, IF(id % 2 = 0, '偶数', '奇数') AS parity FROM orders;

# ③ 判断整除
SELECT id FROM orders WHERE total % 100 = 0;    # 总价是整百的订单
```

### 5. 原子更新：库存扣减（把运算写进 UPDATE）

```sql
# 危险写法：先 SELECT 再 UPDATE，并发下会超卖
# 安全写法：让数据库在同一语句里完成"读-算-写"
UPDATE stock SET num = num - 1 WHERE id = 10086 AND num >= 1;
# 影响行数为 0 说明库存不足，直接据此判断，无需额外加锁
```

> `UPDATE t SET num = num + 1` 里的 `num` 取的是==该行更新前的最新值==，天然原子，是防超卖的标准手法。

### 6. SELECT 中不能引用同层别名

```sql
-- 报错：Unknown column 'total' in 'field list'
SELECT price * qty AS total, total * 0.9 AS discounted FROM orders;

-- 正确：重复表达式，或用子查询/CTE
SELECT price * qty AS total, price * qty * 0.9 AS discounted FROM orders;

SELECT total, total * 0.9 AS discounted
FROM (SELECT price * qty AS total FROM orders) x;
```

> 例外：别名可以用在 `ORDER BY`、`GROUP BY`、`HAVING` 中（它们的执行顺序在 SELECT 之后）。

## 九、跨数据库差异（易踩坑清单）

| 行为 | MySQL | PostgreSQL | SQL Server | Oracle |
|------|-------|-----------|-----------|--------|
| 整数 `/` 整数 | 得小数 `0.5000` | ==得整数 `0`== | 得整数 `0` | 得小数 |
| 整除运算符 | `DIV` | 无（用 `div()` 或 `CAST`） | 无 | 无 |
| 取模 | `%`、`MOD()` | `%`、`mod()` | `%` | `MOD()`，**无 `%` 运算符** |
| `+` 拼字符串 | ❌ 报/转数字 | ❌ | ==✅ `'a'+'b'='ab'`== | ❌（用 `\|\|`） |
| `\|\|` 含义 | 逻辑 OR | 字符串拼接 | 逻辑 OR | 字符串拼接 |
| 除零 | `SELECT` 返 NULL | 直接报错 | 直接报错 | 直接报错 |

**除零的完整说明（MySQL）：**

```sql
SELECT 5 / 0;      # NULL（附 warning: Division by 0）
SELECT 5 DIV 0;    # NULL
SELECT 5 % 0;      # NULL
```

MySQL 在**纯查询**中把除零当 NULL，但在 `INSERT` / `UPDATE` 里、且开启严格模式（`STRICT_TRANS_TABLES`，8.0 默认开启）时会**直接报错**：

```sql
INSERT INTO t VALUES (1/0);
# ERROR 1365 (22012): Division by 0
```

> 所以 `SELECT` 里"跑得通"不代表 `INSERT` 里也跑得通。防御性写法：
> `SELECT a / NULLIF(b, 0) FROM t;` —— 把 0 转成 NULL，结果统一为 NULL，且严格模式下不报错。

## 十、速查小结

1. `/` 恒为小数，`DIV` 向零截断，`%` 符号随被除数。
2. **NULL 会污染整个表达式**，用 `IFNULL` / `COALESCE` / `NULLIF` 兜底。
3. 字符串参与运算按**数字前缀**转换，转不动当 0，**只警告不报错** → 隐式转换是静默 bug 源头。
4. 日期运算只用 `+ INTERVAL` / `DATE_ADD`，日期差只用 `DATEDIFF`，**绝不用减号**。
5. 金额用 `DECIMAL`，禁用 `FLOAT`/`DOUBLE`；整数溢出会报错，不是回绕。
6. `SELECT` 同层不能用别名；`ORDER BY` / `HAVING` 可以用。
7. 加减乘除模同级（`DIV`、`MOD` 也是），**同级左结合**，复杂表达式一律加括号。

## 十一、常见面试题

**Q1：`7 / 2` 和 `7 DIV 2` 有什么区别？**
> `/` 是真除法，结果为 `3.5000`（DECIMAL，默认 4 位小数）；`DIV` 是整除，结果为 `3`，且对负数**向零截断**（`-7 DIV 2 = -3`，不是 `-4`）。

**Q2：`NULL + 1` 的结果是什么？为什么 `SUM` 里不会出问题？**
> 结果是 `NULL`——算术运算遇到 NULL 具有传染性。而 `SUM()`/`AVG()` 是聚合函数，会**跳过 NULL 行**再计算，所以二者行为不同；这也意味着 `AVG` 的分母是"非 NULL 行数"，统计口径要留意。

**Q3：`SELECT 'abc' + 1` 会报错吗？**
> 不会，结果是 `1`（`'abc'` 被当作 0），只抛 warning。这正是隐式转换危险的地方，建议显式 `CAST`。

**Q4：如何安全地计算 `a / b` 并避免除零？**
> `SELECT a / NULLIF(b, 0)`。`NULLIF(b,0)` 在 `b = 0` 时返回 NULL，整体结果为 NULL；这比 `CASE WHEN b = 0 THEN 0 ELSE a/b END` 更简洁，且在严格模式的 INSERT/UPDATE 中也不会触发 1365 报错。注意两者**语义不同**：`NULLIF` 方案结果是 NULL，`CASE` 方案结果是 0。

**Q5：为什么金额字段不能用 `DOUBLE`？**
> `DOUBLE` 是二进制浮点，无法精确表示 `0.1` 这类十进制小数，累加会产生 `0.30000000000000004` 的误差。`DECIMAL` 是定点数，精确存储十进制值，故金额、单价等用 `DECIMAL(m,2)`。

**Q6：`MOD(id, 10)` 在分库分表里有什么用？**
> 做**哈希分片**：用 `id % 分片数` 决定数据落到哪个库/表。缺点是分片数一变（如 4 → 5）几乎所有数据都要迁移，因此生产上更常用一致性哈希或"先按范围分、再取模"的两级策略。
