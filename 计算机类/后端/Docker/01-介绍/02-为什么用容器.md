# 为什么用容器

"本地能跑，线上跑不起来"通常不是代码问题，而是依赖版本、系统库、环境变量不一致。容器把应用和它的运行环境一起打包，换台机器还是同一套东西。

一个常见的例子：开发机装的是 Python 3.12，服务器还是 3.8，`numpy` 版本也不一样。用镜像把版本写死：

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "main.py"]
```

`python:3.12-slim` 固定了解释器和基础库，`requirements.txt` 固定第三方依赖。构建出来的镜像有 digest，测试环境和线上跑的是同一份字节。出了问题也能直接回滚到上一个 tag，而不是"把服务器上的包降个版本试试"。镜像推到仓库后，测试、预发、生产引用同一个 digest，也就没有"部署时又装了一遍依赖"这种事。

## 收益不止环境一致

| 原来头疼的事 | 容器带来的变化 | 代价 |
| --- | --- | --- |
| 环境漂移 | 镜像不可变，回滚就是换 tag | 要维护构建流程 |
| 交付慢 | 镜像推拉替代手工部署 | 要有仓库和网络 |
| 机器利用率低 | 一台机器塞多个容器 | 需要编排和监控 |
| 扩容靠加机器 | 起容器是秒级 | 应用得无状态 |

镜像还能像代码一样打标签、进仓库、回滚。配合 CI，构建、测试、推送可以串成一条流水线，具体做法见 [[04-持续集成|持续集成]]。

## 启动快、密度高

容器不引导操作系统，启动时间通常几十毫秒到几秒；虚拟机要引导内核和 init，往往几十秒。这个差距在扩容时很直观：流量上来，起 20 个容器可能几秒钟，起 20 台 VM 要等几分钟。

密度也是同理。同样 8C16G 的机器，跑十几个虚拟机内存就满了，跑几十个容器还有余量，因为每个容器只带应用自己的开销。

## 代价也要算

数据默认跟着容器走，删了就没了，得上卷；网络多一层命名空间，排查比宿主机麻烦；共享内核意味着隔离弱于虚拟机，不可信负载要谨慎。镜像构建本身也有学习成本：层缓存、多阶段、体积控制，都得踩一遍。

> [!warning] 别为了容器而容器
> 一个静态页面、一个单机定时脚本，直接部署可能更省事。容器适合的是需要一致环境、需要频繁交付、需要横向扩容的场景，收益要和运维复杂度一起算。
