# 运行时配置

容器能启动，和容器能长期稳定运行，是两回事。同一份镜像，资源限制、重启策略、日志配置不同，线上表现可能完全不一样。

## 配置从哪来

环境变量是最常见的注入方式，`-e KEY=VALUE` 或者 compose 的 `environment`。量多时用 `--env-file`，但文件里的值仍然会出现在 `docker inspect` 里。密码、token 这类东西不要用明文环境变量传：Compose 支持 `secrets` 挂成文件，Swarm 有 `docker secret`，Kubernetes 有 Secret，云上还有各自的密钥管理服务。共同点是运行时以文件或内存注入，不进入镜像层。

```bash
docker run -d --name api \
  --env-file .env.production \
  --memory=512m --memory-swap=512m \
  --cpus=1 \
  --restart unless-stopped \
  --log-driver json-file \
  --log-opt max-size=10m --log-opt max-file=3 \
  my-api:1.0
```

`--memory` 是硬上限，超过会触发 OOM kill，容器退出码 137。`--memory-swap` 设成和 memory 相同表示禁用 swap，行为更好预测。`--cpus=1` 限制的是 CPU 时间配额，不是绑核；要绑核用 `--cpuset-cpus`。

## 重启策略

| 策略 | 行为 |
| --- | --- |
| `no` | 默认，不重启 |
| `on-failure[:N]` | 非 0 退出才重启，可限制次数 |
| `always` | 总是重启，daemon 重启后也拉起 |
| `unless-stopped` | 除手动 stop 外都重启 |

应用自身陷入崩溃循环时，`always` 会让它一直重启，日志刷得飞快。临时改成 `no` 或者 `docker update --restart=no <容器>`，先把问题定位清楚。

## 健康检查

`HEALTHCHECK` 判断的是“容器里的进程还能不能干活”，和 `docker ps` 显示 Up 不是一回事。没有健康检查时，进程活着就算健康；有了之后，`docker ps` 会显示 `(healthy)` 或 `(unhealthy)`，compose 和其他编排工具也能据此做依赖等待。

```yaml
healthcheck:
  test: ["CMD", "curl", "-fsS", "http://localhost:3000/health"]
  interval: 30s
  timeout: 5s
  retries: 3
  start_period: 20s
```

检查命令要轻，别在 healthcheck 里查全表。`curl -f` 在 4xx/5xx 时返回非 0，正好符合语义。

## 日志和文件系统

Docker 默认的 json-file 驱动不会自动轮转，一个话多的服务几天就能写满磁盘。上面例子里的 `max-size` 和 `max-file` 是最低要求；需要集中收集时换成 `journald`、`syslog` 或 fluentd 驱动。

`--read-only` 把根文件系统挂成只读，应用要写的地方用 `--tmpfs /tmp` 或挂卷单独放开。这能挡掉一部分漏洞利用和误写，代价是先确认应用不会往 `/var`、`/run` 里写东西。

> [!tip] 限制要提前设
> 资源限制和日志轮转应该在第一次部署时就加上。等容器把宿主机内存吃光再补，通常是在事故现场。
