# 包管理器

镜像里装软件，靠的还是发行版那一套：Debian/Ubuntu 用 `apt`，RHEL/CentOS/Fedora 用 `dnf`（老系统 `yum`），Alpine 用 `apk`，Arch 用 `pacman`。写 Dockerfile 时，包管理器的用法直接决定镜像大小、构建速度和可复现性。

## 一条 RUN 里做完

```dockerfile
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*
```

拆开写有两个问题：`apt-get update` 和 `install` 落在不同层，缓存可能过期；索引文件留在镜像里，白占几十 MB。`--no-install-recommends` 省掉推荐包，`curl` 这类工具通常只需要它自己和少数依赖。

Alpine 对应写法：

```dockerfile
RUN apk add --no-cache curl ca-certificates
```

`--no-cache` 让 apk 不把索引写进 `/var/cache/apk`，不需要额外 `rm`。这是 Alpine 镜像通常更小的原因之一。

> [!warning] 别在镜像里 apt upgrade
> 全量升级会拉进一堆不可控的包，构建结果随日期变化，也容易把基础镜像弄坏。只装需要的东西，基础镜像的更新交给上游 tag。

## 四大包管理器对照

| 发行版 | 工具 | 索引位置 | 安装 | 清理索引 | 特点 |
| --- | --- | --- | --- | --- | --- |
| Debian / Ubuntu | `apt-get`（脚本里别用 `apt`） | `/var/lib/apt/lists` | `apt-get install -y --no-install-recommends` | `rm -rf /var/lib/apt/lists/*` | 生态最大，`deb` 包，`apt-cache policy` 查版本 |
| RHEL / CentOS / Fedora | `dnf`（老系统 `yum`） | `/var/cache/dnf` | `dnf install -y` | `dnf clean all` | `rpm` 包，弱依赖可用 `--setopt=install_weak_deps=False` 关掉 |
| Alpine | `apk` | `/var/cache/apk` | `apk add --no-cache` | `--no-cache` 直接不写索引 | musl libc + busybox，体积最小 |
| Arch | `pacman` | `/var/lib/pacman` | `pacman -S --noconfirm` | `pacman -Scc --noconfirm` | 滚动发行版，版本不可控，不适合稳定镜像 |

**apt 和 apt-get 的区别**：`apt` 面向交互，会输出进度条和“建议使用”的提示；`apt-get` 输出稳定，适合脚本和 Dockerfile。构建镜像一律用 `apt-get`，避免 `apt` 的警告和未来行为变化。

**dnf 的弱依赖**：RHEL 系默认会装 `Recommends` 类依赖，镜像里通常不需要。用 `--setopt=install_weak_deps=False` 关掉，能少装一批包。极简镜像里可能只有 `microdnf`，命令基本兼容，但功能少一些。

**apk 的 `--no-cache`**：它让 apk 把索引放在内存里用完即弃，不写 `/var/cache/apk`。所以 Alpine 不需要像 Debian 那样再补一条 `rm -rf`，这也是 Alpine 镜像通常更小的原因之一。需要编译扩展时，用虚拟包把构建依赖打包，装完一起删：

```dockerfile
RUN apk add --no-cache --virtual .build-deps gcc musl-dev \
 && pip install --no-cache-dir some-package \
 && apk del .build-deps
```

**pacman** 是滚动发行版，`-Sy` 只更新索引、不升级系统，容易造成部分升级（partial upgrade）问题。镜像里要固定版本很麻烦，一般不作为生产基础镜像。

## 为什么 update 和 install 必须在同一层

镜像构建按层缓存。如果把两条命令拆开：

```dockerfile
RUN apt-get update
RUN apt-get install -y curl
```

第一层 `apt-get update` 会被缓存。某天基础镜像更新、或者缓存被复用，第二层仍然拿着旧的索引去装包，而仓库里旧版本已经被清理，构建就会报 `404 Not Found`。合并成一条 `RUN` 后，两层要么一起命中缓存，要么一起失效，索引和安装始终来自同一次快照。

清理索引也有同样的陷阱：

```dockerfile
RUN apt-get update && apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*
```

第二条 `RUN` 只是在新的可写层里放了一个 whiteout，把下层目录“遮住”，但索引文件仍然存在于前一层，镜像体积一点没小。必须在同一个 `RUN` 里删除，才算真正没有写进最终层：

```dockerfile
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*
```

这条规则对所有包管理器都成立：更新索引、安装、清理，放在一条 `RUN` 里。

## 固定版本 vs 浮动版本

不锁版本时，`apt-get install curl` 每次构建都可能拿到不同版本，今天能构建、下周可能因为仓库清理旧包而失败，镜像也不可复现。锁版本写成：

```dockerfile
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl=7.88.1-10+deb12u5 \
 && rm -rf /var/lib/apt/lists/*
```

版本号用 `apt-cache policy curl` 查。Alpine 对应 `apk add curl=8.5.0-r0`，dnf 用 `dnf install curl-8.5.0-1.el9`。

两种策略的取舍：

| 策略 | 优点 | 缺点 | 适合 |
| --- | --- | --- | --- |
| 锁死每个包版本 | 构建可复现，变更可控 | 安全更新不会自动进来，旧版本可能从仓库消失 | 生产镜像、需要审计 |
| 只锁基础镜像 tag/digest | 维护简单，能吃到上游安全更新 | 包版本随时间漂移 | 开发镜像、快速迭代 |
| 锁 digest + 定期重建 | 兼顾可复现和更新 | 需要 CI 定时任务和测试 | 大多数生产团队 |

折中做法是：基础镜像用 digest 固定，应用依赖用 lockfile 固定，系统包锁住关键版本；CI 定期跑一次“更新依赖并重建”的任务，让安全补丁进来，同时用测试兜底。锁太死不是安全，只是把更新推迟到某个更难受的时刻。

## 基础镜像谱系

| 基础镜像 | 基础层体积 | libc | 有 shell | 兼容性 | 适合 |
| --- | --- | --- | --- | --- | --- |
| `scratch` | 0 | 无 | 无 | 只放静态二进制 | Go/Rust 静态编译 |
| `distroless/static` | 几 MB | 无 | 无 | 静态二进制 | Go/Rust 静态二进制，自带 CA 证书 |
| `distroless/base` | 二十 MB 级 | glibc | 无 | 动态链接的 C/C++/Go（CGO） | 需要 glibc 但不想要 shell |
| `alpine` | ~5 MB | musl | busybox | 大部分包，但预编译二进制和 wheel 可能不兼容 | 追求小体积、能接受 musl |
| `debian:slim` | ~75 MB | glibc | bash | 兼容性最好 | Python、Java、Node 原生模块 |
| `ubuntu` | 更大 | glibc | bash | 兼容性好，包新 | 需要 Ubuntu 特有包 |
| 完整 `debian`/`ubuntu` | 几百 MB | glibc | bash | 构建工具齐全 | 只适合构建阶段 |

选择顺序可以记成一句话：**先用 `-slim` 把功能跑通，再考虑往 Alpine 或 distroless 收**。Alpine 的 musl libc 和 glibc 不完全兼容，预编译的二进制、Python 的 manylinux wheel、某些 JNI 库可能直接跑不起来；distroless 没有 shell，排障要靠旁路容器，但攻击面最小。

另外，`scratch` 里没有 CA 证书、时区数据，也没有 `/etc/passwd`；`distroless/static` 自带 CA 证书和基础用户文件。需要 HTTPS 时把 `ca-certificates.crt` 从构建阶段复制进 `scratch`；需要本地时区时复制 `/usr/share/zoneinfo`，或者直接用带基础文件的 distroless 变体。

## 常见坑

- **在镜像里 `apt-get upgrade`**：会把基础镜像里的所有包升到最新，构建结果随日期变化，还可能把基础镜像弄坏。只装需要的包，基础镜像的更新交给上游 tag。
- **忘了 `ca-certificates`**：容器里 `curl https://...` 报证书错误，不是网络问题。
- **`tzdata` 交互式提问**：安装时卡在时区选择，构建挂起。加 `DEBIAN_FRONTEND=noninteractive`，或设置 `TZ`。
- **只删索引不删缓存**：`/var/cache/apt/archives`、`/var/cache/dnf` 里的 deb/rpm 也会占空间，必要时一起清。
- **架构不匹配**：在 Apple Silicon 上构建 amd64 镜像，或者拉了 arm64 的包，报 `Exec format error`。用 `--platform` 明确目标架构。
- **GPG 签名过期**：旧基础镜像里的仓库密钥过期，`apt-get update` 报 `NO_PUBKEY`。更新基础镜像，别在 Dockerfile 里临时绕过签名。
- **`--no-install-recommends` 忘写**：Debian 系会多装一批推荐包，镜像白胖几十 MB。
