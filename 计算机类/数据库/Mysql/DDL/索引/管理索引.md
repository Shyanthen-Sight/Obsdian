# 索引管理 —— 创建、查看与维护

> [!abstract] 一句话
> 索引是数据库的"目录"：用**额外的空间和维护成本**，换取**更少的磁盘扫描**。
> 管理索引就四件事：**建得对、看得见、改得动、删得掉**。

> [!info] 索引与约束是一体两面
> 在 MySQL 里，`PRIMARY KEY`、`UNIQUE`、`FOREIGN KEY` 都靠索引实现。所以：
> - 删唯一约束 → `DROP INDEX`
> - 删外键 → `DROP FOREIGN KEY`
> - 删主键 → `DROP PRIMARY KEY`
>
> 详见 [[数据约束概述]]、[[Alter Table]]。

---

## 一、先搞懂 InnoDB 的两种索引

### 1.1 聚簇索引（Clustered Index）

> [!abstract] 一句话
> InnoDB 的**表数据本身就按主键顺序存放在 B+ 树叶子节点里**——主键索引就是聚簇索引，聚簇索引就是表。

| 要点 | 说明 |
| --- | --- |
| 叶子节点存什么 | **整行数据** |
| 一张表有几个 | **最多一个** |
| 谁来做 | 有主键 → 主键；没主键 → 第一个 `UNIQUE NOT NULL` 索引；都没有 → 隐藏 6 字节 `row_id` |
| 主键为什么重要 | 它决定了数据物理顺序，直接影响插入、查询、二级索引大小 |

```sql
-- 有主键：聚簇索引就是 PRIMARY KEY (id)
CREATE TABLE student (
    id   BIGINT NOT NULL AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL,
    PRIMARY KEY (id)
);
```

> [!tip] 主键设计的三个关键词：**短、递增、不变**
> - **短**：二级索引叶子存的是主键值，主键越长，所有二级索引越大
> - **递增**：`AUTO_INCREMENT` 顺序追加，减少 B+ 树页分裂
> - **不变**：主键被改，整行要搬家，所有二级索引都要跟着改
>
> 所以 `BIGINT AUTO_INCREMENT` 通常优于随机 UUID。业务唯一键（学号、身份证）另加 `UNIQUE`，不要拿来当聚簇主键。

### 1.2 二级索引（Secondary Index）

> [!abstract] 一句话
> 二级索引是"**索引列 → 主键值**"的目录。查到主键后，还要回聚簇索引取整行，这一步叫**回表**。

```text
聚簇索引叶子：  [id=1, 整行数据] → [id=2, 整行数据] → [id=3, 整行数据]
二级索引叶子：  [name='张三', id=1] → [name='李四', id=2] → [name='王五', id=3]
```

| 对比项 | 聚簇索引 | 二级索引 |
| --- | --- | --- |
| 叶子节点内容 | 整行数据 | 索引列 + 主键值 |
| 数量 | 一张表一个 | 可多个 |
| 查询非索引列 | 直接拿到 | 需要**回表** |
| 范围查询 | 按主键顺序 | 按索引列顺序，再回表 |

### 1.3 回表与覆盖索引

```sql
-- 假设有索引 idx_name (name)
SELECT id, name FROM student WHERE name = '张三';
-- ✅ 覆盖索引：id 是主键、name 是索引列，二级索引里都有 → 不用回表
-- EXPLAIN Extra: Using index

SELECT name, age FROM student WHERE name = '张三';
-- ❌ age 不在二级索引里 → 先查 id，再回聚簇索引取 age → 回表
```

> [!success] 覆盖索引（Covering Index）
> 当**查询需要的所有列**都能从二级索引里拿到时，就不需要回表。
> `EXPLAIN` 的 `Extra` 出现 **`Using index`**，就是覆盖索引生效。
>
> 注意：覆盖索引不是一种"索引类型"，而是一种**使用状态**。联合索引设计得好，就能顺便覆盖高频查询。

## 二、索引类型速查

| 类型 | 关键字 / 写法 | 结构 | 典型用途 | 备注 |
| --- | --- | --- | --- | --- |
| 主键索引 | `PRIMARY KEY` | 聚簇 B+ 树 | 唯一标识一行 | 一张表一个 |
| 唯一索引 | `UNIQUE KEY` | B+ 树 | 值唯一，允许多个 `NULL` | 唯一约束靠它实现 |
| 普通索引 | `KEY` / `INDEX` | B+ 树 | 加速等值、范围、排序 | 最常用 |
| 联合索引 | `KEY idx (a, b, c)` | B+ 树 | 多条件查询、覆盖索引 | 遵循最左前缀 |
| 前缀索引 | `KEY idx (email(20))` | B+ 树 | 长字符串 | 只索引前 n 个字符 |
| 全文索引 | `FULLTEXT` | 倒排索引 | 文本关键词搜索 | 中文需 `ngram` 解析器 |
| 空间索引 | `SPATIAL` | R 树 | 地理坐标、范围检索 | 列必须 `NOT NULL` |
| 降序索引 | `KEY idx (a ASC, b DESC)` | B+ 树 | 混合排序 | MySQL 8.0 才真正生效 |
| 函数索引 | `KEY idx ((YEAR(col)))` | B+ 树 | 按表达式查询 | 8.0.13+ |
| 不可见索引 | `INVISIBLE` | B+ 树 | 安全删索引前的观察期 | 8.0+ |
| 哈希索引 | `HASH` | 哈希表 | 等值查询 | InnoDB 只支持自适应哈希，不能手动建 |

> [!note] InnoDB 没有"手动哈希索引"
> `HASH` 索引主要出现在 `MEMORY` 引擎。InnoDB 会在后台自动维护**自适应哈希索引（AHI）**，你既不能显式创建，也不应该依赖它。
> 需要等值查询加速时，建普通 B+ 树索引即可。

## 三、创建索引

### 3.1 建表时一起建

```sql
CREATE TABLE student (
    id         BIGINT       NOT NULL AUTO_INCREMENT,
    stu_no     CHAR(10)     NOT NULL,
    name       VARCHAR(50)  NOT NULL,
    gender     CHAR(1)      DEFAULT 'U',       -- M男 F女 U未知
    age        TINYINT,
    class_id   INT,
    score      DECIMAL(5,2),
    created_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (id),                          -- 主键索引（聚簇）
    UNIQUE KEY uk_stu_no (stu_no),             -- 唯一索引
    KEY idx_class_age (class_id, age),         -- 联合索引
    KEY idx_created_at (created_at)            -- 普通索引
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 3.2 建表后追加

```sql
-- 普通索引
CREATE INDEX idx_name ON student (name);
ALTER TABLE student ADD INDEX idx_age (age);

-- 唯一索引
CREATE UNIQUE INDEX uk_phone ON student (phone);
ALTER TABLE student ADD UNIQUE KEY uk_email (email);

-- 联合索引
CREATE INDEX idx_class_score ON student (class_id, score);

-- 主键只能通过 ALTER TABLE 加
ALTER TABLE student ADD PRIMARY KEY (id);
```

> [!warning] `CREATE INDEX` 不能建主键
> 主键用 `ALTER TABLE ... ADD PRIMARY KEY (...)`。而且加主键会**重建表**，大表上要按 DDL 的代价来评估。

### 3.3 联合索引与最左前缀

以 `KEY idx_class_age_score (class_id, age, score)` 为例：

| 查询条件 | 能否用索引 | 说明 |
| --- | --- | --- |
| `WHERE class_id = 1` | ✅ | 用到第 1 列 |
| `WHERE class_id = 1 AND age = 18` | ✅ | 用到前 2 列 |
| `WHERE class_id = 1 AND age = 18 AND score > 90` | ✅ | 三列都用上 |
| `WHERE age = 18` | ❌ | 跳过最左列 `class_id` |
| `WHERE class_id = 1 AND score > 90` | ⚠️ 部分 | `class_id` 能用；`age` 缺失，`score` 不能继续缩小范围（可能靠 ICP 在索引层过滤） |
| `WHERE class_id > 1 AND age = 18` | ⚠️ 部分 | 第 1 列是范围，后面的列无法继续用于缩小范围 |
| `ORDER BY class_id, age` | ✅ | 与索引顺序一致 |
| `ORDER BY age, score` | ❌ | 不符合最左前缀 |

> [!tip] 联合索引的两条铁律
> 1. **最左前缀**：从索引最左列开始连续使用，不能跳列。
> 2. **等值在前，范围在后**：`=` 条件放前面，`>`、`<`、`BETWEEN`、`LIKE 'x%'` 放最后。
>
> 设计口诀：**把最常一起出现、选择性最高的等值列放左边，把范围列放右边。**

### 3.4 前缀索引

长字符串（邮箱、地址、URL）如果整列建索引太大，可以只索引前 n 个字符：

```sql
CREATE INDEX idx_email_prefix ON user (email(20));
```

**n 怎么选？** 让前缀的区分度尽量接近完整列：

```sql
SELECT COUNT(DISTINCT LEFT(email, 10)) / COUNT(*) AS sel_10,
       COUNT(DISTINCT LEFT(email, 20)) / COUNT(*) AS sel_20,
       COUNT(DISTINCT email)          / COUNT(*) AS sel_full
FROM user;
```

> [!warning] 前缀索引的三个限制
> 1. **不能做覆盖索引**：索引里没有完整列值，必须回表取原值。
> 2. **不能用于 `ORDER BY 完整列` / `GROUP BY 完整列`**：前缀顺序不完全等于完整值顺序。
> 3. **`BLOB` / `TEXT` 必须指定前缀长度**，否则报 `ERROR 1170`。
>
> 选择标准：前缀区分度接近完整列（比如达到 95% 以上），再长就是浪费空间。

### 3.5 全文索引

```sql
-- 中文必须指定 ngram 解析器，否则按空格分词，中文整段算一个词
CREATE FULLTEXT INDEX ft_article ON article (title, body) WITH PARSER ngram;

SELECT id, title
  FROM article
 WHERE MATCH(title, body) AGAINST('数据库 索引' IN BOOLEAN MODE);
```

| 要点 | 说明 |
| --- | --- |
| 适用场景 | 文章标题/正文关键词搜索 |
| 不适用 | 精确匹配、短词、高频词 |
| 中文分词 | `WITH PARSER ngram`，`ngram_token_size` 默认 2 |
| 查询写法 | `MATCH(索引列) AGAINST(关键词)` |
| 注意 | `MATCH` 里的列必须和全文索引列一致 |

> [!tip] 全文索引不是搜索引擎
> 数据量大、需要相关性排序、高亮、拼写纠错时，用 Elasticsearch / OpenSearch 更合适。
> MySQL 全文索引适合"数据量中等、不想引入外部组件"的站内搜索。

### 3.6 函数索引（8.0.13+）

```sql
-- 按年份查订单：普通索引会失效
SELECT * FROM orders WHERE YEAR(created_at) = 2026;

-- 方案一：函数索引（注意表达式外要两层括号）
CREATE INDEX idx_created_year ON orders ((YEAR(created_at)));

-- 方案二：生成列 + 普通索引（兼容更低版本）
ALTER TABLE orders
    ADD COLUMN created_year SMALLINT AS (YEAR(created_at)) STORED;
CREATE INDEX idx_created_year2 ON orders (created_year);
```

> [!tip] 更推荐的写法：把函数从列上拿掉
> ```sql
> WHERE created_at >= '2026-01-01'
>   AND created_at <  '2027-01-01'
> ```
> 这样普通索引 `idx_created_at` 就能用，不依赖 8.0 的函数索引，兼容性最好。

### 3.7 降序索引（8.0+）

```sql
CREATE INDEX idx_a_b ON t (a ASC, b DESC);

-- 适合这类"一升一降"的排序
SELECT * FROM t ORDER BY a ASC, b DESC;
```

> [!warning] 8.0 之前是"假降序"
> MySQL 5.7 及以前会解析 `DESC` 但**直接忽略**，仍然按升序建索引。
> 8.0 开始才真正支持降序索引；混合排序场景下可以避免 `Using filesort`。

### 3.8 不可见索引（8.0+）

```sql
-- 建一个优化器"看不见"的索引（仍然维护，写入仍有成本）
CREATE INDEX idx_maybe_useless ON student (name) INVISIBLE;

-- 观察一段时间，确认没有查询依赖它
ALTER TABLE student ALTER INDEX idx_maybe_useless VISIBLE;

-- 确认无用后真删
DROP INDEX idx_maybe_useless ON student;
```

> [!success] 安全删索引的标准流程
> **先设为 `INVISIBLE` → 观察一个业务周期 → 无异常再 `DROP`**
> 直接删索引，一旦有慢查询回滚，恢复成本远高于多等几天。

### 3.9 空间索引

```sql
CREATE TABLE poi (
    id       BIGINT NOT NULL AUTO_INCREMENT,
    name     VARCHAR(100),
    location POINT NOT NULL SRID 4326,
    PRIMARY KEY (id),
    SPATIAL INDEX sp_location (location)
) ENGINE=InnoDB;
```

> [!note] 空间索引的前提
> - 列类型必须是 `GEOMETRY` / `POINT` / `LINESTRING` / `POLYGON` 等
> - 列必须 `NOT NULL`
> - 最好显式指定 `SRID`
> - 空间索引是 R 树，不是 B+ 树

### 3.10 命名规范

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `pk_` | 主键 | `pk_student` |
| `uk_` | 唯一 | `uk_stu_no` |
| `idx_` | 普通/联合 | `idx_class_age` |
| `ft_` | 全文 | `ft_article` |
| `sp_` | 空间 | `sp_location` |
| `fk_` | 外键 | `fk_student_class` |

> [!tip] 名字要能读出"哪张表、哪些列"
> `idx_class_age` 比 `index1` 好排查太多。报错、慢查询、`EXPLAIN` 里都会显示索引名。

## 四、查看索引

### 4.1 最常用：`SHOW INDEX`

```sql
SHOW INDEX FROM student;
SHOW KEYS FROM student;          -- 同义词
SHOW CREATE TABLE student\G      -- 看完整建表语句，最直观
```

`SHOW INDEX` 各列含义：

| 列 | 含义 | 重点看什么 |
| --- | --- | --- |
| `Table` | 表名 | — |
| `Non_unique` | `0` 唯一，`1` 普通 | 判断是否唯一索引 |
| `Key_name` | 索引名 | `PRIMARY` 是主键 |
| `Seq_in_index` | 在联合索引中的列位置 | `1,2,3...` 还原索引顺序 |
| `Column_name` | 列名 | 联合索引包含哪些列 |
| `Collation` | `A` 升序 / `D` 降序 / `NULL` 未排序 | 降序索引用 |
| `Cardinality` | **估算**的不同值个数 | 越大区分度越高 |
| `Sub_part` | 前缀长度 | 前缀索引显示 |
| `Packed` | 压缩方式 | 一般 `NULL` |
| `Null` | 是否允许 `NULL` | `YES` / 空 |
| `Index_type` | `BTREE` / `FULLTEXT` / `SPATIAL` / `HASH` | 索引结构 |
| `Comment` | 备注 | `disabled` 表示不可用 |
| `Index_comment` | 建索引时写的 `COMMENT` | 业务说明 |
| `Visible` | `YES` / `NO` | 8.0 不可见索引 |
| `Expression` | 函数索引表达式 | 8.0.13+ |

> [!warning] `Cardinality` 是估算值，不是精确值
> InnoDB 通过**采样**统计，可能和真实值差很多。刚导入大量数据、或统计信息过期时，`Cardinality` 会明显失真。
> 需要更新时执行：
> ```sql
> ANALYZE TABLE student;
> ```

### 4.2 从 `information_schema` 查

```sql
SELECT INDEX_NAME,
       SEQ_IN_INDEX,
       COLUMN_NAME,
       NON_UNIQUE,
       CARDINALITY,
       SUB_PART,
       INDEX_TYPE,
       IS_VISIBLE,
       EXPRESSION
  FROM information_schema.STATISTICS
 WHERE TABLE_SCHEMA = 'school'
   AND TABLE_NAME   = 'student'
 ORDER BY INDEX_NAME, SEQ_IN_INDEX;
```

> [!tip] 批量找"没建索引的表"
> ```sql
> SELECT t.TABLE_SCHEMA, t.TABLE_NAME
>   FROM information_schema.TABLES t
>   LEFT JOIN information_schema.STATISTICS s
>     ON s.TABLE_SCHEMA = t.TABLE_SCHEMA
>    AND s.TABLE_NAME   = t.TABLE_NAME
>  WHERE t.TABLE_TYPE = 'BASE TABLE'
>    AND t.TABLE_SCHEMA NOT IN ('mysql','sys','performance_schema','information_schema')
>    AND s.INDEX_NAME IS NULL;
> ```
> 只能说明"一个索引都没有"，不代表"该建的都建了"。

### 4.3 找冗余索引和未使用索引

```sql
-- 冗余索引：(a) 和 (a,b) 同时存在时，(a) 通常冗余
SELECT * FROM sys.schema_redundant_indexes
 WHERE table_schema = 'school';

-- 未被使用过的索引（实例启动以来）
SELECT * FROM sys.schema_unused_indexes
 WHERE object_schema = 'school';
```

> [!warning] "未使用"不等于"可以删"
> `sys.schema_unused_indexes` 统计的是**实例启动以来**的使用情况。
> 月底报表、季度对账这类低频查询可能还没跑过；主从切换、故障演练也可能临时用到。
> 结论：**结合业务周期观察，再配合 `INVISIBLE` 灰度删除。**

## 五、修改与删除索引

### 5.1 重命名

```sql
ALTER TABLE student RENAME INDEX idx_old TO idx_new;
```

> [!note] MySQL 没有 `ALTER INDEX ... RENAME`
> 也不支持直接"改索引的列"。要换列，只能 **先 `DROP` 再 `CREATE`**，或者用在线改表工具。

### 5.2 删除

```sql
DROP INDEX idx_name ON student;
ALTER TABLE student DROP INDEX idx_name;
ALTER TABLE student DROP INDEX idx_a, DROP INDEX idx_b;   -- 一次删多个
```

| 要删的东西 | 正确写法 |
| --- | --- |
| 普通/联合索引 | `DROP INDEX idx_name ON t;` |
| 唯一约束 | `DROP INDEX uk_name ON t;` |
| 主键 | `ALTER TABLE t DROP PRIMARY KEY;` |
| 外键 | `ALTER TABLE t DROP FOREIGN KEY fk_name;` |
| 全文索引 | `DROP INDEX ft_name ON t;` |
| 空间索引 | `DROP INDEX sp_name ON t;` |

> [!danger] 删主键前先处理 `AUTO_INCREMENT`
> 自增列必须依附于一个键。直接删主键会报：
> `ERROR 1075: Incorrect table definition; there can be only one auto column and it must be defined as a key`
>
> 正确顺序：
> ```sql
> ALTER TABLE student MODIFY id BIGINT NOT NULL;   -- 1. 去掉 AUTO_INCREMENT
> ALTER TABLE student DROP PRIMARY KEY;            -- 2. 再删主键
> ```

> [!warning] 外键依赖的索引不能直接删
> 报 `ERROR 1553: Cannot drop index 'idx_x': needed in a foreign key constraint` 时：
> **先删外键，再删索引。**
> ```sql
> ALTER TABLE `order` DROP FOREIGN KEY fk_order_user;
> ALTER TABLE `order` DROP INDEX fk_order_user;
> ```

### 5.3 重建索引

```sql
-- 方式一：先删后建（同一条 ALTER 里完成，减少一次表操作）
ALTER TABLE student
    DROP INDEX idx_name,
    ADD INDEX idx_name (name);

-- 方式二：重建整张表（同时整理数据和索引碎片）
ALTER TABLE student ENGINE = InnoDB;

-- 方式三：OPTIMIZE TABLE（InnoDB 内部映射为重建表）
OPTIMIZE TABLE student;
```

> [!warning] 别把 `OPTIMIZE TABLE` 当日常任务
> 它会重建表，消耗大量 I/O，期间可能影响写入。只在**碎片明显、空间需要回收**时做，并避开业务高峰。
> InnoDB 的 `OPTIMIZE TABLE` 本质上接近 `ALTER TABLE ... FORCE`，不是"一键加速器"。

## 六、索引统计与维护

### 6.1 统计信息为什么会过期

InnoDB 依赖**索引统计信息**估算 `rows`、选择执行计划。大量插入/删除/更新后，统计信息可能失真，优化器就会选错索引，甚至放弃索引。

```sql
-- 手动更新统计信息
ANALYZE TABLE student;

-- 看相关参数
SHOW VARIABLES LIKE 'innodb_stats_persistent';          -- 默认 ON
SHOW VARIABLES LIKE 'innodb_stats_auto_recalc';         -- 默认 ON
SHOW VARIABLES LIKE 'innodb_stats_persistent_sample_pages'; -- 默认 20
```

| 参数 | 作用 |
| --- | --- |
| `innodb_stats_persistent` | 统计信息持久化到磁盘，重启不丢 |
| `innodb_stats_auto_recalc` | 数据变化超过阈值时自动重新统计 |
| `innodb_stats_persistent_sample_pages` | 采样页数，越大越准、越慢 |

> [!tip] 什么时候手动 `ANALYZE`
> - 批量导入/删除大量数据后
> - 大表刚加完索引
> - `EXPLAIN` 的 `rows` 明显离谱
> - 执行计划突然从走索引变成全表扫描

### 6.2 索引碎片

B+ 树在频繁插入、删除后会产生页分裂和空洞，表现为：

- 表数据文件很大，但实际行数没那么多
- `SHOW TABLE STATUS` 里 `Data_free` 很大
- 范围扫描变慢

```sql
SHOW TABLE STATUS LIKE 'student'\G
-- 关注 Data_length（数据大小）、Index_length（索引大小）、Data_free（空闲空间）
```

> [!note] 碎片不是"必须马上处理"
> 轻度碎片对查询影响很小。只有在**空间浪费明显**或**扫描性能下降**时才重建。
> 重建前确认 `innodb_file_per_table = ON`，否则空间未必能还给操作系统。

### 6.3 监控索引使用情况

```sql
-- 哪些索引从未被使用
SELECT * FROM sys.schema_unused_indexes;

-- 哪些索引是冗余的
SELECT * FROM sys.schema_redundant_indexes;

-- 底层表：按索引统计读写次数（需 performance_schema）
SELECT OBJECT_SCHEMA, OBJECT_NAME, INDEX_NAME, COUNT_STAR
  FROM performance_schema.table_io_waits_summary_by_index_usage
 WHERE OBJECT_SCHEMA = 'school'
 ORDER BY COUNT_STAR DESC;
```

### 6.4 在线 DDL 与锁

```sql
-- 建/删二级索引通常支持 INPLACE + 并发 DML
ALTER TABLE student
    ADD INDEX idx_name (name),
    ALGORITHM = INPLACE,
    LOCK = NONE;

-- 等锁超时立刻失败，避免拖垮线上
SET SESSION lock_wait_timeout = 5;
```

| 操作 | 是否支持在线 | 说明 |
| --- | --- | --- |
| 加/删二级索引 | ✅ 通常 `INPLACE` | 仍消耗 I/O |
| 加主键 | ❌ 多为 `COPY` | 会重建表 |
| 改列类型 | 视情况 | 可能 `COPY` |
| 加列到末尾（8.0.12+） | ✅ `INSTANT` | 秒级完成 |

> [!danger] 大表加索引不是"免费的"
> 虽然支持在线 DDL，但建索引仍要**全表扫描 + 排序 + 写索引页**，会占用大量 I/O 和 buffer pool。
> 千万级以上的表，优先用 `pt-online-schema-change` / `gh-ost`，并做好监控和回滚预案。

## 七、索引设计原则

### 7.1 选择性（Selectivity）

```sql
SELECT COUNT(DISTINCT gender) / COUNT(*) AS sel_gender,
       COUNT(DISTINCT class_id) / COUNT(*) AS sel_class,
       COUNT(DISTINCT stu_no) / COUNT(*) AS sel_stu_no
FROM student;
```

| 选择性 | 含义 | 是否适合单独建索引 |
| --- | --- | --- |
| 接近 1 | 几乎每行都不同（学号、手机号） | ✅ 很适合 |
| 较低 | 重复值多（性别、状态） | ❌ 单独建索引收益低 |
| 极低 | 只有几个值 | ❌ 优化器通常直接全表扫描 |

> [!tip] 低区分度列不是永远不能建索引
> 它可以是**联合索引的一部分**，用来和选择性高的列组合。
> 例如 `(class_id, stu_no)` 比单独 `(class_id)` 有用得多。

### 7.2 联合索引的列顺序

排序原则：

1. **等值条件列在前，范围条件列在后**
2. 等值列之间，**选择性高的放左边**（但也要兼顾最左前缀的使用频率）
3. 把 `ORDER BY` / `GROUP BY` 的列接在等值列后面
4. 列数控制在 **3~5 列**，太多会增大索引、降低写入性能

```sql
-- 高频查询：
-- WHERE class_id = ? AND age = ? ORDER BY score DESC
-- 推荐：
KEY idx_class_age_score (class_id, age, score)
-- class_id、age 是等值，score 用于排序，顺序刚好
```

> [!warning] 范围列之后的列，别指望它继续缩小范围
> 索引 `(a, b)`，查询 `WHERE a > 1 AND b = 2`：
> `a` 能用索引做范围扫描，但 `b` **不能**继续用于缩小扫描范围（只能靠 ICP 在索引层过滤）。
> 如果 `b = 2` 很高频，考虑把索引改成 `(b, a)`。

### 7.3 覆盖索引优先

高频查询如果只需要少数几列，可以让索引"顺便覆盖"：

```sql
-- 查询：WHERE class_id = ? ORDER BY score DESC，只要 id/name/score
KEY idx_class_score_name (class_id, score, name)
-- 叶子节点已有 class_id、score、name、id（主键）
-- 查询列全在其中 → Using index，不回表
```

> [!warning] 覆盖索引不是越宽越好
> 把 `SELECT *` 的所有列都塞进索引，会让索引膨胀、写入变慢，得不偿失。
> 只覆盖**高频、列少**的查询。

### 7.4 避免过度索引

| 成本 | 说明 |
| --- | --- |
| 写入放大 | 每次 `INSERT` / `UPDATE` / `DELETE` 都要维护所有相关索引 |
| 空间 | 每个索引都是一棵 B+ 树 |
| 优化器负担 | 索引太多，选择执行计划的时间变长，也可能选错 |
| 缓冲池占用 | 索引页和數據页争抢 buffer pool |

> [!danger] 这些索引通常是"白建的"
> - `(a)` 和 `(a, b)` 同时存在：`(a, b)` 已能服务 `a` 的最左前缀，`(a)` 多半冗余
> - 完全重复的索引
> - 选择性极低、从不被使用的单列索引
> - 频繁更新的列上的索引（除非查询确实需要）

### 7.5 索引长度限制

| 限制 | 数值 |
| --- | --- |
| 单表最大索引数 | **64** 个（二级索引） |
| 联合索引最大列数 | **16** 列 |
| InnoDB 索引键最大长度 | **3072 字节**（`DYNAMIC` / `COMPRESSED` 行格式） |
| 旧行格式最大长度 | 767 字节（`REDUNDANT` / `COMPACT`） |
| `utf8mb4` 单字符 | 最多 4 字节 |

> [!note] 3072 字节能存多少个 `utf8mb4` 字符？
> `3072 / 4 = 768` 个字符。所以 `VARCHAR(1000)` 的 `utf8mb4` 列**不能整列建索引**，必须用前缀索引或改类型。

## 八、实战：给 `student` 表配索引

### 8.1 先列出高频查询

```sql
-- Q1 学号精确查
SELECT * FROM student WHERE stu_no = '2026000001';

-- Q2 班级 + 年龄
SELECT * FROM student WHERE class_id = 1 AND age = 18;

-- Q3 班级下按成绩排名（只要 id/name/score）
SELECT id, name, score
  FROM student
 WHERE class_id = 1
 ORDER BY score DESC
 LIMIT 10;

-- Q4 最近注册的 10 个学生
SELECT id, name
  FROM student
 ORDER BY created_at DESC
 LIMIT 10;

-- Q5 姓名前缀搜索
SELECT id, name FROM student WHERE name LIKE '张%';

-- Q6 姓名 + 班级
SELECT id, name FROM student WHERE name = '张三' AND class_id = 1;
```

### 8.2 逐条匹配索引

| 查询 | 推荐索引 | 原因 |
| --- | --- | --- |
| Q1 | `UNIQUE KEY uk_stu_no (stu_no)` | 唯一等值查询，`type=const` |
| Q2 | `KEY idx_class_age (class_id, age)` | 两列等值，最左前缀 |
| Q3 | `KEY idx_class_score (class_id, score)` | `class_id` 等值 + `score` 排序，避免 filesort |
| Q4 | `KEY idx_created_at (created_at)` | 排序 + `LIMIT`，可倒序扫描 |
| Q5 | `KEY idx_name (name)` | `LIKE '张%'` 是前缀匹配，能用索引 |
| Q6 | `KEY idx_name_class (name, class_id)` | 两列等值；`name` 选择性更高，放左边 |

> [!warning] Q2 和 Q3 的索引不能合并成一个
> 看起来 `(class_id, age, score)` 能同时服务 Q2 和 Q3，但：
> - Q2 用 `(class_id, age)` 没问题
> - Q3 是 `WHERE class_id = 1 ORDER BY score`，中间缺了 `age` 的条件，索引顺序 `(class_id, age, score)` **无法保证按 `score` 有序**
>
> 所以 Q3 需要单独的 `(class_id, score)`。**索引是给查询用的，不是给表"配齐"用的。**

### 8.3 最终 DDL

在 §3.1 的建表基础上（已有 `uk_stu_no`、`idx_class_age`、`idx_created_at`），补上另外三个索引：

```sql
ALTER TABLE student
    ADD KEY idx_class_score (class_id, score),   -- Q3：班级 + 按成绩排序
    ADD KEY idx_name (name),                     -- Q5：姓名前缀搜索
    ADD KEY idx_name_class (name, class_id);     -- Q6：姓名 + 班级
```

如果从空表开始，完整定义如下：

```sql
CREATE TABLE student (
    id         BIGINT       NOT NULL AUTO_INCREMENT,
    stu_no     CHAR(10)     NOT NULL,
    name       VARCHAR(50)  NOT NULL,
    gender     CHAR(1)      DEFAULT 'U',
    age        TINYINT,
    class_id   INT,
    score      DECIMAL(5,2),
    created_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_stu_no (stu_no),
    KEY idx_class_age (class_id, age),
    KEY idx_class_score (class_id, score),
    KEY idx_created_at (created_at),
    KEY idx_name (name),
    KEY idx_name_class (name, class_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 8.4 用 `EXPLAIN` 验收

```sql
EXPLAIN SELECT id, name, score
  FROM student
 WHERE class_id = 1
 ORDER BY score DESC
 LIMIT 10;
```

期望看到：

| 字段 | 期望值 | 说明 |
| --- | --- | --- |
| `type` | `ref` | 等值匹配 |
| `key` | `idx_class_score` | 命中联合索引 |
| `key_len` | 索引前缀长度 | 确认用了 `class_id`（可能还有 `score`） |
| `rows` | 远小于全表行数 | 扫描行数可接受 |
| `Extra` | `Using index`（若列被覆盖）或 `Using where; Using index` | **不应出现 `Using filesort`** |

> [!success] 验收标准
> - `type` 不是 `ALL` / `index`
> - `key` 是你预期的索引
> - `rows` 明显小于表总行数
> - 高频排序查询不出现 `Using filesort`
> - 高频查询尽量出现 `Using index`

## 九、常见报错与坑

> [!failure] ERROR 1061：Duplicate key name
> 索引名重复。先 `SHOW INDEX FROM t;` 看看已有哪些名字。

> [!failure] ERROR 1072：Key column 'xxx' doesn't exist in table
> 索引里写了不存在的列，或列名拼错。

> [!failure] ERROR 1068：Multiple primary key defined
> 表已经有主键，不能再加第二个。

> [!failure] ERROR 1075：Incorrect table definition...
> 自增列失去了键的身份。参考 §5.2，先去掉 `AUTO_INCREMENT` 再删主键。

> [!failure] ERROR 1071：Specified key was too long; max key length is 3072 bytes
> 索引列太长。用前缀索引，或缩短 `VARCHAR`，或改行格式。

> [!failure] ERROR 1170：BLOB/TEXT column used in key specification without a key length
> `BLOB` / `TEXT` 建索引必须指定前缀长度，例如 `KEY idx (content(100))`。

> [!failure] ERROR 1553：Cannot drop index ... needed in a foreign key constraint
> 索引被外键依赖。先删外键，再删索引。

> [!failure] ERROR 1069：Too many keys specified; max 64 keys allowed
> 单表索引超过 64 个。先清理冗余索引。

> [!failure] ERROR 1215：Cannot add foreign key constraint
> 外键两端**类型、符号、字符集、排序规则**必须完全一致。常见于 `BIGINT` 对 `INT`、`utf8mb4` 对 `utf8`。

## 十、常见面试问答

> [!question] Q1：聚簇索引和非聚簇索引有什么区别？
> - **聚簇索引**：叶子节点存整行数据，InnoDB 的主键索引就是聚簇索引，一张表只有一个。
> - **非聚簇索引（二级索引）**：叶子节点存"索引列 + 主键值"，查非索引列需要**回表**。
> - 因此主键要短、递增、稳定，否则所有二级索引都会变大。

> [!question] Q2：什么是回表？怎么避免？
> 二级索引查到主键后，再回聚簇索引取整行，叫回表。
> 避免方式：**覆盖索引**——让查询需要的列全部包含在二级索引中，`EXPLAIN` 出现 `Using index`。

> [!question] Q3：为什么 MySQL 用 B+ 树而不是 B 树 / 哈希？
> - **B+ 树**：非叶子节点只存键，单页能放更多键，树更矮；数据全在叶子，叶子有链表，**范围查询和排序友好**。
> - **B 树**：数据分散在所有节点，范围查询要中序遍历，磁盘随机 I/O 多。
> - **哈希**：等值查询 O(1)，但**不支持范围、排序、最左前缀**，所以 InnoDB 默认用 B+ 树。

> [!question] Q4：联合索引的最左前缀原则是什么？
> 索引 `(a, b, c)` 可以服务 `(a)`、`(a,b)`、`(a,b,c)`，但不能跳过 `a` 直接用 `b` 或 `b,c`。
> 另外，某列用了范围条件后，它右边的列通常无法继续用于缩小扫描范围。

> [!question] Q5：索引越多越好吗？
> 不是。每个索引都会增加写入成本、磁盘空间和 buffer pool 占用，还可能让优化器选错计划。
> 原则：**只为高频、收益明确的查询建索引；定期清理冗余和未使用索引。**

> [!question] Q6：前缀索引有什么优缺点？
> 优点：长字符串索引更小、写入更快。
> 缺点：不能覆盖索引、不能用于完整列的排序/分组，区分度可能不足。
> 选择前缀长度时，让 `COUNT(DISTINCT LEFT(col, n)) / COUNT(*)` 尽量接近完整列。

> [!question] Q7：为什么主键推荐自增？
> 自增主键按顺序追加，B+ 树只在最右侧分裂，页利用率高；
> 随机主键（如 UUID）会导致频繁页分裂、数据页不连续、二级索引膨胀。

> [!question] Q8：`Cardinality` 是什么？
> 索引列中**不同值的估算个数**，用来衡量区分度。`Cardinality` 越高，索引选择性越好。
> 它是采样估算值，可能失真，必要时 `ANALYZE TABLE` 更新。

> [!question] Q9：不可见索引有什么用？
> 删除索引前先设为 `INVISIBLE`，优化器不再使用它，但索引仍被维护。
> 观察一个业务周期，确认没有查询依赖后再真正 `DROP`，是一种安全的灰度删索引方式。

> [!question] Q10：大表加索引要注意什么？
> - 评估表的行数、索引大小、磁盘空间
> - 使用 `ALGORITHM=INPLACE, LOCK=NONE` 尽量在线
> - 避开业务高峰，监控 I/O、锁等待、主从延迟
> - 千万级以上优先用 `pt-online-schema-change` / `gh-ost`
> - 加完后 `ANALYZE TABLE`，再用 `EXPLAIN` 验收

## 十一、索引管理自查清单

- [ ] 主键是 `BIGINT AUTO_INCREMENT`，短、递增、不变
- [ ] 高频等值查询有唯一/普通索引
- [ ] 联合索引遵循"等值在前、范围在后"
- [ ] 高频排序/分组字段在索引顺序中
- [ ] 高频查询尽量覆盖索引，避免 `SELECT *`
- [ ] 长字符串用前缀索引，前缀区分度足够
- [ ] 没有重复索引、冗余索引、从未使用的索引
- [ ] 统计信息不过期，必要时 `ANALYZE TABLE`
- [ ] 删索引前先 `INVISIBLE` 观察
- [ ] 大表 DDL 已评估锁和 I/O，必要时用在线工具
- [ ] 索引命名规范：`pk_` / `uk_` / `idx_` / `ft_` / `sp_`

---

> [!quote] 一句话记忆
> **聚簇索引存整行，二级索引存主键；查非索引列要回表，列全在索引里就覆盖。**
> **联合索引最左前缀，等值在前范围在后；索引不是越多越好，写入成本要算清。**
