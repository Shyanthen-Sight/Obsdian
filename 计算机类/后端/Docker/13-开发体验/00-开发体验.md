# 开发体验

容器把运行环境固定下来了，代价是开发时的反馈变慢：改一行代码要重新 build，断点打不进去，测试依赖得手动起，CI 又是另一套命令。这一阶段就是把这几处摩擦磨平，让容器成为日常开发的手感，而不是每次上线前才碰的东西。

四个问题对应四篇笔记：

- [[01-热重载|热重载]]：用绑定挂载把源码送进容器，再让文件监听器重启进程，省掉重建镜像。
- [[02-调试器|调试器]]：把调试端口开在 `0.0.0.0`，映射到宿主后用 IDE attach。
- [[03-测试|测试]]：Testcontainers 按需拉起真实依赖，或者用 compose 跑整套集成环境。
- [[04-持续集成|持续集成]]：在 CI 里复用同一份 Dockerfile，构建、测试、扫描、推送一次完成。

建议按这个顺序读。热重载和调试器解决的是“改得快”，测试解决“改得对”，CI 解决“别人拿到也跑得对”。前两个只需要会 `docker run` 和挂载，后两个会用到 compose 和镜像仓库。

一条判断标准：本地开发循环里，从保存文件到看到结果超过两三秒，就值得检查是不是每步都在重建镜像；CI 里同一条命令在本地跑不通，说明环境还有没被容器接住的部分。

如果只能先做一件事，配好 `docker compose up --watch`：它在起服务的同时按 `develop.watch` 规则同步文件，把依赖启动和热重载合成一步。这个命令要求 Compose 2.22 以上，配置写法见热重载那篇。

```bash
docker compose up --watch
# 只观察某个服务
docker compose up --watch api
```

`--watch` 会在文件变化时按 `develop.watch` 的 `action` 执行 sync、rebuild 或 sync+restart，比自己写一堆 `-v` 和轮询参数更稳定。

学完这一阶段，应该能做到：新同事 clone 仓库后，用一条 `docker compose up` 起依赖；本机直接跑应用并热重载；集成测试不依赖手工准备的数据库；合并请求里自动产出带版本标签和 digest 的镜像。
