# 运行容器

镜像只是模板，真正干活的是容器。这一阶段讲的是把镜像变成可用服务：命令怎么下、参数怎么给、多个容器怎么编排、跑起来之后怎么保证稳定。

学习顺序上，先把 `docker run` 的十几个高频参数用熟，尤其是 `-d`、`-p`、`-v`、`-e`，以及前台和后台的区别；然后换成 compose，用 YAML 描述同样的东西，体会声明式和命令式的差异；等这些顺了，再补资源限制、重启策略、健康检查和日志。前两步解决“跑起来”，第三步解决“跑得住”。

选工具的判断不复杂：单个容器、一次性任务、临时调试，用 `docker run`；两个以上有依赖关系的服务，直接写 `compose.yaml`。见过不少人用一长串 `docker run` 起 MySQL、Redis 和后端，第三天就没人记得密码和卷名了。

同样一个 Redis，两种写法：

```bash
docker run -d --name redis -p 6379:6379 redis:7-alpine
```

```yaml
services:
  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
```

`docker compose up -d` 起后者，`docker compose down` 收尾。命令式适合临时试验，声明式适合需要反复启动、多人共享的环境；两者不是替代关系，而是场景不同。

容器起来之后要会看三样东西：`docker ps` 看状态和端口，`docker logs` 看应用输出，`docker inspect` 看实际生效的配置。退出码也有信息量，`137` 多半是被 OOM kill，`1` 是应用自己报错，`0` 是正常结束；反复重启时，`State.ExitCode` 和 `RestartCount` 往往比日志更早暴露问题。

端口这块有个新手常踩的坑：`-p` 只负责把宿主流量转进容器，应用本身必须监听 `0.0.0.0`。如果它绑在 `127.0.0.1`，容器内测试正常，从宿主机却始终连不上。

学完这一阶段，应该能用一个 compose 文件把本地开发环境拉起来，知道服务之间怎么互相解析，也能在容器反复重启时判断问题出在配置、依赖还是资源上。
